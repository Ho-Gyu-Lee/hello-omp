# 프로젝트 지도

사용자가 `/project-map`을 호출했습니다. 입력: `$ARGUMENTS`

1. 전역 지침에 명시된 OKF 절대경로에서 `project-navigation.md`와 `project-map-design.md`를 읽고, 설치된 `project-map` 스킬의 `SKILL.md`를 읽습니다. 현재 프로젝트 루트와 기존 설계/상태 문서·유지 선언을 확인합니다. 홈·파일시스템 루트나 다른 프로젝트로 범위를 확대하지 않습니다.
2. `status`는 읽기 전용입니다. 스킬의 `status`로 기존 진입점·manifest와 실제 입력 경로 집합/fingerprint, 게시 파일 해시를 대조해 `일치/변경/추가/삭제/미분류`, 영향 받은 지도, 확인된 구현/검증 상태와 진행 가능한 확정 계획·차단 조건·미확정 제안을 보고합니다. 파일·선언·상태를 변경하거나 렌더러를 실행하지 않습니다. 지도가 없으면 없다고 보고하며 자동 생성하지 않습니다.
3. 빈 입력은 현재 프로젝트의 지도를 초기화하거나 기존 지도를 갱신하고 지속 관리하도록 하는 요청입니다. 그 밖의 자연어 입력은 지도 범위/목적이며 셸 코드로 실행하지 않습니다. 일회성 생성이나 유지 중지를 명시하면 그 범위를 따릅니다. 기존 지침에 유지 선언을 추가하되 덮어쓰지 않고, 지침이 없으면 프로젝트 루트 `AGENTS.md`에 선언만 만듭니다. 기존 선언이 `프로젝트 지도: 사용 안 함`이면 사용자가 `/project-map`을 직접 호출한 것을 명시적 재요청으로 보고, 지속 관리를 요청한 경우에만 그 선언 줄을 `유지` 선언으로 바꿉니다. 일회성 요청이면 선언을 바꾸지 않습니다.
4. 위치·범위·검증을 짧게 알리고 진행합니다. 기존 문서 경로·소스·설정으로 판단 가능한 것을 질문하지 않습니다. 실질적인 사용자 선택이나 필수 권한 승인만 묶어 확인합니다. 명령 실행 자체에 대해 다시 승인받지 않습니다.
5. 실제 코드/등록/참조를 읽어 전체 지도, 필요한 상세 지도, 책임·파일·핵심 심볼 목차와 구현/검증 상태를 만듭니다. 할 일·제안·칸반 카드의 구분과 근거·신선도(작업 트리 기반과 커밋 근거)는 `project-navigation.md`, 영역 화면의 구성과 게시 전 점검은 `project-map-design.md`를 따릅니다. 계획 등록만으로 실행하지 않습니다. 단순 폴더 나열, 가상의 매니저, 고정 노드/함수 상한, 실행 근거 없는 호출선을 사용하지 않습니다. 화면은 `project-map` 스킬의 공용 템플릿으로 만들고 내용은 스킬의 `src/` 데이터로 씁니다.
6. 설치된 Archify 스킬과 `project-map` 스킬을 읽고 사용합니다. 스킬이나 실행 환경이 없으면 없는 전제를 명시하고 접근 가능한 목차·상태를 완성하되 렌더링·게시 성공을 주장하지 않습니다. 패키지·브라우저·MCP 설치나 보호 완화를 묵시적으로 수행하지 않습니다.
7. `project-map` 스킬의 `init`·`build`·`publish` 순서로 모든 gate를 통과한 후보만 게시합니다. 작업 디렉터리·영수증 보존·게시본의 바이트 일치 확인·실패 시 이전 정본과 증거 보존은 `project-navigation.md`의 「작업·갱신·게시 절차」를 따릅니다.
8. 진입점·현재 확인 범위·변경/유지된 구조·검증과 남은 항목을 보고합니다. 지속 관리가 활성화된 범위에서는 일반 변경 작업의 완료 과정에 문서 갱신을 포함하며 반복 승인을 받지 않습니다. 읽기 전용 리뷰나 단순 질의는 지도 쓰기를 유발하지 않습니다.

이 명령은 작업 지침입니다. 자동 코드 분석/감시 서비스나 Git 커밋·외부 공개를 수행하는 명령이 아닙니다.
