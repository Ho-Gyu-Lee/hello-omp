# 인터뷰

사용자가 `/interview`를 호출했습니다. 입력: `$ARGUMENTS`

목표는 구현 전에 사용자의 의도와 에이전트의 이해를 맞추는 것입니다. 사용자가 당연하다고 여겨 말하지 않은 조건은 모델이 알 수 없으므로 질문으로 끌어냅니다.

1. 입력과 대화에서 정렬할 대상을 정합니다. 비어 있으면 무엇을 정렬할지 한 번 묻습니다.
2. 사실은 먼저 직접 찾습니다. 코드·문서·프로젝트 지침·전역 지침의 OKF 절대경로에 있는 `direction.md`·기존 용어집·결정 기록으로 답할 수 있으면 사용자에게 묻지 않습니다. 탐색이 넓으면 scout에 맡기고, 그 결과에 의존하지 않는 질문은 기다리지 않고 진행합니다.
3. 정할 것을 결정 트리로 정리합니다. 선행 결정이 모두 정해진 결정이 지금 물을 수 있는 질문입니다.
4. 차례마다 지금 물을 수 있는 질문을 모두 한 번에 묻습니다. 앞선 답에 따라 달라지는 질문은 다음 차례로 미룹니다. 질문마다 번호·짧은 제목·선택지(있으면)·추천 답과 이유를 붙이고 "예"가 추천안 수락이 되게 씁니다. 선택지가 분명한 질문은 `ask` 도구로 묶고 서술형은 번호 목록으로 묻습니다.
5. 답을 받으면 트리를 다시 정리해 다음 차례를 묻습니다. 답이 코드·문서와 어긋나면 바로 짚습니다(예: "코드는 주문 전체를 취소하는데 방금 항목 하나만 취소한다고 하셨습니다. 어느 쪽인가요?"). 모호하거나 여러 뜻인 용어는 정확한 용어를 제안해 확정하고, 경계를 시험하는 구체적 시나리오를 제시합니다.
6. 확정된 내용은 그때그때 프로젝트 문서에 남깁니다. 사용자가 원하지 않으면 생략합니다.
   - 용어: 프로젝트의 기존 용어집 또는 설계 문서의 용어 절에 정의만 적습니다. 구현 세부·진행 상태는 쓰지 않습니다. 둘 다 없으면 처음 확정된 용어가 생길 때 둘 위치를 확인합니다.
   - 결정: 되돌리기 비싸고, 맥락 없이는 의아하고, 실제 대안 사이의 선택이었던 것만 프로젝트의 결정 기록(설계 문서의 결정 절 또는 기존 결정 기록 위치)에 '무엇을·왜·버린 대안'으로 짧게 남깁니다.
   - 프로젝트 `AGENTS.md`에는 앞으로의 작업이 지켜야 할 현행 지침이 생겼을 때만 한 줄과 링크를 추가합니다.
   - 프로젝트와 무관한 사용자 방향이 드러나면 OKF `learning/accumulation.md`에 따라 전역 방향 문서를 고칩니다.
7. 물을 것이 남지 않으면(트리의 모든 가지를 확인했고 묵시적으로 가정한 것이 없으면) 확정된 결정·용어·수락 기준·범위 밖 항목을 한 화면으로 요약합니다. 사용자가 이해가 맞았다고 확인할 때까지 구현을 시작하지 않습니다.

이 명령은 정렬 절차입니다. 구현·커밋·외부 공개를 승인하지 않습니다.
