# 구조 리뷰

사용자가 `/arch-review`를 호출했습니다. 입력: `$ARGUMENTS`

기능이 동작해도 구조가 얽히면 한 곳을 고칠 때 엉뚱한 곳이 깨집니다. 이 명령은 그런 마찰을 일찍 찾아 보고하는 데까지만 하며 코드를 고치지 않습니다.

1. 범위를 먼저 정합니다. 입력이 영역을 지정했으면 그곳만 봅니다. 없으면 최근 커밋 이력에서 자주 바뀌는 파일·영역부터 봅니다. 프로젝트 지침·설계 문서·결정 기록·용어집을 먼저 읽습니다. 기록된 결정을 뒤집는 후보는 결정을 다시 볼 만큼 마찰이 클 때만 그 사실을 표시해 올립니다.
2. 넓은 탐색은 scout에 맡기고 다음을 찾습니다.
   - 개념 하나를 이해하려고 작은 모듈 여러 개를 오가야 하는 곳.
   - 인터페이스가 구현만큼 복잡한 얕은 모듈, 호출자와 구현이 하나뿐인 전달 계층.
   - 소유 경계를 넘어 상태·불변조건이 새는 곳(특히 스레드·서버 사이의 소유권).
   - 현재 인터페이스로는 테스트하기 어렵거나 테스트가 없는 곳.
   의심되는 모듈에는 삭제 시험을 적용합니다. 지웠을 때 복잡도가 여러 호출자로 퍼지면 가치 있는 모듈이고, 그냥 사라지면 전달 계층입니다.
3. 후보마다 관련 파일, 문제(왜 다음 변경을 어렵게 하는가), 제안(무엇을 합치거나 옮기는가), 이점(변경이 한곳에 모이는 점·테스트가 쉬워지는 점), 위험과 비용, 권장 강도(강함/검토 가치/추정)를 적습니다. 필요하면 전후 구조를 Mermaid로 보입니다. 전역 지침의 OKF 절대경로에 있는 `direction.md`와 요청 밖 리팩터링 금지 원칙에 맞는 후보만 올립니다.
4. 보고는 터미널을 기본으로 하고, 끝에 가장 먼저 다룰 후보와 이유를 적은 뒤 어느 후보를 진행할지 묻습니다. 후보가 없으면 없다고 보고합니다.
5. 사용자가 후보를 고르면 `/interview` 방식으로 제약·의존성·새 인터페이스 모양·유지할 테스트를 정렬한 뒤에 구현합니다. 사용자가 분명한 이유로 후보를 거절하면, 다음 리뷰가 같은 제안을 반복하지 않도록 프로젝트 결정 기록에 남길지 묻습니다.

이 명령은 보고 절차입니다. 코드 수정·커밋을 승인하지 않습니다.
