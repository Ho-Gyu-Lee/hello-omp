# 구현 전 설계 검토 (goldfish-review)

설계자(메인 세션)와 검토자(`design-reviewer`)를 대화가 아니라 설계 문서 하나로만 연결합니다. 검토자는 대화를 보지 못하므로 문서에 빠진 결정·전제·영향이 지적으로 드러납니다. 출처와 수정 내역은 [UPSTREAM.md](UPSTREAM.md)에 있습니다.

## 경계

- 대상 판정은 전역 워크플로(`workflow.md`의 독립 검토 절)를 따릅니다. 이 스킬은 판정 뒤의 절차입니다. 시작할 때 대상으로 본 이유와 경로를 한 줄로 알리고 승인을 기다리지 않고 진행합니다.
- 요구·범위가 정해지지 않았으면 검토 전에 사용자 결정을 한 번에 묶어 묻습니다. 검토자에게 요구를 정하게 하지 않습니다.
- 이 검토는 구현 후 검토와 완료 전 독립 검토를 대체하지 않습니다. 보안 영향이 있으면 `security-reviewer` 검토를 더합니다.
- 절차가 끝나기 전에는 제품 코드·설정·운영 환경을 바꾸지 않습니다. 사실 확인을 위한 읽기·조회는 됩니다. 작업 디렉터리 안에서 본 코드 트리를 고치지 않고 공유 환경·영속 데이터·자격증명에 접근하지 않는 탐색용 시제품·실험은 검토 전에 만들 수 있고, 그 결과는 설계 문서의 근거로 씁니다. 검토는 본 코드·공유 환경·영속 데이터에 넣기 전에 합니다.

## 1. 설계 문서와 검토 기록

- **작업 디렉터리:** 사용자·프로젝트가 지정한 작업 경로, 없으면 `<프로젝트 루트>/.omp-artifacts/<작업-ID>/`입니다. 아래 `design/`·`review/`는 이 디렉터리 안에 둡니다.
- **설계 문서 위치:** `design/design.md`입니다. 검토자에게는 이 `design/` 경로만 넘깁니다. 프로젝트 지침이 변경별 설계 문서 위치를 명시한 경우에만 그곳에 둡니다.
- **형식:** [design-doc.md](design-doc.md)를 따릅니다. 해당 없는 절은 지우지 않고 "해당 없음"으로 적습니다. 끝의 출처 주석은 옮기지 않습니다.
- 사용자가 확정한 요구·금지·제약은 목표·비목표·제약 절에 적습니다. 대화에만 있는 결정은 검토자가 볼 수 없습니다.
- **검토 기록 위치:** 항상 `review/`이며 `design/` 밖에 둡니다. 검토자를 호출할 때마다 결과 원문(`<단계번호>-<렌즈>[-r<재검토번호>].findings.md`)과 메인의 지적별 판정(같은 이름의 `.md`)을 따로 저장해 덮어쓰지 않습니다. 첫 Zoom Out을 호출할 때 검토한 문서의 사본을 `review/1-zoom-out.design.md`로 남깁니다. 검토 대상 문서에는 검토 기록을 쓰지 않습니다.
- 이미 검토받은 문서가 있으면 현재 목표·설계·영향 범위와 맞는지 먼저 확인합니다. 바뀌었으면 문서를 고쳐 다시 검토합니다.
- 결정을 프로젝트 결정 기록으로 올리는 것은 전역 지식 기록 기준(되돌리기 비싸고, 맥락 없이는 의아하고, 실제 대안 사이의 선택)에 맞을 때만입니다.

## 2. 경로

| 경로 | 언제 | 단계(순차) |
|---|---|---|
| 표준 | 전체 경로에 해당하지 않는 대상. 필수 조건에 걸려도 기존 동작·데이터·권한·인터페이스 계약을 바꾸지 않고 새 접근 경로(엔드포인트·권한)도 열지 않는 순수 추가(새 함수·모듈 추가, 데이터 이전 없음)는 표준입니다 | Zoom Out → Design Critic → Implementation Readiness(문서가 기존 코드를 참조하면 Codebase Details를 같은 단계에서 병렬) |
| 전체 | 필수 조건에 걸리면서 기존 동작·데이터·권한·인터페이스 계약을 바꾸거나 새 접근 경로를 여는 변경: 되돌릴 수 없거나 비싼 결과(영속 데이터·이미 밖으로 나간 결과), 신뢰 경계(보안·권한·서버 권위), 동시성·정합성, 되돌리기 어려운 운영 환경 변경 | Zoom Out → Comprehension → Design Critic → 중간 Zoom Out → Implementation Readiness + Codebase Details(병렬) |

- 경로를 낮춰도 필수 조건의 구현 후 독립 검토(보안 영향이 있으면 `security-reviewer` 포함)는 그대로 합니다.
- 각 단계는 앞 단계의 수정이 반영된 문서를 검토합니다. 병렬은 같은 단계 안에서만 합니다.
- 중간 Zoom Out은 앞 단계 지적을 반영하며 늘어난 방어 로직·절차가 과잉인지 봅니다. 렌즈 파일의 "중간 모드"로 호출하고 첫 Zoom Out 결과 원문(`review/1-zoom-out.findings.md`)과 그때 검토한 문서 사본(`review/1-zoom-out.design.md`)을 함께 넘깁니다. 원문에 이미 나온 결정은 다시 지적하지 않습니다.

## 3. 검토 호출

- 렌즈마다 `design-reviewer`를 새 task로 호출합니다. 이전 검토자를 재사용하거나 대화를 이어 붙이지 않습니다.
- task에 넣는 것:
  - 렌즈 파일 `skill://goldfish-review/lenses/<렌즈>.md` (`zoom-out`, `comprehension`, `design-critic`, `implementation-readiness`, `codebase-details`)
  - 대상 문서 절대경로와 검토 범위(문서 전체 또는 구현 계획 절)
  - 읽어야 할 파일 목록(문서가 참조하는 코드·문서 외에 필요한 것)
  - 중간 Zoom Out(재검토 포함)에만: "중간 모드" 지정, 첫 Zoom Out 결과 원문 경로, 첫 Zoom Out이 검토한 문서 사본 경로. 메인의 판정 파일은 넘기지 않습니다.
- 넣지 않는 것: 대화 요약, 메인의 판단("충분히 안전하다" 등), 기대하는 답, 다른 렌즈의 지적, 위 경우 밖의 검토 기록.
- 검토자가 `검토 불완전`을 반환하거나 결과를 주지 못하면 통과가 아닙니다. 원인을 고쳐 다시 호출하고(재검토 횟수에 넣지 않음), 그래도 실패하면 그 단계를 차단으로 보고합니다.
- 검토자의 실제 실행 모델은 지정 역할이 아니라 자식 세션 기록(`model_change`)으로 확인합니다. fallback으로 메인과 같은 provider가 됐으면 보고에 교차 모델 검토가 아니었다고 적습니다.

## 4. 판정과 반영

- 지적마다 메인이 판정하고 그 단계의 검토 기록 파일에 적습니다.
  - **수정:** 문서를 고칩니다.
  - **반박:** 코드·문서·실행 근거가 있어야 합니다. 근거는 문서 본문(위험과 대응, 검토한 대안 등)에 반영해 다음 검토자가 문서만으로 판단할 수 있게 합니다.
  - **사용자 결정:** 범위·trade-off처럼 사용자만 정할 수 있는 것만 모읍니다.
- 지적을 사용자에게 그대로 넘기지 않습니다. 결정이 필요한 것만 한 번에 묶어 질문마다 추천과 이유를 붙여 묻습니다.

## 5. 수렴 조건

- **통과:** 그 단계에 남은 Blocker가 0건입니다.
- **Blocker는 메인이 닫지 않습니다.** 수정했든 반박했든 같은 단계를 새 검토자로 다시 실행해 Blocker가 나오지 않아야 닫힙니다. 재검토자에게는 검토 기록을 넘기지 않습니다. 예외로 중간 Zoom Out의 재검토에는 첫 Zoom Out 결과 원문과 문서 사본을 넘깁니다.
- 같은 단계의 재검토는 1회까지입니다. 마지막 단계에서 반영한 수정이 구현 계획 절(대상 파일·단계·검증 계획·데이터·운영 절차)이나 인터페이스·오류 처리 결정을 바꾸면 마지막 단계를 다시 실행하며, 이것이 그 단계의 재검토 1회입니다.
- 재검토 뒤에도 Blocker가 남거나, 재검토 뒤 위 항목을 다시 바꿔야 하면 구현하지 않습니다. 남은 문제와 바꿀 내용을 선택지·추천과 함께 사용자 결정으로 올립니다.
- 사용자 결정을 받으면 문서에 반영합니다. 사용자가 위험을 수용하기로 했으면 제약 또는 위험과 대응 절에 "사용자 수용"으로 적고 남은 위험으로 보고합니다. 그다음 결정이 영향을 준 단계를 새 검토자로 다시 실행하고, 남은 단계를 원래 순서대로 이어 갑니다. 이미 통과한 마지막 단계가 영향을 받았으면 그것도 다시 실행합니다. 이 재실행은 결정마다 1회이며 재검토 상한에 넣지 않습니다. 여기서도 Blocker가 남으면 다시 사용자 결정으로 올립니다.
- Major는 수정하거나, 근거 있는 반박을 문서에 반영하거나, 수용한 trade-off로 기록하고 보고합니다. Nit는 메인이 판단합니다.

## 6. 보고와 구현

- 수렴하면 문서 상태를 `검토 완료`로 바꾸고 구현합니다. 구현은 문서의 구현 계획을 따르고, 위임할 때는 이 문서 경로를 넘깁니다.
- 사용자에게는 터미널로 설계 문서와 검토 기록 경로, 사용자 결정 사항, 수용한 trade-off, 남은 위험을 보고합니다. 단계별 상세는 검토 기록에 둡니다.
