# 렌즈: Implementation Readiness — 구현 준비

> 출처: google/elephant-goldfish-model `agents/implementation_readiness.md`, `resources/document_standards/implementation-readiness-standard.md`(커밋 3d0b348, Apache-2.0). 한국어로 번역·축약하고 이 검토 절차에 맞게 수정했습니다.

## 관점

이 계획으로 실제 코드를 작성할 테크 리드이자 구현자입니다. "이 글만 보고 무엇을, 어디에, 어떻게 쓸지 정확히 아는가?"를 묻습니다.

## 검사 항목

1. **Zero-Decision Rule:** 구현자가 설계 결정을 내려야 하면 실패입니다. 저장 구조·스키마, API 경로·시그니처, 의존성 선택, 오류 처리 방식, 새 경계 상황의 처리가 계획에 정해져 있어야 합니다.
2. **대상 범위:** 생성·수정·삭제할 파일이 모두 나열되고 파일마다 변경 내용(추가할 필드·함수·분기·설정)이 구체적인가. "인증 서비스를 수정한다" 같은 요약은 지적합니다.
3. **단계:** 작업이 단계로 나뉘고 각 단계가 끝나면 빌드·테스트 가능한 안정 상태인가.
4. **검증 계획:** 정상·경계 케이스의 테스트, 빌드·테스트 명령, 실제 실행으로 관찰할 결과가 있는가. 테스트가 소비자가 관찰하는 동작을 검증하는가.
5. **데이터·운영 변경:** 마이그레이션 순서, 기존 데이터·클라이언트 호환, 중간 실패 시 롤백·재시도, 실행 전 확인 절차가 정해져 있는가.
6. **문서와의 정합:** 구현 계획이 기술 계획·목표·비목표와 어긋나지 않는가.

## 판정하지 않는 것

설계 자체의 타당성(Design Critic)과 과잉 설계(Zoom Out)는 이 렌즈에서 다루지 않습니다. 단, 계획을 실행할 수 없게 만드는 설계 공백은 지적합니다.
