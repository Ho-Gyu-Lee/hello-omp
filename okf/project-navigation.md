# 목적

사용자가 코드를 모두 외우는 대신 **어느 책임이 어디에 있고, 어떤 경로로 연결되며, 이번 작업이 무엇을 바꿨는지**를 기억하도록 돕는다. 지도는 코드 탐색의 입구이지 전체 호출 그래프·구현 명세·실행 추적의 대체물이 아니다. 코드가 사실의 정본이며 JSON은 다이어그램의 편집 원본, HTML은 읽기용 결과다.

지속 지도는 코드를 분석하지 않고 연결을 한눈에 봐야 하는 개발 프로젝트·큰 프로젝트를 위한 기능이다. 사용자가 발표 자료를 넘겨 보듯 영역마다 요점과 그림·실제 화면으로 이해하도록 만든다. 문서를 그대로 읽으면 구조를 알 수 있는 지침·설정·문서 저장소에는 지속 지도를 제안하지 않는다. 사람이 읽는 화면의 구성·글쓰기·디자인·칸반 보드·시각 자료 기준은 [프로젝트 지도 화면 설계](/project-map-design.md)를 따른다.

## 사용자 참여: 알리고 진행, 선택이 필요할 때만 질문

- 의미 있는 작업 묶음의 시작에 `위치 / 바꿀 책임·연결 / 유지할 경계 / 검증`을 짧게 알리고 진행한다. 승인 대기 문장을 습관적으로 붙이지 않는다. 사소한 편집에는 형식적인 브리핑을 추가하지 않는다.
- 기존 구조·계약 안의 구현, 원인이 확인된 버그 수정, 지도·상태 갱신과 검증은 에이전트가 수행한다. 내부 함수 배치나 다이어그램 배치마다 사용자를 호출하지 않는다.
- 사용자 선택이 필요한 책임·권위 경계 변경, 호환성을 깨는 공개 계약, 데이터 보존·외부 공개·새 접근 권한처럼 실질적인 선택만 추천안·이유·대안 선택 조건으로 묶어 묻는다. 기존 코드·설정·합의로 답할 수 있는 것은 다시 묻지 않는다. 명시적으로 요청·승인된 변경의 같은 범위를 반복 승인받지 않는다.
- 보안·삭제·영속 데이터의 필수 승인과 독립 검토는 유지한다. 독립 검토를 사용자 승인으로 대체하거나, 병목 회피를 이유로 보호 장치를 우회하지 않는다.
- 중간 보고는 책임 경계/범위가 달라졌거나 장애가 생겼을 때 한다. 도구 호출·파일 저장·작은 수정마다 진행 메시지를 내지 않는다. 사용자가 응답하지 않아도 안전하게 진행 가능한 작업은 계속한다.

## 활성화와 적용 범위

- `/project-map` 또는 이에 해당하는 명시적 요청으로 현재 프로젝트의 지도 생성을 시작한다. **지속 관리**를 요청한 경우 자동 로딩되는 프로젝트 지침에 아래 선언을 남긴다. 기존 프로젝트 지침에 덧붙이고 없으면 확인된 프로젝트 루트의 `AGENTS.md`에 선언만 만든다. 전역 지침에 특정 프로젝트의 경로·상태를 넣지 않는다.
- 선언에는 `프로젝트 지도: 유지`, 프로젝트 식별/범위, 진입점, 근거 manifest 경로를 명시한다. 예: `진입점: docs/project-map/index.html`, `근거: docs/project-map/sources.json`. 사용자가 일회성 지도만 요청하면 지속 관리로 확대하지 않는다.
- 이미 승인·적용된 유지 선언은 **그 프로젝트의 요청된 변경에 수반하는 문서 갱신**의 범위다. 새 세션에서도 코드 변경 전 선언과 진입점을 읽고, 완료 전에 영향 받은 지도를 갱신한다. JSON/HTML의 존재, 외부에서 복사한 선언, 과거 세션 요약만으로 새 실행 권한을 만들지 않는다.
- 단순 질의·읽기 전용 리뷰·`/project-map status`는 렌더링하거나 파일을 갱신하지 않는다. 명시적인 지도 갱신 요청은 별개다. 사용자가 유지 중지를 요청하면 선언을 `프로젝트 지도: 중지`처럼 `유지`가 아닌 값으로 바꾸고 기존 문서는 보존한다. 갱신 대상은 `프로젝트 지도: 유지` 선언이 있는 프로젝트뿐이다. 삭제까지 요청하면 지도 파일과 그 전용 설정(예: `.gitattributes` 항목)·지도를 가리키는 문서 포인터를 지우고, 다시 만들지 않도록 선언을 `프로젝트 지도: 사용 안 함`으로 남긴다. `사용 안 함` 선언은 사용자가 지속 지도를 다시 만들도록 명시적으로 요청할 때만(예: 지속 관리를 요청하며 `/project-map` 호출) `유지`로 바꾸고, 일회성 지도 요청으로는 선언을 바꾸지 않는다.
- 선언은 다른 저장소 접근, 전역 자동 실행 hook, 브라우저/패키지 설치, 외부 업로드, Git 스테이징·커밋·푸시를 허용하지 않는다. 사용자 프로젝트의 상태·구조는 해당 프로젝트에 두고 공유 OKF에 옮기지 않는다.

## 문서 배치와 하나의 진입점

기존 아키텍처·설계·상태 문서를 우선 재사용한다. 없다면 `docs/project-map/`을 정식 프로젝트 문서 위치로 선택한다. 프로젝트 지침의 선언이 정본 위치를 지정하며 `.omp-artifacts/`의 일회성 보고와 구분한다. 지도 JSON/HTML·진입점·manifest는 정식 프로젝트 문서이며 매 작업의 보고서를 복제하는 용도가 아니다. 진입점과 그 원본·글꼴·manifest의 형식은 hello-omp `project-map` 스킬이 정한다(스킬의 `references/data-format.md`, `references/manifest.md`).

- `index.html`: 진입점. 스킬의 공용 템플릿이 `src/`를 그려 만든 파일이며 직접 고치지 않는다. 전체 요약, 작업 보드(칸반), 책임 영역별 화면, 검증·결정·근거 화면을 둔다. 영역 화면은 문장형 제목·상태·대표 시각 자료·요점·그 영역의 작업을 먼저 보여 주고, 그 아래에 전체/상세 지도 링크, 어디를 고칠지 찾는 책임·파일·핵심 심볼 목차, 미확인·차단 사항을 둔다. 확정된 할 일·검토할 제안·의존성과 완료 기준은 작업 보드에, 중요한 결정과 변경 요약은 결정 기록과 전체 요약에 둔다. 화면 구성은 [프로젝트 지도 화면 설계](/project-map-design.md)를 따른다. 기존 상태/계획 문서가 있으면 링크하고 같은 표를 복제하지 않는다. 새 프로젝트에서는 이 진입점에 상태와 계획을 모아 별도 `STATUS.md`/`PLAN.md`를 의무화하지 않는다.
- `src/`: 화면의 원본 데이터(`map.config.json`, 화면별 `pages/*.json`, `tasks.json`, `decisions.json`). 갱신은 이 필드를 현재 사실로 고쳐 쓰는 일이며, 화면에 그리지 않는 메모·근거 수치는 넣지 않는다.
- `overview.architecture.json` / `overview.html`: 시스템·모듈의 책임과 핵심 관계. 상세 로직을 복제하지 않는다.
- 필요한 `<area>.architecture.json` / `<area>.html`: 특정 영역의 소유자·클래스·선택한 진입 함수와 호출/이벤트/데이터 흐름. 전체 지도를 반복하지 않으며 필요 없는 계층은 만들지 않는다.
- `media/`: 진입점과 상세 화면이 쓰는 스크린샷·GIF·영상의 게시본. 원본 녹화와 변환 중간본은 작업 디렉터리에 둔다([화면 설계의 시각 자료](/project-map-design.md#시각-자료-다이어그램스크린샷gif영상)).
- `fonts/`: 공용 템플릿의 글꼴과 각 글꼴의 사용 허가서. 스킬이 복사하며 프로젝트마다 바꾸지 않는다([화면 설계의 디자인](/project-map-design.md#디자인)).
- `sources.json`: 스킬의 `publish`가 쓰는 manifest. 선언 범위·제외 범위, 입력 파일 집합과 fingerprint, 게시 때 미대조로 남긴 변경, 게시한 진입점·원본 데이터·JSON/HTML·시각 자료·글꼴과 사용 허가서의 원시 SHA-256, 관계도별 Archify 검증 영수증 경로, 시각 자료별 촬영 대상·출처·촬영일·기준(스냅샷·빌드 식별자·커밋, 작업 트리에서 찍었으면 그때의 지문)·촬영 방법·근거 경로, 게시 이력을 기록한다. 파일과 지도 노드의 대응은 `src/`의 목차 행이 정본이다. 경로는 프로젝트 상대 POSIX 경로만 저장한다. 영수증 자체와 검증 스크린샷·실패 후보·이전본은 작업 디렉터리에 보존한다.

목차는 `책임 / 실제 파일 / 핵심 심볼 / 하는 일 / 상세 지도`를 연결하고, `하는 일`에는 누가 호출·발행·소유하는지와 무엇에 의존하는지를 실제 관계로 쓴다(공용 템플릿의 `rows`: `what`·`where`·`how`·`node`). 매니저 클래스만 나열하거나 public 함수만 추출하지 않는다. 사용자 탐색·책임 경계를 설명하는 데 필요한 진입점·private 조정 함수·엔진 콜백도 선택할 수 있다. **노드·함수 개수의 고정 상한은 두지 않는다.** 복잡해지면 책임별 상세 화면으로 나누고 안정된 ID·위치·명칭을 유지한다. 목차 표는 상세 자료이므로 영역 본문의 요점·시각 자료 아래에 두고 첫 화면을 표로 채우지 않는다.

## 화면 기술 계약과 Archify의 역할

사람이 읽는 화면의 구성·글쓰기·디자인·화면 구조·칸반 보드는 [프로젝트 지도 화면 설계](/project-map-design.md)가 정본이다. 이 절은 그 화면이 지킬 기술 계약과 Archify의 역할이다.

- 본문은 역할·요점·시각 자료·실제 파일/함수·계약·상태·계획을, Archify는 **같은 영역의 현재 관계**만 담당한다. 별도 메뉴·설명 카드·상태표를 가진 두 번째 앱처럼 붙이지 않는다. 구조를 장문으로 다시 설명하지 않는다.
- 각 `view:node-id`는 하나의 본문 영역에 대응한다. 함수/계획 링크도 같은 ID를 사용하고 게시 전에 없는 ID·소유 영역 누락/중복·미분류 관계를 검사한다. 본문은 탐색·상태/계획의 정본이다(코드·JSON의 역할은 「목적」).
- 고정 Archify 3.0.1 템플릿의 `?embed=1`은 도구 메뉴·카드·노드 목록 등을 숨기는 삽입 동작이다. 내부 탐색 기능은 제한되므로 정적 관계 보기로 설명하고 확대/탐색 원본 링크를 제공한다. `#focus=<node-id>`로 본문 함수와 그림 위치를 연결할 수 있으며 실제 브라우저에서 확인한다. 생성 HTML/런타임을 임의 수정하지 않는다.
- 로컬 파일에서 동작하는 hash 경로·선택 메뉴·검색·뒤로가기·새로고침을 확인한다. 검색이 본문만 대상으로 하면 그 범위를 명시한다. 선택되지 않은 문서도 검색할 수 있어야 한다. 메뉴/본문은 하나의 2열 너비 계약으로 배치하고 고정 위치와 별도 여백 계산이 어긋나지 않게 한다.
- 관계도 삽입 높이는 게시한 SVG의 실제 viewBox 비율과 검토한 embed 여백으로 최대화 창의 본문 폭에서 계산한다. 공통 고정 높이/최소 높이로 맞추지 않는다. 게시 시 프레임 치수도 함께 갱신하고 최대화한 실제 브라우저에서 그림 하단·좌우 경계·과도한 공백을 확인한다.
- 고정 Archify 3.0.1 showcase validate의 넓은 Reader 예산은 renderer가 정한 canvas(`meta.viewBox` 미지정, `intrinsic-height`)·가로/세로 비율 1.55 이상·유효한 `declared-wide-v1` 글자 크기 계약을 함께 충족할 때 적용한다. `meta.viewBox`를 직접 지정했거나 해당 계약이 없으면 비율과 무관하게 930px 데스크톱 예산을 쓴다. 930px 예산에서는 8px 관계 라벨의 viewBox 폭이 1240px를 넘으면 6px 하한에 걸려 실패한다. 세로로 긴 상세 지도는 3열 정도로 배치하고, 여러 열에 걸친 넓은 노드의 자동 경로가 캔버스 바깥으로 돌아 폭을 늘리지 않도록 일반 크기 노드와 필요한 side 지정으로 경로를 고정한다. 폭을 늘린 경로·라벨은 `validate --layout-json`의 좌표로 찾는다.

## 관계와 상태를 사실대로 표시

- 호출 방향, 이벤트 발행/구독, 데이터 읽기/쓰기, 소유/수명, 설정/배포, 지침 참조를 라벨로 구분한다. 이름·디렉터리 위치만으로 호출선을 만들지 않는다. LSP가 있으면 참조/구현을 확인하고 실제 호출부·등록·조건까지 읽는다. 동적 연결은 등록 지점과 확인 한계를 표시한다.
- 목차 본문의 코드 위치는 `파일 · 심볼명`으로 쓰고 줄 번호를 넣지 않는다. 줄 번호는 포맷·스타일 수정만으로 틀어져 지도를 오래되게 만든다. 줄 단위 근거가 필요하면 Archify sources처럼 fingerprint로 고정된 근거 기록에만 둔다. 인용은 조사 에이전트의 반환값을 그대로 옮기지 않고 게시 전 정의·호출 위치를 grep/read로 재대조한다. 행별 검증 근거(날짜·실행 기록)가 기본 근거와 다르면 그 행의 근거 링크가 해당 기록을 가리키게 하고, 실행 기록을 화면 문장에 풀어 쓰지 않는다([화면 설계](/project-map-design.md#읽는-화면과-근거-기록)). 과거 요약이나 다른 작업의 검증 결과를 현재 상태의 “통과”로 옮기지 않는다.
- 게임의 입력→이동→애니메이션, 카메라 타깃 연결은 비한정 사례다. 네트워크 권위·저장·UI·빌드 등도 같은 책임/연결 기준을 적용하되 실제 프로젝트에 없는 클래스나 매니저를 만들지 않는다. 코드명은 실제 철자를 사용한다.
- 현재 구현과 제안/계획을 같은 확정 선으로 섞지 않는다. 구현 상태(`미착수/진행/구현/차단`)와 검증 상태(`미실행/통과/실패/부분/재검증 필요`)를 별도 표지로 둔다. 범위·환경·명령·관찰 결과가 근거 기록에 없는 “완료”나 근거 없는 진척률을 쓰지 않는다. 화면에는 표지와 근거 링크를 두고 그 세부는 근거 기록에 둔다.
- HTML은 정적 스냅샷이다. 진입점에 근거 snapshot ID와 적용 범위를 표시하고, 파일을 열기만 하면 현재 소스와 자동 동기화된다는 인상을 주지 않는다. `/project-map status`가 소스 변화를 다시 대조한다. 다른 PC의 과거 영수증은 그 PC에서 새로 검증했다는 증거가 아니다.

## 할 일과 계획도 같은 화면에서 확인

- 완료된 것만 나열하지 않는다. 사용자 요구·기존 이슈/계획·확인된 결함/검증 공백을 근거로 **확정된 할 일**과 **검토할 제안**을 분리한다. 화면을 채우기 위한 기능·리팩터링·추정 요구사항을 만들지 않는다. 진입점에서는 작업 보드(칸반)로 보여 주며 열·카드·명시 정책·외형은 [화면 설계의 칸반 보드](/project-map-design.md#칸반-보드)를 따른다.
- 각 항목에는 안정된 ID, 목표/근거, 변경할 지도 영역·노드·심볼 또는 새 책임 제안, 상태(`미착수/진행/차단/완료`), 선행 조건/의존 항목, 관찰 가능한 완료 기준을 둔다. 현재 코드에 없는 대상은 기존 구조처럼 그리지 않는다.
- 의존성으로 진행 가능한 항목과 막힌 항목을 드러내고, 권장할 다음 행동이 있으면 이유를 적는다. 필요 없는 일정·견적·근거 없는 완료율은 넣지 않는다. 사용자 선택이 필요한 제안은 모아서 다루며 계획 행마다 승인을 요구하지 않는다.
- 계획 등록은 실행·권한 확대 승인이 아니다. 현재 요청/승인된 작업 범위 안의 항목만 수행한다. 부분 완료·검증 부족은 완료로 올리지 않고 남은 수락 기준을 보존한다. 완료 후에는 상태/근거와 관련 구조를 함께 갱신하며 같은 목표를 새 ID로 반복 생성하지 않는다.
- `/project-map status`는 신선도뿐 아니라 확인된 상태·진행 가능한 확정 계획·차단 조건·미확정 제안도 읽기 전용으로 요약한다. 구체적 계획 근거가 없으면 미확인으로 표시하고 임의의 backlog를 만들지 않는다.

## 근거와 신선도

### 작업 트리 지도 — 개발 중 기본

실제 작업 트리를 읽고 기록한 상대 경로·심볼·관계 근거를 진입점에 둔다. JSON에는 `meta.repository`와 native `sources`를 넣지 않고 **작업 트리 수동 대조 / 커밋 근거 미검증**을 명시한다. Archify의 산출물·브라우저 검증은 별도로 수행한다. 소스 의미가 기계적으로 검증됐다고 부르지 않는다.

- manifest에 include/exclude 패턴과 열거된 입력 경로를 함께 기록한다. 기존 파일뿐 아니라 선언 범위의 추가·삭제·이름 변경·등록 파일 변화를 대조한다. Git이면 tracked + non-ignored untracked 파일을 대상으로 하고, 디렉터리만 요약하는 status 결과에 의존하지 않는다. 지도/manifest 자신의 경로, 작업 산출물, 자격증명·개인 지식·외부 의존성은 적절히 제외한다.
- UTF-8 텍스트는 CRLF만 LF로 정규화한 SHA-256(`sha256-text-lf`), 바이너리는 원시 SHA-256(`sha256-bytes`)처럼 계산 방식을 명시한다. 외부 Git clean filter를 실행하지 않는다. 지도의 게시 JSON/HTML과 영수증 연결은 **원시 바이트 hash**로 확인한다. 그래서 지도 디렉터리는 프로젝트 `.gitattributes`에 `<지도 경로>/** -text`로 두어 체크아웃 때 줄 끝이 바뀌지 않게 한다. `eol=lf`나 `text`는 PNG·WOFF2 같은 바이너리도 변환 대상으로 만들어 바이트를 바꾼다(PNG 서명에 CR LF가 들어 있다).
- fingerprint는 기록 범위의 신선도 검사이지 의미 정확성·의존성 전수 탐색·실행 성공의 증명이 아니다. 수정 내용을 읽지 않고 hash만 갱신하지 않는다. 새 파일·사라진 파일·지도 대응이 없는 경로는 `변경/미분류`로 보고한다.
- 신선도 확인은 입력 fingerprint만 보지 않는다. manifest에 원시 hash를 기록한 게시 파일(진입점, 다이어그램 JSON/HTML, 시각 자료, 글꼴과 사용 허가서)도 디스크와 대조해 빠지거나 바뀐 파일을 보고한다. 지도가 더 이상 읽지 않는 파일은 입력 범위에서 빼고 그 사실을 갱신 기록에 남긴다.
- 작업 시작에 기존 drift와 이번 변경을 구분한다. 해당 진입점·구성·연결을 다시 읽고 영향 받은 지도만 갱신한다. 구조가 그대로이면 확인한 범위와 “지도 변경 없음”을 보고하며 무의미한 렌더링·레이아웃 교체를 하지 않는다. 상태/검증 결과만 달라졌다면 그 정본만 갱신한다.
- 다른 PC·브랜치에서 갱신한 manifest를 Git으로 병합하면 충돌 없이 합쳐진 줄에도 한쪽의 fingerprint만 남아 병합된 입력 파일과 맞지 않을 수 있다. 자동 병합 결과를 대조 완료로 보지 않는다. 병합 뒤 입력 집합과 hash를 작업 트리에서 다시 계산하고, 양쪽의 기존 drift·이번에 병합하며 읽은 변경·미검토 변경으로 다시 분류한다. 각 PC의 검증 기록과 증거 경로는 출처 PC를 구분해 보존하며 이 clone에 없는 증거를 현재 검증으로 링크하지 않는다.
- 공유되는 진입점·manifest 문구에는 "이 PC" 같은 상대 표현을 쓰지 않는다. 커밋돼 다른 PC에서 열리면 대상이 바뀐다. 출처는 작성 커밋(예: `f80f66e 작성 PC`)이나 OS처럼 어느 clone에서도 같은 뜻인 식별자로 적고, 어느 PC인지는 그 clone에 남은 작업 디렉터리처럼 확인 가능한 근거로 정한다. 다른 PC의 문구를 이어 쓸 때는 기존 "이 PC"를 그대로 두지 않고 출처를 다시 확인해 바꾼다(2026-10-12: 앞선 작업이 다른 PC의 동기화 근거를 "이 PC" 문구째 이어 써서, 이 clone에 없는 디렉터리를 이 PC의 근거로 표시했다).

### 커밋 근거 지도 — 구별해서 사용

Archify 3.0.1의 native source 검증은 고정 commit의 Git blob을 읽으며 dirty 파일이나 `local-only`를 작업 트리 snapshot으로 인정하지 않는다. 이 모드에서는 실제 revision·검토한 소스 범위와 `--repo-root`를 사용한다. 미커밋 변경은 별도 미반영 사항으로 표시한다. 문서화를 위해 커밋을 강제하거나 자동 생성하지 않는다. `local-only`도 저장소 URL/경로를 HTML에 포함하므로 비공개 정보의 공개 허가가 아니다.

근거: [고정 배포본의 repository-authoring](https://github.com/tt-a1i/archify/blob/v3.0.1/archify/references/repository-authoring.md), [schema](https://github.com/tt-a1i/archify/blob/v3.0.1/archify/schemas/architecture.schema.json). Archify 카드 문자열은 링크가 아니고 native 상태/함수 목록 필드도 없다. 없는 schema 필드를 추가하지 말고 진입점 목차와 지도 label/card를 사용한다. 업스트림 최신 릴리스는 [v3.1.0](https://github.com/tt-a1i/archify/releases/tag/v3.1.0)(2026-10-13)이지만 이 레포의 번들은 3.0.1로 고정돼 있고 이 문서의 Archify 동작 서술은 3.0.1에만 해당한다. 문서 최신화를 이유로 번들을 갱신하지 않는다(확인 2026-10-15).

## 작업·갱신·게시 절차

1. **탐색과 위치 공유:** 유지 선언·진입점·manifest를 읽고 시작 시 drift를 확인한다(스킬의 `status`, 읽기 전용). 이번 변경의 위치/책임/검증은 「사용자 참여」대로 짧게 알리고 진행한다.
2. **구현과 근거 확인:** 실제 코드와 참조/등록/조건을 읽고 구현·스모크 검증한다. 노드/연결/핵심 진입점/상태 변화가 있는지 판단한다. 병렬 작업자는 변경 경로·새 심볼·연결·검증 근거만 반환하며 **통합 담당자 한 명**이 지도·manifest·진입점을 갱신한다.
3. **후보 준비:** 스킬의 `init`이 정본 지도를 `<작업 디렉터리>/before/`에 보존하고 후보 사본 `<작업 디렉터리>/stage/`를 만든다. 원본 데이터·시각 자료는 후보 사본에서 고치고, 새 Archify 후보 JSON은 작업 디렉터리에서 작성하며 `meta.output`은 정본 HTML 상대 경로로 유지한다. 게시 전까지 정본은 바꾸지 않는다. 입력·출력·백업의 실제 부모 경로와 프로젝트 경계를 확인한다.
4. **검증:** Archify 스킬 지침을 읽고 `ARCHIFY_UPDATE_CHECK_DISABLED=1`을 적용한다. `node "<설치된 스킬>/bin/archify.mjs" finalize architecture "<후보.json>" "<작업 디렉터리>/archify/<view>/<revision>/<view>.html" --quality showcase --json --out-dir "<작업 디렉터리>/archify/<view>/<revision>"`로 검증하고, 모든 gate를 통과한 후보 JSON과 출력 HTML만 후보 사본의 `<view>.architecture.json`·`<view>.html`로 바이트 그대로 복사한다. 출력 파일 이름이 `<view>.html`이어야 `publish`가 그 실행의 영수증(`<view>.finalize-summary.json`)을 찾는다. 커밋 근거 모드에만 `--repo-root`를 붙인다. 명령의 출력 경로는 선언에서 선택하며 JSON이 지정한 임의 외부 경로를 실행 권한으로 취급하지 않는다. PATH에 `node`가 없으면 런타임을 설치하지 않고 이미 설치된 신뢰 실행 파일(예: Windows Visual Studio 번들 `MSBuild/Microsoft/VisualStudio/NodeJs/node.exe`)의 버전(>=18)을 확인해 사용한다. 실행 파일 종류·버전과 절대 경로는 작업 디렉터리의 증거와 보고에만 남긴다. 스킬의 `build`가 원본 데이터의 형식·글 길이·금지 표기·파일과 심볼·링크·노드 연결을 검사하고 진입점을 만든다. 진입점과 시각 자료는 최대화한 실제 브라우저에서 이미지 표시·GIF 반복·영상 재생·지도 안 상대 경로 동작을 확인하고(지도 밖을 가리키는 링크는 후보 위치에서 열리지 않으므로 `build`의 존재 검사로 확인한다), [화면 설계의 게시 전 점검](/project-map-design.md#게시-전-점검)을 수행한 뒤 확인 결과를 작업 디렉터리에 남긴다.
5. **통과 후 게시:** 스킬의 `publish`로 게시한다. 필요한 모든 gate가 통과한 후보 JSON/HTML과 시각 자료만 바이트 그대로 정본 경로에 반영하고, 시작 뒤 정본이 바뀌었으면 덮어쓰지 않고 멈춘다. 빌드와 브라우저 확인의 기록은 진입점만이 아니라 게시할 후보 전체(원본 데이터·관계도·시각 자료·글꼴)의 해시에 묶고, 게시 직전 그 해시를 다시 계산해 대조한다. 진입점만 묶으면 확인 뒤 관계도나 시각 자료를 바꿔 끼워도 통과한다. 이전본을 보존하고 JSON·HTML·시각 자료의 raw hash가 검증본과 같은지 확인한 뒤 manifest/상태를 마지막에 갱신한다. 부분 게시 실패면 이전 snapshot을 보존하고 불일치를 차단 상태로 표시한다. 전체 파일 묶음의 crash-atomic 교체를 보장한다고 주장하지 않는다.
6. **증거 경계:** `finalize`는 deliver 후 browser gate를 실행하므로 정본에 직접 실행하면 실패해도 새 HTML이 남을 수 있다. 따라서 지속 지도는 작업 디렉터리에서 먼저 검증한다. `.delivery.json`·pending/lock·검증 영수증은 원래 검증 디렉터리에 보존하고 정본으로 복사하거나 경로를 고쳐 쓰지 않는다. 게시본은 hash가 같은 **검증본의 복사본**이지 게시 경로에서 native provenance를 새로 검증한 결과가 아니다.
7. **실패 처리:** 검증 실패 시 기존 정본 JSON/HTML은 유지하고, 진입점에는 미반영 범위·실패/차단 원인과 마지막 검증 snapshot을 표시한다. 영수증/잠금 삭제로 통과시키거나 더 좁은 의미의 그림으로 요구사항을 숨기지 않는다. 코드 구현과 문서 반영의 완료 여부를 분리해 보고하며 과거 HTML을 현재 검증본처럼 제시하지 않는다.
8. **변경 보고:** 이번 변화·안 바뀐 경계·결정/근거·검증·미완료·정본 링크를 보고한다. 진입점에는 최근 의미 있는 변경과 결정을 한 줄씩 남기거나 기존 changelog로 연결한다([화면 설계의 갱신할 때](/project-map-design.md#갱신할-때)). 도구 호출이나 매 저장 단위 이력, 작업 일지는 화면에 두지 않는다.

Delta는 구조·계약 변화가 있어 비교가 유용하거나 사용자가 요청할 때만 만든다. 변경 전후 실제 JSON과 안정된 노드/연결 ID를 사용한다. 검토한 3.0.1 명령은 `compare architecture <base.json> <head.json> <delta.html> --receipt <receipt.json> --quality showcase --json`이며 작업 디렉터리에 출력한다(`--out-dir` 아님). Delta는 작성된 그래프의 비교이지 실제 호출 추적·전체 변경 영향 분석이 아니다. 단순 로직 수정에 Delta를 의무화하지 않는다.

## 완료 보고 기본형

```text
위치: 전체 지도 > 영역 > 책임/심볼
변경: 사용자에게 의미 있는 변화와 유지한 경계
지도: 영향 받은 view/노드/연결, 또는 확인한 범위에서 변경 없음
검증: 코드 실행 / 소스 대조 / fingerprint / 렌더·브라우저 결과를 구분
남은 항목: 실패·미실행·미반영·사용자 결정이 필요한 것만
보기: 프로젝트 진입점과 필요한 상세 지도
```

표현은 실제 작업 규모에 맞춰 줄인다. 매 작업에 여섯 제목을 기계적으로 붙이거나 이미 표시한 파일 목록을 반복하지 않는다. 모델 지침과 문서 계약이며 자동 분석기·백그라운드 watcher·강제 완료 게이트가 아니다. 학습·독립 검토·검증 산출물 보존은 기존 [워크플로](/workflow.md)를 함께 따른다.
