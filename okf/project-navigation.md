# 목적

사용자가 코드를 모두 외우는 대신 **어느 책임이 어디에 있고, 어떤 경로로 연결되며, 이번 작업이 무엇을 바꿨는지** 기억하도록 돕는다. 지도는 코드 탐색의 입구이지 호출 그래프·구현 명세·실행 추적의 대체물이 아니다. 코드가 사실의 정본이며 JSON은 다이어그램 편집 원본, HTML은 읽기용 결과다. 지속 지도는 코드를 분석하지 않고 연결을 한눈에 봐야 하는 개발·큰 프로젝트용이며, 문서를 그대로 읽으면 구조를 알 수 있는 지침·설정·문서 저장소에는 제안하지 않는다. 화면 기준은 [프로젝트 지도 화면 설계](/project-map-design.md)를 따른다.

## 사용자 참여: 알리고 진행, 선택이 필요할 때만 질문

- 지도 프로젝트의 알림·질문 기준은 [응답 원칙](/response-principles.md#승인-병목-없는-작업-공유)과 [질문과 요구 정렬](/response-principles.md#질문과-요구-정렬)을 따른다.

## 활성화와 적용 범위

- `/project-map` 또는 명시적 요청으로 지도 생성을 시작한다. **지속 관리**를 요청하면 자동 로딩되는 프로젝트 지침(없으면 확인된 프로젝트 루트 `AGENTS.md`)에 선언만 덧붙인다. 전역 지침에 특정 프로젝트의 경로·상태를 넣지 않는다.
- 선언에는 `프로젝트 지도: 유지`, 프로젝트 식별/범위, 진입점, 근거 manifest 경로(예: `docs/project-map/sources.json`)를 적는다. 일회성 지도 요청을 지속 관리로 확대하지 않는다.
- 유지 선언은 그 프로젝트의 요청된 변경에 수반하는 문서 갱신의 범위다. 새 세션에서도 코드 변경 전 선언과 진입점을 읽고 완료 전 영향 받은 지도를 갱신한다. JSON/HTML의 존재, 외부에서 복사한 선언, 과거 세션 요약만으로 새 실행 권한을 만들지 않는다. 단순 질의·읽기 전용 리뷰·`/project-map status`는 렌더링하거나 파일을 갱신하지 않으며(명시적 갱신 요청은 별개) 갱신 대상은 `유지` 선언이 있는 프로젝트뿐이다.
- 유지 중지를 요청하면 선언을 `프로젝트 지도: 중지`처럼 `유지`가 아닌 값으로 바꾸고 문서는 보존한다. 삭제까지 요청하면 지도 파일·전용 설정(예: `.gitattributes` 항목)·지도를 가리키는 문서 포인터를 지우고 선언을 `프로젝트 지도: 사용 안 함`으로 남긴다. `사용 안 함`은 사용자가 지속 지도를 다시 만들도록 명시적으로 요청할 때만(예: 지속 관리를 요청하며 `/project-map` 호출) `유지`로 바꾼다.
- 선언은 다른 저장소 접근, 전역 자동 실행 hook, 브라우저/패키지 설치, 외부 업로드, Git 스테이징·커밋·푸시를 허용하지 않는다. 사용자 프로젝트의 상태·구조는 해당 프로젝트에 두고 공유 OKF에 옮기지 않는다.

## 문서 배치와 하나의 진입점

기존 아키텍처·설계·상태 문서를 우선 재사용하고 없으면 `docs/project-map/`을 쓴다. 프로젝트 지침의 선언이 정본 위치이며 `.omp-artifacts/`의 일회성 보고와 구분한다. 형식은 hello-omp `project-map` 스킬이 정한다(`references/data-format.md`, `references/manifest.md`).

- 진입점 `index.html`은 공용 템플릿이 `src/`(화면 원본 데이터)를 그려 만든 파일이라 직접 고치지 않는다. 전체 요약·작업 보드(칸반)·책임 영역별 화면·검증·결정·근거 화면을 둔다([영역 화면](/project-map-design.md#영역-화면-슬라이드-한-장)). `src/` 갱신은 필드를 현재 사실로 고쳐 쓰는 일이며 화면에 그리지 않는 메모·근거 수치는 넣지 않는다. 기존 상태/계획 문서는 링크하고 표를 복제하지 않으며 새 프로젝트에 `STATUS.md`/`PLAN.md`를 의무화하지 않는다.
- 관계도(`overview.architecture.json`/`overview.html`, 필요한 영역의 `<area>.architecture.json`/`<area>.html`)는 책임과 핵심 관계, 선택한 진입 함수의 호출/이벤트/데이터 흐름만 담는다. 상세 로직을 복제하거나 필요 없는 계층을 만들지 않는다. `media/`(시각 자료)·`fonts/`(공용 글꼴·사용 허가서, 프로젝트마다 바꾸지 않음)·`sources.json`(manifest, 프로젝트 상대 POSIX 경로만)은 스킬이 게시하고, 영수증·검증 스크린샷·실패 후보·이전본·원본 녹화는 작업 디렉터리에 보존한다.

목차는 `책임 / 실제 파일 / 핵심 심볼 / 하는 일 / 상세 지도`를 연결하고 `하는 일`에는 누가 호출·발행·소유하는지와 무엇에 의존하는지를 실제 관계로 쓴다. 매니저 클래스만 나열하거나 public 함수만 추출하지 않으며 책임 경계 설명에 필요한 진입점·private 조정 함수·엔진 콜백도 고를 수 있다. **노드·함수 개수의 고정 상한은 두지 않는다.** 복잡해지면 책임별 상세 화면으로 나누고 안정된 ID·위치·명칭을 유지하며, 목차 표는 영역 본문의 요점·시각 자료 아래에 둔다.

## 화면 기술 계약과 Archify의 역할

본문은 역할·요점·시각 자료·실제 파일/함수·계약·상태·계획을, Archify는 **같은 영역의 현재 관계**만 담당한다. 별도 메뉴·카드·상태표를 가진 두 번째 앱처럼 붙이거나 구조를 장문으로 다시 설명하지 않는다. 각 `view:node-id`는 하나의 본문 영역에 대응하고 함수/계획 링크도 같은 ID를 쓴다.

- 고정 Archify 3.0.1 템플릿의 `?embed=1`은 도구 메뉴·카드·노드 목록을 숨기는 삽입 동작이며 내부 탐색은 제한된다. 정적 관계 보기로 설명하고 확대/탐색 원본 링크를 제공한다. `#focus=<node-id>`로 본문 함수와 그림 위치를 연결할 수 있다. 생성 HTML/런타임은 임의 수정하지 않는다.
- 관계도 삽입 높이는 게시한 SVG의 실제 viewBox 비율로 계산하고 공통 고정 높이로 맞추지 않는다. 로컬 파일로 연 최대화 브라우저에서 그림 경계·공백·hash 경로·검색·뒤로가기·새로고침을 확인한다.
- 고정 Archify 3.0.1 showcase validate의 넓은 Reader 예산은 renderer가 정한 canvas(`meta.viewBox` 미지정, `intrinsic-height`)·가로/세로 비율 1.55 이상·유효한 `declared-wide-v1` 글자 크기 계약을 함께 충족할 때만 적용한다. `meta.viewBox`를 직접 지정했거나 해당 계약이 없으면 비율과 무관하게 930px 데스크톱 예산을 쓰며, 이때 8px 관계 라벨의 viewBox 폭이 1240px를 넘으면 6px 하한에 걸려 실패한다. 세로로 긴 상세 지도는 3열 정도로 배치하고, 여러 열에 걸친 넓은 노드의 자동 경로가 캔버스 바깥으로 돌아 폭을 늘리지 않도록 일반 크기 노드와 필요한 side 지정으로 고정한다. 폭을 늘린 경로·라벨은 `validate --layout-json` 좌표로 찾는다.

## 관계와 상태를 사실대로 표시

- 호출·이벤트·데이터 읽기/쓰기·소유/수명·설정/배포·지침 참조는 라벨로 구분한다. 이름·디렉터리 위치만으로 호출선을 만들지 않고 실제 호출부·등록·조건까지 읽으며 동적 연결은 등록 지점과 확인 한계를 표시한다.
- 코드 위치는 `파일 · 심볼명`으로 쓰고 줄 번호를 넣지 않는다(포맷 수정만으로 틀어진다). 줄 단위 근거는 fingerprint로 고정된 근거 기록에만 둔다. 조사 에이전트가 반환한 인용은 게시 전 grep/read로 재대조한다. 행별 검증 근거가 기본 근거와 다르면 그 행의 근거 링크가 해당 기록을 가리키게 하고 실행 기록을 화면 문장에 풀어 쓰지 않는다([화면 설계](/project-map-design.md#읽는-화면과-근거-기록)).
- 현재 구현과 제안/계획을 같은 확정 선으로 섞지 않는다. 구현 상태(`미착수/진행/구현/차단`)와 검증 상태(`미실행/통과/실패/부분/재검증 필요`)를 별도 표지로 두고 범위·환경·명령·관찰 결과가 근거 기록에 없는 "완료"를 쓰지 않는다. 백분율·진행 막대·일정은 쓰지 않고 진척은 열별 카드 수로만 보인다([칸반 보드](/project-map-design.md#칸반-보드)).
- HTML은 정적 스냅샷이다. 진입점에 근거 snapshot ID와 적용 범위를 표시하고 열기만 하면 현재 소스와 동기화된다는 인상을 주지 않는다(`/project-map status`가 소스 변화를 다시 대조한다). 검증 근거는 그것을 만든 환경·snapshot에만 귀속하며 과거 요약·다른 작업·다른 PC의 영수증을 현재 "통과"로 옮기지 않는다.

## 할 일과 계획도 같은 화면에서 확인

- 사용자 요구·기존 이슈/계획·확인된 결함/검증 공백을 근거로 **확정된 할 일**과 **검토할 제안**을 분리한다. 완료된 것만 나열하지 않으며 화면을 채우려고 기능·리팩터링·추정 요구사항을 만들지 않고 현재 코드에 없는 대상은 기존 구조처럼 그리지 않는다. 진입점에서는 작업 보드로 보여 주며([칸반 보드](/project-map-design.md#칸반-보드)) 각 항목은 안정된 ID, 근거, 대상 영역·노드, 상태(`미착수/진행/차단/완료`), 의존 항목, 관찰 가능한 완료 기준을 갖는다.
- 계획 등록은 실행·권한 확대 승인이 아니며 계획 행마다 승인을 요구하지도 않는다. 현재 요청/승인된 범위 안의 항목만 수행하고 진행 가능·막힌 항목과 권장 다음 행동의 이유를 드러낸다. 백분율·진행 막대·일정·견적은 넣지 않고 진척은 열별 카드 수로만 보인다([칸반 보드](/project-map-design.md#칸반-보드)). 부분 완료·검증 부족은 완료로 올리지 않고 남은 수락 기준을 보존하며 같은 목표를 새 ID로 반복 생성하지 않는다.

## 근거와 신선도

### 작업 트리 지도 — 개발 중 기본

실제 작업 트리를 읽고 기록한 상대 경로·심볼·관계 근거를 진입점에 둔다. JSON에는 `meta.repository`와 native `sources`를 넣지 않고 **작업 트리 수동 대조 / 커밋 근거 미검증**을 명시한다. Archify의 산출물·브라우저 검증은 별도로 수행하며 소스 의미가 기계적으로 검증됐다고 부르지 않는다.

- UTF-8 텍스트는 CRLF만 LF로 정규화한 SHA-256(`sha256-text-lf`), 바이너리는 원시 SHA-256(`sha256-bytes`)처럼 계산 방식을 명시하고 외부 Git clean filter를 실행하지 않는다. 게시 JSON/HTML과 영수증 연결은 **원시 바이트 hash**로 확인하므로 지도 디렉터리는 프로젝트 `.gitattributes`에 `<지도 경로>/** -text`로 둔다. `eol=lf`나 `text`는 PNG·WOFF2 같은 바이너리도 변환해 바이트를 바꾼다(PNG 서명에 CR LF가 들어 있다).
- fingerprint는 기록 범위의 신선도 검사이지 의미 정확성·의존성 전수 탐색·실행 성공의 증명이 아니다. 수정 내용을 읽지 않고 hash만 갱신하지 않으며 새 파일·사라진 파일·지도 대응이 없는 경로는 `변경/미분류`로 보고한다.
- 근거는 그것을 만든 PC·브랜치·snapshot에 귀속한다. 다른 PC·브랜치에서 갱신한 manifest를 Git으로 병합하면 충돌 없이 합쳐진 줄에도 한쪽의 fingerprint만 남을 수 있으므로 자동 병합을 대조 완료로 보지 않고, 입력 집합과 hash를 작업 트리에서 다시 계산해 기존 drift·이번에 읽은 변경·미검토 변경으로 재분류한다. 각 PC의 검증 기록·증거 경로는 출처를 구분해 보존하고 이 clone에 없는 증거를 현재 검증으로 링크하지 않는다. 공유되는 진입점·manifest 문구에는 "이 PC" 같은 상대 표현을 쓰지 않고 OS·환경 라벨처럼 어느 clone에서도 같은 뜻인 식별자로 출처를 적으며, 커밋 해시는 진입점에 두지 않고 manifest·근거 기록에만 둔다.

### 커밋 근거 지도 — 구별해서 사용

Archify 3.0.1의 native source 검증은 고정 commit의 Git blob을 읽으며 dirty 파일이나 `local-only`를 작업 트리 snapshot으로 인정하지 않는다. 이 모드에서는 실제 revision·검토한 소스 범위와 `--repo-root`를 사용하고 미커밋 변경은 별도 미반영 사항으로 표시한다. 문서화를 위해 커밋을 강제하거나 자동 생성하지 않는다. `local-only`도 저장소 URL/경로를 HTML에 포함하므로 비공개 정보의 공개 허가가 아니다. Archify 카드 문자열은 링크가 아니고 native 상태/함수 목록 필드도 없으므로 없는 schema 필드를 추가하지 말고 진입점 목차와 지도 label/card를 쓴다([repository-authoring](https://github.com/tt-a1i/archify/blob/v3.0.1/archify/references/repository-authoring.md), [schema](https://github.com/tt-a1i/archify/blob/v3.0.1/archify/schemas/architecture.schema.json), 확인 2026-10-15). 이 레포의 번들은 3.0.1로 고정돼 있고 위 Archify 동작 서술은 3.0.1에만 해당한다. 업스트림에 [v3.1.0](https://github.com/tt-a1i/archify/releases/tag/v3.1.0)이 있어도 문서 최신화를 이유로 번들을 갱신하지 않는다.

## 작업·갱신·게시 절차

1. **탐색과 위치 공유:** 유지 선언·진입점·manifest를 읽고 시작 시 drift를 확인해(스킬의 `status`, 읽기 전용) 기존 drift와 이번 변경을 구분한다. 이번 변경의 위치/책임/검증은 「사용자 참여」대로 알리고 진행한다. 구조가 그대로이면 확인한 범위와 "지도 변경 없음"을 보고하며 무의미한 렌더링·레이아웃 교체를 하지 않는다.
2. **구현과 근거 확인:** 실제 코드와 참조/등록/조건을 읽고 구현·스모크 검증하며 노드/연결/핵심 진입점/상태 변화가 있는지 판단한다. 병렬 작업자는 변경 경로·새 심볼·연결·검증 근거만 반환하고 **통합 담당자 한 명**이 지도·manifest·진입점을 갱신한다.
3. **후보 준비:** 스킬의 `init`이 정본을 작업 디렉터리 `before/`에 보존하고 후보 사본 `stage/`를 만든다. 원본 데이터·시각 자료와 새 Archify 후보 JSON(`meta.output`은 정본 HTML 상대 경로)은 후보에서 고치고 게시 전까지 정본은 바꾸지 않는다. 입력·출력·백업의 실제 부모 경로와 프로젝트 경계를 확인한다.
4. **검증:** Archify 스킬 지침을 읽고 `ARCHIFY_UPDATE_CHECK_DISABLED=1`을 적용한다. `node "<설치된 스킬>/bin/archify.mjs" finalize architecture "<후보.json>" "<작업 디렉터리>/archify/<view>/<revision>/<view>.html" --quality showcase --json --out-dir "<작업 디렉터리>/archify/<view>/<revision>"`로 검증하고, 모든 gate를 통과한 후보 JSON과 출력 HTML만 후보 사본의 `<view>.architecture.json`·`<view>.html`로 바이트 그대로 복사한다(출력 이름이 `<view>.html`이어야 `publish`가 영수증 `<view>.finalize-summary.json`을 찾는다). 커밋 근거 모드에만 `--repo-root`를 붙이고, 출력 경로는 선언에서 고르며 JSON이 지정한 외부 경로를 실행 권한으로 취급하지 않는다. PATH에 `node`가 없으면 런타임을 설치하지 않고 이미 설치된 신뢰 실행 파일(예: Windows Visual Studio 번들 `MSBuild/Microsoft/VisualStudio/NodeJs/node.exe`)의 버전(>=18)을 확인해 쓰며 그 종류·버전·절대 경로는 작업 디렉터리의 증거와 보고에만 남긴다. 이어서 스킬의 `build`로 원본 데이터를 검사해 진입점을 만들고 최대화한 실제 브라우저에서 이미지·GIF·영상·지도 안 상대 경로 동작을 확인한 뒤(지도 밖 링크는 후보 위치에서 열리지 않으므로 `build`의 존재 검사로 확인) [화면 설계의 게시 전 점검](/project-map-design.md#게시-전-점검)을 수행하고 결과를 작업 디렉터리에 남긴다.
5. **통과 후 게시:** 스킬의 `publish`로 모든 gate를 통과한 후보만 바이트 그대로 정본에 반영하며 시작 뒤 정본이 바뀌었으면 덮어쓰지 않고 멈춘다. 빌드와 브라우저 확인의 기록은 진입점만이 아니라 게시할 후보 전체(원본 데이터·관계도·시각 자료·글꼴)의 해시에 묶고 게시 직전 다시 계산해 대조한다(진입점만 묶으면 확인 뒤 바꿔 끼운 관계도·시각 자료가 통과한다). 이전본을 보존하고 JSON·HTML·시각 자료의 raw hash가 검증본과 같은지 확인한 뒤 manifest/상태를 마지막에 갱신한다. 부분 게시 실패면 이전 snapshot을 보존하고 불일치를 차단 상태로 표시하며 전체 파일 묶음의 crash-atomic 교체를 주장하지 않는다.
6. **증거 경계:** `finalize`는 deliver 후 browser gate를 실행하므로 정본에 직접 실행하면 실패해도 새 HTML이 남을 수 있다. 지속 지도는 작업 디렉터리에서 먼저 검증한다. `.delivery.json`·pending/lock·검증 영수증은 원래 검증 디렉터리에 보존하고 정본으로 복사하거나 경로를 고쳐 쓰지 않는다. 게시본은 hash가 같은 **검증본의 복사본**이지 게시 경로에서 native provenance를 새로 검증한 결과가 아니다.
7. **실패 처리:** 검증 실패 시 기존 정본은 유지하고 진입점에는 미반영 범위·실패/차단 원인과 마지막 검증 snapshot을 표시한다. 영수증/잠금 삭제로 통과시키거나 더 좁은 의미의 그림으로 요구사항을 숨기지 않는다. 코드 구현과 문서 반영의 완료 여부를 분리해 보고한다.
8. **변경 보고:** 이번 변화·안 바뀐 경계·결정/근거·검증·미완료·정본 링크를 보고한다. 진입점에는 최근 의미 있는 변경과 결정을 한 줄씩 남기거나 기존 changelog로 연결한다([갱신할 때](/project-map-design.md#갱신할-때)).

Delta는 구조·계약 변화가 있어 비교가 유용하거나 사용자가 요청할 때만 만든다. 변경 전후 실제 JSON과 안정된 노드/연결 ID를 사용한다. 검토한 3.0.1 명령은 `compare architecture <base.json> <head.json> <delta.html> --receipt <receipt.json> --quality showcase --json`이며 작업 디렉터리에 출력한다(`--out-dir` 아님). Delta는 작성된 그래프의 비교이지 호출 추적·전체 변경 영향 분석이 아니며 단순 로직 수정에 의무화하지 않는다.

## 완료 보고 기본형

```text
위치: 전체 지도 > 영역 > 책임/심볼
변경: 사용자에게 의미 있는 변화와 유지한 경계
지도: 영향 받은 view/노드/연결, 또는 확인한 범위에서 변경 없음
검증: 코드 실행 / 소스 대조 / fingerprint / 렌더·브라우저 결과를 구분
남은 항목: 실패·미실행·미반영·사용자 결정이 필요한 것만
보기: 프로젝트 진입점과 필요한 상세 지도
```

표현은 작업 규모에 맞춰 줄이고 여섯 제목을 기계적으로 붙이거나 이미 표시한 파일 목록을 반복하지 않는다. 독립 검토·검증 산출물 보존은 [워크플로](/workflow.md)를 함께 따른다. 이 문서는 모델 지침이며 자동 분석기·watcher·강제 완료 게이트가 아니다.
