# 워크플로

## 개발 흐름
설계 → 검증 → 계획 → 구현 → 테스트 → 리뷰 → 통합 최종 응답. 필요한 선행 결정·정보는 대화와 기존 산출물에서 확인하고, 없으면 확보하거나 사용자에게 확인한다. 각 단계마다 새 문서를 만들라는 뜻은 아니며 보고 매체는 [응답 원칙](/response-principles.md)의 기준으로 선택한다.

## 검증·독립 평가
- 검증 없이 완료 선언 금지 — 실행 가능한 체크(테스트/빌드/린트)의 증거로만 "완료"를 주장한다.
- 생성자가 자기 결과를 평가하지 않는다 — 독립 평가는 fresh context `reviewer`·`security-reviewer` 에이전트에 맡긴다. 필요한 검토 결과를 받기 전에 완료 답변을 공개하지 않는다. 비동기 advisor의 활성 상태나 대기 설정은 독립 검토 완료의 증거가 아니다.

## 수락 기준-증거 폐루프
- 다단계·대규모 작업은 구현 전에 사용자 요구를 원자화하고, 각 요구에 관찰 가능한 완료 결과와 검증 경로를 대응시킨다. 활동 목록이나 구현 세부만으로 완료 기준을 대신하지 않는다.
- 완료 증거는 실제 실행·관찰한 명령 또는 시나리오, 종료 상태나 관찰 결과, 판정에 필요한 출력, 산출물·정본 위치로 제한한다. 완료 주장은 이 증거가 직접 검증한 계약 범위를 넘지 않는다.
- 완료 근거로 쓰는 검사는 결함이 있을 때 실패해야 한다. 성공 표시는 모든 단언이 통과한 뒤에만 내고, 부재를 완료 근거로 삼을 때는 같은 판정기가 알려진 양성 대상을 탐지하는지 확인하며, 사용자가 제시한 목표 수치의 달성은 구현 결과나 정본에서 독립 측정한다.
- 미충족·차단·포기한 기준은 삭제하거나 축소하지 않고 원래 요구, 시도한 수단, blocker, 재개 조건과 함께 드러낸다. 하나라도 남으면 전체 완료라고 표현하지 않는다.
- 단순 사실 답변이나 사소한 편집에는 별도 원장·체크리스트를 만들지 않는다. 조용한 범위 축소의 위험이 구조화 비용보다 큰 작업에만 적용한다.

## 작업 파일의 저장 위치
- **정본과 작업용 파일을 구분한다.** 제품 코드·영구 회귀 테스트·설정·정식 문서는 프로젝트의 기존 위치를 유지한다. 이 규칙은 작업용 스크립트·재현 데이터·로그·스크린샷·필요한 보고서·복구 사본처럼 작업 수행을 위해 따로 만드는 파일에 적용한다. 파일 생성 필요 여부는 [응답 원칙](/response-principles.md)을 먼저 따르며, 빈 디렉터리·보고서·목록 파일을 의무적으로 만들지 않는다.
- **작업 루트는 하나다.** 사용자 지정 경로 → 프로젝트에 명시된 작업 산출물 경로 → `<프로젝트 루트>/.omp-artifacts/<작업-ID>/` 순으로 선택한다. 지정 경로가 공용 산출물 루트이면 작업-ID 하위로 나누고 특정 작업 디렉터리이면 그대로 쓴다. 프로젝트 루트는 Git 작업 트리 루트이며, 비 Git 작업은 확인된 작업 디렉터리를 쓴다. 홈·파일시스템 루트·경계 불명확 시 범위를 먼저 확인하며 OMP 사용자 설정 루트를 작업 루트로 쓰지 않는다. 하위 cwd마다 별도 루트를 만들지 않는다. 작업 파일만을 위해 `.omp/`를 만들지 않는다. 비어 있지 않은 `.omp/`가 상위 프로젝트 지침 탐색을 가릴 수 있으므로 OMP 설정 경로와 분리한다(근거: `omp://context-files.md`의 nearest non-empty `.omp` 규칙).
- **작업-ID는 작업 단위로 고정한다.** 재개·위임에서는 선택한 산출물 루트를 직접 열거하거나 ignore를 적용하지 않는 탐색으로 기존 작업 디렉터리를 확인한다. 대화·완료 보고·생성 기록으로 같은 작업임이 확인되면 기존 ID를 재사용하며 파일명 유사성만으로 다른 작업을 합치지 않는다. 식별이 모호하면 관련 경로를 확인받고 중복 디렉터리를 만들지 않는다. 새 작업만 목적명과 충돌 방지 식별자를 조합하고 분석·구현·검증·리뷰에서 재사용한다. 다른 작업의 파일을 덮어쓰지 않는다. 파일은 바로 아래에 두되 필요할 때만 `scripts/`, `evidence/`, `backups/` 같은 하위 디렉터리를 만든다. 단계별·도구별로 프로젝트 루트·`/tmp`·홈에 별도 저장소를 늘리지 않는다.
- **위임에도 같은 계약을 전달한다.** 부모는 정확한 작업 루트·작업-ID·파일 소유권을 지정한다. 공유 가능한 실행 환경에서는 같은 작업 루트의 소유 경로만 쓰며, 서로의 파일을 덮어쓰지 않는다. 격리 worktree·원격·샌드박스가 공유 경로를 지원하지 않으면 그 환경의 대응 작업 디렉터리를 쓰고, 부모에게 실제 경로·확인 방법을 반환한다. 격리 종료 시 사라질 증거는 종료 전에 부모의 작업 루트에 수집하며, 원본과 최종 보존본을 구분해 보고한다.
- **출력 경로를 선택할 수 있으면 실행 전에 지정한다.** 테스트·브라우저·빌드 도구의 작업용 출력도 같은 디렉터리로 지정하되, 프로젝트 정본·빌드 계약을 깨지 않는다. 고정 출력 경로·프로젝트 밖 샌드박스·외부 리소스는 실제 위치/ID와 이유를 보고한다. OMP가 관리하는 `local://`·`artifact://`·세션·DB·blob 저장소는 파일 경로처럼 재배치하지 않는다. 사용자가 보존·확인해야 할 증거라면 보존 가능한 작업 루트로 내보내고 그 경로를 보고한다.
- **기존 파일과 보안 경계를 보존한다.** 산재한 기존 파일은 이 규칙만으로 옮기거나 삭제하지 않는다. 상위 경로의 링크·권한 때문에 작업 경계를 벗어나면 임의로 쓰지 않고 안전한 위치를 확인한다. Git에서는 기존 ignore 규칙을 우선하고, 추가가 필요하면 `git rev-parse --git-path info/exclude`로 확인한 로컬 제외 파일에 작업 경로만 추가한다. 공유 `.gitignore` 변경은 사용자가 요청했거나 저장소 정책 정비 범위에 포함된 경우에만 한다. `.omp/` 전체를 무시하지 않으며 `.omp-artifacts/`처럼 선택한 산출물 경로만 제외한다. ignore는 비밀 보호가 아니므로 크리덴셜·PII를 저장하지 않는다. 정식 소스·테스트로 채택하는 파일은 프로젝트 정본 경로에서 관리한다.
- **배치와 정리는 별개다.** 경로가 통일되어도 자동 삭제 승인이 생기지 않는다. 아래 보존 규칙을 유지하며 완료 보고에 작업 루트·예외 위치·상태·확인 방법·정리 영향을 적는다. `/cleanup`은 정해진 경로뿐 아니라 생성 기록과 소유·사용 여부를 확인한다.

## 검증 산출물 보존과 정리
- 테스트·스모크 테스트·버그 재현에서 만든 파일·데이터·설정·실행 리소스 중 사용자가 결과를 직접 확인할 수 있는 산출물은 검증 후에도 보존한다. 에이전트의 테스트 통과 보고가 사용자의 직접 검증 가능성을 대체하지 않는다.
- 보존은 실제로 생성된 검증 산출물에 적용한다. 보존 규칙을 충족하려고 보고·실행 로그를 새 파일로 만들지 않는다. 터미널 출력으로 충분한 검증은 명령·결과·판정 근거를 대화에 남긴다.
- 완료 보고에 각 보존 산출물의 정확한 위치, 현재 상태, 확인 방법을 적고, 남은 정리 대상과 정리 시 영향을 구분해 알린다. 자동 삭제·원복하지 않으며 사용자가 명시적으로 정리를 요청한 뒤 수행 내역까지 보고한다.
- 테스트 러너가 에이전트 제어와 무관한 자체 수명주기로 처리하고 완료 보고의 검증 근거로 참조하지 않는 내부 캐시·격리 샌드박스만 보존 대상이 아니다. 사용자 검증 대상은 재생성 가능 여부와 무관하게 보존한다. 러너가 종료 시 제거하는 산출물이 필요하면 검증 전에 지속 가능한 사용자 확인 경로를 지정한다.
- 크리덴셜·PII, 비용 발생 리소스, 보안·운영 영향을 주는 상태는 검증 증거로 방치하지 않는다. 처음부터 비민감 샌드박스나 격리를 사용하고, 불가피하게 위험 상태가 생기면 파괴적 정리 전에 사용자에게 확인한다. 현재 노출 중인 크리덴셜이나 무단 접근처럼 즉시 차단해야 하는 보안 사고만 먼저 격리·폐기한 뒤 마스킹된 증거와 정확한 조치 내역을 남긴다.
- 이 규칙은 일반적인 마지막 cleanup보다 우선한다. 마지막 cleanup은 제품 코드의 미완성 스캐폴드·디버그 우회·제품 동작 오염 상태 제거에 적용하며 검증 산출물 정리를 포함하지 않는다. 검증 산출물 정리는 사용자 명시 요청 시 별도 작업으로 수행한다.

## 정본 검증 (프록시가 아니라 실제 경로·소스)
- 디버그 툴·에뮬레이터·에디터·로컬 실행은 배포 경로와 **다른 코드 경로**를 탈 수 있다(권한 모드·엔드포인트·환경변수 분기 차이). 프록시에서 성공했다고 배포 안전을 주장하지 않는다 — 실제 배포 경로·실행 환경에서 검증한다. 로컬↔배포 분기가 있으면 로컬에서 배포 환경변수를 주입해 그 경로를 강제 재현한다.
- 코드 생성·템플릿 산출물(생성 설정 파일·codegen)은 업데이트·재임포트 시 플레이스홀더로 되돌아갈 수 있다. 도구 UI가 "완료"로 보여도 런타임이 읽는 정본이 비어 있을 수 있다 — 실제 값이 채워진 산출물을 VCS에 커밋하고, 도구 UI가 아니라 **런타임이 읽는 정본**을 직접 검증한다.

## 독립 검토 시점과 최종 응답
- 접근·해석의 불확실성이 높아 확정 전 검토가 필요할 때, 같은 오류가 반복되거나 수렴하지 않을 때, 검증된 작업의 완료를 선언하기 전에 독립 검토를 수행한다. 단순 사실 답변·사소한 편집에 형식적인 검토 절차를 추가하지 않는다.
- 보안·영속 데이터·서버 권위·동시성 정합성에 영향을 주는 위험 변경은 구현 전 설계·불변조건·영향 범위·복구 가능성을 독립 검토한다. 재화·아이템·인증·인가·DB 마이그레이션은 비한정 사례이며, 작은 수정도 위험 기준에 해당하면 사소한 편집 예외를 적용하지 않는다. 구현 후 독립 검토·실행 검증도 유지하고, 검토가 필요한 승인·백업·복구 수단을 대체하지 않게 한다.
- 검토 대상은 실제 작업 산출물과 실행 증거, 내부에서 준비한 답변 초안이다. 코드·설정 변경은 해당 파일에 반영하되, 답변·검토 내용을 먼저 파일로 저장해야 한다는 조건은 두지 않는다.
- 순서는 내부 초안 → 독립 검토 결과 수신 → 지적별 타당성 판단 → 필요한 수정·재검증 → 통합 최종 응답이다. 유효한 지적을 반영하고 중요 지적을 채택하지 않으면 근거를 밝힌다. 검토 전 공개 메시지는 짧은 진행 상황·확인 질문·위험 경고로 제한한다. 검토가 실패하거나 결과를 받지 못했으면 검토 완료로 보고하지 않고 미완료 상태와 남은 한계를 명시한다.
- 비동기 advisor는 작업 중 위험 감시를 위해 기본 활성화(`advisor.enabled=true`)한다. 출력 정리나 최종본 혼선을 해결하려고 감시를 임의로 끄지 않는다. 이는 완료 전 독립 검토를 대체하지 않는다. OMP의 `advisor.syncBacklog=1`은 누적 검토를 제한적으로 기다리는 설정이지 응답을 검토 완료까지 숨기는 출력 게이트가 아니다. 완료 전 필요한 독립 검토는 결과를 직접 수신할 수 있는 fresh context 에이전트로 수행하고, 이미 수신한 advisor 지적도 타당성을 판단해 유효한 지적을 반영한다. 동작 근거: `omp://advisor-watchdog.md`.
- 비동기 의견이 공개된 답변의 수정을 요구하면 타당성을 확인하고 수정한 뒤 [응답 원칙](/response-principles.md)의 통합 최종본 규칙으로 다시 전달한다. 변경분만 덧붙이거나 이전 답변을 사용자가 조합하게 하지 않는다.

## 컨텍스트 관리
- 압축보다 리셋. 세션 간 이어갈 진행 맥락·일회성 선호는 에이전트 메모리에 남긴다. 컨텍스트 전달만을 위한 핸드오프 파일을 임의로 만들지 않으며, 사용자가 요청하거나 문서 자체가 필요한 경우는 [응답 원칙](/response-principles.md)의 보고 매체 기준을 따른다.
- 규칙·결정·구조·반복 오류의 재발 방지책처럼 영속 사실은 설정 레포의 소스 OKF에 남긴다. 배포본 OKF는 클린 재배포 대상이고, AGENTS.md 변경은 관리 레포에서만 수행한다.
- OKF 학습 축적은 [OKF 학습 축적 루프](/learning/accumulation.md) 기준으로 처리한다.
- 작업 전 관련 메모리·히스토리(최근 커밋·이전 결정)를 확인하고, 실제 코드/파일로 현재 상태를 검증한 뒤 진행한다.

## 배치 실행
- 대규모 작업은 계획 수립 후 실행. 배치 단위로 진행하고 체크포인트에서 검증, 실패 시 즉시 중단.
