# 워크플로

## 검증

- 완료는 실행 가능한 검증(테스트·빌드·린트·실제 실행)의 증거로만 주장하고, 그 증거가 직접 확인한 범위를 넘지 않는다. 린트·타입 검사·빌드 통과는 각 검사 범위의 증거일 뿐이다. 의미 있는 동작 변경은 실제 CLI·UI·API·게임 화면을 실행해 관찰하고, 실행할 수 없으면 검증 한계와 미충족 기준을 밝힌다.
- 동작을 테스트로 검증할 수 있으면 테스트를 먼저 쓰고 실패하는 것을 확인한 뒤 구현한다(red → green). 한 번에 한 동작씩 진행한다. 테스트는 공개 경계에서 소비자가 관찰하는 동작을 검증하며, 구현과 같은 계산으로 기대값을 만드는 동어반복이나 내부 호출·문구만 고정하는 테스트는 만들지 않는다.
- 완료 근거로 쓰는 검사는 결함이 있을 때 실패해야 한다. 판정기·검증 러너·검사 조건을 새로 만들거나 바꾸면 일부러 결함을 넣은 입력으로 한 번 실행해 실제로 실패하는지 확인한다(실패 확인 테스트). 부재를 근거로 삼을 때는 같은 판정기가 알려진 양성 대상을 탐지하는지 확인한다.
- 통과 표시를 얻으려고 검증기·기대값·수락 기준을 바꾸거나 실패 테스트를 삭제·skip하거나 대상을 제외·규칙을 끄거나 종료 코드를 숨기지 않는다. 검증기가 통과해도 금지된 수단을 썼거나 필수 제약을 어겼으면 완료가 아니다. 요청된 계약 변경이나 검증기 결함 때문에 검증 코드를 고칠 때는 근거와 바뀐 판정 범위를 밝힌다.
- Markdown 지침이나 로컬 lint 명령이 있다는 것만으로 병합·배포를 막는 강제 장치라고 주장하지 않는다. 강제는 실패로 처리되는 규칙·종료 코드·CI 연결까지 확인한 뒤에 말한다.
- 주석·커밋 메시지·구현자의 설명은 검증할 주장이지 근거가 아니다. 원래 요구와 실제 변경, 관련 호출·데이터 흐름을 독립적으로 대조하고, 확인된 결함과 미확인 후보를 구분해 보고한다.

## 수락 기준

- 다단계 작업은 구현 전에 사용자 요구를 원자화하고 요구마다 관찰 가능한 완료 결과와 검증 경로를 대응시킨다. 단순 답변·사소한 편집에는 별도 체크리스트를 만들지 않는다.
- 미충족·차단·포기한 기준은 지우거나 축소하지 않고 원래 요구·시도한 수단·차단 원인·재개 조건과 함께 드러낸다. 하나라도 남으면 전체 완료라고 하지 않는다. 차단 항목을 보존한 채 같은 요청의 독립 항목은 진행할 수 있다.

## 작업 파일의 저장 위치

- 제품 코드·영구 테스트·설정·정식 문서는 프로젝트의 정본 위치를 유지한다. 작업용 스크립트·재현 데이터·로그·스크린샷·필요한 보고서·복구 사본은 사용자 지정 경로 → 프로젝트에 명시된 산출물 경로 → `<프로젝트 루트>/.omp-artifacts/<작업-ID>/` 순으로 고른 한 디렉터리에 둔다. 필요한 파일만 만든다.
- 프로젝트 루트는 Git 작업 트리 루트, 비 Git이면 확인된 작업 디렉터리다. 홈·파일시스템 루트·OMP 설정 루트를 작업 루트로 쓰지 않는다. 작업 파일만을 위해 `.omp/`를 만들지 않는다. 비어 있지 않은 가장 가까운 `.omp/`가 프로젝트 지침 탐색을 가로채기 때문이다(`omp://context-files.md`).
- 작업-ID는 작업 단위로 고정한다. 재개·위임 때는 ignore를 적용하지 않는 탐색으로 기존 작업 디렉터리를 확인해 같은 작업이면 재사용하고, 새 작업만 목적명과 충돌 방지 식별자로 만든다. 위임할 때 작업 루트·작업-ID·파일 소유권을 전달한다.
- 도구가 선택할 수 있는 출력 경로는 실행 전에 작업 디렉터리로 지정한다. 도구 제약으로 기본 위치를 쓸 수 없으면(예: Windows 경로 길이 한도로 vcpkg 빌드가 실패해 clone만 짧은 경로에 둠) 예외 위치와 이유를 보고한다. 전역 Git 설정을 바꾸는 우회는 쓰지 않는다.
- 기존 산재 파일은 이 규칙만으로 옮기거나 지우지 않는다. 산출물 경로만 로컬 제외 파일(`git rev-parse --git-path info/exclude`)에 추가하고 공유 `.gitignore`는 요청이 있을 때만 바꾼다. Git 제외는 삭제 보호가 아니다. `git clean -x`/`-X`와 `git stash --all`은 무시된 파일도 지우므로 작업 루트를 그 대상에 넣지 않는다.

## 검증 산출물 보존과 정리

- 테스트·스모크 테스트·버그 재현에서 만든 파일·데이터·설정·실행 리소스 중 사용자가 결과를 직접 확인할 수 있는 것은 재생성 가능 여부와 무관하게 보존한다. 테스트 러너가 자체 수명주기로 관리하고 보고에서 근거로 쓰지 않는 내부 캐시·격리 샌드박스만 예외다.
- 보존은 실제로 만든 산출물에 적용한다. 보존 규칙을 채우려고 로그·보고 파일을 새로 만들지 않는다.
- 완료 보고에 보존 산출물의 위치·상태·확인 방법, 남은 정리 대상과 정리 시 영향을 적는다. 적기 전에 그 경로에 파일이 있는지 확인한다. 정리는 사용자가 명시적으로 요청한 뒤에만 한다. 이 규칙은 일반적인 마무리 cleanup보다 우선하며, 마무리 cleanup은 제품 코드의 미완성 스캐폴드·디버그 우회 제거에만 적용한다.
- 크리덴셜·PII, 비용이 드는 리소스, 보안·운영에 영향을 주는 상태는 처음부터 격리된 환경을 써서 만들지 않는다. 이미 생겼으면 파괴적 정리 전에 사용자에게 확인하되, 지금 노출 중인 크리덴셜처럼 즉시 막아야 하는 사고만 먼저 격리하고 마스킹된 증거와 조치를 남긴다.

## 검증 대상의 동일성

- 검증은 실제 소비자가 읽는 유효 설정·입력·의존성·실행 경로를 대상으로 하며, 증거는 그 환경과 snapshot에만 귀속한다. 디버그 툴·에디터·로컬 실행·생성기 UI의 성공으로 배포 경로나 런타임이 읽는 정본을 대신 증명하지 않는다. 로컬과 배포 사이에 분기가 있으면 배포 조건(환경 변수 등)을 주입해 그 경로를 재현한다.
- 검증용 사본에서 외부 접속 대상을 가짜로 바꿀 때는 활성 설정(주석이 아닌 실제 할당)을 바꾸고 활성 대상이 정확히 하나인지 단언한다. 교체가 빠져도 접속이 실패하도록 외부 이름 해석·네트워크를 막은 환경을 먼저 검토한다.
- 생성 코드는 생성기와 런타임의 버전을 대조한다. protobuf C++는 생성 코드와 런타임의 정확한 버전 일치를 요구한다([공식 보증 범위](https://protobuf.dev/support/cross-version-runtime-guarantee/#cpp), 확인 2026-10-15). 재생성 뒤 입력이 바뀌지 않은 산출물이 byte 단위로 같은지 확인해 도구체인 재현성을 증명한다.
- 커밋 전 선별 스테이징 검증은 실제 커밋할 인덱스 snapshot에서 한다. `git checkout-index --all --ignore-skip-worktree-bits --prefix=<작업 루트>/staged-tree/`로 만들고, 절대 경로가 박힌 생성 빌드 계약은 복사하지 말고 snapshot 안에서 다시 생성한다. snapshot 일치는 인덱스 사본을 `GIT_INDEX_FILE`에 **절대 경로**로 주고 `git --git-dir=<원 .git> --work-tree=<snapshot> diff`로 확인하되, 먼저 파일 하나를 바꿔 차이가 잡히는지 본다. 상대 경로 `GIT_INDEX_FILE`과 다른 `--work-tree`를 함께 쓰면 차이가 있어도 출력 없이 종료 코드 0이었다(Git 2.53.0.windows.4, 2026-10-12 관찰).
- 작업 중 사용자가 같은 작업 트리를 편집하면 그 파일을 고치거나 되돌리지 않는다. 작업 시작 기준(HEAD 또는 시작 시 보존한 snapshot)에 이번 변경만 적용한 격리 사본에서 같은 검증을 실행해 작업 트리 결과와 분리해 보고한다.

## 독립 검토 시점과 최종 응답

- 판단의 불확실성이 높을 때, 같은 오류가 반복되거나 수렴하지 않을 때, 검증된 작업의 완료를 선언하기 전에 fresh context `reviewer`·`security-reviewer`로 독립 검토한다. 생성자가 자기 결과를 평가하지 않는다. 단순 사실 답변·사소한 편집에는 형식적인 검토를 붙이지 않는다.
- 결함이 나면 비용이 크고 되돌리거나 알아채기 어려운 변경은 작은 수정도 구현 전에 설계·불변조건·영향 범위·복구 가능성을, 구현 후에 결과를 검토한다. 분야가 아니라 결함의 결과로 판단하며 아래 각 항목의 예는 모두 비한정이다. (a) 되돌릴 수 없거나 비싼 결과: 예) 영속 데이터에 영향을 주는 쓰기·형식 변경·삭제·마이그레이션, 이미 밖으로 나간 결과(배포된 클라이언트·발송·지급·결제). (b) 신뢰 경계: 예) 인증·인가·입력 검증·비밀값·개인정보·권한, 서버 권위. (c) 넓은 영향: 예) 공유 서비스·인프라·운영 환경과 운영 스크립트, 다른 소비자나 여러 버전이 쓰는 인터페이스·프로토콜·스키마. (d) 알아채기 어려운 결함: 예) 동시성·순서·시간, 부분 실패·재시도. 재화·아이템·DB 마이그레이션도 같은 성격의 사례다. 독립 검토는 필요한 승인·백업·복구 수단을 대체하지 않는다.
- 구현 전 설계 검토 대상은 메인이 변경·변경 위임·운영 실행 전에, 그리고 새 작업이나 범위가 바뀔 때마다 다음 순서로 판정한다. ① 바로 위의 필수 조건(작은 수정 포함). ② 여러 모듈에 걸친 새 기능·인터페이스·프로토콜·스키마의 본 코드 통합, 여러 릴리즈 브랜치·버전에 대한 이식, 기존 방향·코드로 정해지지 않고 잘못 고르면 되돌리기 비싼 대안 선택. ③ ①②에 해당하지 않는 조사·질의, 보고서·답변 초안, 한 지점의 버그 수정, 기계적 변경, 문서·지침 편집은 제외한다. '간단히'·'바로' 같은 지시는 설명과 산출물을 줄이는 조건이지 ①의 면제가 아니다.
- 작업 디렉터리(사용자·프로젝트가 지정한 경로, 없으면 `.omp-artifacts/<작업-ID>/`) 안에서 본 코드 트리를 고치지 않고 공유 환경·영속 데이터·자격증명에 접근하지 않는 탐색용 시제품·실험은 ①②여도 검토 전에 만들 수 있다. 시제품을 본 코드·공유 환경·영속 데이터에 넣기 전에 판정한다.
- 대상이면 `goldfish-review` 스킬로 설계 문서를 쓰고 대화 맥락이 없는 `design-reviewer`에게 렌즈별로 순차 검토받는다. Blocker가 남으면 구현하지 않고 사용자가 정할 결정만 올린다. 보안 영향이 있으면 `security-reviewer` 검토를 더한다. 이 검토는 구현 후 검토와 완료 전 독립 검토를 대체하지 않고 `/interview`의 요구 정렬을 다시 하지 않는다. 이미 받은 설계 검토는 현재 목표·설계·영향 범위에 여전히 맞을 때만 쓴다.
- 순서는 내부 초안 → 검토 결과 수신 → 지적별 타당성 판단 → 수정·재검증 → 통합 최종 응답이다. 중요한 지적을 채택하지 않으면 근거를 밝힌다. 검토가 실패하거나 결과를 받지 못했으면 검토 완료로 보고하지 않는다. 검토 전 공개 범위와 최종본 형식은 [응답 원칙](/response-principles.md)을 따른다.
- 비동기 advisor는 이 설정이 켠다(`advisor.enabled=true`, OMP 기본값 `false`). 출력 정리를 이유로 끄지 않는다. `advisor.syncBacklog=1`은 advisor backlog가 비워질 때까지 주 에이전트가 최대 30초 기다리는 설정이지 응답을 검토 완료까지 막는 게이트가 아니다(`omp://advisor-watchdog.md`, OMP 18.12.1). advisor 활성 상태는 독립 검토 완료의 증거가 아니며, 받은 advisor 지적도 타당성을 판단해 반영한다.

## 컨텍스트 관리

- 긴 작업을 압축 요약에 기대어 이어 가지 않는다. 진행 맥락·미완료 항목은 대화와 완료 보고에 남기고, 맥락이 길어지면 그 기록으로 새 세션에서 재개하도록 안내한다. 컨텍스트 전달만을 위한 핸드오프 파일을 임의로 만들지 않는다. OMP `memory.backend` 기본값은 `off`이고 이 설정도 켜지 않는다.
- 메모리·요약·과거 대화는 탐색 단서이지 현재 계약이나 실행 권한의 증거가 아니다. 압축·재개 뒤에는 목표·수락 기준·금지사항·사용자 결정, 진행·차단 항목, 실패·미검증 상태를 실제 파일·실행 상태와 대조해 복구한다. 증거가 없으면 미검증으로 둔다.
- 영속할 지식의 기록 기준과 위치는 [OKF 학습 축적](/learning/accumulation.md)을 따른다.
