# 게임 정적·동적 데이터와 DB 설계

방향 요약은 [사용자 개발 방향](/direction.md)의 「설계」에 있고 이 문서는 그 세부와 적용 경계다. DB 제품별 계약은 [DB 제품별 비자명 계약](/database/design.md), 콘텐츠 게시·캐시는 [데이터 형식·콘텐츠 게시 계약](/development/data-formats.md), 동적 상태의 권위·내구성은 [게임 서버 영속화](/game/server-persistence.md)가 정본이다.

아래는 사용자의 기본 선호이며 모든 게임의 업계 표준이나 기술 우열 주장이 아니다. 기존 프로젝트의 코드·스키마·배포·접근 패턴과 명시 정책을 먼저 확인하고, 이 문서를 기존 FK·저장 프로시저 제거, DB 교체, 대규모 스키마 개편의 승인으로 해석하지 않는다. 근거상 더 나은 안은 제안하되 기존 정책을 조용히 덮지 않으며, 제안은 확인한 사실·관련 원칙·변경 필요성·해결안·이득과 위험·검증 조건으로 나누어 쓴다.

## 기본 방향

- **목적:** 서버·클라이언트 응답성, 첫 플레이까지의 로딩, 정합성·안정성, 단순성·유지보수, 콘텐츠 의미, 비개발자의 저작·운영, 장애 대응을 함께 본다. 성능을 이유로 논리 구조·정확성·안정성을 희생하거나 실측 없이 기술 우열을 단정하지 않는다.
- **데이터 구분:** 저작자가 관리하는 콘텐츠 정의·규칙은 정적, 플레이·운영으로 바뀌는 유저·월드 상태는 동적이다. 정적 데이터도 갱신될 수 있다. 동적 데이터는 MySQL·SQL Server 같은 관계형 DB를 기본 후보로 두되 실제 게임 로직과 기존 저장 계약을 따른다.
- **정적 데이터 흐름:** 기획자·콘텐츠 담당자가 Excel·CSV로 작성해 내부 관리 도구로 올리면 서버가 파싱·검증해 대상별 산출물을 만든다. 클라이언트용은 JSON 등으로 CDN에 배포하고 시작·갱신 때 버전을 확인해 필요한 것만 받아 메모리에 적재한다. 서버용은 DB에 저장하고 시작·갱신 때 필요한 집합을 메모리에 적재한다. 모든 데이터·필드를 양쪽에 두거나 JSON·CDN·관계형 DB를 모든 프로젝트에 강제하지 않는다.
- **런타임 표현:** 클라이언트·서버 모두 정적 테이블을 메모리에 들고 멀티 키 맵(단일·복합 키, 비고유 키는 키 → 목록)으로 조회하는 것이 기본이다. 구간·최근접 조회(랭킹 보상 구간, 희소 레벨 곡선, 시즌 기간)와 표시 순서 순회는 정렬된 배열(키 → 정렬 목록 포함)과 `lower_bound`로 처리하고, 원소가 적으면 선형 탐색도 된다. MasterMemory·Luban 같은 전용 런타임 대신 이 자료구조를 직접 구현한다. 두 런타임의 조회도 인덱스별 정렬 배열과 이진 탐색([MasterMemory](https://github.com/Cysharp/MasterMemory) `TableBase.cs`), `HashMap`+`Vector` 적재([Luban](https://github.com/focus-creative-games/luban) C++ bin 런타임)여서 런타임 성능상 이점이 없다(확인 2026-10-15).
- **조회 구조와 비용:** 키 반복 조회는 해시 맵, 순차·작은 집합은 배열을 쓴다. 반복 조회 절감과 초기 인덱스 구성·메모리 비용을 함께 보고, 모든 데이터·인덱스의 선행 적재를 기본 최적화로 보지 않는다. C#의 LINQ는 금지하지 않되 실행 위치·반복 열거·중간 materialization·할당을 본다.
- **프로토타입 저장소:** 서버 DB가 결정·셋업되지 않은 프로토타입은 SQLite로 시작하고 DB가 정해지면 옮긴다. 이전 대상과의 타입 차이를 줄이려면 [STRICT 테이블](https://sqlite.org/stricttables.html)(3.37.0+)을 검토한다. SQLite는 DB 파일당 writer가 하나뿐이므로([When to use](https://sqlite.org/whentouse.html)) 동적 데이터 쓰기 경합이 커지면 이전 근거로 삼는다. upsert·자동 증가·시각 타입 같은 방언 차이는 이전 작업에서 확인한다.
- **논리 응집도:** 테이블 수를 줄이려고 서로 다른 콘텐츠 책임을 합치지 않는다. 책임·저작 목적·수명이 같으면 합칠 수 있다. 논리 테이블과 물리 배포 단위(JSON·압축·패키지)는 별개이며, 묶거나 나눠도 논리 의미와 참조를 유지한다. 판단 기준은 독립 수정 필요성, 클라이언트·서버 소비, 첫 로딩 필요, 크기, 참조, 변경·보존 주기, 유지 비용이다.
- **저장 모델 책임:** 기획자는 규칙과 필요한 데이터를 정하고 서버 개발자는 로직·저장 구조·접근·정합성을 설계한다. 저작 테이블을 그대로 DB 스키마로 쓰지 않는다. 불필요한 정규화·분할보다 함께 조회·갱신하는 접근 패턴과 수명을 먼저 보되, JOIN 비용·반정규화 중복·넓은 행·원자성을 따로 확인한다.
- **FK:** DB 수준 FK를 기본으로 두지 않는다. 운영·관리가 물리 제약에 기대는 것을 줄이려는 선택이며 성능·유지보수 우월성 주장이나 논리 참조 폐기가 아니다. 참조 존재, 부모 삭제·변경, 고아 방지, 마이그레이션, 관리·배치 writer, 정합성 점검·복구는 앱·운영 계약이 맡는다. 존재 SELECT와 사후 고아 검사만으로는 동시 참조 무결성이 보장되지 않는다.
- **앱 코드와 저장 프로시저:** 복잡한 콘텐츠 규칙과 트랜잭션 경계는 서버 앱 코드가 관리한다. 저장 프로시저는 월드 보스 HP 같은 공유 경합이나 DB 작업 묶음의 이득이 명확할 때 검토한다. 프로시저라는 이유만으로 원자성·잠금·오류 처리가 해결되지 않으며, 일반 SQL·앱 트랜잭션으로 같은 요구를 안전하게 만족하면 그 방식을 유지한다.

## 적용 경계

- 클라이언트 전용·서버 전용·공통 대상을 나누고 비밀은 배포하지 않으며 서버 권위를 유지한다. 같은 전체 데이터를 양쪽에 둘 의무는 없다.
- 정적 갱신의 전체 삭제·재삽입은 조건부 전략이다. 게시 전 검증, staging·버전 공간, 활성화, 구버전 호환·복구를 검토하고 실제 DB 엔진의 DML·DDL·rollback 차이를 확인한다. hot reload·증분 갱신을 무조건 만들지 않는다.
- PK·UNIQUE·조회 인덱스와 실행 계획, 조건부 UPDATE·잠금·낙관적 동시성 제어, 여러 변경의 원자성, 중복 요청, 실패·재시도를 함께 확인한다. FK를 두지 않는다고 PK·UNIQUE·트랜잭션·인덱스를 생략하지 않는다.
- 동적 메모리의 판정 권위·내구 원본·파생 캐시를 구분하고 저장·무효화 실패, 다중 작성자, 늦은 완료, 재접속·복구를 정의한다. [게임 서버 영속화](/game/server-persistence.md)의 A/B/C 선언을 이 선호로 바꾸지 않는다.
- 첫 설치·재실행·업데이트 뒤의 버전 확인, 다운로드, 해제·파싱, 메모리·인덱스 구성, 참조 검증, 플레이 가능까지의 경과를 나눠 잰다. 지연 로딩으로 첫 사용을 멈추게 하거나 필수 데이터 실패를 정상 빈값으로 숨기지 않는다.
