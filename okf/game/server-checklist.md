# 게임 서버 기능/성능 체크리스트

- [ ] 메모리: 힙 할당 최소화·풀링(GC 일시정지·틱 흔들림 회피)
- [ ] 동시성: 정확성·객체 수명·진행 보장을 우선하고 경합 측정 후 락 축소·샤딩·lock-free를 선택. 다중 필드·교차 shard 불변조건과 트랜잭션 경계·데드락/기아·메모리 회수를 검증([코딩 스타일](/coding-style.md))
- [ ] 네트워크: 버퍼 재사용·직렬화 비용 고려·비동기 I/O
- [ ] 틱/루프: 처리량·지연 예산 내 동작, 무거운 작업 프레임/잡 분산
- [ ] 반응성: 계약상 허용된 클라이언트 예측에 서버 보정을 제공하되 경제 결과는 서버 커밋 성공 후 확정. pending 표시·수신 ACK를 사용 가능한 권위 상태로 취급하지 않음([게임 보안](/security/game.md))
- [ ] 상태 수락: 입력의 형식·권한·순서·게임 불변조건 검증을 마친 뒤에만 권위 상태·baseline·통계를 갱신
- [ ] 보정 전파: 최종 accepted 값을 시뮬레이션·저장·복제·송신자 reconciliation·관전자 전파 전체에 사용
- [ ] 순서/생명주기: sequence 중복·역순·wraparound와 session/entity generation을 검증해 stale packet 차단
- [ ] 권위 이전: old/new authority·handoff generation·commit 시점·in-flight message 처리 정책 명시
- [ ] 전달/혼잡: 메시지별 전달·순서·중복·만료 의미를 정의하고 느린 연결에 coalesce·drop·backpressure·disconnect 정책 적용
- [ ] 가시성/관심 관리: 플레이어별 전송 대상을 서버에서 계산하고 observer 변화 때 누락·과다 전파 없이 수렴
- [ ] 콘텐츠 판정 데이터: 몬스터 스폰 영역·수·리스폰 주기처럼 서버가 판정하는 테이블은 클라이언트 배포 맵·연결 데이터와 분리해 서버만 로드한다. 공개 계약(출현 타이머 UI 등)에 없는 다음 리스폰 시각·스폰 상태는 클라이언트에 복제하지 않는다. 테이블 검증 실패는 빈 월드나 기본값으로 대체하지 않고 해당 월드 진입을 막는다(fail-closed). 근거: 서버 에뮬레이터 [TrinityCore의 `creature` 표](https://trinitycore.info/database/335/world/creature)는 스폰 위치·`spawntimesecs`(리스폰 초)·`wander_distance`를 서버 world DB에 둔다(조회 2026-10-07, 특정 상용 서비스의 내부 구현을 주장하지 않음). 복제 범위는 [게임 보안](/security/game.md)의 "알 권한이 있는 정보만 서버에서 선별해 전송" 원칙으로 정한다
- [ ] 검증: 결정적 알고리즘 테스트와 codec·검증·dispatch를 지나는 통합 테스트, 손실·역순·재접속·장시간 누적 시나리오 보유

## Gateway와 단일 로직 스레드의 분리

아래는 이 구조를 선택한 서버의 설계·검증 기준이다. 모든 게임의 필수 구조나 특정 서비스의 내부 구현을 주장하지 않는다.

| 경계 | 책임 | 하지 않는 일 |
|---|---|---|
| Gateway | 클라이언트 연결·프레이밍·인증된 세션 결합·라우팅·송수신 큐·브로드캐스트 팬아웃 | 이동·피해·재화·아이템의 권위 판정 |
| Game Server의 로직 스레드 | 소유 월드/존/인스턴스의 상태 변경, 명령 검증, 이동·전투·AI·퀘스트, 공개 가능한 결과와 수신 대상 결정 | 소켓 송신 완료·DB·파일 I/O의 동기 대기 |
| Game Server의 I/O 작업자 | Gateway 연결·DB·파일 작업, 완료 메시지 전달 | 로직 스레드 소유 객체의 직접 변경 |

- [ ] **콘텐츠 로직의 단일 작성자**를 소유 단위별로 명시한다. 서비스 전체가 하나의 스레드라는 뜻도, 게임 서버에 네트워크 I/O가 없다는 뜻도 아니다. 여러 프로세스/존으로 확장해도 같은 객체를 여러 소유자가 동시에 변경하지 않는다.
- [ ] Gateway와 콘텐츠 서버 사이에 명시적인 메시지 경계를 둔다. Gateway는 접속·송신 병목을 분리하지만 콘텐츠 계산 자체를 병렬화하지 않는다. 별도 hop·큐잉·직렬화 비용도 측정한다.
- [ ] 프로토콜은 버전·메시지 종류·길이 상한, 인증된 세션/캐릭터 결합, session generation, 입력 sequence와 라우팅/authority generation의 의미를 정의한다. 필드명·wire 형식은 실제 계약에서 정한다.
- [ ] 서버·클라이언트가 공유하는 고정 상한(예: 캐릭터당 동시 상태 수)을 바꾸면 wire 호환성부터 판정한다. 개수 기반 배열은 바이트가 같아도 고정 길이로 채우는 보조 배열·서비스 간 이전 이미지·검증 상한은 바뀔 수 있다. golden/고정 바이트 테스트로 실제 변화를 확인하고, 바뀌면 프로토콜 버전을 올려 서버와 클라이언트를 함께 배포한다. 내구 저장 형식·콘텐츠 identity 영향은 따로 확인하고, 메모리 예산 단언과 상한을 채운 검사를 같은 변경에 포함한다.
- [ ] 메시지·RPC 식별자는 공유 스키마에서 명시적으로 할당하고 중복을 생성·등록 단계에서 실패로 처리한다. 타입명·메서드 시그니처의 16-bit hash는 다른 언어(GDScript·C++)에서 재현하기 어렵고, 이름을 바꾸면 wire ID가 바뀌며, 충돌하면 경고만 남기고 handler를 교체해 다른 처리로 조용히 분기할 수 있다([Mirror `RegisterHandler`](https://github.com/MirrorNetworking/Mirror/blob/c4f3739966e151f405be1762d33502794fd034ff/Assets/Mirror/Core/NetworkServer.cs), 조회 2026-10-11). dirty mask 같은 고정 폭 bitmask는 shift 피연산자를 mask 폭 타입으로 만들고 선언한 개수 상한을 등록 시 거부로 강제한다. C/C++에서 승격된 왼쪽 피연산자 폭 이상의 shift는 정의되지 않은 동작이고, C#은 shift 수를 폭으로 나눈 나머지로 처리해 다른 bit를 가리킨다. 31/32번째·63/64번째 경계를 테스트한다.
- [ ] Gateway 검증은 인증·프레이밍·크기·빈도·라우팅 경계이고, 콘텐츠 서버는 자기 권위·세션·순서·게임 상태를 검증한다. Gateway가 전달했다는 이유로 이동·충돌·경제 결과를 신뢰하지 않는다. 비공개 네트워크 배치만으로 내부 peer 인증·인가를 대신하지 않는다.
- [ ] I/O 콜백은 큐에 완료 결과를 넣고 로직 스레드가 적용한다. 요청 ID·세션/객체 generation·상태 버전을 확인해 역순 DB 완료, 로그아웃 후 완료, 다른 존으로 이동한 객체의 낡은 결과를 차단한다.
- [ ] 비동기 작업에는 불변 snapshot이나 수명이 보장된 메시지를 전달한다. 작업자가 변경 중인 월드 객체를 읽게 하지 않는다. 풀링 버퍼는 모든 소비자의 사용 종료 전에 재사용하지 않는다.

## 상시 운영 메모리와 계측

- [ ] 초기화·접속/TLS 수립·정상 메시지·오류/종료의 할당을 분리한다. packet buffer 외에도 queue node·문자열·JSON·codec parser 상태·비동기 operation·TLS 내부를 포함한다. 풀의 존재나 `reserve`를 무할당·총량 제한의 증거로 삼지 않는다.
- [ ] 풀 고갈의 heap fallback과 반환 블록 보관량도 상한을 가진다. 처리 대기 중인 live bytes, 반환된 cache, 소유권을 잃은 누수를 구분하며 raw pointer/크기를 지운 뒤 반환하는 순서를 만들지 않는다. callback 취소 요청이 아니라 마지막 사용과 deallocate까지 저장소 수명을 유지한다.
- [ ] codec의 입력 byte 상한뿐 아니라 내부 count/type/depth를 객체 생성 전에 검사한다. 호출별 편의 API가 parser stack·객체 tree를 새로 할당하면 소유자별 재사용 parser와 bounded visitor/sink를 검토하고, 오류 다음 정상 메시지에서 상태 초기화를 검증한다.
- [ ] 완결된 단위(datagram, 길이로 잘린 frame) 안의 내부 길이가 남은 바이트를 넘거나 정수 변환에서 넘치면 "데이터 부족 대기"가 아니라 프로토콜 오류로 즉시 연결을 끊는다. 대기로 처리하면 그 연결의 수신 큐가 영구 정지하고 이후 batch가 무제한 쌓인다. Mirror는 이 경우 큐를 비우고 예외로 끊도록 고쳤으므로([고정 소스의 `Unbatcher`](https://github.com/MirrorNetworking/Mirror/blob/c4f3739966e151f405be1762d33502794fd034ff/Assets/Mirror/Core/Batching/Unbatcher.cs), 조회 2026-10-11) fork를 쓰면 upstream 보안 수정의 반영 여부를 대조한다. 부족 대기는 stream 재조립 경계에만 상한과 함께 둔다. 컬렉션은 요소 수 상한만 두지 말고(Mirror 고정 소스의 `AllocationLimit`은 요소 수 기준) `개수 × 요소의 최소 wire 크기 ≤ 남은 바이트`와 메시지별 의미 상한으로 할당 전에 판정한다. 길이로 경계가 정해진 메시지는 선언 길이를 먼저 검증·소비해 경계를 정하고, 그 안의 해석 실패·남은 바이트는 위와 같은 프로토콜 오류로 처리한다. 선언 길이만큼 건너뛰고 계속하는 것은 협상된 선택적 확장처럼 계약이 허용한 메시지로 한정한다.
- [ ] TLS 유휴 buffer 반납은 반복 할당과 연결별 점유 메모리의 선택이다. [OpenSSL mode 문서](https://docs.openssl.org/3.6/man3/SSL_CTX_set_mode/)의 `SSL_MODE_RELEASE_BUFFERS`와 전송 wrapper가 실제 설정하는 값을 확인한다. 보관을 선택해도 연결 상한·최종 SSL 해제는 유지하며 SSL 객체 자체 재사용이나 allocator 교체와 혼동하지 않는다.
- [ ] Asio의 [associated allocator](https://think-async.com/Asio/asio-1.30.2/doc/asio/overview/core/allocation.html)가 [즉시 완료](https://think-async.com/Asio/asio-1.30.2/doc/asio/overview/composition/immediate_completion.html)·composed operation·executor 전달에서도 보존되는지 고정 소스로 확인한다. type erasure가 모든 allocator property를 전달한다고 가정하지 않으며, inline 재귀를 허용해 할당만 줄이지 않는다.
- [ ] 무할당 계측에는 알려진 양성 할당을 검출하는 대조를 둔다. `operator new`만 세면 `malloc`·`aligned_alloc`·TLS C 할당을 놓칠 수 있다. Asio 1.32/Linux 검증에서 캐시를 끄는 경우 `ASIO_DISABLE_STD_ALIGNED_ALLOC`까지 적용해 기본 경로가 계측한 `operator new`로 이어지는지 확인하거나 aligned 할당을 별도로 판정한다. 캐시 비활성 분기의 [upstream 수정](https://github.com/chriskohlhoff/asio/commit/57bf938c7dc1f6ea1e224fb74e274e397edebcd1)은 재현 가능한 의존성 패치로 관리하고 설치 헤더를 직접 고치지 않는다.
- [ ] 측정 thread·warmup·peer 수·요청 순서·누락한 라이브러리 경로를 명시한다. I/O 소유자 하나와 프로세스 전체 thread 하나는 다르다. 접속/종료 반복·느린 수신자·고갈·취소에서 FD와 live/retained 메모리를 확인하며, RSS가 그대로인 관측이나 제한된 무할당 결과를 단편화 없음·전체 프로세스 무할당·운영 CCU 보장으로 확대하지 않는다.

## 큐·브로드캐스트·성능

- [ ] 수신·명령·DB 완료·송신 큐에 메시지 수와 바이트 상한을 둔다. 큐 깊이뿐 아니라 가장 오래된 메시지의 대기, 유입/소비율, 세션별 점유·공정성, 거부/대체/연결 종료를 관측한다.
- [ ] `accept`의 descriptor/메모리 부족과 일시 네트워크 오류 때문에 이미 성립한 연결까지 종료하지 않는다. 소유자에 한 개의 유한 재시도 대기를 두어 busy loop를 막고 종료 때 취소한다. 시작 시 연결 상한에 reactor·로그·수용/거절용 FD 여유를 더해 OS soft limit을 확인하며, 실행 중 한도 변화·고갈 뒤 복구도 검사한다. 근거: [Linux accept(2)](https://man7.org/linux/man-pages/man2/accept.2.html)의 pending network errors와 EMFILE/ENFILE/ENOBUFS/ENOMEM 구분.
- [ ] 큐가 빌 때까지 무제한으로 처리하지 않는다. 틱의 입력/완료 소비 예산과 과부하 정책을 정해 입력 폭주가 이동·AI·다른 세션을 굶기지 않게 한다. 클라이언트가 요청한 입력 시간의 누적도 서버가 허용한 시뮬레이션 시간 안으로 제한한다.
- [ ] 연결마다 frame 하나를 application이 소비해야 다음 frame을 읽는 transport(소비 시점에 수신 정책을 바꾸는 장벽)라면, 서비스 loop가 빈 event 뒤에 고정 sleep하지 않게 한다. 여러 세션이 공유하는 내부 연결(Gateway→World 등)이 loop 반복당 frame 하나로 묶여, 1ms sleep이면 1초 약 900개 미만이라는 상한이 생긴다. 고주기 입력이 이를 넘으면 지연이 끝없이 쌓인다. event 발행 시 깨우는 bounded wait로 바꾸고, 소비하지 않은 event가 남아 있으면 즉시 반환되므로 peek한 event는 반드시 소비한다. 실제 사례에서 32명 이상의 30Hz 입력이 8.5초씩 밀렸고, event 대기로 바꾼 뒤 64명에서 미확인 입력이 6 이하로 유지됐다.
- [ ] 용량 검증은 snapshot 수신 신선도로 판정하지 않는다. 같은 상황에서 snapshot은 100ms 안에 도착했지만 입력 처리 경계(ack)는 수 초 뒤처져 있었다. 유지 시간 동안 세션별 미확인 입력 수(또는 입력→처리 지연)와 RTT를 표본으로 기록하고, 가득 찬 World 하나와 다른 지역 사용자가 공존하는 시나리오를 포함한다.
- [ ] 시뮬레이션 tick 시간과 DB commit 지연만으로 수용 인원을 판정하지 않는다. tick과 commit이 예산 안에 있어도 로직 스레드 전체 CPU가 포화하면 입력 ack가 수 초 밀리고 신규 접속자의 상태 설치가 끊길 수 있다. 입력 ack 지연·RTT와 함께 로직 스레드 CPU와 loop 구간별 시간을 기록하고, 포화 구간을 분해한 뒤에 완화책을 정한다. 최악 밀집 장면에서 측정하고, 개발 머신의 다른 서비스와 CPU를 공유한 측정은 contended로 표시한다.
- [ ] 로직 loop에서 공개·송신 대상 확인을 **반복마다 모든 세션에 대해** 하지 않는다. 연결 하나의 frame을 소비해야 다음 frame을 읽는 구조에서는 반복 수가 수신 frame 수(인원×입력 주기)에 비례하므로, 반복마다 세션 전체를 훑으면 비용이 대략 인원의 제곱으로 커지고, 세션별 조회가 세션 배열 전체를 선형 탐색하면 정원 상수(배열 칸 수)만큼 더 곱해진다. 공개 구간을 계측할 때는 이 순회와 snapshot 생성을 **다른 구간으로 나눈다**. 한 지역 밀집 장면에서는 snapshot 하나가 담는 관찰 대상도 인원과 함께 늘어 생성 비용도 인원보다 빠르게 커질 수 있으므로, 둘을 합친 구간만 보면 원인을 잘못 고른다. 실제 사례에서 합친 공개 구간이 loop 시간의 60~80%였고 처음에는 순회를 원인으로 봤지만, 나눠 재자 포화 지점에서 snapshot 생성이 절반 정도, 순회가 4분의 1 정도였다. 개선책은 이 분해 결과에 맞춰 정하고 같은 계측으로 효과를 확인한다.
- [ ] 외부 연결 상한은 World/지역 수 × World 수용 인원 + 인증·재접속·전환 여유에서 도출한다. 고정 상한이 World 하나의 정원과 같으면 그 World가 가득 찼을 때 다른 지역 사용자의 TLS 접속까지 막혀, 수용 인원 자체를 검증할 수 없다.
- [ ] 교체 가능한 상태 snapshot은 계약에 맞게 병합할 수 있지만 구매·보상·발사 같은 의미 있는 명령/이벤트를 임의 삭제하지 않는다. delta baseline과 생성/제거 순서를 깨뜨리는 병합도 금지한다. 처리 불가능한 명령은 명시적으로 거부하거나 복구 가능한 실패로 처리한다.
- [ ] 콘텐츠 측이 정한 공개 범위·수신 대상을 Gateway가 팬아웃한다. AOI 멤버십 변경/권한 철회와 송신 대기의 정합성을 유지한다. 개인별 비공개 필드를 공용 방송 버퍼에 섞지 않는다.
- [ ] 동일 공개 payload는 필요할 때만 직렬화·불변 버퍼 공유를 적용하되, 연결별 암호화·압축·baseline이 다르면 결과를 무조건 공유하지 않는다. AOI 계산·대상 목록 생성·프로세스 간 전송 비용은 Gateway 분리만으로 사라지지 않는다.
- [ ] 모든 참여자의 갱신을 모두에게 보내는 장면은 참여자 수에 따라 팬아웃이 제곱 수준으로 커질 수 있다. Gateway 증설만으로 해결한다고 가정하지 않고 관심 영역·변경분·복제 빈도와 최악 밀집 장면을 함께 검증한다.
- [ ] 격자 AOI(예: 셀 = 가시 반경, 주변 3×3 검사)에서는 진입 반경보다 이탈 반경을 크게 두어(히스테리시스) 경계 개체가 spawn(full state)·despawn을 반복하지 않게 한다. 기존 관찰자의 유지 여부를 현재 관찰 집합에서 이탈 반경으로 판정하거나, 셀 크기를 이탈 반경 이상으로 두거나, `ceil(이탈 반경 / 셀)` 고리까지 검사하는 방법 중 하나를 쓴다. 후보를 3×3 검사 결과에서만 다시 만들면 그 범위가 진입 반경까지만 닿는 방향의 히스테리시스가 사라진다. 관찰 관계는 양방향으로 갱신한다. 이동한 개체를 "보는 쪽"만 다시 계산하면 이동한 플레이어가 새로 보게 될 정지 NPC가 주기 전체 재계산 때까지 늦게 나타난다. 관찰자 후보(플레이어) index를 전체 개체 index와 나눠 재계산 비용이 몬스터 밀도에 비례하지 않게 하고, 셀 이동 재계산과 주기 전체 재계산 비용을 따로 측정한다. 관찰 집합을 거치지 않는 전역 broadcast(일시정지·상태 플래그 등)는 공개 범위를 우회하고 나중에 들어온 관찰자에게 빠지므로 spawn 상태에 포함해 관찰자에게만 보낸다.
- [ ] 틱 예산 안에 입력 처리·시뮬레이션·AOI·출력 생성이 들어가는지 실제 부하에서 확인한다. 평균 CPU가 아니라 로직 스레드의 p95/p99 지연·틱 초과·큐 대기와 코어별 병목을 본다. 피크 CPU GHz만으로 장비를 고르지 않는다.
- [ ] Gateway는 연결 수·PPS·송신 바이트·느린 소비자·재접속 폭주, 콘텐츠 서버는 밀집 전투·AI·AOI·단일 로직 코어, DB는 완료 지연·큐 적체를 각각 측정한다. 각각의 증설 효과와 전체 응답 지연을 구분한다.
- [ ] N개 Gateway와 M개 콘텐츠 서버는 네트워크와 콘텐츠 소유 단위를 각각 확장하는 구조다. 이미 포화된 단일 존의 전투 계산은 Gateway 추가로 빨라지지 않는다. 존/인스턴스 배치·입장 제한·소유권 분할 중 요구에 맞는 정책을 정하고 교차 경계 정합성을 검증한다.

## 영속화·이동·장애

- [ ] 메모리를 실행 상태의 기준으로 삼는 것과 경제 데이터 내구성은 별개다. 주기적 snapshot 저장만으로 구매·거래·보상 성공을 확정하지 않는다. 필요한 트랜잭션 또는 내구 로그의 커밋·멱등성을 보장하고 I/O 대기 중인 작업은 pending으로 둔다.
- [ ] 위치처럼 매 tick 바뀌는 연속 상태는 tick마다 내구화하지 않아도 된다. 일반적인 서버는 로그아웃(연결 해제 뒤 소유 반환)·영역 이전 때 저장하고 주기적으로 자동 저장하며, 거래 같은 경제 결과는 주기 저장을 기다리지 않고 즉시 한 트랜잭션으로 커밋한다(예: TrinityCore의 [`WorldSession::LogoutPlayer`→`SaveToDB`](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/game/Server/WorldSession.cpp), [`PlayerSaveInterval` 기본 90초](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/worldserver/worldserver.conf.dist)와 첫 저장 시점 분산, [거래 트랜잭션](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/game/Handlers/TradeHandler.cpp)). 의미 있는 결과 레코드에 그 시점 위치를 함께 실으면 결과와 위치가 어긋나지 않는다. 크래시 때 위치가 얼마나 되돌아가도 되는지(주기)를 명시적으로 정한다.
- [ ] 단일 작성자 SQLite 서비스는 캐시한 prepared statement를 scope 종료(성공·실패·조기 반환 포함)마다 reset한다. 결과를 다 읽지 않은 SELECT가 `SQLITE_ROW`에 머물면 이후 COMMIT 뒤에도 같은 연결의 읽기 트랜잭션이 남아 WAL checkpoint가 진행되지 않고 WAL이 계속 커진다([SQLite 포럼 설명](https://sqlite.org/forum/forumpost/9fba47556b)). checkpoint 임계값을 넘는 커밋 뒤 WAL 크기·완전 checkpoint를 회귀로 확인한다. 식별 metadata는 테이블이 없는 빈 DB에서만 초기화하고, 테이블이 있는데 metadata가 없는 DB는 어떤 변경 전에도 fail-closed로 거부한다.
- [ ] 단일 스레드도 비동기 대기 전후에 다른 명령이 끼어들 수 있다. 예약/pending 상태 또는 적용 시 버전 검증 등으로 중복 소비와 낡은 완료의 덮어쓰기를 막는다. 분산 거래는 한 로직 스레드만으로 원자적이지 않다.
- [ ] 조건부 갱신(`UPDATE … SET gold = gold - ? WHERE id = ? AND gold >= ?`)은 statement별 영향 행 수([`sqlite3_changes`](https://sqlite.org/c3ref/changes.html))가 기대값과 같을 때만 성공으로 보고, 다르면 트랜잭션 전체를 되돌린다. 묶음 전체의 성공 flag나 영향 행 합계만 보면 0행 일치를 성공으로 오인하고 어느 조건이 실패했는지 알 수 없다. 결과를 모르는 timeout 뒤 재시도에 대비해 작업 ID를 업무 갱신과 같은 트랜잭션에서 먼저 `(계정·캐릭터 ID, 작업 ID)` 쌍의 UNIQUE 기록([`INSERT … ON CONFLICT DO NOTHING`](https://sqlite.org/lang_upsert.html))으로 남긴다. 클라이언트가 고른 ID를 전역 UNIQUE로 두면 다른 사용자의 결과를 받거나 그 작업을 막을 수 있다. 그 INSERT의 영향 행이 0이면 이미 적용된 작업이므로 업무 갱신을 실행하지 않고 처음 실행 때 작업 ID와 함께 저장한 결과를 돌려준다. 요청 내용의 digest도 함께 저장해 같은 작업 ID에 다른 내용이 오면 저장 결과를 돌려주지 않고 거부한다. 권한·문법 같은 영구 오류는 재시도하지 않는다. 값은 문자열 조립 대신 bind로 넘기고 수치·시각은 locale과 무관한 형식(정수·UTC epoch)으로 저장한다. 모델 전체를 덮어쓰는 갱신 대신 서버가 계산하는 증감이나 version 비교 갱신을 쓴다(SQLite 문서 조회 2026-10-11).
- [ ] 내구 저장소가 콘텐츠 identity(공개·비공개 카탈로그 전체와 맵 바이트의 digest)에 결속돼 있으면 표시 전용 필드·아이콘 경로·맵 재게시처럼 판정과 무관해 보이는 변경도 identity를 바꿔 기존 DB를 열 수 없게 만든다. 구현 전에 식별 입력을 코드로 확인하고, 데이터 배치(식별 대상 카탈로그/별도 표시 데이터)와 기존 DB 처리(백업 후 새 DB·명시적 재결속 도구)를 사용자 결정으로 드러낸다. 계정 credential·provision digest도 identity에 묶였다면 DB만 옮기면 재프로비저닝이 거부되므로 같은 세대로 함께 보존·교체한다. 산출물을 다시 생성하기 전에 이전 identity와 일치하는 데이터셋을 보존해야 복구가 가능하며, 검사 우회·자동 reset으로 불일치를 감추지 않는다.
- [ ] 존 이동은 old owner 정지/fencing, 상태 인계, new owner 활성화, 라우팅 교체와 실패 복구를 하나의 계약으로 정한다. 중간 실패·늦은 입력·중복 완료에도 소유자가 둘이 되거나 명령이 이중 적용되지 않아야 한다.
- [ ] 파티·인스턴스 멤버십은 재생성·교체 때 바뀌는 개체 ID가 아니라 캐릭터·세션의 안정 ID로 저장한다. 보조 index(개체 ID→연결)는 ID 할당 **뒤**에 등록하고 끊김·교체·로그아웃의 모든 경로에서 제거한다. 할당 전에 등록하면 0이나 이전 ID로 매핑되어 조회가 실패한다. 멤버를 제거할 때는 남은 멤버뿐 아니라 제거된 본인에게도 그룹 ID가 담긴 탈퇴 통지를 보내고(해산과 구분), 클라이언트는 현재 그룹과 다른 ID의 늦은 통지를 무시한다.
- [ ] 인스턴스(던전)는 생성 중→활성→비움 유예→파괴의 서버 상태 머신으로 둔다. 참가자는 [게임 보안](/security/game.md)의 기준대로 서버 그룹 상태에서 정해 슬롯을 예약하고, 생성(비동기 로드) 중 끊긴 참가자와 접속하지 않은 대상의 예약도 해제한다. 해제하지 않으면 인스턴스가 영원히 비지 않아 파괴되지 않는다. 파괴 조건은 작업을 실행하는 시점에 다시 확인하고, 파괴 전에 내부 개체를 despawn하며, 이미 무효가 된 인스턴스도 목록에서 정리한다. 생성·파괴 작업 큐는 한 작업의 예외가 큐 전체를 멈추지 않게 작업별로 격리하고 계정·전역 요청 수에 상한을 둔다. 유예·초대 만료는 단조 시계로 잰다.
- [ ] Gateway 장애에서 연결은 복구 대상이고 월드 상태의 소유권은 콘텐츠 서버에 남는다. 재접속은 기존 연결 무효화·새 generation·권위 snapshot으로 재개하며 무손실/투명 복구를 자동 보장하지 않는다.
- [ ] Gateway는 콘텐츠 서버 링크 하나의 상실을 그 지역의 장애로 처리하고 프로세스를 종료하지 않는다. 그 지역에 묶인 클라이언트뿐 아니라 보류 중인 이전 commit, 로그아웃이 기다리는 이전 대상 같은 모든 연관을 정리하며, 다른 지역 클라이언트의 큐·슬롯 불변조건을 유지한다. 재연결은 유한 backoff로 하고 새 handshake(서버 identity·incarnation)를 다시 검증한 뒤에만 라우팅한다. 이전 연결 ID는 종료 event까지 퇴역 상태로 남겨 늦은 frame이 새 링크로 섞이지 않게 한다. 감독 프로세스는 시작 장벽 전에는 어떤 자식 종료도 시작 실패로 보고, 장벽 뒤에는 콘텐츠 서버 하나의 종료를 격리한다. 콘텐츠 서버의 SIGKILL·SIGTERM·링크 단절을 각각 실제로 주입해 다른 지역의 snapshot·입력 ack가 끊기지 않는지 검증한다.
- [ ] 콘텐츠 프로세스 장애는 내구 상태·재생 정책으로 복구한다. 프로세스 생존과 로직 진행을 별도로 감시하고 정지한 owner를 대체할 때 기존 owner의 쓰기 권한을 차단한다.
- [ ] 실제 검증은 밀집 레이드, 느린 클라이언트, Gateway/콘텐츠 서버 종료, DB 지연·실패, 큐 상한, 중복/낡은 메시지, 존 이동 실패를 포함한다. 접속만 유지하는 봇 부하를 실제 콘텐츠 처리량으로 보고하지 않는다.
- [ ] 적대 AI가 있는 실제 맵의 통합 probe는 참가자를 보호 구역에서 함께 출발시키고 동시에 이동시키며, 검증 대상 요청 **직전에** 생존·위치(사용 반경) 같은 전제를 확인해 정확한 실패 사유를 남긴다. 먼저 도착한 참가자가 대기 중 사망·부활 이동하면 그 결과가 프로토콜 거절(예: INVALID)로 보여 제품 결함으로 오인된다. 재사용하는 영속 테스트 계정은 이전 실행이 남긴 지역·상태를 가정하지 말고 실제 게임 경로(이동·포탈·부활)로 전제를 정규화하며 DB를 직접 고치지 않는다.

- [오딘: 발할라 라이징 — Games on AWS 2022 발표](https://www.slideshare.net/slideshow/8-mmorpg-300-games-on-aws-2022/254068948): 11~13쪽의 multi I/O/single logic과 선택 이유, 19~21쪽의 Gateway 방송 전담·N:M 구조·콘텐츠별 확장, 43쪽의 운영 조건에 맞는 장애/성능/확장 테스트 권고를 확인했다. 행사는 [AWS 공식 일정](https://pages.awscloud.com/rs/112-TZM-766/images/games-on-aws-2022-agenda.pdf)으로 교차 확인했다.
- 발표는 분리 구조의 실서비스 사례이지 위 체크리스트의 큐·fencing·커밋 프로토콜을 공개한 구현 명세가 아니다. 위 항목은 서버 권위·동시성·복구 원칙을 그 구조에 적용한 설계 기준이다.
- 발표 10쪽의 메모리 우선/주기적 DB 저장을 무손실 경제 트랜잭션의 보장으로 읽지 않는다. 공개 자료만으로 실제 내구성·장애 복구 세부를 확정할 수 없다.
- 발표 당시 EC2·Aurora 비교와 ENA 버퍼/RSS/하이퍼스레딩 튜닝값은 해당 환경의 관측이다. 현재 장비·OS·드라이버의 기본값/권장값으로 복제하지 않으며 공식 지원 범위와 실제 부하로 검증한다.
