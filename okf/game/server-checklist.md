# 게임 서버 기능/성능 체크리스트

공통 메모리·동시성·프로토콜 등록/codec·비동기 수명·큐 상한/고갈은 [서버 운영](/development/server-checklist.md), 메시지별 전달/혼잡은 [공통 전달 계약](/development/network-delivery.md)을 따릅니다. 아래는 그 기준의 게임 권위·복제·부하 적용입니다.

- [ ] 틱/루프: 처리량·지연 예산 내 동작, 무거운 작업 프레임/잡 분산
- [ ] 반응성: 계약상 허용된 클라이언트 예측에 서버 보정을 제공하되 경제 결과는 서버의 권위 확정 뒤에 성공으로 확정한다. 내구 커밋 전에 공개할지는 [영속화·장애 체크리스트](/game/server-persistence.md)의 A/B/C 선언을 따른다. pending 표시·수신 ACK를 사용 가능한 권위 상태로 취급하지 않음([게임 보안](/security/game.md))
- [ ] 상태 수락: 입력의 형식·권한·순서·게임 불변조건 검증을 마친 뒤에만 권위 상태·baseline·통계를 갱신([게임 보안](/security/game.md)의 서버 권위 원칙)
- [ ] 보정 전파: 최종 accepted 값의 사용 범위는 [게임 보안](/security/game.md)의 서버 권위 원칙을 따른다
- [ ] 순서/생명주기: sequence 중복·역순·wraparound와 session/entity generation을 검증해 stale packet 차단([네트워크 동기화](/game/network-sync.md))
- [ ] 권위 이전: old/new authority·handoff generation·commit 시점·in-flight message 처리 정책 명시([네트워크 복구·전달 의미론](/game/network-delivery.md))
- [ ] 전달/혼잡: 메시지별 전달·순서·중복·만료와 느린 연결의 coalesce·drop·backpressure·disconnect는 [공통 전달 계약](/development/network-delivery.md), 큐 상한·관측은 [서버 운영](/development/server-checklist.md#큐입장처리-예산)을 따른다. 게임 복제 baseline·명령 의미는 [게임 전달 의미론](/game/network-delivery.md)을 유지한다.
- [ ] 가시성/관심 관리: 플레이어별 전송 대상을 서버에서 계산하고 observer 변화 때 누락·과다 전파 없이 수렴
- [ ] 콘텐츠 판정 데이터: 몬스터 스폰 영역·수·리스폰 주기처럼 서버가 판정하는 테이블은 클라이언트 배포 맵·연결 데이터와 분리해 서버만 로드한다. 공개 계약(출현 타이머 UI 등)에 없는 다음 리스폰 시각·스폰 상태는 클라이언트에 복제하지 않는다. 테이블 검증 실패는 빈 월드나 기본값으로 대체하지 않고 해당 월드 진입을 막는다(fail-closed). 근거: 서버 에뮬레이터 [TrinityCore의 `creature` 표](https://trinitycore.info/database/335/world/creature)는 스폰 위치·`spawntimesecs`(리스폰 초)·`wander_distance`를 서버 world DB에 둔다(조회 2026-10-07, 특정 상용 서비스의 내부 구현을 주장하지 않음). 복제 범위는 [게임 보안](/security/game.md)의 "알 권한이 있는 정보만 서버에서 선별해 전송" 원칙으로 정한다

## Gateway와 단일 로직 스레드의 분리

아래는 이 구조를 선택한 서버의 설계·검증 기준이다. 모든 게임의 필수 구조나 특정 서비스의 내부 구현을 주장하지 않는다.

| 경계 | 책임 | 하지 않는 일 |
|---|---|---|
| Gateway | 클라이언트 연결·프레이밍·인증된 세션 결합·라우팅·송수신 큐·브로드캐스트 팬아웃 | 이동·피해·재화·아이템의 권위 판정 |
| Game Server의 로직 스레드 | 소유 월드/존/인스턴스의 상태 변경, 명령 검증, 이동·전투·AI·퀘스트, 공개 가능한 결과와 수신 대상 결정 | 소켓 송신 완료·DB·파일 I/O의 동기 대기 |
| Game Server의 I/O 작업자 | Gateway 연결·DB·파일 작업, 완료 메시지 전달 | 로직 스레드 소유 객체의 직접 변경 |

- [ ] **콘텐츠 로직의 단일 작성자**를 소유 단위별로 명시한다. 서비스 전체가 하나의 스레드라는 뜻도, 게임 서버에 네트워크 I/O가 없다는 뜻도 아니다. 여러 프로세스/존으로 확장해도 같은 객체를 여러 소유자가 동시에 변경하지 않는다.
- [ ] Gateway와 콘텐츠 서버 사이에 명시적인 메시지 경계를 둔다. Gateway는 접속·송신 병목을 분리하지만 콘텐츠 계산 자체를 병렬화하지 않는다. 별도 hop·큐잉·직렬화 비용도 측정한다.
- [ ] 프로토콜은 버전·메시지 종류·길이 상한, 인증된 세션/캐릭터 결합, session generation, 입력 sequence와 라우팅/authority generation의 의미를 정의한다. 필드명·wire 형식은 실제 계약에서 정한다.
- [ ] Gateway 검증은 인증·프레이밍·크기·빈도·라우팅 경계이고, 콘텐츠 서버는 자기 권위·세션·순서·게임 상태를 검증한다. Gateway가 전달했다는 이유로 이동·충돌·경제 결과를 신뢰하지 않는다. 비공개 네트워크 배치만으로 내부 peer 인증·인가를 대신하지 않는다.

## 큐·브로드캐스트·성능

- [ ] 용량 검증은 snapshot 수신 신선도로 판정하지 않는다. 같은 상황에서 snapshot은 100ms 안에 도착했지만 입력 처리 경계(ack)는 수 초 뒤처져 있었다. 유지 시간 동안 세션별 미확인 입력 수(또는 입력→처리 지연)와 RTT를 표본으로 기록하고, 가득 찬 World 하나와 다른 지역 사용자가 공존하는 시나리오를 포함한다.
- [ ] 시뮬레이션 tick 시간과 DB commit 지연만으로 수용 인원을 판정하지 않는다. tick과 commit이 예산 안에 있어도 로직 스레드 전체 CPU가 포화하면 입력 ack가 수 초 밀리고 신규 접속자의 상태 설치가 끊길 수 있다. 입력 ack 지연·RTT와 함께 로직 스레드 CPU와 loop 구간별 시간을 기록하고, 포화 구간을 분해한 뒤에 완화책을 정한다. 최악 밀집 장면에서 측정하고, 개발 머신의 다른 서비스와 CPU를 공유한 측정은 contended로 표시한다.
- [ ] 로직 loop에서 공개·송신 대상 확인을 **반복마다 모든 세션에 대해** 하지 않는다. 연결 하나의 frame을 소비해야 다음 frame을 읽는 구조에서는 반복 수가 수신 frame 수(인원×입력 주기)에 비례하므로, 반복마다 세션 전체를 훑으면 비용이 대략 인원의 제곱으로 커지고, 세션별 조회가 세션 배열 전체를 선형 탐색하면 정원 상수(배열 칸 수)만큼 더 곱해진다. 공개 구간을 계측할 때는 이 순회와 snapshot 생성을 **다른 구간으로 나눈다**. 한 지역 밀집 장면에서는 snapshot 하나가 담는 관찰 대상도 인원과 함께 늘어 생성 비용도 인원보다 빠르게 커질 수 있으므로, 둘을 합친 구간만 보면 원인을 잘못 고른다. 실제 사례에서 합친 공개 구간이 loop 시간의 60~80%였고 처음에는 순회를 원인으로 봤지만, 나눠 재자 포화 지점에서 snapshot 생성이 절반 정도, 순회가 4분의 1 정도였다. 개선책은 이 분해 결과에 맞춰 정하고 같은 계측으로 효과를 확인한다.
- [ ] 외부 연결 상한은 World/지역 수 × World 수용 인원 + 인증·재접속·전환 여유에서 도출한다. 고정 상한이 World 하나의 정원과 같으면 그 World가 가득 찼을 때 다른 지역 사용자의 TLS 접속까지 막혀, 수용 인원 자체를 검증할 수 없다.
- [ ] 구매·보상·발사 같은 의미 있는 명령/이벤트는 병합·삭제 대상으로 두지 않고, 처리할 수 없으면 명시적으로 거부하거나 복구 가능한 실패로 처리한다. 교체 가능한 상태 snapshot을 병합할 때도 delta baseline과 생성/제거 순서를 깨뜨리지 않는다. 병합·coalesce·drop의 메시지별 의미는 [공통 전달 계약](/development/network-delivery.md), 게임 baseline·명령 계약은 [게임 전달 의미론](/game/network-delivery.md)을 따른다.
- [ ] 콘텐츠 측이 정한 공개 범위·수신 대상을 Gateway가 팬아웃한다. AOI 멤버십 변경/권한 철회와 송신 대기의 정합성을 유지한다. 개인별 비공개 필드를 공용 방송 버퍼에 섞지 않는다.
- [ ] 동일 공개 payload는 필요할 때만 직렬화·불변 버퍼 공유를 적용하되, 연결별 암호화·압축·baseline이 다르면 결과를 무조건 공유하지 않는다. AOI 계산·대상 목록 생성·프로세스 간 전송 비용은 Gateway 분리만으로 사라지지 않는다.
- [ ] 모든 참여자의 갱신을 모두에게 보내는 장면은 참여자 수에 따라 팬아웃이 제곱 수준으로 커질 수 있다. Gateway 증설만으로 해결한다고 가정하지 않고 관심 영역·변경분·복제 빈도와 최악 밀집 장면을 함께 검증한다.
- [ ] AOI 인덱스는 거리형 오픈월드·방/포털형 월드, 질의 반경·객체 크기·밀집도·이동률에 맞춰 선택한다. 정적 후보 목록을 여러 관찰자가 공유해도 최종 인가 목록은 아니며 생성/제거/이동/공개 규칙 변경의 갱신과 개인별 필터를 유지한다. *Game Programming Gems 3* 한국어판 PDF p.631–634와 [Unreal Replication Graph](https://dev.epicgames.com/documentation/en-us/unreal-engine/replication-graph-in-unreal-engine)의 grid/room 선택·공유 목록 원리이며 특정 트리의 우위를 보장하지 않는다.
- [ ] 격자 AOI(예: 셀 = 가시 반경, 주변 3×3 검사)에서는 진입 반경보다 이탈 반경을 크게 두어(히스테리시스) 경계 개체가 spawn(full state)·despawn을 반복하지 않게 한다.
  - 기존 관찰자의 유지 여부를 현재 관찰 집합에서 이탈 반경으로 판정하거나, 셀 크기를 이탈 반경 이상으로 두거나, `ceil(이탈 반경 / 셀)` 고리까지 검사하는 방법 중 하나를 쓴다. 후보를 3×3 검사 결과에서만 다시 만들면 그 범위가 진입 반경까지만 닿는 방향의 히스테리시스가 사라진다.
  - 관찰 관계는 양방향으로 갱신한다. 이동한 개체를 "보는 쪽"만 다시 계산하면 이동한 플레이어가 새로 보게 될 정지 NPC가 주기 전체 재계산 때까지 늦게 나타난다.
  - 관찰자 후보(플레이어) index를 전체 개체 index와 나눠 재계산 비용이 몬스터 밀도에 비례하지 않게 하고, 셀 이동 재계산과 주기 전체 재계산 비용을 따로 측정한다.
  - 관찰 집합을 거치지 않는 전역 broadcast(일시정지·상태 플래그 등)는 공개 범위를 우회하고 나중에 들어온 관찰자에게 빠지므로 spawn 상태에 포함해 관찰자에게만 보낸다.
- [ ] 틱 예산 안에 입력 처리·시뮬레이션·AOI·출력 생성이 들어가는지 실제 부하에서 확인한다. 평균 CPU가 아니라 로직 스레드의 p95/p99 지연·틱 초과·큐 대기와 코어별 병목을 본다. 피크 CPU GHz만으로 장비를 고르지 않는다.
- [ ] Gateway는 연결 수·PPS·송신 바이트·느린 소비자·재접속 폭주, 콘텐츠 서버는 밀집 전투·AI·AOI·단일 로직 코어, DB는 완료 지연·큐 적체를 각각 측정한다. 각각의 증설 효과와 전체 응답 지연을 구분한다.
- [ ] N개 Gateway와 M개 콘텐츠 서버는 네트워크와 콘텐츠 소유 단위를 각각 확장하는 구조다. 이미 포화된 단일 존의 전투 계산은 Gateway 추가로 빨라지지 않는다. 존/인스턴스 배치·입장 제한·소유권 분할 중 요구에 맞는 정책을 정하고 교차 경계 정합성을 검증한다.

## 근거와 적용 한계

- [오딘: 발할라 라이징 — Games on AWS 2022 발표](https://www.slideshare.net/slideshow/8-mmorpg-300-games-on-aws-2022/254068948): 11~13쪽의 multi I/O/single logic과 선택 이유, 19~21쪽의 Gateway 방송 전담·N:M 구조·콘텐츠별 확장, 43쪽의 운영 조건에 맞는 장애/성능/확장 테스트 권고를 확인했다. 행사는 [AWS 공식 일정](https://pages.awscloud.com/rs/112-TZM-766/images/games-on-aws-2022-agenda.pdf)으로 교차 확인했다.
- 발표는 분리 구조의 실서비스 사례이지 위 체크리스트와 [공통 서버 운영](/development/server-checklist.md)·[서비스 수명](/development/service-lifecycle.md)·[영속화·장애 체크리스트](/game/server-persistence.md)의 큐·fencing·커밋 프로토콜을 공개한 구현 명세가 아니다. 위 항목은 서버 권위·동시성·복구 원칙을 그 구조에 적용한 설계 기준이다.
- 발표 10쪽의 메모리 우선/주기적 DB 저장을 무손실 경제 트랜잭션의 보장으로 읽지 않는다. 공개 자료만으로 실제 내구성·장애 복구 세부를 확정할 수 없다.
- 발표 당시 EC2·Aurora 비교와 ENA 버퍼/RSS/하이퍼스레딩 튜닝값은 해당 환경의 관측이다. 현재 장비·OS·드라이버의 기본값/권장값으로 복제하지 않으며 공식 지원 범위와 실제 부하로 검증한다.
