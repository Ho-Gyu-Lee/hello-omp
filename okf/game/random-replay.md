# 게임 기록·재생·락스텝의 권위와 진단

[난수·절차 생성·재현 계약](/development/randomness.md)을 게임에 적용합니다. 고정 seed나 같은 소스만으로 동일 결과가 보장되지는 않으며, 기록/재생은 서버 권위·경제 멱등성·전송 보안의 대체가 아닙니다.

## 기록·재생과 락스텝

- 락스텝을 선택하면 같은 초기 상태에 같은 확정 명령열을 같은 순서로 적용해야 합니다. 로컬 플레이어 특례·카메라·벽시계·미초기화 값·해시 순회/동률·병렬 합류·부동소수 설정을 시뮬레이션 결정에 섞지 않습니다. 입력 도착 지연과 느린 시뮬레이션 노드가 진행을 제한할 수 있으며, 정책 없이 가변 dt로 따라잡으면 동일 연산열을 깨뜨릴 수 있습니다. 상태 전송량과 결정성/대기 비용의 교환이지 모든 게임의 권장 구조가 아닙니다.
- desync는 결과를 덮어 감추기보다 논리 tick별 정규 상태 hash와 원인 명령·하위 시스템 상태로 최초 차이를 좁힙니다. 주소·padding을 hash하지 않습니다. 복구/이탈 정책은 선언한 프로토콜을 따릅니다. 전체 월드를 모든 클라이언트가 시뮬레이션하는 구조는 숨겨야 할 정보까지 보유할 수 있으므로 [정보 가시성](/security/game.md#정보-가시성관전자) 요구와 양립하는지 먼저 판단합니다.
- 테스트를 위한 확률/결과 고정·무적·임의 상태 주입은 출하 클라이언트나 무인가 서버 경로에서 사용 가능하지 않게 합니다. 봇 테스트는 실제 명령·게임 규칙을 거치고, 의도적으로 비정상 상태를 만든 시험은 정상 플레이 실패와 구분하되 제품이 허용하는 입력의 결함을 '테스트 도구 문제'로 기각하지 않습니다.

## 근거와 적용 범위

- 테스트 훅·고수준 게임 이벤트 재생의 근거: *Game Coding Complete* 1판 한국어 제공본 PDF p.614–624. 난수/생성 근거와 이식성 한계는 [공통 정본](/development/randomness.md)에 보존합니다.
- *Game Programming Gems 3* 한국어판 5.1–5.2(PDF p.588–595)의 락스텝·desync 사례를 [Factorio의 deterministic lockstep](https://www.factorio.com/blog/post/fff-76)과 대조했습니다. 서버 권위 정책을 클라이언트 소유 권위로 바꾸는 근거로 채택하지 않습니다. 현대 문서 확인 2026-10-15.
- 책의 성능·버그 탐지 비율이나 자체 난수 구현을 그대로 채택하지 않습니다. 위 항목은 재사용 설계 기준이며 이 작업에서 멀티플레이어 락스텝 제품을 구현·실행한 것은 아닙니다.
