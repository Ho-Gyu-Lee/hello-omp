# 게임 네트워크 복구·전달 의미론

상위 개념: [게임 네트워크 동기화](/game/network-sync.md)

## 복구·전달 의미론
- 증분 event·command·delta를 쓰는 시스템은 손실·중복·역순·장기 이탈 뒤 권위 상태로 수렴할 경로를 둔다. snapshot·replay log·state hash·재조회 중 요구에 맞는 방식을 선택한다.
- 이전 baseline에 의존하는 프로토콜은 양측이 공유하는 accepted baseline을 식별하고 불일치·만료 시 bounded recovery 또는 full-state resync를 제공한다.
- **컨테이너·필드 delta와 신규 관찰자:** 목록·사전을 연산 로그(op-log)로 복제하면, 이번 송신 전에 이미 상태에 반영된 연산이 신규 관찰자의 full state에도 들어가고 다음 delta에도 실려 두 번 적용됩니다. full state에 "반영됐지만 아직 보내지 않은 연산 수"(또는 컨테이너 version)를 함께 보내 수신측이 그만큼 건너뛰게 합니다. 관찰자가 없을 때는 연산을 기록하지 않고 첫 관찰자는 full state로 시작합니다. index 삽입·삭제 같은 위치 기반 연산과, 송신할 때마다 baseline이 전진하는 연쇄 delta는 신뢰·순서 보장 stream에서만 성립합니다. 모든 관찰자가 하나의 직렬화 baseline을 공유하면 신규 관찰자의 초기값도 현재 값이 아니라 그 baseline(마지막 직렬화 값)이어야 합니다. 비신뢰 delta는 연결별 ACK baseline을 쓰거나, 공유 baseline을 신뢰 채널로 보내고 delta에 baseline tick을 붙여 불일치 delta를 버립니다. 근거: [Mirror `SyncList`](https://github.com/MirrorNetworking/Mirror/blob/c4f3739966e151f405be1762d33502794fd034ff/Assets/Mirror/Core/SyncList.cs)의 `changesAhead`, [`NetworkTransformReliable`](https://github.com/MirrorNetworking/Mirror/blob/c4f3739966e151f405be1762d33502794fd034ff/Assets/Mirror/Components/NetworkTransform/NetworkTransformReliable.cs)의 초기 상태 처리, [`NetworkClient`](https://github.com/MirrorNetworking/Mirror/blob/c4f3739966e151f405be1762d33502794fd034ff/Assets/Mirror/Core/NetworkClient.cs)의 unreliable baseline tick 대조(조회 2026-10-11).
- 검증되지 않은 ACK·baseline ID로 권위 상태나 수신 window를 갱신하지 않는다. transport ACK와 애플리케이션 상태 수락의 구분은 [입력 처리 ACK와 로컬 재실행](/game/network-prediction.md#입력-처리-ack와-로컬-재실행)을 따른다.
- 메시지마다 전달·순서·중복·만료·최신값 대체 가능성·복구 의미를 정의한다. transport의 reliable/unreliable 이름만으로 애플리케이션 계약을 대신하지 않는다.
- authority handoff는 이전·현재·예정 authority와 handoff generation·commit 시점·in-flight message 처리 정책을 명시한다. host/local fast path도 원격 경로와 같은 검증·권한·정규화 결과를 보장한다.
- 느린 연결의 송신 큐는 무한히 증가시키지 않는다. 메시지 의미에 따라 coalesce·drop·backpressure·disconnect 정책을 적용한다.
- 최신 상태가 self-contained여도 한 번만 실린 불연속 marker까지 자동 복구되는 것은 아닙니다. 같은 연결 세대의 snapshot 병합·결과 메시지에 의한 상태 대체에서 반드시 필요한 marker를 최신 상태로 승계하거나 별도 재전달 계약을 둡니다. full-state/identity 교체·queue reset에서는 이전 marker를 비웁니다. soft 보정에도 증가하는 revision을 hard snap의 대용으로 쓰지 않으며 일회성 연출의 제한된 전달과 권위 상태 정합성을 구분합니다.
- 완료 결과의 소유권은 실행 호스트의 outbox → 실제로 접수된 불변 송신 메시지 → 수신 소비자로 이어진다. snapshot 주기가 느리거나 송신 큐가 가득 찼다는 이유로 결과를 지우지 않는다. 큐잉된 명령과 아직 넘기지 못한 완료 결과를 같은 서버 측 용량 예산에 포함하면 장애 시 전체 취소도 결과 배열 상한을 넘지 않게 할 수 있다.
- terminal 장애에서 실제로 시뮬레이션한 입력 경계와 폐기한 입력 경계를 구분한다. 폐기된 입력을 실행한 것처럼 이동 ACK로 재실행하지 않으며, 이미 적용된 제어 동작을 제외한 미실행 게임 명령에 성공·실행 거부 결과를 붙이지 않는다. 확인되지 않은 결과는 미확정으로 남긴다. 재동기화 상태에서도 순서 보장 전송이 이미 소유한 정상 선행 응답의 결과 prefix는 검증·소비해야 terminal 응답을 해석할 수 있다. 이 결과 정리는 예측 재실행·플레이 재개와 분리한다.
- 살아 있는 월드에 붙는 신규 접속과 재접속은 같은 full-state 설치 경로를 쓰고 월드를 재설정하지 않는다. 재접속 요청에는 마지막으로 **보낸** 명령이 아니라 마지막으로 **발급한** 명령 번호를 담아 아직 프레이밍하지 않은 명령까지 판정 범위에 넣는다. 서버는 이전 연결을 먼저 차단(fence)하고 그 대기열을 정리한 뒤 최고 수신 번호를 확정하며, 모든 uplink 메시지에 연결 epoch를 실어 다른 epoch의 늦은 메시지를 폐기한다. 클라이언트는 "서버가 받지 못함"과 "결과 보존 기한을 넘겨 알 수 없음"을 로컬 상태로 구분하고 자동 재전송하지 않는다. 재개 식별자의 생성·비교·로그 비노출·인스턴스 변경 시 만료 통지는 [게임 보안](/security/game.md)의 세션 재개 증명 기준을 따른다. 보존한 결과는 클라이언트 확인 뒤에만 해제한다.
- **지역·인스턴스 전환의 downlink 차단:** 클라이언트가 새 지역을 설치하기 전에 도착한 개체 갱신은 대상 lookup 실패로 버려집니다. 변경분 복제라면 다음 변경까지 복구되지 않아 원격 플레이어가 보이지 않습니다. 전환 통지를 보내기 **전에** 서버가 그 연결을 not-ready로 바꿔 상태 복제를 멈추고, 클라이언트가 전환 세대를 담은 ready를 보낸 뒤 새 위치 기준의 관찰 집합을 즉시 계산해 full state로 설치합니다. 서버가 개별 despawn 없이 관찰 관계를 비웠다면 클라이언트는 재설치 묶음(시작·끝 표시)에 다시 포함되지 않은 이전 개체를 제거합니다.
- 끊김 감지(heartbeat/liveness)와 재개 유예(grace)는 다른 값이다. 감지는 유효 입력·시계 probe가 끊긴 시간으로 판정하고, grace는 감지 뒤 같은 개체로 돌아올 수 있게 세션을 보관하는 시간이다. 서버는 클라이언트의 수락 응답 설치 여부를 직접 관측할 수 없다. 수락 응답을 설치해야만 보낼 수 있는 uplink(응답이 발급한 현재 세션·연결 epoch에 바인딩된 입력·probe 또는 설치 확인)를 한 번도 받지 못한 신규 세션은 재개 주체가 확인되지 않은 것으로 보고 grace 없이 제거한다. 설치 전 handshake·probe는 이 확인으로 세지 않는다. 설치 직후 첫 uplink 전에 끊겨 세션이 제거된 클라이언트에는 재개 만료를 알리고 신규 접속으로 복구하게 한다. 한 번이라도 확인된 세션은 재개 응답이 전달 중이어도 grace를 유지한다. 판정은 서버가 받은 메시지로 하고, 전송 계층이 클라이언트 내부 상태를 들여다보는 방식으로 대신하지 않는다. 명시적 해제·재접속·세션 재설정·장애·liveness 만료가 모두 같은 서버 측 끊김 처리로 모이게 한다. 남용 방지 규칙(예: 첫 입력 전 세션의 즉시 제거)을 제거하거나 바꿀 때는 그 규칙이 암묵적으로 처리하던 정상 경로의 정리 책임부터 확인한다. 새 토큰은 활성 세션뿐 아니라 재개 요청이 여전히 대조하는 만료 세션 기록, 재사용할 슬롯의 옛 기록과도 달라야 한다.

### 전송 보장·I/O API·RPC의 구분
- [TCP](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2)는 연결 안의 신뢰성 있는 순서 보장 byte stream이다. 그 위에 UDP용 패킷 재전송/재정렬을 기계적으로 중복 구현하지 않는다. 메시지 프레이밍·부분 송수신·큐 상한과 재접속/콘텐츠 처리 경계는 별도 계약이며 TCP ACK는 게임 커밋이 아니다.
- [epoll](https://man7.org/linux/man-pages/man7/epoll.7.html)은 I/O readiness API이고, [gRPC](https://grpc.io/docs/what-is-grpc/core-concepts/)는 RPC/stream 계층이다. [gRPC over HTTP/2](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)와 자체 TCP 프레이밍은 동일 프로토콜이 아니며 서버 권위·복제 방식은 그 상위의 게임 계약이다. 특정 전송을 모든 게임의 기본값으로 강제하지 않는다.
- 상태 병합은 전송 계층에 제출하지 않은 완전한 메시지에만 적용하고 부분 제출된 프레임·라이브러리 소유 버퍼를 수정하지 않는다. [gRPC flow control](https://grpc.io/docs/guides/flow-control/)의 write 반환도 실제 네트워크 송신 완료를 뜻하지 않는다. RPC timeout/cancel은 이미 적용된 업무 결과의 rollback이나 미실행 증거가 아니며, 재접속·재호출의 업무 멱등성은 별도로 보장한다.
- 순서 보장 stream 하나(TCP·WebSocket·reliable UDP)에 큰 메시지를 실으면 뒤의 snapshot·입력 ACK·시간 표본이 그 전송 시간만큼 밀립니다(head-of-line). [kcp2k 고정 소스](https://github.com/MirrorNetworking/Mirror/blob/c4f3739966e151f405be1762d33502794fd034ff/Assets/Mirror/Transports/KCP/kcp2k/highlevel/KcpPeer.cs)도 최대 크기 reliable 메시지가 수신 window 전체를 채운다고 경고합니다. 애플리케이션 메시지 상한을 작게 정하고, 맵·목록 같은 큰 데이터는 별도 경로로 보내거나 같은 stream이라면 조각을 실시간 frame 사이에 끼워 보내는 연결별 송신 스케줄러를 둡니다. 조각을 한꺼번에 큐에 넣으면 나눠도 지연은 같습니다. 커널 송신 버퍼에 이미 들어간 바이트는 앞지를 수 없으므로 미송신량도 제한합니다(Linux `TCP_NOTSENT_LOWAT`, [ip-sysctl 문서](https://docs.kernel.org/networking/ip-sysctl.html)). 송신 batch는 메시지를 쪼개지 않으며, UDP는 경로 MTU 안의 datagram 하나로, TCP는 대기 frame을 묶어 한 번에 씁니다. 상한을 넘는 송신을 로그만 남기고 버리면([Mirror `NetworkConnection.Send`](https://github.com/MirrorNetworking/Mirror/blob/c4f3739966e151f405be1762d33502794fd034ff/Assets/Mirror/Core/NetworkConnection.cs)) 신뢰 stream에서 메시지가 조용히 빠져 순서·완전성 가정이 깨지므로 호출자 오류나 연결 종료로 처리합니다(조회 2026-10-11).
- 공유 연결 송신 스케줄러를 "실시간 frame을 먼저 보내고, 조각은 실시간 publication 하나 분량의 여유를 남길 때만 보낸다"로만 만들면, 실시간 배출이 계속될 때 비워지는 공간을 실시간이 매번 먼저 채워 조각이 끝내 들어가지 못합니다. 로그인·전환의 상태 설치가 멈추는 새 정체입니다. 조각이 바이트 부족으로 거절된 연결에서는 그 뒤 admit한 실시간 바이트에 상한을 두고, 상한에 닿으면 조각 frame 하나가 들어갈 때까지 결과·snapshot을 보류합니다. 이렇게 하면 실시간 앞에 쌓이는 조각 바이트와 대기 조각 앞에 admit되는 실시간 바이트에 각각 상한이 생기고, 바이트·slot 조건이 처음 충족되는 호출에 조각이 들어갑니다. 연결 handshake·설치 완료 같은 control은 보류하지 않습니다. 이것은 admit량과 서비스 순서의 보장이지 경과 시간 상한이 아닙니다. 느린 reader나 slot 부족이 계속되면 시간은 제한되지 않습니다. 여러 연결이 송신 frame 풀을 공유하면 연결별 slot 예약 합계가 풀 전체를 차지하지 않게 하고(실제 송신 중인 연결만 세고 풀 크기로 상한), 순회 시작점은 연결별로 회전합니다. 다른 연결의 성공이 막힌 route의 차례를 덮어쓰면 안 됩니다. 공유 풀 부족은 연결 사이에서 따로 중재하되, 이번 회차에 이미 송신을 받은 연결이 자기 다른 route의 거절로 다시 선두가 되지 않게 합니다. 보장은 drain된 바이트가 아니라 스케줄러가 admit한 양과 "조건이 처음 충족되는 호출에 큐잉"으로 서술합니다. transport가 쓰기를 연달아 이어 가면 호출 사이에 window 전체가 비워질 수 있기 때문입니다. 위 결함은 2026-10-11 실제 구현에서 독립 리뷰가 단계적으로 찾아냈고, 각 규칙을 결정적 모델 테스트와 변이 검사로 확인했습니다. 느린 reader에서의 live 지연은 측정하지 않았습니다.
- 서버 권위의 신뢰 경계(클라이언트의 위치/상태 보고는 검증 자료일 뿐 무검증 정본이 아님)는 [게임 보안](/security/game.md)이 정본이다. 입력 이력 재실행·명중 rewind·전체 물리 rollback은 각각의 게임 요구에 맞춰 선택하며, 서버 권위만을 이유로 모두 의무화하지 않는다.

### 모바일 경로 전환과 세션 복구

- TCP 재접속, [QUIC의 살아 있는 연결 migration](https://www.rfc-editor.org/rfc/rfc9000.html#section-9), 여러 경로의 동시 사용, 게임 세션 resume을 구분합니다. CID는 transport 상태의 라우팅 식별자이지 계정·캐릭터 권위나 만료된 연결을 복원하는 증명이 아닙니다. 주소가 바뀌어도 같은 transport owner로 도달해야 하며, CID 라우팅만으로 Gateway 장애 시 상태가 복제되지는 않습니다.
- [Android NetworkCallback](https://developer.android.com/develop/connectivity/network-ops/reading-network-state)·[Apple NWPathMonitor](https://developer.apple.com/documentation/network/nwpathmonitor)는 경로 관찰 신호입니다. Wi-Fi/셀룰러 표기나 사용 가능 알림을 인증된 서비스 도달성으로 대체하지 않습니다. 정상 연결을 모든 알림마다 끊거나 reachability 사전 검사만으로 접속을 막지 않으며, 경로 신호와 실제 I/O·애플리케이션 timeout을 함께 사용합니다. 주소 캐시·진행 중 DNS와 주소군별 접속 후보도 회선 세대에 맞춰 처리해 이전 경로의 주소 하나만 무한 재사용하지 않습니다. TLS 검증용 서비스 identity는 dial IP와 분리합니다.
- 연결·DNS·TLS·재시도는 한 소유자의 상태 전이와 attempt generation으로 묶고, 낡은 callback·취소된 재시도를 무효화합니다. 재시도 간격·횟수·대기 자원에는 예산을 둡니다. 네이티브 작업 스레드도 [iOS 앱 suspension](https://developer.apple.com/documentation/uikit/extending-your-app-s-background-execution-time)과 [Android Doze의 네트워크 제한](https://developer.android.com/training/monitoring-device-state/doze-standby)을 우회하지 못합니다.
- 소켓 연결/TLS handshake 성공과 권위 full-state 설치 완료는 별개입니다. 프로세스 내부의 token·명령 이력 보존으로 앱 프로세스 종료 후 복구까지 보장하지 않습니다. 재실행·grace 만료·거절은 재인증·권위 상태 복구·미확정 결과 처리 계약을 따릅니다.
- 전송 선택은 같은 입력/명령·복제 부하에서 인증된 READY 복구, 상태 나이, 입력→권위 결과의 꼬리 지연, 중복 실행·미확정 결과, CPU wakeup·메모리·단말 에너지로 비교합니다. HTTP 처리량이나 영상 FPS를 게임 지연으로 치환하지 않습니다. [STORM, USENIX ATC 2025](https://www.usenix.org/system/files/atc25-hu-liekun.pdf)은 이동 중 서로 다른 품질의 경로를 함께 사용하면 단일 경로보다 영상 지연/프레임률이 나빠질 수 있음을 보인 사례이며, 해당 수치를 모든 게임·단말의 성능 예측으로 사용하지 않습니다.
- 크로스플랫폼 전송 구현을 공유해도 앱 수명·소켓별 네트워크 문맥 같은 OS 통합이 사라지지는 않습니다. 엔진의 공통 알림을 재사용하고 부족한 연결 문맥만 작은 경계에 둡니다. 그 경계에 송수신·TLS·재시도·게임 세션 상태 머신을 복제하지 않으며, 라이브러리가 이름을 받는다는 사실만으로 플랫폼의 connect-by-name 의미를 제공한다고 판단하지 않습니다.
- [Apple TN3151](https://developer.apple.com/documentation/technotes/tn3151-choosing-the-right-networking-api)은 크로스플랫폼 코드의 BSD sockets 사용을 허용하지만 시스템 resolver·Happy Eyeballs·소켓별 원래 DNS 이름 연관(`ne_socket_set_domains`)·성립된 소켓의 viability 관찰을 별도 책임으로 둡니다. 수동 DNS→주소 연결은 Happy Eyeballs를 구현해도 VPN On Demand와 호환되지 않는다고 설명합니다. domain tagging은 content filter 등에 문맥을 주는 수단이며 이 제한을 해소한다는 근거는 아닙니다(조회 2026-10-08). 이미 연결된 VPN 경로는 별도 검증 대상입니다. 자체 TLS/CA 검증은 Apple의 시스템 신뢰 평가 권고와 다른 선택이므로 Safari/OS의 신뢰·폐기·사용자/기업 anchor 정책과 동등하다고 주장하지 않습니다.
