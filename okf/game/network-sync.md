# 게임 네트워크 동기화

## 상태 계층
- 권위 시뮬레이션 상태, 클라이언트 예측 상태, 보간 목표, 최종 표시 상태를 구분한다.
- 표시 상태는 시각적 연속성을 위한 결과이며 서버 검증·저장·delta baseline으로 역주입하지 않는다.
- 서버가 보정·정규화·재계산한 최종 accepted 상태를 저장·시뮬레이션·복제·송신자 보정·관전자 전파 전체에 사용한다.

## 시간·순서·생명주기
- 원격 timestamp와 로컬 시간을 직접 비교하지 않는다. 의미·단위·기준 시계를 명시하고 변환하며, 로컬 경과 시간은 단조 증가 시간원으로 측정한다.
- 아직 적용 시점이 오지 않은 샘플과 새 데이터가 끊겨 적용 가능 기간을 지난 샘플을 구분해 대기·외삽·재동기화 정책을 각각 적용한다.
- sequence의 중복·역순·손실·wraparound와 재접속 후 generation 변경을 처리한다. 큰 sequence 하나로 수신 window를 임의 전진시키지 못하게 한다.
- 재사용 가능한 entity ID에는 generation 또는 동등한 생명주기 식별자를 결합해 늦은 패킷이 새 객체에 적용되지 않게 한다.

### 공통 시간 계층과 네트워크 시간

- 속도·쿨다운·보정처럼 시간에 의존하는 규칙보다 시간의 소유권·단위·기준점을 먼저 정의합니다. 공통 구현/계약을 사용하는 것과 모든 용도를 하나의 `GetTime()` 값으로 처리하는 것은 다릅니다. 기능별 독립 시계·임의 float 누적을 만들지 않고 도메인과 단위를 API에 드러냅니다.
- 로컬 단조 경과시간, 서버가 실제 처리한 시뮬레이션 tick/시간, 클라이언트의 서버 기준시각 추정, 지연된 원격 표시 시각, 필요한 경우의 선행 예측 시각을 구분합니다. 클라이언트 추정기·표시 보정이 서버 시계를 변경하거나 추가 이동 시간을 승인하지 못하게 합니다.
- 서버 기준시계와 처리한 논리 tick은 pause·부하·따라잡기 제한으로 다른 의미를 가질 수 있습니다. 필요한 대응 기준점을 결과와 함께 전달하며 `floor(추정 서버시간 × tickRate)`만으로 실제 처리 완료 tick을 단정하지 않습니다. 명령 sequence 역시 tick과 별개의 순서 식별자입니다.
- 절대 시각/누적량은 정밀도를 보존하는 정수 duration/tick 또는 double을 사용하고 작은 단위의 float를 계속 더해 정본 시각을 만들지 않습니다. 변환의 단위·범위·오버플로와 tick 간격의 잔여량을 다룹니다. 순수 코어에는 승인된 시뮬레이션 시간 문맥을 전달하고 OS/엔진 시계 조회는 호스트 경계에 둡니다.
- 네트워크 동기화의 RTT·offset·drift는 측정과 추정입니다. 송수신/큐잉 측정 지점을 정의하고 초기 동기화·이상 표본·신선도·재접속/epoch 교체를 처리합니다. 네 timestamp 방식도 편도 지연 비대칭을 제거하지 못하며 RTT/2나 표본 분산만으로 정확한 편도 지연·절대 동기 오차를 보장하지 않습니다.
- 실측으로 표시하는 핑은 실제 요청 송신부터 대응 응답 수신까지 단조 시계로 측정합니다. 로컬 연결이라는 이유로 0을 대입하지 않습니다. 애플리케이션 RTT에는 해당 측정 경로의 큐잉·서버 처리가 포함되며, 처리시간을 뺀 전송 지연 추정과 구분합니다. 소수 정밀도의 원값을 보존하고 UI에서만 반올림합니다. 아직 측정하지 않았거나 만료된 표본은 유효한 0과 구분하고, 상관 ID·세대·echo 시각이 맞지 않는 응답으로 표본 나이를 갱신하지 않습니다.
- 초기 기준점 설정과 실행 중 보정을 구분합니다. offset 추정의 갱신을 게임이 소비하는 시각에 그대로 점프 적용하지 않고, 연속 시각의 역행·진행률 제한·큰 불연속의 명시적 재동기화 정책을 정합니다. 표시/예측 시각의 조정과 서버의 승인된 시뮬레이션 진행량은 별개입니다.
- 같은 프로세스의 로컬 클라이언트/서버도 시간의 작성자와 읽는 측을 구분하고 명령·결과의 시간 계약을 유지합니다. 같은 기준시계의 알려진 대응을 사용할 수 있으며 소켓·직렬화·가짜 RTT를 필수로 만들지 않습니다. 원격 추정 계산은 전송과 분리하여 서로 다른 가상 시계·지연·drift로 검증할 수 있습니다. 제품 로컬 경로와 원격 조건을 가정한 검증을 혼동하지 않습니다.
- 고정 스텝·송신 주기·렌더 주기는 별개입니다. 다른 제품의 tick rate·보간 지연·catch-up 배율을 그대로 채택하지 않으며, 공통 시간 시스템이 결정성·스피드핵 방어·전체 rollback을 자동 제공한다고 표현하지 않습니다. 동기화 표본·pending 요청·보간/예측 이력은 개수와 보존 범위를 제한합니다.

- [Valve의 Yahn Bernier 작성 논문 원문 보관본](https://web.cs.wpi.edu/~claypool/courses/4513-B03/papers/games/bernier.pdf): 서버 권위, timestamp 이력의 지연 보간, 자기 입력 예측과 별도 hit rewind를 구분합니다. 9쪽 각주 6은 시계 대응을 가정하고 smoothing을 별도 문제로 두므로 이 논문을 완성된 NTP 동기화 구현으로 인용하지 않습니다.


### 이동 속도·시간 예산 검증

- 이동 입력/목적지를 권위 코어가 시뮬레이션하는 방식과, 클라이언트 좌표 보고를 검증해 수락하는 방식을 구분합니다. 전자는 클라이언트 좌표를 위치 정본으로 대입하지 않으며, 이미 이 구조인 코어를 스피드핵 검사 때문에 무검증 좌표 수락 모델로 바꾸지 않습니다. 후자는 아래 이동량·상태·경로 검증이 모두 필요합니다.
- 허용 속도는 서버가 소유하는 캐릭터 규칙·상태에서 결정합니다. 클라이언트가 보고한 속도·buff·이동 모드 자체를 승인 근거로 삼지 않습니다. 속도 변화는 적용 tick과 연결하고 변화 구간의 허용 이동량을 계산합니다. 월드 좌표의 이동과 아이소메트릭 화면/애니메이션 좌표를 혼용하지 않습니다.
- **고정 delta만으로 처리 시간 예산이 보장되지는 않습니다.** 메시지가 많거나 클라이언트 시계가 빠르다는 이유로 같은 권위 구간에 추가 이동 step을 부여하지 않습니다. 신뢰하는 실행 호스트가 단조 시간과 정책에 따라 처리할 tick/누적 시간을 제한하고, 순수 코어는 그 실행 문맥을 받아 계산합니다. 로컬 호스트의 시계 검사는 공격자가 소유한 클라이언트를 신뢰 가능한 서버로 만들지 않습니다.
- 좌표 보고는 마지막 수락 위치·권위 시간 구간·세션/월드 세대와 대응시킵니다. 클라이언트 예측 위치와 다른 시점의 서버 현재 위치를 그대로 비교하지 않습니다. 미검증 timestamp·큰 sequence·지연 신고로 허용 구간을 무제한 넓히지 않습니다. 일치하는 과거 권위 상태와의 위치 오차 검사는 시간당 이동 허용량 검사와 목적이 다릅니다.
- 거리/경과 시간 검사는 필요조건이지 합법 경로의 증명이 아닙니다. 지터·뭉쳐 도착한 입력에는 상한이 있는 이동 여유/누적 창을 사용하되 매 패킷마다 오차 여유를 새 이동권으로 지급하지 않습니다. 입력 분할·미세 초과 반복·무제한 idle 적립으로 이동량을 늘릴 수 없어야 합니다. 거부 시 last-good 위치를 보존하는 것과 서버 시계/예산 장부를 진행시키는 것은 별개이며, 같은 경과 시간을 반복 적립하지 않습니다.
- 속도 상한 이내라도 충돌 구간을 관통하거나 이동 금지 상태를 위반한 경로는 거부합니다. 대시·넉백·이동 발판 같은 합법 이동은 권위 상태의 다른 규칙으로 계산하고, teleport/respawn은 서버가 승인한 불연속 전환으로 처리합니다. 클라이언트가 보낸 예외 플래그로 검증을 우회하지 않습니다.
- 무효 보고를 정본·last-good으로 채택하지 않되 정상 권위 시뮬레이션은 계속 진행할 수 있습니다. 거부 요청의 처리 완료 ACK·거부 기록·이상 징후 누적은 별도 계약입니다. 단일 속도/시간 불일치를 치트 확정이나 영구 제재로 연결하지 않고, 먼저 잘못된 이동의 이득을 차단하고 권위 상태로 보정합니다.

## 예측·보간·보정
- 외삽은 시간·거리·회전량 또는 도메인별 오차 예산으로 제한하고 권위 샘플 없이 무기한 진행하지 않는다.
- 보정은 의도된 별도 기준점이 없다면 현재 표시 상태에서 시작해 오래된 목표로 점프한 뒤 다시 이동하는 이중 보정을 피한다.
- teleport·respawn·scene transfer·authority change 같은 불연속 전환마다 속도·각속도·보간 버퍼·오차 누적·timestamp·delta baseline을 preserve·reset·recompute 중 하나로 명시한다.
- 정지·sleep·dirty 판정은 위치뿐 아니라 회전·애니메이션·상태 플래그 등 관찰 가능한 변화를 포함한다.
- 각도·주기 값은 비교와 delta 계산 전에 시스템이 정한 canonical representation 또는 shortest-path 규칙을 일관되게 적용한다. 누적 회전량이 의미 있는 값은 별도로 표현한다.

### 애니메이션·연출 시간
- 애니메이션 프레임 번호를 렌더 FPS나 위치 전송 주기와 일치시키는 것을 동기화로 보지 않는다. 상태·동작 인스턴스 식별자·시작 기준시각/처리 경계·지속시간/재생률·취소/사망 revision 중 실제 동작에 필요한 정보를 전달하고 각 표시 타임라인에서 재생 위치를 계산한다. 모든 루프 클립의 위상을 서버가 반드시 복제해야 한다는 뜻은 아니다.
- 원격 위치를 지연된 snapshot 시각으로 그린다면 애니메이션·연결된 월드 연출도 그 표시 시각에 대응시킨다. 패킷 도착 시점부터 무조건 0번 프레임으로 시작하지 않으며, 지연 도착·중복·취소·관찰 재진입에서 현재 위상과 일회 효과의 소비를 구분한다.
- 보행 루프는 의미상 이동 시간이나 누적 이동 거리에서 위상을 구하는 방식을 검토한다. 위치 보정용 시각 오프셋을 실제 보행 거리로 누적하지 않는다. 정상 정지·벽에 막힘·입력 부족·보간 표본 부족을 같은 idle 전환으로 처리하지 않고, 의도·실제 변위·데이터 신선도에 따라 위상 유지/정지와 전환 정책을 명시한다.
- 엔진의 자동 애니메이션이 scaled delta로 진행하는지 확인한다. 게임 이동을 독립된 단조 시간으로 실행해도 자동 재생은 엔진 배속·pause에 영향을 받을 수 있다. 서버 현재·로컬 예측·지연 보간은 서로 다른 시각이므로 같은 벽시계 순간의 그림 프레임을 강제로 일치시키지 않는다.
- 공격·피격·스킬·사망의 판정은 권위 상태 전이와 시간 계약이 결정한다. 애니메이션 콜백·프레임 도달·소리 재생이 피해나 자원 소비를 확정하지 않는다. 예측 연출은 재실행 시 중복 부수효과를 막고 거부/취소에 대응하며, root motion·대시·넉백이 게임 위치를 바꾼다면 서버가 검증할 이동 규칙과 분리하지 않는다.


### 입력 처리 ACK와 로컬 재실행
- 입력 예측이 필요한 게임에서는 서버 검증 가능한 입력과 session generation·sequence를 보내고 클라이언트에 미확정 입력을 제한된 크기로 보관한다. 클라이언트가 보낸 위치·delta time·timestamp·명중 신고 자체가 권위 상태는 아니다.
- 서버는 권위 상태와 **그 상태까지 처리한 입력의 경계**를 함께 반환한다. Gateway의 수신/전달 ACK나 TCP ACK를 게임 로직 처리 완료로 해석하지 않는다.
- 누적 ACK를 쓰려면 같은 세션의 순서가 확정된 입력 prefix여야 한다. 수락과 거부 결과를 구분하고 거부 입력은 상태에 적용하지 않되 클라이언트가 해당 예측을 폐기할 수 있게 한다. 누락/역순 입력을 건너뛰고 큰 sequence 하나를 처리 완료 경계로 삼지 않는다.
- 병합·접수 거부·중복도 완료 의미를 정의한다. 이미 sequence를 가진 입력을 병합할 때는 대체 완료 등 명시적인 결과로 처리 경계를 닫고, 큐에서 단순 삭제해 ACK 구멍을 만들지 않는다. 접수 전 번호 부여 여부와 실패 시 pending 정리 정책을 정하며, 이미 전송한 번호는 timeout만으로 다른 요청에 재사용하지 않는다. 중복은 기존 pending/완료 결과를 재사용하고 다시 실행하지 않는다.
- 클라이언트는 ACK까지의 확정된 입력을 제거하고, 받은 권위 상태를 예측 기준으로 삼아 미확정 입력만 순서대로 재실행한다. 재실행이 발사 요청·소리·재화 변경을 중복 발생시키지 않도록 표시/외부 부수효과와 시뮬레이션을 구분한다.
- 예측 복원 checkpoint에는 같은 후속 입력에서 미래 동작을 결정하는 상태가 들어 있어야 한다. 위치·최종 목적지만으로 진행 중 경로를 다시 탐색하면 시작 셀 중심으로 되돌아가는 등 기존 경로와 달라질 수 있다. 전체 경로를 복제하지 않더라도 정규 경로의 원점·목표·진행 cursor처럼 동일한 경로를 재구성하고 검증할 정보를 보존한다. 아날로그 방향은 공격으로 바뀔 수 있는 바라보는 방향이나 입력 부족 시 0이 되는 관측 속도로 대체하지 않는다.
- 정상 snapshot에서 입력 프레임 ACK와 명령 완료 ACK를 함께 보내면 각각의 송신 최대값뿐 아니라 **같은 실행 입력 prefix에 속하는 조합인지** 검증한다. terminal 폐기 경계는 아래 복구 계약처럼 실제 적분 경계와 별도로 검증한다. 이력을 제거한 뒤에도 마지막 ACK의 기준 상태를 별도로 유지하여 같은 ACK의 새 권위 보정과 동일 보정의 중복을 구분한다. 메시지·완료 결과·checkpoint 전체를 검증한 뒤 한 번에 baseline·이력·게임 상태를 반영한다.
- RTT 길이만으로 이력을 자르는 것과 서버가 처리한 입력을 식별하는 것은 다르다. 지터·서버 큐 대기·입력 거부가 있는 경로에서 시간 추정으로 ACK를 대체하지 않는다.
- 같은 이동 코드를 양쪽에서 사용해도 timestep·충돌 환경·다른 개체 상태·부동소수점 차이로 예측은 틀릴 수 있다. 임의 물리 엔진 간 결정성을 가정하지 않는다. 이력 상한을 넘거나 필요한 입력이 없으면 무한 재실행 대신 권위 상태로 재동기화한다.
- 아날로그 조향처럼 연속 갱신되는 조작은 순서 번호와 완료 결과를 가진 명령보다 **tick별 절대 입력 상태**로 보내는 편이 안전하다. 명령 창 고갈·결과 폭증·결과 때문에 강제된 snapshot을 피하고, 폐기된 입력이 있어도 다음 상태가 스스로 완전하다. 목적지·공격·취소 같은 이산 의도만 명령으로 둔다. 서버와 예측이 같은 프레임 적용 순서(예: 명령 → 방향 상태 → 적분)를 공유하고, 한쪽만 실행할 수 있는 조건(예: 방향 중 목적지 거부)도 같은 함수에 둔다.
- 서버가 수신 시각에 적용하는 제어 효과가 클라이언트 예측에서 재현될 수 없다면 parity가 깨진다. 수신 시점 효과는 이미 대기 중인 명령의 취소처럼 클라이언트도 알 수 있는 결과로 제한하고, 이동 정지는 해당 프레임 안의 명령 위치에서 양쪽이 같게 적용한다. 입력 부족 hold가 0으로 만든 속도처럼 이후 계산에 쓰이지 않는 출력 전용 필드는 재실행 필요 판정에서 제외한다.
- 서버 입력 버퍼 깊이는 클라이언트의 입력 생성률을 미세 조정해(예: 0.9–1.1배) 목표 여유로 유지할 수 있다. 서버 보고는 과거 상태이므로 **보고 이후 이미 적용한 보정량을 차감**해야 하며, 이를 빼면 RTT가 길 때 한계 순환으로 발산한다. 소비된 입력이 없는 구간은 "표본 없음"으로 보내 추정치를 유지한다. 오래된 명령 없는 입력의 강제 제거는 추가 이동권을 주지 않는 복구 수단이지만, 제거된 입력만큼 입력 ACK가 tick보다 앞설 수 있다는 불변식을 클라이언트 검증에 함께 반영한다.
- 같은 세션의 귀환처럼 **옛 입력이 새 위치에 적용되면 안 되는 불연속 전환**에서는 명령 큐가 비었다는 사실만으로 입력이 정숙하다고 판단하지 않습니다. 명령 창 용량(credit)을 쓰지 않는 방향 상태의 현재 값·미ACK 이력·권위 대기열까지 중립이어야 하며, 그렇지 않으면 명시적인 세션/epoch fence로 옛 입력을 폐기합니다. 경로 폐기가 필요한 전환은 보정 전에 경로를 정지합니다. 권위 표본 설치까지 새 입력을 보류하는 계약에서는 같은 세션 세대 안에서 보류 시작 시 기록한 목표 불연속 식별자와 같거나 이후인 표본이 설치될 때만 hold를 해제합니다. 그보다 이전의 중간 표본에서는 불연속 카운터가 증가했더라도 해제하지 않습니다. 식별자 wrap은 프로토콜의 순서 비교 규칙을 따릅니다. disconnect/resync는 hold를 정리하되 full-state 설치를 마치기 전(READY 전)의 입력은 계속 거부합니다.

### 원격 개체 보간과 판정 지연 보상
- 자기 캐릭터의 예측/보정, 다른 개체의 snapshot 보간, 서버의 명중 판정 지연 보상은 서로 다른 기능이다. 원격 개체는 수신한 권위 샘플 사이의 표시 시각으로 보간하고, 샘플 부족에는 제한된 외삽/정지/재동기화 정책을 적용한다.
- 시뮬레이션 틱·복제 송신 주기·클라이언트 렌더 프레임을 구분한다. 원문의 예시 갱신 빈도나 보간 지연을 제품 고정값으로 채택하지 않는다.
- 주기 상향의 비용과 이득을 따로 산정한다. 비용은 **CPU(초당 tick 작업량), uplink(입력 메시지 생성률), downlink(복제 주기 × 관찰 대상 수 × 대상당 bytes)**로 나눈다. tick 주기와 입력 주기를 1:1로 묶으면 CPU뿐 아니라 uplink도 tick에 비례하고, snapshot 주기가 분리돼 있으면 tick만 낮춰도 downlink는 줄지 않는다. 관찰자별 복제 대상 선정·정렬·직렬화 비용은 관찰자 수와 후보 수에 따라 늘어나므로 시뮬레이션 tick 비용과 따로 측정한다. 이득은 입력이 각 고정 스텝 경계를 기다리는 시간이 단계마다 최대 한 틱 간격만큼 줄어드는 것이다. [Apex Legends 서버·넷코드 설명(2021-04-28, 조회 2026-09-29)](https://www.ea.com/games/apex-legends/apex-legends/news/servers-netcode-developer-deep-dive)의 "20→60 Hz는 대역폭·CPU 3배, 최선 약 2프레임 단축"은 **tick마다 전체 월드 상태를 복제하는 모델**의 계산이며 다른 복제 모델에 그대로 적용하지 않는다. 프로토타입·엔진 기본 고정 스텝을 제품 서버 주기로 간주하지 않고, 목표 밀집도의 tick 꼬리 지연·AOI fanout·메시지/패킷 수와 조작 수락 기준을 함께 측정해 주기를 고른다.
- 입력 프레임과 권위 step을 1:1로 대응시키는 구조에서 서버 주기만 낮추면 입력 큐가 매초 두 주기의 차만큼 증가한다. 클라이언트 입력·예측 주기를 함께 바꾸거나 입력 시간을 권위 step에 대응시키는 규칙을 먼저 정의한다.
- 원격 보간 타임라인은 서버 상태 시각 영역으로 진행한다. tick × step은 서버가 버린 시간 부채·입력 부족 hold를 반영하지 못해 거짓 표본 부족을 만든다. 개체별 불연속은 그 개체의 버퍼만 재설정하고 공유 타임라인을 되감지 않는다. 버퍼 포화에는 최신 표본 거부보다 가장 오래된 표본 제거가 안전한 경우가 많다. 재접속·세대 변경에서는 타임라인과 지연·drift EMA를 함께 초기화해 긴 공백이 지터 추정을 오염시키지 않게 한다. HP·사망·공격 시작 같은 계단 값도 같은 표시 타임라인에서 표본화한다.
- 과거 명중 판정이 필요한 전투만 서버가 보유한 제한된 권위 이력으로 검사한다. 클라이언트 발사 시각은 검증 가능한 시계 대응·허용 rewind 범위·현재 권한/발사 조건으로 제한한다. 엄폐 후 피격 같은 공정성 대가도 게임 정책으로 정한다.
- 지연 보상은 게임 전체·경제 상태의 무제한 rollback이 아니다. Gateway가 명중 여부를 결정하거나 클라이언트가 보고한 과거 상태를 정본으로 삼지 않는다.
- 시각적 수렴 알고리즘을 이식할 때 빈 이력·0/비유한 시간·보간 계수 범위·각도 wrap·teleport와 이동 종료를 검증한다. 특정 게임의 수렴 상수 하나로 모든 이동 모델을 해결하지 않는다.

## 복구·전달 의미론
- 증분 event·command·delta를 쓰는 시스템은 손실·중복·역순·장기 이탈 뒤 권위 상태로 수렴할 경로를 둔다. snapshot·replay log·state hash·재조회 중 요구에 맞는 방식을 선택한다.
- 이전 baseline에 의존하는 프로토콜은 양측이 공유하는 accepted baseline을 식별하고 불일치·만료 시 bounded recovery 또는 full-state resync를 제공한다.
- transport ACK와 애플리케이션 상태 수락을 구분한다. 검증되지 않은 ACK·baseline ID로 권위 상태나 수신 window를 갱신하지 않는다.
- 메시지마다 전달·순서·중복·만료·최신값 대체 가능성·복구 의미를 정의한다. transport의 reliable/unreliable 이름만으로 애플리케이션 계약을 대신하지 않는다.
- authority handoff는 이전·현재·예정 authority와 handoff generation·commit 시점·in-flight message 처리 정책을 명시한다. host/local fast path도 원격 경로와 같은 검증·권한·정규화 결과를 보장한다.
- 느린 연결의 송신 큐는 무한히 증가시키지 않는다. 메시지 의미에 따라 coalesce·drop·backpressure·disconnect 정책을 적용한다.
- 완료 결과의 소유권은 실행 호스트의 outbox → 실제로 접수된 불변 송신 메시지 → 수신 소비자로 이어진다. snapshot 주기가 느리거나 송신 큐가 가득 찼다는 이유로 결과를 지우지 않는다. 큐잉된 명령과 아직 넘기지 못한 완료 결과를 같은 서버 측 용량 예산에 포함하면 장애 시 전체 취소도 결과 배열 상한을 넘지 않게 할 수 있다.
- terminal 장애에서 실제로 시뮬레이션한 입력 경계와 폐기한 입력 경계를 구분한다. 폐기된 입력을 실행한 것처럼 이동 ACK로 재실행하지 않으며, 이미 적용된 제어 동작을 제외한 미실행 게임 명령에 성공·실행 거부 결과를 붙이지 않는다. 확인되지 않은 결과는 미확정으로 남긴다. 재동기화 상태에서도 순서 보장 전송이 이미 소유한 정상 선행 응답의 결과 prefix는 검증·소비해야 terminal 응답을 해석할 수 있다. 이 결과 정리는 예측 재실행·플레이 재개와 분리한다.
- 살아 있는 월드에 붙는 신규 접속과 재접속은 같은 full-state 설치 경로를 쓰고 월드를 재설정하지 않는다. 재접속 요청에는 마지막으로 **보낸** 명령이 아니라 마지막으로 **발급한** 명령 번호를 담아 아직 프레이밍하지 않은 명령까지 판정 범위에 넣는다. 서버는 이전 연결을 먼저 차단(fence)하고 그 대기열을 정리한 뒤 최고 수신 번호를 확정하며, 모든 uplink 메시지에 연결 epoch를 실어 다른 epoch의 늦은 메시지를 폐기한다. 클라이언트는 "서버가 받지 못함"과 "결과 보존 기한을 넘겨 알 수 없음"을 로컬 상태로 구분하고 자동 재전송하지 않는다. 재개 식별자는 작은 세대 번호가 아니라 CSPRNG 토큰으로 두고 상수 시간 비교·로그 비노출을 지키며, 서버 재시작처럼 인스턴스가 바뀐 경우는 토큰 불일치와 구별해 만료로 알린다. 보존한 결과는 클라이언트 확인 뒤에만 해제한다.
- 끊김 감지(heartbeat/liveness)와 재개 유예(grace)는 다른 값이다. 감지는 유효 입력·시계 probe가 끊긴 시간으로 판정하고, grace는 감지 뒤 같은 개체로 돌아올 수 있게 세션을 보관하는 시간이다. 서버는 클라이언트의 수락 응답 설치 여부를 직접 관측할 수 없다. 수락 응답을 설치해야만 보낼 수 있는 uplink(응답이 발급한 현재 세션·연결 epoch에 바인딩된 입력·probe 또는 설치 확인)를 한 번도 받지 못한 신규 세션은 재개 주체가 확인되지 않은 것으로 보고 grace 없이 제거한다. 설치 전 handshake·probe는 이 확인으로 세지 않는다. 설치 직후 첫 uplink 전에 끊겨 세션이 제거된 클라이언트에는 재개 만료를 알리고 신규 접속으로 복구하게 한다. 한 번이라도 확인된 세션은 재개 응답이 전달 중이어도 grace를 유지한다. 판정은 서버가 받은 메시지로 하고, 전송 계층이 클라이언트 내부 상태를 들여다보는 방식으로 대신하지 않는다. 명시적 해제·재접속·세션 재설정·장애·liveness 만료가 모두 같은 서버 측 끊김 처리로 모이게 한다. 남용 방지 규칙(예: 첫 입력 전 세션의 즉시 제거)을 제거하거나 바꿀 때는 그 규칙이 암묵적으로 처리하던 정상 경로의 정리 책임부터 확인한다. 새 토큰은 활성 세션뿐 아니라 재개 요청이 여전히 대조하는 만료 세션 기록, 재사용할 슬롯의 옛 기록과도 달라야 한다.

### 전송 보장·I/O API·RPC의 구분
- [TCP](https://www.rfc-editor.org/rfc/rfc9293.html#section-2.2)는 연결 안의 신뢰성 있는 순서 보장 byte stream이다. 그 위에 UDP용 패킷 재전송/재정렬을 기계적으로 중복 구현하지 않는다. 메시지 프레이밍·부분 송수신·큐 상한과 재접속/콘텐츠 처리 경계는 별도 계약이며 TCP ACK는 게임 커밋이 아니다.
- [epoll](https://man7.org/linux/man-pages/man7/epoll.7.html)은 I/O readiness API이고, [gRPC](https://grpc.io/docs/what-is-grpc/core-concepts/)는 RPC/stream 계층이다. [gRPC over HTTP/2](https://github.com/grpc/grpc/blob/master/doc/PROTOCOL-HTTP2.md)와 자체 TCP 프레이밍은 동일 프로토콜이 아니며 서버 권위·복제 방식은 그 상위의 게임 계약이다. 특정 전송을 모든 게임의 기본값으로 강제하지 않는다.
- 상태 병합은 전송 계층에 제출하지 않은 완전한 메시지에만 적용하고 부분 제출된 프레임·라이브러리 소유 버퍼를 수정하지 않는다. [gRPC flow control](https://grpc.io/docs/guides/flow-control/)의 write 반환도 실제 네트워크 송신 완료를 뜻하지 않는다. RPC timeout/cancel은 이미 적용된 업무 결과의 rollback이나 미실행 증거가 아니며, 재접속·재호출의 업무 멱등성은 별도로 보장한다.
- 서버 권위는 서버의 검증·판정 책임이다. 클라이언트의 위치/상태 보고를 검증 자료로 받을 수 있지만 무검증 정본으로 쓰지 않는다. 입력 이력 재실행·명중 rewind·전체 물리 rollback은 각각의 게임 요구에 맞춰 선택하며, 서버 권위만을 이유로 모두 의무화하지 않는다.


## 검증
- 동기화 알고리즘과 transport를 분리해 테스트하되 codec·검증·dispatch·보정 전체를 지나는 통합 테스트를 별도로 둔다.
- 고정 seed·통제된 timestep·직접 snapshot 주입·권위 trace로 결정적 회귀를 재현한다.
- 고정 조건만으로 충분하다고 가정하지 않는다. 가변 timestep·clock drift·burst loss·중복·역순·sequence wrap·재접속·handoff·장시간 누적을 검증한다.
- 절대 허용 기준과 이전 기준선 대비 회귀를 함께 추적한다. simulation 정확도·수렴 시간·표시 연속성을 서로 다른 지표로 측정한다.
- ACK 경계와 snapshot의 일치, 거부 입력 제거, 재실행 부수효과 중복, 이력 상한 초과, 로컬 플레이어와 원격 플레이어의 버퍼 분리를 검증한다.
- 권위 tick과 이동량을 독립된 단조 경과시간에도 대조한다. 거리/tick만 확인하면 tick 자체가 빨라진 오류를 놓칠 수 있다. 경과시간의 끝점은 마지막 상태 표본의 관측 시각과 맞추고, 렌더 전 콜백의 이전 표시를 새 판정 결과와 같은 프레임의 최종 화면으로 간주하지 않는다. 현재 서버 위치와 선행 예측 위치의 차이, 동일 입력 ACK에서의 보정 오차, 표시 수렴 오차는 별도 지표다.
- RTT 정상화·전송 큐 해소·최종 위치 수렴과 입력 처리 나이의 회복을 별도로 검증한다. 같은 생성/소비율의 입력 이력은 유한 정체 뒤에도 처리 지연을 유지할 수 있으므로 독립된 시계의 미세 drift와 반복 정체를 포함한다. 입력 나이는 선언한 범위로 돌아오거나 명시적으로 복구해야 하며, 이를 위해 권위 이동 시간 예산을 늘리거나 완료 식별자가 있는 명령을 조용히 버리지 않는다.

## 학습 근거·적용 범위
- Gabriel Gambetta의 [Part I: 서버 권위](https://www.gabrielgambetta.com/client-server-game-architecture.html), [Part II: 입력 sequence·보정](https://www.gabrielgambetta.com/client-side-prediction-server-reconciliation.html), [Part III: 원격 보간](https://www.gabrielgambetta.com/entity-interpolation.html), [Part IV: 명중 지연 보상](https://www.gabrielgambetta.com/lag-compensation.html)을 개념 근거로 사용한다. 큐 상한·거부 ACK·generation·경제 커밋은 원문의 단순화된 예제를 운영 계약에 적용할 때 필요한 별도 설계 기준이다.
- KinematicSoup의 [Client-side Prediction for Smooth Multiplayer Gameplay](https://www.kinematicsoup.com/blog/multiplayerprediction/)는 Kazap.io의 입력/변위 이력·속도 오차에 따른 재실행·렌더 수렴 사례다. 본문의 `CONVERGE_MULTIPLIER = 0.05`는 그 게임의 선택이며 범용 상수가 아니다. 게시된 의사코드는 완성 라이브러리가 아니고 경계 처리를 별도로 검증해야 한다.
- 이 글들은 Gateway/게임 프로세스 분리나 MMORPG 처리량을 증명하지 않는다. 서버 분리 구조와 성능 검증은 [서버 체크리스트](/game/server-checklist.md)를 따른다.
