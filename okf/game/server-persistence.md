# 게임 서버 영속화·장애 체크리스트

상위 개념: [게임 서버 기능/성능 체크리스트](/game/server-checklist.md)

관계형 PK·인덱스·FK 대체 책임·앱/SP·격리/DDL·재시도·동적 cache의 제품별 조건은 [공통 DB 설계](/database/design.md), 콘텐츠 게시·CDN/서버 메모리의 버전 활성화는 [데이터 생명주기](/development/data-lifecycle.md)를 함께 확인한다. 게임 정적/동적 분류·공개·권위 경계는 [게임 정적 데이터](/game/static-data.md)를 따른다. 이 연결이 아래 A/B/C의 결과 공개·내구성·소유권 계약을 바꾸지는 않는다.

비동기 재진입·identity 결속·heartbeat·프로세스/컨테이너·소유권 펜싱은 [공통 서비스 수명](/development/service-lifecycle.md), statement/WAL·조건부 갱신·멱등 영수증과 실패 검증은 [공통 DB의 SQLite 적용](/database/design.md#sqlite-조건부-갱신멱등-영수증실패-검증)을 따른다. 아래 게임 정책과 결합할 때도 각 원문의 전제·조회일·실측 한계를 유지한다.

## 영속화·이동·장애

- [ ] 메모리를 실행 상태의 기준으로 삼는 것과 경제 데이터 내구성은 별개다. 주기적 snapshot 저장을 구매·거래·보상의 내구 확정으로 보고하지 않는다. 필요한 트랜잭션 또는 내구 로그의 커밋·멱등성을 보장한다. 결과를 클라이언트에 공개하는 시점과 내구 수준은 아래 A/B/C 중 콘텐츠별로 선언한 방식으로 정한다. B·C로 선언한 결과는 I/O 확인 전까지 pending으로 두고, A로 선언한 결과는 메모리 권위 적용 시 공개하되 아래 동반 조건과 손실 범위 선언을 지킨다.
- [ ] 위치처럼 매 tick 바뀌는 연속 상태는 tick마다 내구화하지 않아도 된다. 일반적인 서버는 로그아웃(연결 해제 뒤 소유 반환)·영역 이전 때 저장하고 주기적으로 자동 저장하며, 거래 같은 경제 결과는 주기 저장을 기다리지 않고 즉시 한 트랜잭션으로 커밋한다(예: TrinityCore의 [`WorldSession::LogoutPlayer`→`SaveToDB`](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/game/Server/WorldSession.cpp), [`PlayerSaveInterval` 기본 90초](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/worldserver/worldserver.conf.dist)와 첫 저장 시점 분산, [거래 트랜잭션](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/game/Handlers/TradeHandler.cpp)). 다만 이 거래 예시는 한 트랜잭션 구성의 근거일 뿐 커밋 완료를 기다린 뒤 응답하는 C의 근거는 아니다(아래 TrinityCore 사례). 의미 있는 결과 레코드에 그 시점 위치를 함께 실으면 결과와 위치가 어긋나지 않는다. 크래시 때 위치가 얼마나 되돌아가도 되는지(주기)를 명시적으로 정한다.
- [ ] 결과 공개(클라이언트 응답·복제)를 내구 저장 뒤로 미룰지는 세 방식으로 나눠 정한다: (A) 메모리 권위로 공개하고 저장은 뒤에서, (B) 내구 큐·로그의 확인 뒤 공개, (C) DB 커밋 뒤 공개. A를 쓸 때는 다음을 함께 둔다:
  - 엔티티 상태를 바꾸는 소유 서버는 하나다.
  - 엔티티별 순번과 멱등 적용을 지킨다.
  - 저장 쪽이 최종 검증권을 갖는다. 거절되면 그 유저만 끊고 DB 상태로 다시 로드한다([NDC2014 「분산서버 구축의 ABC」](https://ndcreplay.nexon.com/NDC2014/sessions/NDC2014_0046.html) 슬라이드 62-63쪽).
  - 로그아웃·재로그인·서버 이동 같은 소유권 이동은 옛 소유자의 마지막 레코드가 적용되고 옛 소유자의 늦은 쓰기가 펜싱된 뒤에만 허용한다.
  - 손실 범위는 "마지막 n초"가 아니라 "저장 확인을 받지 못한 모든 변경"으로 선언한다.
  - 내구 확정(B·C) 뒤에 공개할 결과의 범위는 콘텐츠별 등급으로 선언하고, 한 가지 규칙으로 고정하지 않는다. 대표 후보는 캐릭터 간 가치 이동(거래·우편·경매)과 결제다. 이런 결과는 관련 엔티티를 동결하고 한 트랜잭션과 멱등 키로 처리한 뒤 공개한다. 한 캐릭터 안의 결과는 그 결과를 담은 레코드가 저장 확인될 때까지 그 유저에게 보낼 응답만 보류해도 된다. 다만 다른 관찰자에게 보이는 공유 효과가 있으면 미확정 상태가 노출되지 않게 따로 설계한다.

  사례는 갈린다:
  - 오딘: 메모리가 1차이고 DB는 n초 주기 백업이다([Games on AWS 2022 10쪽](https://www.slideshare.net/slideshow/8-mmorpg-300-games-on-aws-2022/254068948)). n 값과 경제 예외는 공개되지 않았다.
  - 마비노기 모바일: 내구 큐(MemoryDB Stream)에 넣은 뒤 DB에 비동기로 적재한다. 클라이언트 응답 시점은 발표에 없다([Games on AWS 2025 PDF](https://mkt-kr.s3.ap-northeast-2.amazonaws.com/2025+AI+x+Industry+Week/%EB%B0%9C%ED%91%9C%EC%9E%90%EB%A3%8C/Day1_Track1/D1T1S1_%EA%B3%B5%EC%9C%A0%EC%9A%A9+%EC%B5%9C%EC%A2%85.pdf)). 같은 발표 38쪽의 "MemoryDB 동기 쓰기 + Aurora 주기 배치"는 대안 설계 예시라 배포 구조의 근거가 아니다.
  - 쿠키런: 킹덤: 요청마다 이벤트를 DB에 쓴 뒤 응답하고, DB 클러스터 장애로 56시간 점검을 겪었다([NDC2021](https://ndcreplay.nexon.com/NDC2021/sessions/NDC2021_0006.html), [NDC2022](https://ndcreplay.nexon.com/NDC2022/sessions/NDC2022_0040.html)). 액터 샤딩 구조이므로 DB 대기가 서비스 분리 구조에 맞지 않는 것은 아니다. 선택 기준은 반응성과, 저장소 장애가 게임을 멈추게 하는지다.
  - TrinityCore: 거래를 한 트랜잭션에 담지만, 커밋을 비동기 실행기에 넘기고 완료를 기다리지 않은 채 성공을 보낸다([`TradeHandler.cpp`](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/game/Handlers/TradeHandler.cpp), [`DatabaseWorkerPool.cpp`](https://github.com/TrinityCore/TrinityCore/blob/master/src/server/database/Database/DatabaseWorkerPool.cpp)). C의 근거가 아니다.

- [ ] 존 이동은 old owner 정지/fencing, 상태 인계, new owner 활성화, 라우팅 교체와 실패 복구를 하나의 계약으로 정한다. 중간 실패·늦은 입력·중복 완료에도 소유자가 둘이 되거나 명령이 이중 적용되지 않아야 한다.
- [ ] 파티·인스턴스 멤버십은 재생성·교체 때 바뀌는 개체 ID가 아니라 캐릭터·세션의 안정 ID로 저장한다. 보조 index(개체 ID→연결)는 ID 할당 **뒤**에 등록하고 끊김·교체·로그아웃의 모든 경로에서 제거한다. 할당 전에 등록하면 0이나 이전 ID로 매핑되어 조회가 실패한다. 멤버를 제거할 때는 남은 멤버뿐 아니라 제거된 본인에게도 그룹 ID가 담긴 탈퇴 통지를 보내고(해산과 구분), 클라이언트는 현재 그룹과 다른 ID의 늦은 통지를 무시한다.
- [ ] 인스턴스(던전)는 생성 중→활성→비움 유예→파괴의 서버 상태 머신으로 둔다. 참가자는 [게임 보안](/security/game.md)의 기준대로 서버 그룹 상태에서 정해 슬롯을 예약하고, 생성(비동기 로드) 중 끊긴 참가자와 접속하지 않은 대상의 예약도 해제한다. 해제하지 않으면 인스턴스가 영원히 비지 않아 파괴되지 않는다. 파괴 조건은 작업을 실행하는 시점에 다시 확인하고, 파괴 전에 내부 개체를 despawn하며, 이미 무효가 된 인스턴스도 목록에서 정리한다. 생성·파괴 작업 큐는 한 작업의 예외가 큐 전체를 멈추지 않게 작업별로 격리하고 계정·전역 요청 수에 상한을 둔다. 유예·초대 만료는 단조 시계로 잰다.
- [ ] Gateway 장애에서 연결은 복구 대상이고 월드 상태의 소유권은 콘텐츠 서버에 남는다. 재접속은 기존 연결 무효화·새 generation·권위 snapshot으로 재개하며 무손실/투명 복구를 자동 보장하지 않는다.
- [ ] 저장 대기를 엔티티 단위로 좁히는 설계(그 엔티티 소유자에게 보낼 결과만 내구 확인까지 보류하고, 저장이 안 되는 엔티티는 격리)와 틱의 대기를 구분해서 설명한다. 틱이 그 틱에서 생긴 내구 레코드가 확인·격리·퇴장 중 하나로 해결될 때까지 기다리면, 대기 범위와 상한은 줄어도 틱 지연 자체는 남는다(레코드가 없는 틱만 대기 없음). 미내구 상태의 공개를 금지하는 정책(위 B·C)에서 틱을 무대기로 유지하려면 다른 관찰자가 미내구 상태를 보지 않도록 확정된 복제 view(틱 경계 사본을 확인까지 보관)가 따로 필요하다. 미내구 결과의 공개를 허용하는 A에서는 이 view가 필요 없고, 위 A의 동반 조건과 콘텐츠별 확정 등급이 그 자리를 맡는다. 실제 설계 문서를 다시 읽지 않고 "틱은 기다리지 않는다"고 요약했다가 독립 검토에서 정정한 사례가 있다.
- [ ] 실제 검증은 밀집 레이드, 느린 클라이언트, Gateway/콘텐츠 서버 종료, DB 지연·실패, 큐 상한, 중복/낡은 메시지, 존 이동 실패를 포함한다. 접속만 유지하는 봇 부하를 실제 콘텐츠 처리량으로 보고하지 않는다.
- [ ] 적대 AI가 있는 실제 맵의 통합 probe는 참가자를 보호 구역에서 함께 출발시키고 동시에 이동시키며, 검증 대상 요청 **직전에** 생존·위치(사용 반경) 같은 전제를 확인해 정확한 실패 사유를 남긴다. 먼저 도착한 참가자가 대기 중 사망·부활 이동하면 그 결과가 프로토콜 거절(예: INVALID)로 보여 제품 결함으로 오인된다. 재사용하는 영속 테스트 계정은 이전 실행이 남긴 지역·상태를 가정하지 말고 실제 게임 경로(이동·포탈·부활)로 전제를 정규화하며 DB를 직접 고치지 않는다. 여러 클라이언트를 한꺼번에 로그인시키면 서버의 유한 대기열(예: 저장소 요청 staging)이 넘쳐 정상적인 BUSY 거절이 나오고, 매번 다른 클라이언트가 실패해 불안정한 테스트처럼 보인다. 장면은 한 명씩 준비 완료를 확인하며 입장시키거나 거절 사유를 단언하고, harness의 실패 출력에는 클라이언트의 거절·오류 사유를 반드시 포함한다.
  - 새 상태(새 DB)에서는 캐릭터의 처음 위치가 캐릭터 ID로 정해지고 귀환 위치도 작은 스폰 영역에서 고를 수 있다. 그러면 여러 캐릭터가 같은 칸에 겹친다. 서로 떨어진 이동 경로나 모든 카메라 안 배치를 요구하는 다중 클라이언트 시험은 이 상태에서 전제 단계부터 실패한다. 이전 실행으로 캐릭터가 흩어진 상태에서만 통과한 시험이 이런 경우다.
  - 새 실행 환경(예: 컨테이너)에서 그런 실패가 나면 기존 실행 환경의 새 상태에서 같은 시험을 돌려 같은 실패인지 먼저 확인한다.
  - harness는 전제를 실제 게임 경로로 만든다. 예: 귀환 위치가 세션 entropy+스폰 sequence로 칸을 순환한다면, 턴을 알리기 전에 실제 귀환을 반복해 조건을 만족하는 칸으로 옮긴다. 반복 상한은 스폰 영역 칸 수다. 반복 수를 결과에 기록하고, 분리·카메라 단언은 그대로 둔다. 조건을 하나만 보고 반복하면 다른 조건(예: 카메라 한도)에서 다시 실패할 수 있으므로, 반복 기준에는 단언하는 조건을 모두 넣는다.

## 근거와 적용 한계

- 공개 발표 사례(오딘 Games on AWS 2022)의 적용 한계는 [게임 서버 체크리스트의 근거와 적용 한계](/game/server-checklist.md#근거와-적용-한계)를 따른다.
