# Godot UI 재사용과 입력·텍스트·HUD 표시

상위 개념: [Godot와 C++ 게임 개발](/game/godot-cpp.md) · 버전 핀과 [검증 범위](/game/godot-cpp.md#검증-범위와-공개-근거)를 함께 따릅니다.

장치·포인터 수명, 공통 텍스트 배치와 실제 입력·화면 검증은 [UI·입력 공통 기준](/development/ui-input.md)을 따릅니다. 아래는 게임 어댑터와 Godot API·버전별 적용 규칙입니다.

## UI 재사용과 표시 경계

- 공통 UI에는 레이아웃·포커스·모달·표시용 쿨다운·테마 계약만 둡니다. 게임 어댑터가 캐릭터·아이템·퀘스트 데이터와 요청을 소유하며 공통 모듈이 게임별 클래스나 `res://` 경로를 참조하지 않게 합니다. 클릭 요청과 서버가 수락한 쿨다운/피해/보상은 별도 계약입니다.
- 자주 여는 창의 사전 인스턴스·아틀라스·표시 해상도 비동기 선로드와 threaded-load token 회수 같은 리소스 로딩 계약은 [자주 여는 UI의 리소스 계약](/game/godot-simulation.md#관찰-수명월드-로딩모바일-표현-예산)이 정본입니다.
- **모달의 독점 범위:** 배경을 계속 그리는 것, 입력 이벤트를 소비하는 것, 폴링 입력과 로직 갱신을 막는 것은 별개입니다. Godot의 전역 `Input` 상태는 `accept_event`·`set_input_as_handled`로 차단되지 않습니다. 메뉴/텍스트 입력 중 폴링 이동이 새지 않는지 확인하며 온라인 권위 월드를 UI 모달 때문에 멈추지 않습니다. CanvasItem의 렌더 `z_index`도 Control 입력 처리 순서를 자동 결정하지 않으므로 겹친 UI의 실제 pick을 검사합니다([Input](https://docs.godotengine.org/en/4.7/classes/class_input.html), [CanvasItem z_index](https://docs.godotengine.org/en/4.7/classes/class_canvasitem.html#class-canvasitem-property-z-index)).
- 일반 `Button`의 터치→mouse 변환은 다중 터치 gameplay 버튼의 대체가 아닙니다. [TouchScreenButton](https://docs.godotengine.org/en/4.7/classes/class_touchscreenbutton.html)은 다중 터치를 지원하지만 `Node2D`라 Control anchor가 없습니다. 실제 UI 배치·동시 입력 요구에 맞는 연결부를 선택하고 원본 터치와 합성 mouse가 동일 동작을 중복 실행하지 않게 합니다. 중복 방지만을 이유로 기존 UI를 깨뜨리는 전역 에뮬레이션 설정 변경을 하지 않습니다. **수동 터치와 native GUI를 함께 사용할 때:** Godot 4.7.2는 합성 mouse를 원본 touch보다 먼저 전달하므로 원본 touch만 소비해서는 native Button의 중복 클릭을 막지 못합니다. 직접 소유하는 제스처의 합성 press/motion/release도 GUI 이전에 차단하며 소유권을 위치 변화·모달 전환과 독립적으로 유지합니다. 텍스트 컨트롤은 내부 스크롤바 같은 자손까지 native 경로로 남겨야 합니다. 근거: [고정 엔진 Input](https://github.com/godotengine/godot/blob/ed1daf0bf/core/input/input.cpp), [RichTextLabel 내부 스크롤바](https://github.com/godotengine/godot/blob/ed1daf0bf/scene/gui/rich_text_label.cpp).
- **눌림과 포커스 복귀:** [고정 4.7.2의 BaseButton `set_pressed_no_signal`](https://github.com/godotengine/godot/blob/ed1daf0bf/scene/gui/base_button.cpp)은 toggle mode가 아니면 눌림 상태를 바꾸지 않습니다. 수동 터치 버튼은 실제 보이는 feedback과 release/cancel 복구를 별도로 검증합니다. 포커스 차단으로 입력을 비울 때 앱 밖에서 key release를 놓칠 수 있으므로 복귀한 각 키의 새 non-echo press를 인정하고, 하나의 새 키로 다른 held key를 재활성화하지 않습니다.
- **완전한 native 제스처 검증:** [고정 4.7.2의 Windows backend](https://github.com/godotengine/godot/blob/ed1daf0bf/platform/windows/display_server_windows.cpp)는 휠에도 press 뒤 release를 전달합니다. 스모크가 press만 주입하면 [Viewport의 mouse focus mask](https://github.com/godotengine/godot/blob/ed1daf0bf/scene/main/viewport.cpp)가 남아 다른 버튼 클릭까지 실패할 수 있습니다. 이 검증기 결함을 제품의 좌표 보정으로 해결하지 않습니다. 실제 OS 입력과 같은 이벤트 쌍·순서로 확인합니다.
- **Canvas·지도 영역:** Control을 CanvasLayer 아래로 옮길 때 offset-only 레이아웃 override가 full-rect HUD를 0×0으로 만들지 않는지 실제 viewport rect와 대조합니다. 자식끼리의 중앙 정렬만으로는 화면 밖 UI를 잡지 못합니다. 지도 마커의 좌표도 TextureRect의 실제 aspect-fit/covered 표시 사각형과 일치시킵니다. 최소 변으로 fit한 마커를 큰 변으로 확대·crop하는 covered 텍스처 위에 올리지 않습니다.
- 표시 API가 허용하는 최대 길이와 화면에 들어가는 길이는 다릅니다. `Label`의 기본 minimum-size 동작으로 긴 이름이 고정 HUD 프레임 밖으로 확장될 수 있으므로 clipping/ellipsis 또는 의도적인 wrapping을 지정하고, 이름처럼 한 줄인 필드는 `max_lines_visible=1`과 overflow 정책으로 줄바꿈 입력이 컨테이너를 무한히 키우지 않게 합니다. 숫자의 finite/range 검사만으로 수치 문자열의 렌더링 폭이 제한되지는 않습니다. 최대 허용 이름·큰 수치·Unicode에서 실제 화면 경계를 확인합니다.
- 번역 문장의 조립·복수형·문맥, 표시 로캘과 wire 표현, Unicode 길이 단위·키 배열·IME·가상 지역화의 한계는 [지역화](/development/localization.md)를 따릅니다.
- **한글 UI 폰트 번들과 역할 배치:** Godot 4.7 문서의 기본 프로젝트 폰트(Open Sans SemiBold)에는 한글이 없고(4.7.2에서 `has_char` false 확인), `allow_system_fallback` 기본값 때문에 한글은 OS 글꼴로 대체됩니다. 그래서 한 줄 안에서 영문·숫자와 한글의 글꼴이 달라지고, 플랫폼마다 한글 글꼴·글자 폭이 바뀝니다. Godot 문서는 Android의 시스템 글꼴 로딩을 신뢰할 수 없다고 적습니다. 한국어 UI는 한글과 라틴을 함께 가진 폰트를 번들해 Theme 기본 폰트나 `gui/theme/custom_font`로 지정하고 `has_char`로 실제 적용을 확인합니다. 위계는 한 가족의 굵기·크기·색으로 만들고, 장식적인 제목용 폰트는 짧은 글에만 씁니다. 값이 자주 바뀌는 숫자는 고정폭 숫자(`tnum` 또는 기본 고정폭)로 둡니다. 가변 폰트는 기본 인스턴스가 Thin(wght 100)인 경우가 있으므로(Noto Sans KR·SUIT·NanumSquare Neo에서 측정) `FontVariation`에 굵기를 명시합니다. 같은 이름의 폰트도 배포처마다 한글 수록 범위가 다를 수 있습니다(Google Fonts의 일부 한글 제목 폰트는 2,3xx–2,5xx자, 제작사 배포본은 11,172자). 이름·채팅처럼 사용자 입력을 표시하는 곳은 실제 파일의 수록 범위를 확인합니다. OFL은 게임 번들을 허용(단독 판매 금지, 저작권·라이선스 고지)하지만 subset 같은 수정본은 선언된 예약 이름(RFN)을 쓰지 못하고, 일부 기업 무료 폰트는 수정 자체를 금지해 subset할 수 없습니다. `gui/theme/custom_font`에 번들 폰트를 지정한 프로젝트는 `.godot/` 캐시가 없는 새 checkout에서 처음 `--headless --import`를 실행하면 폰트 import 전에 그 설정을 읽어 `Error loading custom project font` 등 오류를 내고 종료 코드 0으로 끝나며, 두 번째 실행부터는 오류가 없습니다(4.7.2, 2026-10-12 관찰). 새 clone 검증은 이 오류를 결함으로 오인하지도 숨기지도 말고 두 번째 import 로그까지 남깁니다. 폰트와 함께 반입한 라이선스 텍스트처럼 출처 바이트·hash를 기록한 텍스트 파일에는 [빌드·실행 검증](/game/godot-build.md#프로젝트-설정과-에디터-도구-의존성)의 「외부 소스 고정」 `-text` 기준을 함께 적용합니다. [Godot 폰트](https://docs.godotengine.org/en/4.7/tutorials/ui/gui_using_fonts.html), [OFL FAQ](https://openfontlicense.org/ofl-faq/), [Apple HIG](https://developer.apple.com/design/human-interface-guidelines/typography), [Material 3](https://m3.material.io/styles/typography/applying-type).
- **글꼴 교체 뒤 고정 크기 글자 재측정:** 글꼴을 바꾸거나 `tnum`을 켜면 같은 크기에서도 숫자·영문 폭이 달라집니다(고정폭 숫자는 모든 숫자를 같은 폭으로 그려 `1` 같은 좁은 숫자가 넓어집니다). 키 힌트 배지·상태 타일의 중첩 수처럼 상자 크기가 고정된 글자를 모두 다시 측정합니다. 상자를 키우거나 옮기면 주변 배치와 터치 영역이 흔들리므로, 상자는 유지하고 넘치는 글자만 읽을 수 있는 최소 크기까지 줄입니다. 저작 크기를 기억해 두고 바인딩·값이 바뀔 때마다 그 크기에서 다시 맞춥니다. 외곽선·그림자처럼 글자 밖으로 그려지는 장식은 그 폭을 상수 하나로 두고 줄이기 판정과 배치 좌표에 함께 넣습니다. 한쪽에만 넣으면 경계 안에 들어온 것이 글자 여백 덕분인 우연이 됩니다. 장식이 실제로 그려지는 폭은 설정값과 다를 수 있으므로 추정하지 않고 렌더링해 잽니다(Godot 4.7.2의 `draw_string_outline` 크기 3은 12–16px에서 잉크 밖 1px로 측정됨). `Font.get_string_size`는 advance 폭이라 장식 없는 글자가 상자 안쪽에 들어가는지 보는 데는 쓸 수 있습니다. 반면 장식이 있는 글자의 경계는 구현 공식을 그대로 다시 계산하는 테스트로 입증되지 않습니다. 실제 렌더러에서 투명 `SubViewport`에 같은 컨트롤을 장식 없이 한 번, 값마다 한 번 그려 바뀐 픽셀의 경계 상자를 상자 테두리와 비교합니다. headless에서는 픽셀을 읽을 수 없으므로 이 검사는 실제 창 실행에 둡니다. 내용이 허용하는 가장 긴 값(예: 상한 중첩 수)도 포함하고, 배치를 일부러 밖으로 민 빌드에서 검사가 실패하는지 확인합니다.
- **실행 중 배치되는 컨트롤의 그린 장식과 그 검증:** `TabContainer`처럼 자식 위치를 실행 중 정하는 컨트롤에는 장식(탭 구분선 등)을 장면 노드로 고정하지 않습니다. 레이아웃과 어긋날 수 있으므로 내부 `TabBar`의 `draw` 신호에서 `get_tab_rect`로 그 프레임의 사각형을 읽고 테마 StyleBox로 그립니다. 노드가 없는 장식은 위치 검사로 입증되지 않습니다. 실제 창에서 `draw` 연결을 잠시 떼고 다시 그린 화면과 붙인 화면을 비교해, 바뀐 픽셀이 기대 영역에만 있는지 봅니다. 반투명 창 뒤에서 월드가 움직이면 차이가 섞이므로 비교하는 동안 `SceneTree.paused`로 처리를 멈추고, 끝나면 연결과 일시정지를 되돌립니다. **[관찰, 4.7.2]** 창 크기를 여러 번 바꾸는 실제 창 실행에서 `root.get_texture().get_size()`가 854×480을 돌려줬습니다. 같은 시점에 `root.size`와 `get_image()`로 얻은 캡처는 1280×720이었습니다. 이 값으로 배율을 잡은 첫 구현은 엉뚱한 영역을 비교해 정상 빌드에서도 실패했습니다. 논리→픽셀 배율은 캡처 이미지 크기 ÷ `get_visible_rect().size`로 구하고, 연결을 뗀 결함 빌드에서 검사가 실패하는지 함께 확인합니다. 픽셀 폭 판정은 배율에서 유도한 상·하한(최소 floor(폭×배율) 픽셀, 최대 ceil(폭×배율)에 반올림·안티에일리어싱 1픽셀을 더한 값)으로 둡니다. 배율이 1보다 작으면(1920×1080 논리 화면을 1280×720 창에 그리면 0.667) 2 논리 px 선과 1 논리 px 선이 모두 1픽셀로 그려질 수 있어 하한이 둘을 구별하지 못합니다. 폭 자체가 계약이면 1:1 배율 `SubViewport`에서 재고, 그러지 못하면 그 한계를 보고합니다(2026-10-12 실제 작업: 폭 6 결함 빌드는 상한에서 실패했고, 1과 2의 구별은 한계로 보고).
- **탭 컨테이너는 컨테이너 사각형까지 검사:** 창 안 `TabContainer`의 검사가 보이는 버튼·라벨이 창 안에 있는지만 보면, 컨테이너 자체가 창 밖으로 넘친 상태를 놓칩니다. **[관찰, 4.7.2]** 660px 설정 창의 `TabContainer`는 앵커 영역보다 길어 아래로 17.5px 넘쳐 있었지만 자식 검사는 통과했습니다. 같은 창에 두 번째 탭을 넣자 탭을 전환한 뒤 offset이 다시 계산되어 컨테이너 전체가 창 왼쪽 위 밖으로 옮겨졌습니다. 원인 단계는 확정하지 못했습니다. 창을 탭 내용의 최소 높이보다 크게 하고 `use_hidden_tabs_for_min_size`를 켜자 offset이 앵커 그대로 유지됐습니다. 검사는 컨테이너 사각형과 `get_combined_minimum_size()`를 앵커 영역과 대조하고, 탭을 전환한 뒤에도 다시 확인합니다. 이 테마에서 `get_tab_rect`의 탭들은 서로 붙어 있었습니다. 탭 사이에 구분선을 그리려면 `tab_separation` 테마 상수로 간격을 둡니다(간격 8에서 두 번째 탭이 8px 밀림 확인, 2026-10-16 실제 작업).
- **한 줄로 읽혀야 하는 인접 컨트롤의 상자:** 같은 줄에 붙은 버튼(목록 헤더와 접기 버튼 등)은 rect가 같아도 상자 스타일이 다르면 높이가 달라 보입니다. 반투명 테두리는 어두운 배경에서 잘 안 보이므로, 테두리가 있는 쪽의 안쪽 면이 테두리 두께만큼 작은 상자로 읽힙니다. 이런 지적이 오면 rect 수치만 보고 "같다"고 판단하지 말고 1:1 렌더로 보이는 상자 경계를 확인합니다. 그 줄의 컨트롤에는 같은 상자 스타일(테마 변형)을 쓰고, 줄 안 간격과 줄 아래 간격도 맞춥니다. normal만이 아니라 hover·pressed·disabled·focus 상태의 StyleBox도 맞춥니다. 새 테마 변형이 기본 변형을 상속하면 지정하지 않은 상태(예: 3px 테두리 focus)가 그대로 남습니다. focus 모양이 언제 보이는지는 `gui/common/show_focus_state_on_pointer_event`가 정합니다. 4.7 기본값 1은 마우스·터치로 얻은 포커스에 텍스트 입력 컨트롤만 focus 모양을 그리므로, 버튼의 상속 focus 테두리는 키보드·게임패드 포커스에서만 보입니다([ProjectSettings 4.7](https://docs.godotengine.org/en/4.7/classes/class_projectsettings.html), 확인 2026-10-15). 클릭 뒤에 테두리가 보인다고 추정하지 말고 이 설정과 실제 입력 경로로 판단합니다. 검사는 같은 위·아래 끝, 같은 상자 스타일 객체(focus 포함), 네 변 테두리 두께, 간격의 기대 수치로 둡니다. 측정한 간격을 다른 측정 간격과만 비교하면 둘이 함께 틀어져도 통과합니다.
- [Button의 `alignment`](https://docs.godotengine.org/en/4.7/classes/class_button.html#class-button-property-alignment)는 텍스트용입니다. 아이콘 전용 버튼은 `icon_alignment`와 `vertical_icon_alignment`도 지정해야 합니다. 두 아이콘 축이 중앙이면 native text가 아이콘 위에 겹치므로 수량·캡션은 별도 영역으로 분리합니다. 텍스처 사각형의 중앙과 SVG/이미지 glyph의 alpha 경계 중앙도 구분하여 렌더링 픽셀로 확인합니다.
- 클릭 판정 검사는 표시용 viewport 논리 좌표·물리 창 좌표·OS 화면 좌표를 구분합니다. `Viewport.push_input(event, true)`로 버튼의 논리 중심만 주입하면 stretch/DPI/창 위치 변환과 실제 마우스 경계 오류를 놓칠 수 있습니다. 실제 OS 입력으로 중앙·안쪽 모서리·바깥쪽을 검사하고, hover/focus 스타일의 확장 여백·장식 부모의 mouse filter·숨김 자식 상태도 확인합니다. 엔진 종료 코드가 0이어도 script error가 있거나 전체 성공 표시가 없으면 통과가 아닙니다.
- 월드와 HUD의 시각적 정합성은 UI 단독 캡처가 아니라 목표 월드 배경 위에서 실제 HUD를 실행하여 판단합니다. 기본 상태뿐 아니라 채팅·추가 액션·모달을 열어 글자 크기, 배경 대비, 겹침, 서로 다른 아트 재질을 비교합니다. 공개 참고 스크린샷으로 만든 컨셉 확인과 정식 에셋 통합·실제 게임 기능을 분리해 표시합니다.
- godot-cpp v10의 가상 입력 메서드에서 `Ref<InputEvent>`를 사용하는 클래스는 등록 번역 단위에서도 타입이 완전하도록 해당 헤더에 `input_event.hpp`를 포함합니다. 확인한 MSVC 조합에서는 `const String + "literal"`이 String/StringName 오버로드 사이에서 모호했으므로 문자열 피연산자를 명시합니다. **ASCII는 `String("literal")`, UTF-8 한글·기호는 `String::utf8("문구 · 기호")`**를 사용합니다. [고정 v10 소스](https://github.com/godotengine/godot-cpp/blob/507ed9d840c01a3c5b2a39af8bb4000bfac30bf5/src/variant/char_string.cpp#L71-L95)에서 `String(const char*)`는 Latin-1, `String::utf8`은 UTF-8 경로입니다. 컴파일이 되는 암시적 연결도 중점 같은 기호를 깨뜨릴 수 있으므로 실제 UI의 Unicode 표시를 확인합니다. 이 원칙을 외부 ABI 이름 변경이나 전체 스타일 재작성으로 확대하지 않습니다.
