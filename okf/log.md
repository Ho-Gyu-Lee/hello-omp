* **Learning — 생성·합성 에셋의 화풍 대조:** [에셋 검수·사용 권리](/development/assets-editor.md#제약-생성의-사례)에 생성·합성 에셋을 같은 화면의 구매 에셋(주민·적 포함)과 원본 배율 통계(몸 높이·명도·채도·밝기로 나눈 미세 질감·그림자 알파의 평균과 단계 수)로 비교하고, 게임 필터·배율의 밝은/어두운 바닥 비교판과 실제 게임 캡처로 확인하며, 최종 미감 판단은 사용자에게 둔다는 기준을 추가했습니다. 채도는 비교 목적에 맞는 정의를 고르고(바닥 위 색 드러남에는 chroma `(max−min)/255`), 경계 명도 비로 외곽선을 판정하지 않으며, 실행 중 tint·alpha를 받는 효과는 원본 텍스처 수치로 비교하지 않습니다.
  - 계기: 한 아이소메트릭 게임의 생성·합성 에셋을 검사했습니다. 처음 측정은 HSV 채도·경계 명도 비·좀비 위주 기준 집합을 썼습니다. 독립 검토가 두 가지를 지적했습니다. 어두운 구매 캐릭터의 HSV 채도 0.43은 정의대로의 값이지만, 바닥 위에서 보이는 색 차이(chroma 0.075)와 크게 달라 이 비교의 목적에 맞지 않았습니다. 외곽선 지표는 구매 캐릭터끼리도 0.78~1.34로 흩어졌습니다. 고친 측정에서 다른 팩 부위로 합성한 NPC 4명은 그림자 평균 알파가 146~147(구매 캐릭터 88~117)이고 알파 단계가 16~17개(구매 43~92)였습니다. 벤더 예제의 그림자 알파 0.7을 그대로 쓴 결과입니다.
  - [2D 텍스처 필터와 화면 배율](/development/rendering-animation.md#픽셀패스표시-범위)의 `scale_mode="integer"` 문장도 다듬었습니다. 정수배가 아닌 큰 창은 배율을 내리고 테두리를 검게 두며, 기준보다 작은 창은 1배로 두고 자릅니다(`window.cpp` 4.7-stable 확인). 카메라 줌을 창 크기·화면비로 보정하는 프로젝트는 그 계수도 최종 배율에 들어간다는 점을 더했습니다.
  - 같은 항목에서 색 수와 필터 판단을 분리했습니다. 처음 사례는 아틀라스 합계 고유 색(약 4.8만·6.7만)으로 "픽셀 아트가 아니므로 전역 Nearest가 어긋난다"고 결론냈습니다. 그런데 합계는 그림 하나가 제한 팔레트인지 보여 주지 않습니다. 독립 advisor 지적에 따라 그림 단위로 다시 셌고(그림 290개가 그림당 79~29,797색, 배우 frame 120개가 frame당 89~119색), 색 수는 팔레트 제한 적용 여부의 관측으로만 남겼습니다. 필터 판단의 근거는 픽셀 격자·최종 배율·실제 화면 비교로 한정했습니다.

* **Learning — 검증 기록은 후보 전체에 묶고 지도 디렉터리는 `-text`:** [프로젝트 지도의 게시 절차](/project-navigation.md#작업갱신게시-절차)에 빌드·브라우저 확인의 기록을 진입점만이 아니라 게시할 후보 전체의 해시에 묶고 게시 직전 다시 대조한다는 기준을, [근거와 신선도](/project-navigation.md#근거와-신선도)에 지도 디렉터리를 `.gitattributes`의 `-text`로 둔다는 기준을 추가했습니다. [보안 리뷰 체크리스트](/security/review-checklist.md)에는 저장소 설정이 정한 경로에서 git을 실행하는 도구의 경로 제한·링크 대조·`core.fsmonitor`/`safe.bareRepository` 고정 항목과, Windows에서 이름만으로 실행한 외부 명령이 현재 디렉터리의 실행 파일로 바뀌는 문제(Bun 1.4.3은 `.exe`·`.bat`, Node 24.17.0은 `.exe`)를 피하는 항목을 추가했습니다.
  - 계기: 스킬의 독립 검토가 진입점 해시만 묶은 게시가 확인 뒤 바꿔 끼운 관계도를 통과시키는 것을 재현했고, 스킬 경로 전체에 건 `text eol=lf`가 예제 PNG의 서명을 바꾸는 것(`git hash-object` 필터 전후 불일치)과, 읽기 전용 `status`도 저장소 설정이 정한 형제 경로에서 git을 실행하는 것을 찾았습니다. 검토가 확인하지 못한 Windows의 명령 탐색 순서는 `git.bat`·`git.exe`를 둔 디렉터리에서 직접 실행해 확인했습니다.

* **Learning — 관찰자당 복제 상한의 우선순위와 상호 관측 판정:** [게임 서버 체크리스트](/game/server-checklist.md#큐브로드캐스트성능)에 관찰자당 복제 개수 상한을 두면 상한 밖 후보 중 무엇을 남길지(플레이어·파티원 우선, 종류별 슬롯)를 게임 요구로 정한다는 항목을 추가했습니다. 거리순으로만 고르면 몬스터 밀집 사냥터에서 근처 플레이어가 사라집니다. 상호 관측 시험은 누락 순간의 snapshot 포화 여부를 함께 기록해 설계상 밀려남과 복제 결함을 구분하고, snapshot마다 새로 계산되는 게이지를 누적 카운터처럼 합산하지 않는다는 기준도 넣었습니다.
  - 계기: 서버 권위 MMORPG의 QA 서버에서 시험 클라이언트 4개의 텔레메트리를 분석하다가, 숲 사냥터에서 매 snapshot이 상한(32개)까지 찬 상태로 20m 안의 다른 플레이어가 상대당 최대 29초 목록에서 빠진 것을 관측했습니다. 서버 코드의 선택이 거리순이고 플레이어 우선이 없음을 확인했고, 빈 슬롯이 있을 때의 누락은 0건이었습니다. 처음 분석기는 snapshot별 잘린 후보 수를 누적 카운터로 합산해 거짓 이상으로 보고했습니다.

* **Fix / Learning — `project-map` 게시 잠금의 경로 별칭과 잘못된 JSON 형태의 빌드 중단:** `project-map` 스킬의 게시 잠금은 `--map` 문자열을 그대로 해시해, 같은 디렉터리를 `docs/project-map`과 `Docs/Project-Map`(Windows 8.3 짧은 이름, `::$INDEX_ALLOCATION`도 같음)으로 부르면 서로 다른 잠금을 잡았습니다. 이제 `--map`의 이미 있는 구간은 디스크의 철자와 같아야 하고(NFC/NFD 차이만 허용), 끝이 `.`·공백인 구간과 `:`가 든 구간은 받지 않으며, 잠금 키는 접은 경로(NFC, 소문자→대문자→소문자, 다시 NFC)로 만들고 잠금을 잡은 뒤 `--map` 검사를 다시 합니다. `.git`·`.omp-artifacts` 금지도 접은 이름으로 비교합니다. 신선도 입력에서 지도 디렉터리를 뺄 때는 이름을 비교하지 않고, 파일 경로에서 지도 깊이에 있는 디렉터리의 장치·파일 ID가 지도 디렉터리와 같은지로 판정합니다. git은 인덱스의 철자로 경로를 알려 주기 때문입니다. 일반 기준은 [보안 리뷰 체크리스트](/security/review-checklist.md)에 추가했습니다.

  - **정정(같은 날):** 위 「접은 경로로 후보를 고르고 실제 경로로 판정」한 방식(`9b785c2`로 게시)도 실제 경로를 소문자로 바꿔 비교했으므로, 지도 `docs/xß`를 두면 NTFS에서 별개 디렉터리인 `docs/xẞ`의 파일이 입력에서 빠졌습니다(JavaScript `toLowerCase`가 `ẞ`를 `ß`로 바꿈). 독립 advisor 지적을 재현한 뒤 판정을 장치·파일 ID 비교로 바꿨고, `xß`/`xẞ`·`straße`/`strasse`·git 인덱스 철자·다른 대소문자의 직접 include·아직 없는 지도 5가지 회귀에서 입력이 빠지거나 남지 않는 것을 확인했습니다. 수정 전 코드는 `xẞ` 경우에서 실패했습니다. 독립 검토 지적에 따라 고유 ID가 없다는 값(0, 모두 1)과 ReFS의 비고유 64비트 ID에 대비해, 그 경우와 Windows에서는 디스크 철자로 돌려받은 실제 경로의 일치도 요구합니다(ReFS 볼륨에서는 실행하지 못했습니다).

* **Learning — 2D 텍스처 필터와 화면 배율:** [렌더링·애니메이션](/development/rendering-animation.md#픽셀패스표시-범위)에 픽셀 아트 지침의 Nearest 필터·제한 팔레트를 적용하기 전에 실제 에셋의 고유 색 수와 반투명 비율을 재고, Nearest는 정수 배율에서만 텍셀 크기를 고르게 지키며(비정수 3.5배면 3·4픽셀이 번갈아), Linear는 아틀라스 extrusion이 필요하다는 기준을 추가했습니다. 판단할 배율은 창 스트레치 × 카메라 줌 × 노드 배율의 곱이고, Godot 4.7의 `scale_mode="integer"`는 창 스트레치만 정수로 내리며 카메라 줌은 바꾸지 않는다는 점과 기본 필터(Linear)도 적었습니다.

* **Learning — 같은 tick 처치자 귀속과 clamp 기준 변경 시 흔들림 재계산:** 같은 개념의 같은 항목을 고쳤습니다.

  - 같은 작업에서 외부 검토가 세 단계의 추론(사망 tick, tick 완결, drop 카운터)마다 남은 오귀속 경로를 지적했습니다. 처치 전용 강조를 제거하고 권위 표지를 선행 조건으로 남겼습니다.

* **Learning — threaded-load token leak과 종료 중 회수:** [Godot C++ 성능 중심 시뮬레이션 코어](/game/godot-simulation.md)의 배경 로딩 항목에, 4.7.2 종료 순서(메인 루프 종료 → GDExtension main-loop shutdown callback → `ResourceLoader::clear_thread_load_tasks()` → SCENE terminator)와 clear·엔진 작업 스레드가 token을 `unreference()`만 하고 삭제하지 않아 생기는 종료 hang·RefCounted leak, `WorkerThreadPool` 작업에서 `ResourceLoader::load`를 부르면 매번 leak이 나고 모듈 소유 `Thread`에서 부르면 inline 로드로 leak이 없다는 실측, `register_shutdown_callback`에서 스레드를 합류시키는 방법·자식 프로세스 회귀를 추가합니다. 고정 커밋 소스와 실제 실행(`--verbose`의 `Leaked instance: RefCounted … Reference count: 0` 관측과 소멸)으로 확인했습니다.
  - 실제 작업(QA 서버 기본 기능 시험)에서 NPC 근처에 저장된 계정으로 접속 직후 종료하면 logout CLOSED를 출력했으나 프로세스가 남는 증상으로 발견했습니다. 기존 항목의 "확장 unload 전에 token 정리를 끝낸다"를 unload 시점의 대기로 구현한 사례이며 제품명·경로는 공개하지 않습니다.

A의 동반 조건은 다섯 가지입니다: 단일 소유, 순번·멱등, 저장 쪽 최종 검증과 거절 시 그 유저만 재로드, 소유권 이동 전 옛 소유자 펜싱, 손실 범위를 "확인받지 못한 모든 변경"으로 선언. 확정 뒤 공개할 결과는 한 규칙으로 고정하지 않고 콘텐츠별 등급으로 선언합니다(대표 후보는 캐릭터 간 가치 이동과 결제). 함께 넣은 근거는 오딘·마비노기 모바일·쿠키런: 킹덤의 공개 근거 수준과, TrinityCore 거래가 커밋을 기다리지 않는다는 점, JetStream PubAck가 fsync를 뜻하지 않는다는 점입니다. 실제 작업에서 에이전트가 "PG 커밋 뒤 응답 + 틱 장벽 유지"를 권고했습니다. 사용자는 "게임 서버도 클라이언트에게는 DB이며 DB 처리는 뒤에서 한다"고 지적했고 에이전트는 권고를 철회했습니다. 이어서 사용자는 확정 뒤 응답 대상을 경제로 고정하지 않고 콘텐츠별로 정하기로 했습니다. 사례 분류와 경제 예외의 원자 경계는 독립 검토로 정정했습니다.

* **Policy — 검색 MCP의 수직 검색만 사용:** 사용자 결정에 따라 일반 웹 검색은 내장 `web_search`를 유지하고, 검색 MCP는 내장에 없는 뉴스·영상·이미지·장소 검색에만 쓰도록 글로벌 지침의 도구 정책, [MCP 정책](/tools/mcp.md), [omp 기본 도구](/tools/builtin.md), README를 고칩니다. 한 서버가 기본 도구와 겹치는 도구를 함께 노출하면 겹치는 도구는 호출하지 않는다는 일반 기준도 둡니다. Brave Search MCP 기준으로 뉴스·영상·이미지와 요금제가 지원할 때의 장소 도구를 쓰고, 일반 웹 검색·본문 추출·요약 도구는 쓰지 않습니다. OMP 18.9.2 `web_search` 문서에서 수직 검색 모드가 없음을 확인했고, 실제 호출에서 뉴스·영상·이미지 검색은 결과를 반환했으며, 장소 검색은 미포함 요금제에서 `OPTION_NOT_IN_PLAN`으로 거절되고 local 검색은 일반 웹 결과로 대체 응답하는 것을 확인했습니다.

* **Learning — 서비스 링크 생존 확인과 동시 로그인 BUSY:** [게임 서버 체크리스트](/game/server-checklist.md)에 서비스 간 링크의 heartbeat 기준을 추가합니다. TCP keepalive로 대신하지 않고, 받은 어떤 frame이든 생존 증거로 세며(소유 검증 통과분만), 응답을 소켓 계층과 로직 loop 중 어디서 하는지가 감지 대상을 정하고, 소비해야 다음 frame을 읽는 구조에서는 자기 정지 뒤 peer를 오판하지 않게 수신을 먼저 소비하고 자기 loop 간격으로 창을 새로 엽니다. 비가역 결과에는 기한을 길게 하거나 2단계로 나누는 사례를 비교해 결정자에게 드러내고, 응답 전용 서비스는 상대를 만료시키지 않으며, 막힌 PONG 재시도를 다른 업무 게이트에서 분리하고 연결당 PONG slot을 남기는 기준입니다. 근거는 LiteNetLib·ENet·kcp2k·Valve GNS·RakNet·yojimbo 소스 기본값, Akka·Orleans·Erlang·etcd·gRPC·ZeroMQ·Linux 공식 문서, BitCraft 2026-08 사후 분석, ArenaNet GDC 2017, TrinityCore(비공식 WoW 에뮬레이터) 소스이며 FFXIV·WoW·EVE 공식 자료에는 내부 링크 값이 없음을 적습니다. 실제 서버 구현에서 사전 독립 검토가 PONG 재시도가 중요 제어 대기 게이트에 묶여 건강한 링크를 만료시키는 경로와 응답 slot 고갈을 찾았고, 사후 검토가 저장소 서비스의 무제한 수신 loop가 PING 흐름에 송신을 굶길 수 있음을 찾아 모두 고친 뒤 SIGSTOP·방향별 blackhole 주입 12개 시나리오가 통과했습니다. 같은 절의 통합 probe 기준에는 여러 클라이언트를 동시에 로그인시키면 서버의 유한 저장소 요청 대기열이 넘쳐 매번 다른 클라이언트가 BUSY로 실패한다는 함정과, 한 명씩 입장시키고 harness 실패 출력에 거절 사유를 포함하는 기준을 추가합니다(실제 probe에서 다섯 번째 동시 로그인이 BUSY로 거절된 것을 사유 출력을 추가한 뒤 확인).
* **Learning / Correction — 글꼴 교체 뒤 고정 크기 글자 재측정:** [Godot + C++ 개발](/game/godot-cpp.md)의 UI 텍스트 기준에, 글꼴을 바꾸거나 `tnum`을 켜면 숫자·영문 폭이 달라지므로 키 힌트 배지·상태 중첩 수처럼 상자가 고정된 글자를 전부 다시 측정하고, 상자는 유지한 채 넘치는 글자만 최소 크기까지 줄이며, 저작 크기에서 다시 맞추고 내용이 허용하는 가장 긴 값까지 측정 검사에 넣는 기준을 추가합니다. 실제 프로젝트에서 한글 UI 글꼴로 바꾼 뒤 `Tab` 키 힌트가 32 논리 px 배지를 넘었고(16px에서 28px 폭), 키 힌트와 중첩 수 모두 상자를 유지하고 글자만 줄여(`Tab` 16→15px) 실제 창 검사로 확인했습니다. **정정(같은 날):** 처음 기록은 상한 중첩 수 `x255`의 "외곽선 포함 폭이 타일 안쪽 한계를 1px 넘었다"고 적었으나, 이는 외곽선을 3px로 가정한 산술 검사의 결과였고 픽셀은 재지 않았습니다. 외부 검토 지적 뒤 투명 `SubViewport`에 실제로 그려 재 보니 크기 3 외곽선은 잉크 밖 1px만 그려졌습니다. 그래서 같은 항목의 검증 기준을 고쳤습니다. 장식 폭은 상수 하나로 줄이기 판정과 배치에 함께 넣습니다. 그 폭은 렌더링으로 잽니다. 장식이 있는 글자의 경계는 구현 공식을 다시 계산하는 테스트가 아니라, 실제 창의 픽셀 차이 검사와 일부러 밖으로 민 빌드에서의 실패 확인으로 입증합니다. 처음 반영본의 "`Font.get_string_size`로 확인" 기준은 장식 없는 글자에만 한정했습니다.
* **Learning — 한글 UI 폰트 번들과 역할 배치:** [Godot + C++ 개발](/game/godot-cpp.md)의 UI 텍스트 기준에, Godot 기본 폰트에 한글이 없어 OS 글꼴로 대체되는 문제와 한국어 UI의 폰트 번들·한 가족 위계·짧은 글에만 쓰는 제목용 폰트·고정폭 숫자·가변 폰트 기본 굵기 함정·배포처별 한글 수록 범위·OFL 예약 이름과 수정 금지 폰트의 subset 제약을 추가합니다. 실제 프로젝트에서 기본 폰트의 한글 미수록(`has_char` false)과 시스템 대체 사용을 Godot 4.7.2로 확인했고, 후보 폰트 파일을 내려받아 한글 수록 수·가변 축 기본값·숫자 폭을 측정했으며, Apple·Microsoft·Material·Godot 문서와 각 폰트의 공식 라이선스를 원문으로 확인했습니다. 폰트 선택 자체는 프로젝트 결정이라 기록하지 않습니다.
* **Learning — HUD RTT 분위수와 WSL localhost 중계:** [네트워크 동기화](/game/network-sync.md) 검증 절에 다음 기준을 추가합니다. 1초 probe 값을 짧은 간격으로 표본화한 p95는 상위 1~2회 측정으로 정해진다는 점, pump 시각 측정의 frame 양자화, 서버 수신·송신 시각이 같으면 서버 대기를 분리할 수 없다는 점을 적습니다. 또 개발 PC에서 Windows→WSL2(NAT) `localhost` 접속은 `TCP_NODELAY` 없는 WSL 중계를 지나 작은 상향 frame이 붙잡힐 수 있다는 측정 함정을 적습니다. 실제 4클라이언트 측정에서 상향 15~50ms 지연이 측정의 20~38%였고, Release 서버에서도 같았습니다. VM IP의 `TCP_NODELAY` 프록시로 우회한 1회 실행에서는 0%였습니다. 메커니즘(Nagle·지연 ACK)은 WSL 2.7.14 소스와 수치가 맞는 가설로 표시합니다.
* **Learning / Correction — 장시간 작업의 진행 정지 판정:** [omp 기본 도구](/tools/builtin.md)의 백그라운드 작업에, 오래 걸리는 정상 작업은 진행 메시지 없이 끝까지 완료시키되 경과 시간으로 실패를 판정하지 않는 기준을 추가합니다. 스크립트·테스트는 일정 간격으로 현재 상태·진행률을 로그로 남기고 조건 대기는 실제 로직 상태를 주기적으로 확인해 기록합니다. 값이 여러 간격 동안 변하지 않는 것은 정체 후보로만 보고, 작업은 유지한 채 프로세스 생존·CPU·디스크 출력·로그·대기 조건을 진단하며, 실패나 진행 불가능의 근거를 확인했을 때만 중단·보고합니다. 사용자가 장시간 무응답 때 확인 질문을 반복했고, 세션 기록으로 앞뒤를 확인한 4건 중 3건은 정상 진행이었지만 1건은 새 규칙과 맞지 않는 검사가 31분간 멈춘 것을 사용자 질문 뒤에야 발견했습니다. 정상 진행 중 중간 보고를 줄이는 기존 지침은 사용자가 유지하기로 했습니다. **정정(같은 날):** 처음 반영본은 실행·대기 상한과 시간 초과 실패를 우선했습니다. 실제 소요보다 짧은 상한으로 실패·재시도를 반복하면 끝날 작업도 완료되지 않는다는 사용자 교정에 따라 짧은 상한 실패·재시도를 금지하고 상한은 바깥 안전선으로만 두었습니다. 이어 긴 링크·컴파일 단계는 정상 실행 중에도 진행 값이 그대로일 수 있다는 검토 의견에 따라, 값 변화 없음을 중단 조건이 아니라 진단 시작 신호로 고쳤습니다.
* **Learning — 실패 확인 테스트와 산출물 존재 확인:** [워크플로](/workflow.md)의 수락 기준-증거 폐루프에, 판정기·검증 러너·검사 조건을 새로 만들거나 바꾸면 일부러 결함을 넣은 입력(단언 하나만 실패시킨 결과, 판정 영역 밖 클릭 등)으로 실제로 실패하는지 한 번 실행해 확인하는 기준을 추가합니다. 산출물 보존 절에는 보고에 적기 전에 경로의 파일 존재와 내용을 확인하고 저장에 실패한 파일을 산출물로 기재하지 않는 기준을 추가합니다. 반복 실수 조사에서 단언 일부 실패를 통과로 판정한 검증 러너, 논리 좌표 주입으로 실제 클릭 어긋남을 통과시킨 검사, 저장되지 않은 스크린샷을 보고에 적은 사례를 확인했고, 이번 작업에서도 저장되지 않은 스크린샷 경로를 보고 전에 발견해 지웠습니다. 기존 "결함이 있을 때 실패해야 한다" 요구에 확인 행위를 붙인 것이며, 앞선 답변의 "음성 테스트" 표현은 이해하기 어렵다는 사용자 지적에 따라 "실패 확인 테스트"로 씁니다.
* **Learning — 지침 적용 중 확인된 네 결함의 일반 기준:** 보강된 네트워크 지침을 실제 서버·공용 코드와 대조해 고친 결과를 일반화합니다. [네트워크 동기화](/game/network-sync.md)에 두 기준을 추가합니다. 첫째, 서버 tick이 스스로 일으키는 불연속(자동 부활)도 보류 입력 폐기 대상이며, 중복 거절 기준과 처리 ACK는 유지합니다. 둘째, 공유 연결 송신 스케줄러를 "실시간 우선 + 조각 여유 예약"으로만 만들면 조각이 기아에 빠집니다. 따라서 대기 조각이 있으면 실시간 admit량에 상한을 두고, slot 예약은 풀 크기로 제한하며, 회전은 연결별로 하고 공유 풀은 연결 사이에서 중재합니다. 이미 송신을 받은 연결은 다시 선두가 되지 않게 하고, 보장은 drain 바이트가 아니라 admit량으로 서술합니다. [게임 보안](/security/game.md)에는 관찰 범위 확인을 실행 시점의 마지막 공개 복제 집합으로 판정하는 경계(카메라 기준 오거절, 선택만으로 통과 금지, 공개 뒤 이탈은 일반 거절, 착탄 재검사 없음, replay 결과 유지, 서버 AI 제외)를 추가합니다. [서버 체크리스트](/game/server-checklist.md)에는 영향 행 확인의 회귀 테스트를 `BEFORE UPDATE` + `RAISE(IGNORE)` 결함 주입으로 만드는 기준을 추가합니다. 네 항목 모두 회귀 테스트를 갖췄습니다. 송신 스케줄러는 독립 사후 검토가 세 차례에 걸쳐 단계적으로 찾은 결함(조각 기아·slot 예약 과다·연결 간 공정성 → 공유 풀 중재 → 서비스받은 연결의 선두 독점과 drain 바이트 상한)을 고친 뒤 승인됐습니다. 느린 reader에서의 live 지연은 측정하지 않았습니다. 프로젝트별 상수·식별자는 공개하지 않습니다.
* **Learning — 작업자별 독립 clone 병렬 빌드와 성능 관측 분리:** [서브에이전트 위임](/tools/subagents.md)에 두 기준을 추가합니다. 격리 백엔드가 submodule·다른 OS 빌드 환경을 재현하는지 확인되지 않은 병렬 C++ 작업은 작업자마다 독립 clone(submodule URL을 로컬 정본으로 지정)에서 빌드·테스트·커밋하고, 통합 담당자가 fetch/cherry-pick한 뒤 통합 트리 전체로 다시 확인합니다. 빌드가 도는 동안에는 FPS·지연을 관측하는 검증을 실행하지 않습니다. 실제 작업에서 세 작업자가 각자 clone에서 테스트를 통과한 커밋을 반환했고 통합 트리 빌드·테스트도 통과했습니다. **정정(같은 날):** 병렬 빌드와 겹친 렌더 검증에서 본 HUD `FPS 1`을 처음에는 빌드 영향으로 설명했습니다. 빌드가 없는 재실행에서도 같은 값이 나왔고 같은 시점 엔진 FPS 표본은 90이었으므로, 1초 간격으로 갱신되는 HUD 값이 세션 직후 아직 갱신되지 않은 것으로 봅니다(추론). Ping 상승은 화면 캡처 단계에서 나타났고, 같은 높은 값이 바로 다음 완료 단계 표본까지 남은 경우가 하나 있었습니다.
* **Learning — 세션 기록 속 자격증명의 마스킹:** [보안 개요](/security/overview.md)에 사용자가 프롬프트에 붙여 넣은 비밀번호·토큰이 세션 기록·프롬프트 이력에 평문으로 남는다는 점과, 이 기록을 분석용 사본이나 외부 모델·분류 API 입력으로 쓰기 전 로컬의 결정적 탐지로 먼저 마스킹하고 비밀 판정을 위해 원문을 외부로 보내지 않는다는 기준을 추가합니다. 반복 실수 조사에서 프롬프트 이력을 작업 디렉터리로 복사했을 때 평문 Git 서버 접속정보 2건이 함께 복사된 것을 확인하고 파생 사본만 마스킹했습니다. 값과 접속 대상은 기록하지 않습니다.
* **Learning — 서버 AI 판정의 신뢰 경계:** [게임 보안](/security/game.md)의 서버 권위 원칙에 서버가 호출하는 결정 모델·LLM 분류기의 결과를 권위 판정 근거로 쓰지 않는 기준을 추가합니다. 플레이어가 작성한 내용이 입력에 들어간 판정은 클라이언트 입력과 같은 신뢰 수준으로 다루고, 비가역 결과는 서버 규칙·사람 검토로 확정하며, 모델 결과는 되돌릴 수 있는 조치에만 직접 연결하고, 원격 호출의 지연·실패·속도 제한 때의 기본 동작을 둡니다. TypeSafe Jev 조사에서 공식 문서가 밝힌 적대적 입력 실패 모드와 JevOut(arXiv 2609.30243)의 문맥 추가에 의한 목표 오답 전환 측정을 원문으로 확인했습니다. 게시 전 독립 검토는 이 항목에서 결함을 찾지 않았으며, 같은 검토의 측정 조건 지적에 따라 전환율이 확률 피드백 탐색의 결과라는 점을 본문에 밝혔습니다. 벤더별 가격·속도 제한·정확도 수치는 변동 사양이므로 기록하지 않습니다.
* **Learning — 동기화 시뮬레이터·보정 전달·영속 갱신 기준:** 실제 프로젝트의 netcode 코드와 동기화 시뮬레이터 결과를 분석해 일반 기준을 추가합니다. [네트워크 동기화](/game/network-sync.md)에 클라이언트 좌표 보고 구조의 owner 보정 전달·빈도 상한·보정 세대·전체 상태 중계, 움직이는 목표를 향한 1차 지연 보정의 정상상태 오차(`e·(k0 + k1·e) = v`)와 offset 감쇠, 생성 쪽 주기 기준의 파생 값(중계 데이터 포함), 변경분 상태의 무수신 freeze 금지, 원격 애니메이션 표시의 정본 선택, 동기화 시뮬레이터의 제품 코드 구동·coverage 단언·버퍼 기준 시각(송신자 현재 시각/최신 수신 표본)별 산정·판정 기준 기록·상태별 오차 보고·delta 뒤 유실·재생 재현 단언을 추가합니다. [서버 체크리스트](/game/server-checklist.md)에 길이 경계 메시지의 경계 검증과 계약상 허용된 건너뛰기 한정, 조건부 갱신의 statement별 영향 행 확인·`(계정, 작업 ID)` 선기록과 중복 시 저장 결과 반환·요청 digest 대조·bind·locale 무관 저장을 추가합니다. SQLite 공식 문서(`sqlite3_changes`, UPSERT)와 Mirror 고정 소스의 타임라인 초기화를 확인했고, 보간 쌍 교체 순간 이동과 원격 상태 머신 충돌은 실행으로 재현하지 않은 추론으로 표시합니다. 게시 전 독립 검토 2건(내부 상수 노출, 시뮬레이터 수치의 원인 오귀속, 길이 경계 규칙 충돌, UPSERT 멱등화의 중복 처리, 중계 데이터의 주기, 추론 표시)과 비동기 검토(최신 표본 기준 버퍼에 편도 지연을 중복 가산)의 지적을 반영했습니다.
* **Learning — netcode 구현 분석의 승계:** 고정 Mirror·kcp2k 소스와 내부 코드 분석에서 확인한 기준을 Godot 클라이언트 + C++ 서버 MMORPG에 적용할 수 있게 일반화합니다. [네트워크 동기화](/game/network-sync.md)에 검증되지 않은 클라이언트 timestamp·수락 이력 통계 학습·N회 연속 위반 보정에 기댄 이동 검증의 우회, 불연속 전환 때 서버 이동 검증 기준점 재설정, 변경분 복제의 정지/재개(tick 시간 표본·마지막 정지 갱신 유실·정지 뒤 이력 재설정·지터 표본), 컨테이너 op-log와 연쇄·공유 baseline delta의 신규 관찰자 처리, 지역 전환 중 downlink 차단과 재설치, 순서 stream의 HOL과 분할·송신 버퍼·상한 초과 송신 처리를 추가합니다. [서버 체크리스트](/game/server-checklist.md)에 명시 opcode와 고정 폭 bitmask, 완결 단위 안 프레이밍 오류의 즉시 종료와 남은 바이트 기준 개수 판정, 이탈 반경까지 유지하는 격자 AOI 히스테리시스와 양방향 갱신, 그룹 멤버십의 안정 ID와 인스턴스 수명 상태 머신을 추가합니다. [게임 보안](/security/game.md)에 타 플레이어 대상 요청의 서버 측 대상 도출, UDP 연결 식별·주소 검증·검증 전 상태 할당 금지(upstream kcp2k의 handshake 전 할당 포함), 제어 채널 분리를 추가하고, [Godot + C++ 개발](/game/godot-cpp.md)에 Web export의 HTTP·WebSocket·WebRTC 한정, 전송 능력 명시, 자기완결 snapshot에 한정한 WebSocket HOL 완화, `wss://`·FQDN 인증서와 handshake header 제약을 추가합니다. upstream 동작은 Mirror 고정 commit `c4f3739`, Godot 4.7 문서, RFC 9000 §8, Linux ip-sysctl 문서에서 확인했습니다. 내부 사례의 상세는 공개하지 않습니다. 게시 전 독립 검토 2건의 지적(클라이언트 timestamp 금지의 과잉 일반화, AOI 검사 범위, HOL 분할의 한계, 공유 baseline의 예외, kcp2k 할당 순서, WebSocket 최신값 대체의 적용 범위)을 반영했습니다.
* **Learning — 공유 데이터 이동과 콘텐츠 identity:** [게임 서버 체크리스트](/game/server-checklist.md)에 클라이언트·서버 공유 코드와 실행 데이터를 별도 레포·디렉터리로 옮길 때 identity가 파일 위치가 아닌 카탈로그 값·맵 바이트에만 의존하는지 먼저 확인하고, 카탈로그 안 리소스 경로 문자열을 유지하며 바이트 그대로 옮긴 뒤 identity를 이전 값과 비교하고, 서버와 개발 실행 클라이언트가 같은 경로 집합을 같은 root로 해석하게 하는 기준을 추가합니다. 실제 3레포 분리에서 옮긴 데이터의 server identity가 이전과 같았고 기존 DB를 그대로 열었으며, 독립 검토가 클라이언트 경로 변환이 서버보다 좁은 집합만 바꾸던 차이를 찾아 일치시켰습니다.
* **Correction — 게시 전 독립 검토 지적 2건:** [게임 보안](/security/game.md)의 타사 로그인 키를 OIDC `sub` 단독에서 검증한 공급자 namespace와 안정적 식별자의 쌍(OIDC는 `(iss, sub)`, OIDC Core §5.7)으로 고칩니다. `sub`는 발급자 안에서만 고유해 여러 발급자를 받으면 다른 사용자가 같은 계정에 묶일 수 있습니다. [클라이언트 체크리스트](/game/client-checklist.md)의 "인증 전 종료도 유예로 남는다"는 [네트워크 동기화](/game/network-sync.md)의 미확인 신규 세션 무유예 제거 기준과 충돌하므로, 확인된 세션의 강제 종료만 유예로 남고 미확인 신규 세션은 유예 없이 정리된다고 정정합니다.
* **Learning — 콘텐츠 서버 링크 상실의 지역 격리:** [게임 서버 체크리스트](/game/server-checklist.md)에 Gateway가 콘텐츠 서버 링크 하나의 상실을 그 지역 장애로 처리하고, 묶인 클라이언트뿐 아니라 보류 이전 commit·로그아웃이 기다리는 이전 대상까지 정리하며, 유한 backoff 재연결·handshake 재검증·이전 연결 ID 퇴역, 감독 프로세스의 시작 장벽 전 엄격/장벽 뒤 격리 정책과 SIGKILL·SIGTERM·링크 단절 주입 검증을 추가합니다. 실제 작업에서 세 장애 주입 모두 다른 지역 snapshot·입력 ack가 유지됐고, 독립 검토가 로그아웃 중 이전 대상 상실로 Gateway 슬롯이 영구 점유되는 경로를 찾아 수정했습니다.
* **Learning — tick 밖 로직 스레드 포화:** 같은 체크리스트에 tick 시간과 DB commit만으로 수용 인원을 판정하지 않고 입력 ack 지연과 로직 스레드 CPU·loop 구간별 시간을 함께 기록하며, 포화 구간을 분해한 뒤 완화책을 정하는 기준을 추가합니다. 한 지역 밀집 측정에서 tick과 commit은 예산 안이었지만 로직 스레드 CPU가 포화해 입력 ack가 밀렸습니다. 다른 서비스와 CPU를 공유한 측정입니다. **정정(같은 날):** 처음 반영본은 프로젝트 측정 수치와 미검증 원인 추정(플레이어별 복제·관심 영역 선택)을 공개 concept에 담았기에 확인된 일반 기준만 남기고 수치는 로컬 concept으로 옮겼습니다.
* **Learning — 설치 단위 게스트 식별 비밀:** [게임 보안](/security/game.md)에 클라이언트 생성 CSPRNG 식별값의 첫 요청 전 영속, 서버의 도메인 분리 digest 저장과 create-or-get 단일 트랜잭션, 상관 충돌 검사의 예산 소비 전 수행, 식별값당 미사용 grant 제한·운영 계정 여유 예약·식별자 없는 거절 집계, 원격 주소 보존 전제, 타사 로그인의 안정적 공급자 식별자 키 기준을 추가합니다. 독립 보안 검토가 전역 예산만으로는 한 식별값이 예산을 비울 수 있음을 찾았고, 식별값당 grant 제한 뒤 단위·실제 스택 검사를 통과했습니다. 프로젝트별 식별자·수치는 공개하지 않습니다.
* **Learning — 반복마다 도는 공개 확인과 snapshot 생성의 분리 계측:** [게임 서버 체크리스트](/game/server-checklist.md)에 연결당 frame 하나를 소비해야 다음 frame을 읽는 구조에서 loop 반복마다 모든 세션의 공개 대상을 확인하면 반복 수가 수신 frame 수에 비례해 비용이 대략 인원의 제곱으로 커진다는 기준과, 공개 구간을 순회와 snapshot 생성으로 나눠 계측하라는 기준을 추가합니다. **정정(같은 날):** 처음 반영본은 합친 공개 구간(60~80%)을 순회 탓으로 적었으나, 나눠 재측정하니 포화 지점에서 snapshot 생성이 절반 정도·순회가 4분의 1 정도였기에 원인 단정을 지우고 분리 계측 기준으로 고쳤습니다.

* **Learning — 정상 종료의 명시 로그아웃:** [클라이언트 체크리스트](/game/client-checklist.md)에 엔진 자동 종료 가로채기, 세션이 묶인 상태에서만 로그아웃 1회 송신·transport pump·짧은 상한 뒤 종료, 로그아웃 뒤 다른 송신·상태 변경 진입점 차단, 이전 확정과 겹칠 때 새 binding 재송신, 연결 종료가 소유 반환 증거가 아님, 즉시 재접속 검증 기준을 추가합니다. 실제 클라이언트에서 수정 전에는 즉시 재접속이 유예로 거절됐고 수정 뒤 즉시 재접속과 연속 두 번 렌더 실행이 통과했습니다. 독립 검토가 로그아웃 대기 중 이전 요청이 상한을 30초로 늘리는 경로를 찾아 진입점 차단으로 고쳤습니다. 이전 확정 재송신은 단위 테스트로만 확인했습니다.
