# 사용자 개발 방향

정상적인 결과에 이르는 길이 여러 개일 때 이 문서의 선택을 기본값으로 한다. 언어 문법·외부 API/ABI 계약, 프로젝트의 명시 규칙·포매터, 같은 영역의 일관된 기존 코드가 이보다 우선한다. 모든 에이전트가 받는 요약은 설정 레포의 `rules/RULES.md`이며 이 문서가 정본이다. 둘은 함께 고친다.

## 사용자

- 20년차 게임 클라이언트·서버 개발자. C/C++로 시작했고 SaaS도 개발한다.
- 기초 설명은 생략하고 결론과 근거만 원한다. 설명은 책임 경계·구현 차이·OS 제약·검증 근거로 하고, 익숙한 개념을 새 용어로 포장하거나 유행 기술을 나열하지 않는다. 제안에 무조건 동의하지 말고 우려·반대를 근거와 함께 말한다.

## 코드 표기

- PascalCase 중심이다. 타입·함수·메서드 `PascalCase`, 필드 `mPascalCase`, 지역·인자 `camelCase`, 정적·내부 상태 `sPascalCase`, 외부 전역 `gPascalCase`, 상수·enum 값·플래그 `UPPER_SNAKE_CASE`. 새 snake_case 함수·변수를 도입하지 않는다.
- 선언·시그니처·호출·체인을 폭 때문에 여러 줄로 접지 않는다. 반대로 여러 문장·블록을 한 줄로 몰아넣지도 않는다.
- 관련 로직은 붙여 두고 독립 제어문과 논리 단락 사이를 빈 줄 하나로 구분한다. 장식용·연속 빈 줄은 넣지 않는다.
- 상세와 언어별 예외는 [언어 공통 코딩 스타일](/language-style.md), C/C++는 [C/C++ 전용 코딩 규칙](/language-style-c-cpp.md)이 정본이다.

## 동시성과 서버 구조

- 멀티스레드 프로그래밍은 게임 개발의 핵심 기법이다. 복잡하다는 이유로 회피하거나 단일 스레드로 물러서는 것을 기본 처방으로 삼지 않는다. 대신 각 데이터를 어느 스레드(작업)가 쓰는지, 스레드 사이에 무엇을 어떻게 넘기는지(큐·불변 snapshot·소유권 이전)를 설계에 명시한다.
- 사용자의 경험 기반은 전통 MMORPG 서버다. 역할별로 나뉜 상태 유지(stateful) 서버 프로세스, 게이트웨이를 통한 클라이언트 연결, I/O 스레드와 게임 로직의 분리를 설계의 기본 어휘로 쓴다.
- 최근 추세의 MSA(역할 단위 서비스 분리·독립 확장·장애 격리)도 좋은 방향으로 본다.
- 게임 로직을 스레드 하나가 처리하는 구조도 좋은 선택지다. 오딘: 발할라 라이징은 여러 네트워크 I/O 스레드 + 메인 로직 스레드 1개 + 여러 데이터 I/O 스레드로 서버를 구성했다. 디버깅 난이도·서버 안정성·신규 개발자 적응·하드웨어 비용을 이유로 단일 로직 스레드를 택했고, 대가로 멀티코어 활용도가 낮아 단일 코어 성능이 중요해졌다. 대규모 전투의 브로드캐스트 부하는 게이트웨이 서버로 분리해 게임 서버와 N:M으로 증설했다([Games on AWS 2022, 라이온하트·카카오게임즈 발표](https://www.youtube.com/watch?v=JNH5fB8B_ec)).
- 단일 로직 스레드와 멀티 로직 스레드(존·샤드별 소유) 중 하나를 정답으로 고정하지 않는다. 처리량·동기화 비용·디버깅·운영·팀 규모를 근거로 고르고 그 근거를 제시한다. 어느 쪽이든 소유 단위마다 쓰는 쪽은 하나(단일 작성자)다. 설계 점검은 [게임 서버 체크리스트](/game/server-checklist.md)와 [공통 서버 체크리스트](/development/server-checklist.md).

## 설계

- 다음 변경이 쉬운 코드를 품질의 첫 기준으로 둔다. 작은 인터페이스 뒤에 동작을 모으는 깊은 모듈을 선호하고, 호출자와 구현이 하나뿐인 얇은 래퍼·선제적 추상 계층·확장점은 만들지 않는다. 구조 개선은 `/arch-review`로 후보만 보고하고 사용자가 고른 것만 진행한다. 구현 선택 순서와 계약·비용 보존은 [코딩 스타일](/coding-style.md).
- 성능이 중요한 시뮬레이션은 C++ 코어로 두고 엔진(Godot 등) 연결부는 얇게 유지한다. 서버로 옮길 수 있는 로직은 엔진에 의존하지 않게 둔다([Godot와 C++ 게임 개발](/game/godot-cpp.md)).

## 작업 방식

- 사실은 에이전트가 찾고 사용자에게는 결정만 묻는다. 묻는 기준과 형식은 [응답 원칙](/response-principles.md)의 「질문과 요구 정렬」, 결정이 많이 얽힌 기능·설계는 `/interview`로 정렬한다.
- 에이전트의 작업·답변·결과물 품질이 첫 우선이고, 토큰·실행 비용은 같은 품질 안에서 줄인다. 품질을 높이는 지식 읽기·검증·독립 검토·맥락 주입을 비용만으로 줄이거나 미루지 않는다. 제품 코드의 성능 비용 계약은 이와 별개로 [코딩 스타일](/coding-style.md)대로 보존한다.
- 사용자가 교정하거나 새로 선택하면 이 문서의 해당 문장을 고친다. 사건 기록이 아니라 현재 방향만 둔다.
