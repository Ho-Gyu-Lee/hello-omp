# UI 재사용·입력과 표시 검증

앱·웹·게임 UI에서 해당 기능을 구현/검증할 때의 기준입니다. 게임 HUD·캐릭터·월드 예시는 도메인 데이터/화면의 사례입니다. Godot·Unity·SDL·OS 관련 문장은 명시한 API/버전의 조건부 근거이며 다른 UI 프레임워크에 그대로 강제하지 않습니다. Godot 구현·고정 버전 관찰·실제 엔진 통합은 [Godot UI](/game/godot-ui.md), 번역·Unicode·IME는 [지역화](/development/localization.md)를 따릅니다.

## 공통 UI와 도메인 경계

- 공통 UI는 표시·배치·포커스·모달·테마를 소유하고, 도메인 어댑터가 업무 모델과 변경 요청을 소유합니다. 범용 모듈이 특정 앱의 모델·리소스 경로를 참조하지 않게 합니다. 클릭을 수신한 상태와 서버/업무 로직이 변경을 수락한 상태는 다릅니다. 게임의 쿨다운·피해·보상 연결은 [Godot UI의 적용 사례](/game/godot-ui.md)를 참조합니다.

## 장치·좌표와 입력 소유권
- 반응형 UI는 논리 viewport와 실제 창 크기를 구분하고 anchor/container를 사용합니다. 플랫폼의 물리 안전 영역은 화면 transform의 역변환으로 UI 좌표에 적용하며 키보드 회피·입력 초점은 호스트 화면에서 검증합니다. Windows의 터치 에뮬레이션·가상 inset 검사를 실제 Android/iOS 노치·DPI·키보드·패키지 검증으로 표현하지 않습니다.
- 여러 입력 장치를 지원할 때 장치 이벤트는 어댑터에서 방향·목적지 같은 게임 의도로 변환합니다. 직접 조작/경로 추종의 우선순위와 해제·취소를 명시하고, 비활성 입력원의 중립값이 다른 활성 이동 모드를 취소하지 않게 합니다. 화면 방향·포인터 좌표를 월드 좌표로 변환해도 입력 세기·최대 속도·충돌 규칙을 보존합니다.
- **입력의 세 의미:** 빠른 press/release 같은 이산 사건은 소비까지 보존하고, 스틱 기울기 같은 절대 상태는 해당 시점의 값을 표본하며, 상대 마우스 이동은 소비 구간의 delta를 누적합니다. 마지막 delta만 남기면 이동량을 잃습니다. 사건 순서가 중요한 조작은 누적 합만으로 대체하지 않습니다. `just_pressed`의 프레임/tick보다 느린 소비자가 있으면 전달 경계를 확인하고, 폴링 입력도 기록·재생 경로를 우회하지 않게 합니다([Input](https://docs.godotengine.org/en/4.7/classes/class_input.html), [SDL 상대 이동](https://wiki.libsdl.org/SDL3/SDL_GetRelativeMouseState)).
- **선택 영역과 표시 지연:** 이미지 알파를 클릭 마스크로 그대로 쓰면 얇은 창살·작은 아이템을 선택하기 어려워질 수 있습니다. 상호작용 의미에 맞는 hit 영역과 겹친 대상 우선순위를 실제 입력으로 확인합니다. 커서 위치 표시·버튼 명령 소비·시뮬레이션 주기도 구분합니다. 하드웨어 커서로 요구를 만족할 수 있으면 엔진 API를 검토하고, Sprite 커서의 추가 프레임 지연을 외형 교체 비용 0으로 보지 않습니다([Godot 커서](https://docs.godotengine.org/en/4.7/tutorials/inputs/custom_mouse_cursor.html), [XAG 107](https://learn.microsoft.com/en-us/xbox/accessibility/xbox-accessibility-guidelines/107)).
- **반복 선택 메뉴:** 방사형/marking menu를 쓰는 경우 명령의 방향을 익힌 사용자를 고려해 같은 문맥의 항목 위치를 안정적으로 유지합니다. 사용 가능 여부·빈도마다 재정렬하면 학습한 방향이 다른 명령을 고를 수 있습니다. 너비·깊이·취소 가능성·오선택 비용과 초보/숙련자의 선택 시간·오류율로 판정하고 모든 목록을 방사형으로 바꾸지 않습니다.
- 터치 포인터는 시작 영역의 UI/조이스틱/월드 소유권을 release/cancel까지 유지합니다. [InputEventScreenTouch](https://docs.godotengine.org/en/4.7/classes/class_inputeventscreentouch.html)의 `index`는 손가락을 구분하고 `canceled`는 해당 터치의 취소를 알립니다. 개별 cancel은 해당 index의 소유권·동작만 정리하고 다른 손가락의 조작을 중단하지 않습니다. UI에서 시작한 드래그가 월드 명령으로 새지 않게 하며, 포커스 상실·앱 비활성화·장면 전환의 전역 입력 정리와 개별 터치 취소를 구분합니다.

## 텍스트와 배치
- 첫 glyph 표시 히치가 문제라면 고정 번역 문구·빈출 문자와 사용자 이름/채팅을 구분해 선생성 범위를 정합니다. font/size·locale별 첫 표시 비용과 캐시 메모리를 측정하고 번역 변경 시 목록도 갱신합니다. 모든 Unicode 선생성이나 MSDF 일괄 도입을 기본값으로 삼지 않습니다([Godot font prerendering](https://docs.godotengine.org/en/stable/tutorials/ui/gui_using_fonts.html#font-prerendering); *Game Coding Complete* 한국어판 PDF p.249–254).
- 중앙 정렬은 텍스트의 줄 높이·부모의 실제 영역과 함께 검증합니다. `MarginContainer` 같은 native container로 폰트 최소 크기를 전파하고, 배지·수치·제목마다 명시적인 영역을 둡니다. 숨긴 Container 자식은 표시 후 정렬되므로 실제로 창을 열고 layout을 기다린 상태에서 geometry를 검사합니다.
- 정렬 정책은 텍스트의 역할별로 정합니다. 짧은 버튼·상태 수치의 중앙 정렬을 채팅 같은 읽기 본문까지 일괄 적용하지 않습니다. 채팅 발신 주체는 표시 이름 비교가 아닌 신뢰할 수 있는 발생 경로/메타데이터로 구분하고 색과 명시적 표기를 함께 사용합니다. `RichTextLabel`은 신뢰하는 서식만 push/pop하고 사용자 문자열은 `add_text()`로 넣어 BBCode로 해석하지 않으며, 동일 이름·서식처럼 보이는 문자열·Unicode·길이/기록 상한을 검사합니다.
- **덮는 창의 경계와 가려지는 컨트롤:** HUD 위에 붙는 비모달 창의 가장자리를 화면 끝 여백만으로 정하지 않습니다. 창이 일부만 덮는 컨트롤(스킬 격자 등)은 창 밖으로 조각만 삐져나와 보이므로, 창 경계를 그 묶음의 경계와 맞추거나 묶음 전체를 비킵니다. 띄워야 하는 상시 표시(EXP 바·Ping 줄 등)와도 동시에 간격을 둡니다. 좌우 창의 높이를 대칭으로 맞추는 것보다 이 두 조건이 우선합니다. 덮인 컨트롤이 창 아래로 나오지 않는지와 상시 표시와의 최소 간격을 모든 지원 해상도·안전 영역에서 검사합니다.
- 폰트는 이름만 아니라 실제 파일의 지원 문자·fallback·수정/배포 라이선스를 확인합니다. 같은 이름도 배포처별 수록 범위가 다르므로 사용자 이름·채팅·번역의 실제 문자로 검증합니다. [OFL](https://openfontlicense.org/ofl-faq/)의 번들 허용은 저작권/라이선스 고지·단독 판매 금지·선언된 RFN의 수정본 이름 제한을 없애지 않으며, 다른 무료 폰트의 subset 허용도 추정하지 않습니다. 엔진별 fallback·가변 폰트 인스턴스·import 관찰은 [Godot UI](/game/godot-ui.md)의 조건부 사례입니다.
- 글꼴·굵기·고정폭 숫자를 바꾸면 고정 영역의 최장 허용 값과 장식 포함 실제 픽셀 경계를 다시 잽니다. advance 폭·컨트롤 rect만으로 ink·외곽선·그림자의 포함을 증명하지 않습니다. 상자 크기/위치 유지가 요구되면 그 조건 안에서 가독성·맞춤을 검증하고, 모든 UI의 상자 크기를 불변으로 강제하지 않습니다. 실제 렌더에서 정상/의도적 경계 위반을 구분하는지 확인하며 배율·안티에일리어싱과 headless 캡처의 한계를 밝힙니다.

## 실제 입력·화면 검증
- [ ] 실제 창 자동 검사와 OS 포커스: 포커스를 잃으면 이동·경로를 취소하는 제품 계약이 있으면, 실제 창에서 도는 자동 검사는 다른 프로세스가 전경 창을 가져가는 순간 이동이 막혀 기한 초과로 실패한다. 병렬 작업자(다른 에이전트·빌드·콘솔/셸 실행)가 새 콘솔 창을 열어도 포커스를 빼앗는다. 실제 창 실행 구간에는 창을 만드는 다른 실행을 직렬화하고(시작/종료 공지), 검사기는 포커스 변화와 전경 창을 실패마다 기록해 포커스 상실 실패와 다른 실패를 구분한다. 포커스가 유지된 실패는 포커스 원인으로 분류하지 않으며, 이후 통과한 재실행은 개별 실패의 원인을 입증하지 않는다.
- OS 입력 검증기는 주입한 DOWN과 UP을 예외 안전한 정리 구간으로 묶습니다. 포커스·좌표 검증이 DOWN 뒤 실패해도 `finally`에서 포커스 검사 없이 해당 UP을 보내고, 실제 OS 눌림 상태와 게임의 release 수신을 관찰합니다. 이 보장은 일반 예외 경로에 한정하며 프로세스 강제 종료까지 보장한다고 주장하지 않습니다.
- 검증 창에 크기·위치를 강제한 성공을 사용자 실행 조건의 성공으로 확대하지 않습니다. 에디터 내장/분리 game view와 별도 창, DPI, 실제 game client 원점, viewport/final transform, OS 커서, native 입력과 `gui_input` 위치를 실패가 발생한 조건에서 대조합니다. 테스트 기대 좌표와 입력 좌표를 같은 transform으로 산출한 결과만으로 화면 정합성을 보증하지 않으며 OS가 실제 표시한 픽셀 경계도 독립 확인합니다. 재현 조건이 특정되지 않았다면 임의의 픽셀 보정이나 해결 선언을 하지 않습니다.
- UI 참고 자료는 출처의 공식 여부와 실제 화면 여부를 따로 판정합니다. 광고 합성·키아트·홍보 프레임에 삽입한 작은 게임 화면은 전체 플레이 HUD의 근거가 아닙니다. 직접 플레이 캡처의 판본·날짜·크롭/에뮬레이터 오버레이·원 저자 워터마크를 표시하고 지도/설명 도해는 보조자료로 구분합니다.

## 서적에서 보강한 입력 기준

*Game Programming Gems 3* 한국어판 PDF p.81–83, 179–195의 계층별 입력·상태/사건·커서·marking menu, *Game Coding Complete* 1판 한국어판 PDF p.188–201, 213–214의 클릭 영역·폴링 입력, *Game Programming Tricks of the Trade* 한국어판 Trick 4의 표시/입력 순서를 현행 API와 대조했습니다(2026-10-15). 당시 DirectInput·Win32·ActiveX 구현과 고정 픽셀/오류율 수치를 채택한 것이 아니며, 위 추가 항목은 설계·검증 기준입니다.
