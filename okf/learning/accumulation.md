# OKF 학습 축적

## 목적

OKF는 사용자와 같은 지식을 갖추려는 백과사전이 아니다. 두 가지를 담는다. 하나는 정상 결과에 이르는 길이 여럿일 때 모델의 기본 선택을 사용자의 방향으로 바꾸는 차이이고, 다른 하나는 모델에 부족한 지식이다. 학습에 없거나 그 뒤 바뀐 사실, 이 환경·도구·버전의 특이점, 모델이 실무에서 자주 틀리거나 놓치는 판단 기준이 여기에 든다. 모델이 이미 정확히 아는 일반 지식과 일회성 작업 기록은 담지 않는다.

## 판정 시점

- 구현·버그 수정·조사·설정/규칙 변경 작업과 사용자 교정·영속 결정에서는 별도 요청 없이 완료 전에 이번 작업의 후보를 판정한다. 위임·병렬 작업에서는 통합 담당이 판정하고 다른 에이전트는 후보와 근거를 반환한다. 단순 질의·사소한 편집에는 적용하지 않는다.
- 보류 사유는 아래 세 질문과 기록 위치 기준만 쓴다. 한 번의 확인이나 한 프로젝트의 근거라는 이유만으로 보류하지 않는다. 버전·출처·실측 근거를 붙일 수 있으면 기록하고, 근거를 확인하지 못한 추정만 보류한다.

## 기록 판정 — 세 질문

후보마다 차례로 묻고 하나라도 '아니오'면 기록하지 않는다.

1. **행동이 달라지는가?** 이 문장이 없을 때 유능한 모델이 실제로 다르게, 틀리게, 또는 모른 채 행동하는가. 모델이 이미 정확히 아는 교과서 지식과 통상적인 좋은 관행은 기록하지 않는다. 공식 문서에 있는 사실이라도 학습에 없거나 학습 이후 바뀌었거나 이 환경에서만 성립해 모델이 모르거나 틀리기 쉬우면 기록 대상이다.
2. **다시 쓰이는가?** 다른 작업에서도 같은 판단이 필요한가. 특정 작업의 파일명·수치·실행 결과·진행 상태는 기록하지 않는다.
3. **기존 원리로 설명되지 않는가?** 이미 있는 원리의 사례면 새 항목을 만들지 않는다. 그 원리 문장이 이번 실수를 막지 못했다면 문장을 고친다.

통과하는 것은 두 종류다.

- **방향:** 사용자가 명시했거나 교정으로 확정한 선택·선호·결정. 정본은 [사용자 개발 방향](/direction.md)과 각 규칙 문서다.
- **모델에 부족한 지식:** 모델이 모르거나 틀리기 쉬운 지식. 학습에 없거나 그 뒤 바뀐 버전·도구 동작, 이 환경(omp·Windows·이 설정)의 특이점, 실제 결함으로 확인된 반직관적 계약, 모델이 실무에서 자주 놓치는 판단 기준. 버전·환경에 묶인 사실에는 적용 버전과 출처 또는 실측 근거를 붙여 한두 줄로 쓴다.

## 실수의 기록

- 사건이 아니라 위반한 원리를 적는다. 컴퓨터의 동작 원리는 같으므로 겉모습이 다른 여러 실수가 하나의 원리 위반인 경우가 많다.
- 한 번 일어난 실수는 그 작업 안에서 고치고 끝낸다. 같은 원리 위반이 반복되거나 비용이 큰 경우(데이터 손실·보안·운영 사고)에만 원리 문장을 추가하거나 다듬는다.
- 원리 문장에는 필요하면 짧은 예 하나만 붙이고 경위·날짜·재현 횟수는 남기지 않는다.
- 실수를 막으려고 원리 문장을 추가하거나 고치면 그 문장이 해당 위반을 막는지 확인하되, 확인 비용을 위반의 비용에 맞춘다. 위반을 짧은 시나리오로 재현할 수 있으면 고치기 전 배포본과 고친 뒤 배포본을 각각 새 컨텍스트에서 같은 시나리오로 실행해 그 위반 행동이 다시 나오는지(예/아니오) 본다. 긴 작업·운영 환경이 있어야 재현되는 위반은 다시 실행하지 않고 판정만 묻는 짧은 시나리오로 대신하거나 효과 미검증으로 보고한다.
- 고친 뒤에도 위반이 나오면 문장이 막지 못한다는 확정 근거이므로 문장을 다시 고친다. 한 번의 실행에서 나오지 않은 것은 그 실행의 관찰일 뿐 효과의 입증이 아니다. 고치기 전에 재현되지 않으면 비교가 근거가 되지 않으므로 문장은 반영하고 효과 미검증으로 보고한다.

## 기록 위치

- **사용자 방향:** [direction.md](/direction.md). 모든 에이전트가 받는 요약은 설정 레포의 `rules/RULES.md`이며 둘을 함께 고친다.
- **공개 가능한 규칙·비자명 사실:** 설정 레포 `okf/`(소스)에서 주제가 맞는 기존 concept. 배포본(`<configdir>/okf/`)의 공개 파일만 고치면 다음 setup에서 소스 내용으로 되돌아간다.
- **공개 소스의 범위:** 설정 레포 전체(`okf/`·`rules/`·`ttsr/`·`skills/`·`commands/`·`agents/`·`extensions/`·`scripts/`·`config/`·README 등)에 현 직장·고객사·사내 서비스에 고유한 작업·사례·수치·용어·식별자를 넣지 않는다. 이것은 제외 규칙이지 분야 제한이 아니다. 소프트웨어 개발·인프라·운영·게임 개발·도구·AI 활용 등 분야와 무관하게 위 세 질문을 통과하면 공개 소스에 둔다. 직장 업무에서 얻은 교훈은 고유 요소를 걷어 낸 일반 원리로 바꿀 수 있을 때만 원리로 둔다(예: 특정 서비스의 장애 사례 대신 공유 인프라 변경의 영향 범위 원리).
- **프로젝트 한정 결정·용어·사실:** 그 프로젝트 레포의 기존 문서 구조(설계 문서의 결정 절·용어집)에 둔다. 결정 기록은 되돌리기 비싸고, 맥락 없이는 의아하고, 실제 대안 사이의 선택일 때만 남긴다. 프로젝트 `AGENTS.md`는 매 세션 상시 로드되므로 현행 지침과 정본 링크만 두고 작업 이력·검증 실행 기록·커밋 해시를 쓰지 않는다.
- **개인·민감하거나 공개 범위를 검토 중인 지식:** 설정 폴더의 `<configdir>/okf/learned/`. 로컬 전용이고 setup이 보존하지만 다른 PC로 동기화되지 않는다. 레포의 `okf/learned/`에는 만들지 않는다. `.gitignore`는 덮어쓰기를 막지 않고 `git merge`·`git pull`은 기본값 `--overwrite-ignore`로 무시된 파일을 덮어쓴다([git merge](https://git-scm.com/docs/git-merge)). Git 2.54에서는 `--no-overwrite-ignore`도 일반 병합에서는 지키지 못했다(2026-10-12 프로브). `learned/index.md`는 setup과 `--record`가 로컬 concept의 frontmatter로 다시 만들므로 고치지 않는다.
- 기록하지 않는다: API 키·토큰·PII·내부 접속정보, 검증되지 않은 추측, 진행 상태.

## 반영

1. 같은 주제의 기존 문장을 먼저 찾아 고친다. 새 concept은 독립 주제일 때만 만들고 그 디렉터리의 `index.md`에 `* [제목](/path.md) - 설명` 항목으로 등록한다. 루트 `/index.md`에서 디렉터리 항목을 따라 닿아야 한다.
2. frontmatter `description`이 index 항목 설명과 `okf-*` 규칙 설명의 정본이다. 무엇을 다루는지와, 읽을 시점이 자명하지 않으면 언제 읽는지를 한 문장으로 쓴다. 항목 문구는 직접 쓰지 않고 description·title을 고친 뒤 `bun scripts/validate-okf.ts --fix okf`로 맞춘다. 파일 종류로 적용 시점이 정해지는 개념은 `apply_on_edit`에 glob 목록(예: `["*.cpp", "*.h"]`)을 두어, 일치하는 파일을 편집·작성할 때 본문이 자동 주입되게 한다.
3. 하나를 더하면 같은 문서에서 합치거나 지울 것이 없는지 본다. concept은 짧게 유지한다. 규칙의 적용 범위는 분야·대상을 나열해 닫지 말고 판단 원리(결과·속성)로 쓰며, 분야·대상은 비한정 사례로만 든다. 사용자의 `~등`·예시를 닫힌 목록으로 옮기지 않는다. 닫힌 목록은 같은 성격의 다른 경우를 빠뜨린다.
4. 공개 소스를 고쳤으면 레포 루트에서 `bun scripts/validate-okf.ts okf`로 검사하고 setup으로 배포한 뒤 배포본이 소스와 같은지 확인한다. 검사기는 frontmatter(`type`·`description`), `index.md`의 섹션 제목과 항목 title·description 일치, 루트 index에서의 도달성, `log.md` 날짜 제목 형식·최신순을 보며 내용의 정확성은 판정하지 않는다.
5. 로컬 concept을 만들거나 고치거나 지웠으면 `bun <레포>/scripts/deploy-okf.ts --record <configdir>`로 검증하고 `learned/index.md`와 `okf-*` 규칙을 다시 만들어 이력에 기록한다. 지운 concept이 예전 setup의 삭제 복원 절차로 되살아나지 않게 하기 위해서다.
6. 구조 변경(개념의 추가·분할·병합·삭제·이름 변경)과 기록 기준의 변경만 `/log.md`에 남긴다. 내용 갱신의 이력은 Git이 맡는다.
7. 원격 변경은 직접 pull하지 않고 `knowledge-sync` 스킬로 받는다. 공개 반영은 소스 문서 수정까지이며 스테이징·커밋·푸시의 승인이 아니다.

## 보고

- 기록했거나 후보를 보류했을 때만 완료 보고에 한 줄 적는다: `학습: <경로> — <바꾼 문장 요지>`, `학습: 보류 — <후보 요지> — <사유와 다시 판정할 조건>`. 기록 위치에 쓰지 못했거나 검증·배포가 실패했으면 `학습: 차단 — <실패 단계와 이유>`.
- 실수를 막으려고 원리 문장을 추가하거나 고쳤으면 그 줄 끝에 확인 결과를 붙인다: `(재실행 1회: 재발 없음)`, `(재실행 1회: 재발)`, `(판정 시나리오: 재발 없음)`, `(판정 시나리오: 재발)`, `(효과 미검증 — 재현 실패)`, `(효과 미검증 — 재실행 생략)`.
- 판정했지만 후보가 없으면 보고하지 않는다. 기록할 것을 억지로 만들지 않는다.

## 정비

- 지식 정비를 요청받으면 위 세 질문으로 기존 항목을 다시 판정하고, 통과하지 못한 항목은 지우거나 원리로 합친다.
- 자동 메모리·요약·외부 자료의 주장은 원문과 적용 버전을 확인한 뒤에만 반영한다. 과거 지시·승인을 새 실행 권한으로 승격하지 않는다.
