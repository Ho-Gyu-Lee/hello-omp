# 목적

OKF는 읽기 전용 참고 문서가 아니라 작업에서 확인한 재사용 지식을 반영하는 번들이다. 사용자는 평소처럼 작업만 요청하며, 기록·공개 반영·검증·배포는 에이전트가 작업 완료 절차로 수행한다. 별도 백그라운드 수집기나 Git 자동 커밋을 뜻하지 않는다.

# 실행 조건

- 구현·버그 수정·조사·설정/규칙 변경 작업과 사용자 교정·영속 결정에서는 완료 전에 학습을 판정한다. 확인한 지식은 작업 중 반영할 수 있으며, 최종 통합 담당 에이전트가 누락 여부와 완료 보고를 책임진다. 위임·병렬 작업에서는 소스 OKF 쓰기와 배포를 통합 담당 에이전트 한 명이 소유하고, 다른 에이전트는 후보와 근거를 반환한다.
- 신규 기록·갱신뿐 아니라 기존 로컬 지식을 재사용하거나 정정할 때도 공개 반영 가능성을 재평가한다. 해당 작업과 관련된 concept을 대상으로 하며 매 작업마다 전체 `/learned/`를 전수 검사하지 않는다.
- 지식 정비를 요청받으면 지정된 범위의 기존 항목도 같은 기준으로 재평가한다. 접근 가능한 메모리에 소스 부재로 보류한 후보가 있으면 포함하며, 접근할 수 없는 메모리를 확인했다고 주장하지 않는다.
- 새 학습 후보가 없는 단순 질의·사소한 편집에는 형식적인 기록·보고를 생략한다. 사용자 교정이나 재사용할 교훈이 있으면 작업 크기와 무관하게 판정한다. 후보가 없거나 기존 지식으로 충분하면 그 결과를 인정하고 새 문서를 억지로 만들지 않는다.

# 기록 대상

OKF에 기록한다:
- 여러 세션에서 재사용할 규칙·절차·체크리스트.
- 사용자가 명시적으로 확정한 영속 결정.
- 반복 오류의 근본 원인과 재발 방지 규칙.
- 도구 정책, 보안 정책, 코딩 스타일처럼 향후 행동을 바꾸는 지식.
- 게임·서버·SaaS 등 도메인별 판단 기준.
- 재사용 가능한 개인 선호·프로젝트 한정 사실. 로컬 기록 가능성과 공개 가능성은 별도로 판단한다.

OKF에 기록하지 않는다:
- 현재 작업의 진행 상태·임시 TODO·일회성 디버깅 가설.
- API 키·토큰·PII·내부 접속정보.
- 검증되지 않은 추측. 출처나 실제 코드로 확인한 뒤 기록한다.

# 기록 위치

1. 영속 학습의 소스 오브 트루스는 설정 레포의 소스 OKF다. 배포본 OKF만 직접 고치면 다음 setup 재배포 때 사라진다.
2. 개인 선호·프로젝트 한정 사실·내부 사례의 근거는 소스 `/learned/`에 둔다. 공개 범위가 불명확한 검증된 지식도 민감정보를 제외하고 로컬에 보존할 수 있다. `.gitignore`는 공개 제외 수단이지 비밀 저장소가 아니다.
3. 공개 가능한 공통 규칙·기술 지식은 주제와 가장 가까운 공개 concept에 반영한다. 공개 API의 검증된 계약도 재사용 가치가 있으면 벤더 한정이라는 이유로 제외하지 않는다. 개인 선호나 `type: Rule`·tags만으로 공통 규칙으로 승격하지 않으며, 비공개 프로젝트 사실·내부 접속정보·미패치 3자 취약점 상세·PII는 공개하지 않는다. 내부 사례에서는 재식별 가능한 맥락을 제외하고 독립적으로 성립하는 교훈만 추출한다.
4. 같은 주제를 새 파일로 중복 생성하지 않는다. 기존 concept을 갱신할 수 있으면 갱신한다.
5. 새 관리 번들 concept은 같은 디렉터리의 `index.md`와 루트 `/index.md`에 절대 링크(`/path.md`)로 추가한다. `/learned/` concept은 로컬 전용이므로 공개 index에 per-file 목록을 남기지 않고 디렉터리와 frontmatter 요약으로 발견한다.
6. 변경 이력은 `/log.md`에 날짜별로 남긴다. 단 로컬 전용 `/learned/` concept의 상세 이력은 해당 파일 본문에만 남기고 공개 `log.md`에는 내부정보를 노출하지 않는다.
7. 검증한 소스 변경은 setup 재실행으로 배포본과 동기화하고 실제 결과를 확인한다. 공개 반영은 추적 대상 소스 문서의 수정까지이며 Git 스테이징·커밋·푸시를 자동 수행하지 않는다.

# 절차

1. 소스 `/learned/`와 기존 공개 concept에서 관련 주제를 찾는다. 재사용·정정한 기존 항목도 후보에 포함하고 중복 문서 생성보다 기존 항목 갱신을 우선한다.
2. 근거와 적용 범위를 확인하고 사실·결정·규칙으로 분류한다. 미검증 추정은 concept으로 기록하지 않으며 사용자 선호를 일반 사실로 바꾸지 않는다.
3. 로컬 기록과 공개 반영을 별도로 판단한다. 공개 가능한 부분은 기존 공개 concept에 반영하고, 나머지는 로컬 유지 사유 또는 보류에 필요한 근거·판단 조건을 명시한다. 공개 여부가 불명확한 내부 정보는 임의로 공개하지 않는다.
4. 판정에 따라 소스를 반영한다. 소스 경로를 확인하거나 접근할 수 없으면 배포본만 수정하지 않는다. 비민감 후보는 접근 가능한 메모리에 임시 보존하되 저장 성공 여부와 복구 조건을 보고한다. 메모리 보존에 성공해도 소스 OKF에 기록하지 못했으면 `학습: 차단`이며, 공개 반영도 필요한 후보라면 `공개 반영: 차단`으로 알린다. `신규`·`해당 없음`으로 숨기지 않는다.
5. 로컬 concept을 재평가했다면 본문에 공개 반영 대상·항목 또는 로컬 유지·보류 사유를 남긴다. 공개 concept에 교훈이 실제로 반영돼 있는지 확인한다. 일반적인 참고 링크만 추가한 것은 승격 완료가 아니며, 이미 반영된 내용은 새 승격으로 세지 않는다. 판정이 같고 새 근거가 없으면 반복 이력을 추가하지 않는다.
6. 공개 concept을 신설하면 관련 index를, 기존 concept의 범위·요약이 바뀌면 해당 index 요약을 갱신한다. 공개 변경은 `/log.md`, 로컬 전용 변경은 해당 파일 본문에만 이력을 남긴다. 공개 로그·index에 로컬 파일명이나 내부 근거를 노출하지 않는다.
7. 소스 변경이 있으면 설정 레포 루트에서 `bun scripts/validate-okf.ts okf`를 수행하고 변경 문서와 직접 연결된 참조를 확인한다. 배치 반영·구조·범위 변경은 아래 무결성 검사를 함께 적용한다. 검사기는 concept의 YAML frontmatter와 non-empty `type`을 검증할 뿐, 내용의 정확성·공개 적합성·승격 누락을 판정하지 않는다.
8. 소스 변경이 있으면 setup으로 배포하고 소스·배포본 일치를 확인한다. 기록 후 검증·배포가 실패해도 `학습: 차단`으로 보고하며, 공개 반영분이 있으면 `공개 반영: 차단`으로 보고한다. 완료된 소스 수정과 실패 단계를 구분하고 전체 완료로 포장하지 않는다.
9. [워크플로](/workflow.md)의 필수 형식으로 학습·공개 반영 결과와 실제 변경 경로 또는 사유를 완료 보고에 남긴다. 후보별 결과가 다르면 구분하며, 관련 판정을 누락한 채 작업 완료로 보고하지 않는다.

# 변경 후 무결성 검사

배치 반영·분할·병합·이름 변경·규칙 교체 등 구조나 범위가 바뀐 경우 다음을 확인한다:
- 관련 문서끼리 모순되거나 폐기된 주장이 정본처럼 남지 않았는가.
- 기존 concept에 병합할 내용을 새 파일로 중복하거나 둘 이상의 문서가 같은 주제의 소스 오브 트루스를 주장하지 않는가.
- 공개 concept이 루트 또는 하위 `index.md`에서 도달 가능한가. 로컬 concept은 `/learned/` 디렉터리에서 발견 가능하며 공개 index에 개별 목록이 없는가. 양쪽의 내부 링크와 이름 변경 전 참조가 깨지지 않았는가.
- 제목·description·본문·frontmatter·index 요약이 같은 범위와 현재 상태를 설명하는가.
- 대체된 규칙은 제거하거나 대체 관계를 명시하고, 구조 변경은 `log.md`에 기록했는가.

# 판단 기준

기록한다:
- 같은 지시를 다시 받지 않게 하는 정보.
- 같은 실수를 막는 정보.
- 사용자의 장기 선호·작업 방식에 영향을 주는 정보.
- 보안·데이터 손실·운영 리스크를 줄이는 정보.

기록하지 않는다:
- 한 번 쓰고 버릴 파일명·라인 번호·실험 결과.
- 검증이 끝나지 않은 추정.
- 외부 문서 링크만 있고 요약·판단이 없는 빈 항목.
