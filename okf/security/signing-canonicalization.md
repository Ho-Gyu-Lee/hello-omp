# 요청 서명 정규화 계약

HMAC/서명 기반 인증에서 서명자와 검증자는 **같은 서명 입력 바이트**를 사용해야 한다. 계약이 수신 rawBody를 쓰는지, 파싱 후 canonical 값을 재구성하는지 먼저 구분한다. 두 쪽 입력이 다르면 서명 검증에 실패하며 응답 코드는 서비스의 오류 매핑에 따른다. 서로 다른 언어·런타임에서는 정규화 규칙 차이가 payload 특정 필드의 문제처럼 보일 수 있다.

정규화 계약은 세 축에서 깨진다.

## 1. 키(필드) 정렬

- 베이스가 키 정렬 순서에 의존하면, 서명자와 검증자가 **같은 정렬 기준**을 써야 한다. 흔한 함정: 한쪽은 문화권(culture-aware/locale) 정렬, 다른 쪽은 ordinal(코드유닛) 정렬.
- `_`(U+005F)·대소문자·숫자 등은 두 정렬에서 상대 순서가 갈린다. 예: ordinal은 대문자 < 소문자지만 문화권 정렬은 다르게 취급. snake_case·camelCase 키가 섞이면 정렬 결과가 바뀌어 특정 키 조합에서만 재발한다.
- 문화권 정렬은 런타임(.NET NLS vs ICU)·머신 로케일에 따라 결과가 달라져, 같은 payload가 환경마다 성패가 갈릴 수 있다. 재현 안 됨이 곧 무결점이 아니다.
- **근본 수정**: 양쪽 계약이 요구하는 정렬 기준을 인코딩 단위까지 명시하고 동일하게 구현한다. UTF-16 코드유닛 계약이면 `StringComparer.Ordinal`·JS 기본 `Array.prototype.sort`를 사용할 수 있지만 UTF-8 바이트 정렬과 전 Unicode 범위에서 같지는 않다. `U+10000`과 `U+E000`은 두 방식의 순서가 반대다([RFC 8785 §3.2.3](https://www.rfc-editor.org/rfc/rfc8785.html#section-3.2.3)). 기존 계약을 확인하지 않고 한쪽 비교자만 바꾸지 않는다.

## 2. 값 문자열화

베이스가 `key=value` 형태로 값을 직렬화하면, 비문자열 값의 문자열화가 런타임마다 갈린다. 각 값이 **단독으로도** 불일치를 낸다(정렬과 무관).

| 값 종류 | 런타임 간 차이 | 원인 |
| --- | --- | --- |
| 안전 정수 범위 밖 long | 정밀도 손실·서로 다른 정수의 합쳐짐 | JS Number는 IEEE754 double이며 절댓값 `2^53-1` 초과 정수는 모두 정확하게 구분할 수 없음 |
| float | `0.1f` → `0.10000000149011612` vs `0.1` | float→double 승격 후 round-trip 포맷 |
| 작은/큰 double | `1E-05` vs `0.00001` | .NET `"R"`와 JS `Number.toString()`의 지수표기 임계가 다름 |
| DateTime/날짜 | JSON 따옴표 포함 vs 미포함 | 한쪽은 JSON 직렬화(따옴표), 다른 쪽은 문자열 취급 |
| bool/null | `True`/`False`, 대소문자 | 언어별 기본 `ToString()` 표기 |

- **값 계약**: 문자열·bool도 따옴표·이스케이프·표기를 합의해야 한다. JS Number의 안전 정수 범위는 절댓값 `2^53-1` 이하이며, 그 밖의 정수·부동소수·날짜는 소비자의 타입·정밀도 계약을 확인한다. 문자열 변환은 소비자와 합의한 경우에만 하며 서명 실패를 피하려고 필드 타입을 임의 변경하지 않는다.
- **근본 수정**: 파싱 후 재구성 모델이면 검증자가 만드는 정렬·숫자·문자열 표현과 동일한 canonical 규칙을 구현한다. 이 모델은 전송 원시 토큰과 바이트가 달라도 정상일 수 있다(예: `1E-05` → `0.00001`). rawBody 모델이면 한 번 직렬화한 같은 바이트를 서명 입력과 전송에 재사용하고 전송층·재시도에서 변형되지 않는지 확인한다. 같은 serializer를 쓴다는 사실만으로 두 모델의 일치를 보장하지 않는다.

## 3. 기대 키 집합

- 검증자가 **미리 정해진 키 집합**으로 베이스를 재구성하면, 클라가 모르는 키를 추가할 때 서명이 깨진다(양쪽 키 집합 불일치). "호환을 위해 old/new 키를 둘 다 보내기"가 오히려 서명 검증 실패를 유발한다 — 분기해서 정확한 키 집합만 보내야 한다.
- 계약 함의: 서명 대상 필드의 추가·이름 변경은 **깨는 변경**이다. 서명 정규화는 느슨한 확장을 허용하지 않는 엄격한 계약으로 다룬다.

## 격리 방법 (결정적)

- **이분 탐색 probe**: 성공 케이스와 실패 케이스에서 변수를 하나씩 바꿔 원인 후보를 좁힌다. 특정 키 쌍만 실패하면 정렬, 특정 값 단독이 실패하면 값 문자열화, 키 추가가 실패시키면 기대 키 집합을 조사한다. 상태코드만으로 확정하지 않고 별도 입력 검증·재시도·오류 매핑을 배제한 뒤 양쪽 서명 입력을 비교한다.
- **양쪽 실측**: .NET 측 문자열화는 .NET 런타임에서, JS 측은 JS 런타임에서 직접 실측해 베이스 문자열을 바이트 비교한다(예: `(...).ToString("R")` vs `Number.prototype.toString`). 추정하지 말고 재구성한 베이스를 나란히 놓는다.
