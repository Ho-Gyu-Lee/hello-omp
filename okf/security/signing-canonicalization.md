# 요청 서명 정규화 계약

서명 베이스의 정렬·값 표현·키 집합은 서명자와 검증자 사이의 바이트 계약이므로 한쪽만 바꾸지 않고 양쪽을 함께 고친다. 런타임(.NET ↔ JS/Go 등)이 다르면 정규화 차이가 특정 필드나 환경별 간헐 실패로 보이며, 재현되지 않는다고 무결하지 않다.

- 계약이 수신 rawBody를 쓰는지 파싱 후 canonical 값을 재구성하는지 먼저 구분한다. rawBody 모델은 한 번 직렬화한 같은 바이트를 서명과 전송에 재사용하고 전송층·재시도에서 변형되지 않는지 확인한다. 재구성 모델은 검증자와 같은 정렬·숫자·문자열 canonical 규칙을 구현하며 전송 원시 토큰과 바이트가 달라도 정상이다(예: `1E-05` → `0.00001`). 같은 serializer를 쓴다는 사실만으로 일치를 보장하지 않는다.
- 키 정렬은 인코딩 단위까지 명시해 양쪽을 같게 구현하고 문화권(culture-aware) 정렬은 쓰지 않는다(.NET NLS/ICU·로케일마다 다르다). UTF-16 코드유닛 계약이면 `StringComparer.Ordinal`·JS 기본 `Array.prototype.sort`를 쓸 수 있지만 UTF-8 바이트 정렬과 전 Unicode 범위에서 같지 않다. `U+10000`과 `U+E000`은 두 방식의 순서가 반대다([RFC 8785 §3.2.3](https://www.rfc-editor.org/rfc/rfc8785.html#section-3.2.3)).
- 비문자열 값의 문자열화(float 승격 포맷, 지수 표기 임계, 날짜의 JSON 따옴표, bool 표기)는 각 값이 단독으로 불일치를 낸다. 표기를 합의하고 서명 실패를 피하려고 필드 타입을 임의로 바꾸지 않는다. 64비트 정수는 소비 런타임의 수 표현 범위(JS는 2^53−1)를 넘으면 문자열로 주고받는다.
- 검증자가 미리 정한 키 집합으로 베이스를 재구성하면 클라이언트가 모르는 키를 추가할 때 서명이 깨진다. "호환을 위해 old/new 키를 둘 다 보내기"가 오히려 검증 실패를 유발하므로 분기해 정확한 키 집합만 보낸다. 서명 대상 필드의 추가·이름 변경은 깨는 변경이다.
- 원인은 상태코드만으로 확정하지 않고 양쪽 런타임에서 직접 만든 서명 입력을 바이트 비교한다.
