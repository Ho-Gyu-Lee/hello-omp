# 요청 서명 정규화 계약

HMAC/서명 기반 인증에서 서명자(예: 클라이언트 SDK)와 검증자(예: 서버)는 요청으로부터 **서명 베이스 문자열**(canonical string)을 각자 재구성한 뒤 비교한다. 두 쪽이 만드는 베이스가 한 바이트라도 다르면 `bad signature`(401)가 난다. 서명자와 검증자가 서로 다른 언어·런타임이면(.NET 클라 ↔ JS/Go 서버, 웹훅 서명 검증, OAuth1 signature base string 등) 정규화 규칙의 미세한 차이가 그대로 서명 불일치가 된다. 이는 payload 특정 필드의 문제로 오인되기 쉬운(필드를 빼면 사라지는) 결함이다.

정규화 계약은 세 축에서 깨진다.

## 1. 키(필드) 정렬

- 베이스가 키 정렬 순서에 의존하면, 서명자와 검증자가 **같은 정렬 기준**을 써야 한다. 흔한 함정: 한쪽은 문화권(culture-aware/locale) 정렬, 다른 쪽은 ordinal(코드유닛) 정렬.
- `_`(U+005F)·대소문자·숫자 등은 두 정렬에서 상대 순서가 갈린다. 예: ordinal은 대문자 < 소문자지만 문화권 정렬은 다르게 취급. snake_case·camelCase 키가 섞이면 정렬 결과가 바뀌어 특정 키 조합에서만 재발한다.
- 문화권 정렬은 런타임(.NET NLS vs ICU)·머신 로케일에 따라 결과가 달라져, 같은 payload가 환경마다 성패가 갈릴 수 있다. 재현 안 됨이 곧 무결점이 아니다.
- **근본 수정**: 서명 정렬을 ordinal 비교자로 고정한다(언어별 등가물: `StringComparer.Ordinal`, `Array.prototype.sort` 기본(코드유닛), `sort.Strings`). 서명자·검증자 양쪽 문서에 정렬 기준을 계약으로 못박는다.

## 2. 값 문자열화

베이스가 `key=value` 형태로 값을 직렬화하면, 비문자열 값의 문자열화가 런타임마다 갈린다. 각 값이 **단독으로도** 불일치를 낸다(정렬과 무관).

| 값 종류 | 런타임 간 차이 | 원인 |
| --- | --- | --- |
| 2^53 초과 정수(long) | 정밀도 손실 | JS Number는 IEEE754 double, 2^53 초과 정수 표현 불가 |
| float | `0.1f` → `0.10000000149011612` vs `0.1` | float→double 승격 후 round-trip 포맷 |
| 작은/큰 double | `1E-05` vs `0.00001` | .NET `"R"`와 JS `Number.toString()`의 지수표기 임계가 다름 |
| DateTime/날짜 | JSON 따옴표 포함 vs 미포함 | 한쪽은 JSON 직렬화(따옴표), 다른 쪽은 문자열 취급 |
| bool/null | `True`/`False`, 대소문자 | 언어별 기본 `ToString()` 표기 |

- **안전한 값**: 문자열, bool(양쪽 표기 합의 시), 2^53 이내 정수. 부동소수·큰 정수·날짜는 서명 전 문자열로 고정(예: `InvariantCulture` 포맷, ISO8601)한다.
- **근본 수정**: 서명 베이스의 값 문자열화를 **전송 body의 원시 토큰과 바이트 동일**하게 만든다. Body와 서명이 같은 직렬화기·컨버터를 공유하거나, 검증자가 수신한 원시 토큰 텍스트로 베이스를 재구성한다. float 승격 제거·지수표기 개별 패치는 케이스별 두더지잡기가 되므로 정규화기를 통일하는 편이 옳다.

## 3. 기대 키 집합

- 검증자가 **미리 정해진 키 집합**으로 베이스를 재구성하면, 클라가 모르는 키를 추가할 때 서명이 깨진다(양쪽 키 집합 불일치). "호환을 위해 old/new 키를 둘 다 보내기"가 오히려 401을 유발한다 — 분기해서 정확한 키 집합만 보내야 한다.
- 계약 함의: 서명 대상 필드의 추가·이름 변경은 **깨는 변경**이다. 서명 정규화는 느슨한 확장을 허용하지 않는 엄격한 계약으로 다룬다.

## 격리 방법 (결정적)

- **이분 탐색 probe**: 성공 케이스와 실패 케이스 사이에서 변수를 하나씩만 바꾸는 probe 배열로 한 번의 실행에서 원인 축(정렬/값/키집합)을 격리한다. 단독 키는 통과하는데 특정 키 쌍만 실패하면 정렬, 특정 값 단독이 실패하면 값 문자열화, 키 추가가 실패시키면 기대 키 집합이다.
- **양쪽 실측**: .NET 측 문자열화는 .NET 런타임에서, JS 측은 JS 런타임에서 직접 실측해 베이스 문자열을 바이트 비교한다(예: `(...).ToString("R")` vs `Number.prototype.toString`). 추정하지 말고 재구성한 베이스를 나란히 놓는다.
