# 보안 검토 체크리스트 (환경·도구 특이 계약)

일반 웹·서버 보안(입력 검증·SQL 바인딩·XSS·CSRF·인증/인가·BOLA·HTTPS·에러 노출)은 기본으로 점검하며 옮기지 않는다. 게임 항목은 [게임 보안](/security/game.md), 즉시 경고·자격증명은 [보안 개요](/security/overview.md)를 따른다.

- [ ] 게이트웨이·프록시가 HTTP 헤더를 내부 메타데이터로 변환할 때 신원·권한 키를 허용 목록으로만 전달하는가. 이름 비교 차단 목록은 라이브러리 기본 매핑의 접두사·대소문자 변환으로 우회될 수 있다. 예: [grpc-gateway `DefaultHeaderMatcher`](https://pkg.go.dev/github.com/grpc-ecosystem/grpc-gateway/v2/runtime#DefaultHeaderMatcher)는 v2.32.0까지 `Grpc-Metadata-` 접두사를 떼어 gRPC 메타데이터로 전달했다([v2.31.0](https://github.com/grpc-ecosystem/grpc-gateway/releases/tag/v2.31.0)은 `Grpc-Metadata-grpcgateway-*`, [v2.32.0](https://github.com/grpc-ecosystem/grpc-gateway/releases/tag/v2.32.0)은 `Grpc-Metadata-X-Forwarded-*`만 거부). [v2.33.0](https://github.com/grpc-ecosystem/grpc-gateway/releases/tag/v2.33.0)(2026-10-27)부터는 기본으로 `Grpc-Metadata-*`를 전달하지 않고 `WithLegacyHeaderMatching`으로만 되살린다(확인 2026-11-03). 그래서 v2.32.0 이하에서는 직접 만든 매처가 `X-Super-Access`처럼 이름만 막아도 `Grpc-Metadata-X-Super-Access`로 우회된다. 권한 수준·신원은 클라이언트가 보낸 값이 아니라 검증된 자격(토큰 검증 결과·수신 리스너·서명)으로 서버가 설정하고 같은 키의 클라이언트 값은 수신 단계에서 먼저 제거한다.
- [ ] 하류 서비스가 게이트웨이 인증 미들웨어가 설정한 신원 헤더에 의존할 때, 그 미들웨어가 같은 이름의 클라이언트 헤더를 먼저 지우는지와 게이트웨이를 거치지 않는 경로가 막혀 있는지 확인했는가. Traefik v3.6.7 forwardAuth는 `authResponseHeaders`에 적은 헤더를 요청에서 먼저 지운 뒤 인증 응답 값으로 넣는다([`forward.go`](https://github.com/traefik/traefik/blob/v3.6.7/pkg/middlewares/auth/forward.go), 확인 2026-11-10). 하류 서비스가 그 헤더를 검증 없이 믿으면 클러스터 안에서 서비스로 직접 호출해 우회할 수 있으므로 메시 인가 정책이나 서비스 간 인증으로 진입 경로를 제한한다. 앱 미들웨어가 신원 헤더를 인증 성공 때만 덮어쓰면 인증 전·거절 경로의 로그와 코드는 클라이언트가 보낸 값을 본다. 게이트웨이 미들웨어로 거는 IP 차단·rate limit·User-Agent 차단도 같은 호스트를 처리하는 다른 진입점이 있으면 우회된다. DNS 가중치 0인 대체 로드밸런서는 DNS 응답에서만 빠질 뿐, 그 로드밸런서 주소로 Host 헤더를 맞춰 보내면 그대로 처리되므로(관찰 2026-11) 그 진입점에도 같은 통제를 두거나 닫는다.
- [ ] 출발지 IP 허용 목록(인그레스·프록시의 IP 필터)을 걸 때 판정 지점이 보는 주소가 실제 클라이언트 주소인지 포트·경로마다 확인했는가. AWS NLB의 IP 대상 TCP·TLS 대상 그룹은 클라이언트 IP 보존이 기본 꺼져 있어 출발지가 LB 노드의 사설 IP가 되고([NLB 대상 그룹 속성](https://docs.aws.amazon.com/elasticloadbalancing/latest/network/edit-target-group-attributes.html), 확인 2026-11-03), 같은 LB라도 리스너마다 설정이 다를 수 있다. 인그레스 파드의 서비스 메시 사이드카가 inbound를 가로채면 출발지가 파드 자신의 IP로 바뀐다(Linkerd edge-26.4.3 + Traefik v3.6.7 관찰 2026-11-03, 해당 포트를 `config.linkerd.io/skip-inbound-ports`로 빼야 실제 주소가 보임). 허용 대역이 VPC·파드 대역을 포함하면 이런 경로의 요청은 모두 통과하므로, 적용 뒤 허용 대역 밖의 주소에서 실제 요청이 거부되는지와 접근 로그의 출발지 주소를 함께 확인한다. 허용 경로를 클러스터 안 시험 파드로 확인할 때는 그 파드를 인그레스 파드와 다른 노드에 둔다. 클라이언트 IP 보존이 켜진 NLB에 대상과 같은 노드의 파드가 접속하면 응답이 노드 안에서 바로 돌아가 연결이 간헐적으로 끊기며(AWS 문서의 hairpin 제약과 같은 원리, 관찰 2026-11-03), 이를 allowlist 차단으로 오인하기 쉽다. 판정 서비스가 `X-Forwarded-For`의 첫 값을 클라이언트 주소로 쓰면, 위조 가능 여부는 앞단이 클라이언트가 보낸 값을 지우는지로 정한다. Traefik v3.6.7 forwardAuth의 `trustForwardHeader=true`는 들어온 `X-Forwarded-For` 뒤에 TCP 출발지를 덧붙이고([`forward.go`](https://github.com/traefik/traefik/blob/v3.6.7/pkg/middlewares/auth/forward.go)), entrypoint는 `forwardedHeaders.trustedIPs`나 `insecure`가 없으면 신뢰하지 않는 출발지가 보낸 `X-Forwarded-*`를 먼저 지운다([`forwarded_header.go`](https://github.com/traefik/traefik/blob/v3.6.7/pkg/middlewares/forwardedheaders/forwarded_header.go), 확인 2026-11-13). 그래서 entrypoint 설정이 바뀌면 같은 미들웨어 설정이 위조 가능한 첫 값을 넘기게 된다.
- [ ] 쿠버네티스 `Service`(type `LoadBalancer`)가 만든 로드밸런서의 출발지 제한을 Service 스펙에 두었는가. AWS Load Balancer Controller가 관리하는 프런트엔드 보안 그룹(`service.k8s.aws/resource=ManagedLBSecurityGroup` 태그)을 콘솔·CLI로 좁히면 재조정(주기 동기화나 Service 변경) 때 스펙대로 되돌아가 `0.0.0.0/0`이 복구된다(v2.6.2, 관찰 2026-11: 수동 축소 두 번이 모두 되돌려짐). `loadBalancerSourceRanges`는 그 Service의 모든 리스너에 같은 범위를 적용하므로, 포트마다 공개 범위가 다르면 내부용 포트를 Service에서 빼거나 별도 Service로 나눈다. 그 보안 그룹을 다른 ENI(VPC 인터페이스 엔드포인트 등)에도 붙였으면 범위 변경이 그 ENI까지 막고, private DNS가 켜진 인터페이스 엔드포인트면 VPC 안에서 그 AWS 서비스의 기본 DNS 이름으로 가는 호출이 막힌다. 바꾸기 전에 `describe-network-interfaces --filters Name=group-id,Values=<그룹 ID>`로 그 그룹을 쓰는 ENI를 확인한다.
- [ ] 인스턴스 보안 그룹의 인바운드 출발지를 좁힐 때, 그 호스트나 같은 VPC의 구성 요소가 자기 공개 도메인·공인 IP로 붙는 연결을 찾았는가. 이 연결은 인터넷 게이트웨이를 돌아 들어와 출발지가 그 연결이 나간 공인 IP(자기 EIP나 NAT 게이트웨이 IP)로 보이므로, 그 IP를 허용하지 않으면 서비스가 자기 자신과의 연결을 잃는다(관찰 2026-11).
- [ ] VPC NACL 규칙의 CIDR이 네트워크 경계에 맞는가. NACL은 경계가 맞지 않는 CIDR을 거부하지 않고 네트워크 주소로 정렬해 저장하므로(관찰 2026-11: `198.51.100.84/29`가 `.80/29`로 저장되어 `.88`부터의 차단이 풀림) 주소를 묶을 때 경계를 계산하고, 적용 뒤 대상 IP마다 번호 순으로 첫 일치 규칙이 deny인지 확인한다. NACL로 IP를 막을 때는 차단 범위도 확인한다. NACL은 그 VPC 서브넷으로 들어오는 트래픽만 거르므로 한 VPC에만 넣으면 같은 행위자가 다른 VPC의 진입점으로 옮겨 가고(관찰 2026-11), CloudFront·API Gateway·Lambda 함수 URL·S3 같은 VPC 밖 공개 엔드포인트는 막지 못해 WAF IP 세트나 리소스 정책에 같은 목록을 따로 넣고 서로 맞는지 대조해야 한다. 규칙 수 상한은 방향마다 20이고 40까지만 늘릴 수 있으며([VPC 할당량](https://docs.aws.amazon.com/vpc/latest/userguide/amazon-vpc-limits.html), 확인 2026-11-13), 기본 거부 규칙(32767)도 그 수에 들어간다(관찰 2026-11: 기본 규칙을 포함해 20개일 때 `NetworkAclEntryLimitExceeded`).
- [ ] 쿠버네티스 NetworkPolicy 객체가 있다는 것만으로 격리됐다고 판정하지 않았는가. Amazon VPC CNI는 네트워크 정책 집행이 꺼져 있으면(관리형 애드온 구성 `enableNetworkPolicy` 미설정, 노드 에이전트 `--enable-network-policy=false`) 정책을 집행하지 않는다(v1.21.1-eksbuild.7, 노드 에이전트 플래그 확인 2026-11-10). 집행을 켜면 이미 있던 정책도 한꺼번에 효력을 가지므로, 켜기 전에 기존 정책이 선택하는 파드와 허용 규칙이 필요한 트래픽을 막지 않는지 본다.
- [ ] 리소스 단위로 좁힌 IAM 정책을 시뮬레이터로 허용·거부 양쪽 다 확인했는가. `Resource`가 생략된 리소스 정책(ECR 저장소 정책 등)을 `simulate-principal-policy --resource-policy`에 그대로 넘기면 그 Deny가 평가되지 않으므로, `Resource`에 그 리소스 ARN을 넣은 사본을 넘긴다(관찰 2026-11). Route53 레코드별 조건 `route53:ChangeResourceRecordSetsNormalizedRecordNames`는 소문자에 끝 점이 없는 이름으로 쓴다(관찰 2026-11: 이 형태로 쓴 이름만 허용되고 다른 이름은 `implicitDeny`). Deny 문장은 막으려는 동작의 결과가 `explicitDeny`로 나오는지로 확인한다. 요청 컨텍스트에 없는 키에 건 조건은 거짓이 되므로([조건 연산자](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference_policies_elements_condition_operators.html), 확인 2026-11-13) 존재하지 않는 키를 긍정 연산자로 건 Deny는 어떤 요청에도 적용되지 않는다. 예를 들어 전역 조건 키 목록에 없는 `aws:RequestedService`에 건 Deny도 정책으로 저장되지만, 막으려던 동작의 시뮬레이터 결과는 `implicitDeny`다(관찰 2026-11).
- [ ] 조회 전용으로 주는 권한이 비밀값을 응답하지 않는가. API Gateway 관리 API의 조회는 IAM 동작이 `apigateway:GET` 하나라서, 리소스를 경로(`/restapis*`·`/apis*`·`/domainnames*` 등)로 좁히지 않으면 `GET /apikeys/{id}?includeValue=true`로 API 키 값까지 읽힌다([IAM으로 API 관리 접근 제어](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-control-access-using-iam-policies-to-create-and-manage-api.html), [GetApiKey](https://docs.aws.amazon.com/apigateway/latest/api/API_GetApiKey.html), 확인 2026-11-13). Lambda 조회 응답의 환경 변수는 [클라우드 침해 조사](/security/cloud-incident-forensics.md)의 Lambda 항목을 따른다.
- [ ] 저장소 안의 설정 파일이 정한 경로(형제 저장소, include 패턴)로 파일을 읽거나 git을 실행하는 도구는 그 경로를 프로젝트 상대 경로와 이름을 명시한 형제 디렉터리로 제한하고 링크·junction이 경계 밖으로 나가지 않는지 실제 경로로 대조하는가. 그 디렉터리의 git은 `-c core.fsmonitor=false -c safe.bareRepository=explicit`로 실행한다. `core.fsmonitor`에 경로가 들어 있으면 git이 그 훅 명령을 실행하고 `safe.bareRepository`는 명령줄·전역·시스템 설정에서만 적용된다([git-config](https://git-scm.com/docs/git-config), 확인 2026-10-17).
- [ ] 저장소 안에서 실행되는 도구가 외부 명령을 이름만으로 실행하지 않는가. Windows에서 Bun 1.4.3의 `Bun.spawn`은 현재 디렉터리의 `git.exe`·`git.bat`을, Node 24.17.0의 `child_process.spawnSync`는 `git.exe`를 PATH보다 먼저 실행했다(관찰 2026-10-17). PATH에서 절대 경로로 해석한 실행 파일(Bun은 `Bun.which`)이 프로젝트 밖에 있는지 확인해 실행하고 작업 디렉터리는 중립 위치로 둔다.
- [ ] 사용자가 준 경로를 이름으로 비교해 막거나 잠금·식별 키로 쓸 때 같은 디렉터리의 다른 표기를 함께 막는가. Windows는 대소문자, 8.3 짧은 이름(`PROJEC~1`), `<이름>::$INDEX_ALLOCATION`으로 같은 디렉터리를 연다(Windows 11 build 26300·Bun 1.4.3에서 세 표기의 `lstat` `ino`가 같음, 관찰 2026-10-17). 소속 판정은 이름이 아니라 `dev`·`ino`(NTFS ID는 2^53을 넘을 수 있어 bigint)로 하되, ID가 0이나 모두 1이면 고유 ID가 없고 ReFS의 64비트 ID는 고유성이 보장되지 않으므로([BY_HANDLE_FILE_INFORMATION](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/ns-fileapi-by_handle_file_information)) 디스크 철자의 실제 경로도 대조한다. 대소문자 접은 키는 파일 시스템보다 넓게 묶고(NTFS에서 `xß`와 `xẞ`는 다른 이름인데 JavaScript `toLowerCase`는 `ẞ`를 `ß`로 바꾼다), 끝이 `.`·공백인 구간과 `:`가 든 구간은 받지 않는다([Naming Files](https://learn.microsoft.com/en-us/windows/win32/fileio/naming-a-file)).
- [ ] 자체 호스팅 서비스를 무인 설치할 때 설치 화면 잠금과 암호화 키 생성을 별개 계약으로 보고, 파일로 넘긴 비밀이 생성 설정에 값으로 복사되는지 확인하는가. [Gitea 28.0.0·28.2.0 `security.go`](https://github.com/go-gitea/gitea/blob/v28.2.0/modules/setting/security.go)는 `INSTALL_LOCK`이 켜지고 `INTERNAL_TOKEN`이 비면 새로 생성해 저장하지만 `SECRET_KEY`(`SECRET_KEY_URI`)가 비면 공개 소스에 적힌 고정 기본값을 그대로 쓴다. 고유 키를 직접 주입하고 보존한다. 같은 버전의 [`config_env.go`](https://github.com/go-gitea/gitea/blob/v28.2.0/modules/setting/config_env.go)는 `GITEA__<섹션>__<키>__FILE` 환경 변수가 가리키는 파일 내용을 읽어 설정 키의 값으로 넣고, 공식 Docker 이미지는 기동마다 그 결과를 `app.ini`에 제자리로 쓴다(`config edit-ini --in-place --apply-env`). 따라서 `app.ini`와 그 영속 볼륨도 비밀 저장소다. 설정에 키를 복사하지 않으려면 `SECRET_KEY_URI=file:...`처럼 참조하되 그 파일을 계속 공급·보존한다(확인 2026-10-30).
