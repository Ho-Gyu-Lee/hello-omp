# 게임 클라/서버 보안

## 서버 권위 원칙
- 클라이언트가 보낸 좌표·수치·상태·timestamp는 검증 자료일 뿐 정본이 아니다. 권위 판정은 요청한 입력(커맨드)을 서버가 검증·계산한 결과다.
- 검증 실패 입력은 권위 상태·last-known-good·통계·delta baseline·replay window를 갱신하지 않는다.
- 서버가 보정·정규화·재계산한 최종 accepted 값을 저장·시뮬레이션·복제·송신자 보정·관전자 전파 전체에 사용한다. host/listen-server/local fast path도 원격 클라이언트와 같은 권한·검증·정규화 불변조건을 만족해야 한다.
- 서버가 호출하는 AI 판정(결정 모델·LLM 분류기)은 권위 판정의 근거가 아니다. 플레이어가 작성한 내용(채팅·닉네임·신고 사유)이 입력에 들어가면 결과는 클라이언트 입력과 같은 신뢰 수준이며([JevOut](https://arxiv.org/abs/2609.30243), 2026-09 arXiv 프리프린트, 확인 2026-10-15: 배경 문맥만 덧붙여 판정을 미리 정한 오답으로 바꿀 수 있다), 제재·재화·소유권 같은 비가역 결과는 서버 규칙과 사람 검토로 확정하고 모델 결과는 숨김·검토 큐·우선순위처럼 되돌릴 수 있는 조치에만 연결한다. 원격 모델 응답을 기다리느라 tick·커맨드 처리를 멈추지 않는다.

## 보안과 반응성의 균형
- 서버의 권한·순서·게임 불변조건 검증과 화면 표시의 네트워크 대기를 구분한다. 계약상 예측 가능한 표시·움직임은 선반영하고 서버 accepted 상태로 보정하되, 반응성을 이유로 검증·멱등성·재전송·커밋 경계·거부 입력 비반영 규칙을 생략하지 않는다.
- 경제 결과의 성공 확인은 서버의 권위 확정(검증을 통과해 순번·멱등 처리와 함께 권위 상태에 적용됨)을 뜻한다. 수신 ACK·timeout은 성공이 아니고 pending·미리보기는 사용 가능 잔액·소유권·보상이나 후속 권위 행동의 근거가 아니다. 내구 커밋을 기다린 뒤 공개할지는 콘텐츠별로 [서버 영속화·장애 체크리스트](/game/server-persistence.md)의 A/B/C 선언을 따른다.

## 게임 커맨드 검증
- 다른 플레이어에게 영향을 주는 요청(파티 초대·소환·인스턴스 동반 입장)의 대상 목록은 서버의 그룹·관계 상태에서 도출한다. 대상을 지정하는 명령의 관찰 범위 인가는 카메라 범위나 클라이언트가 고른 대상이 아니라 실행 시점에 그 세션이 **마지막으로 공개한 복제 집합**으로 판정하며, 공개 뒤 실행 전에 대상이 빠지면 일반 거절로 끝내고 자원·예약을 쓰지 않는다(서버 내부 AI 경로는 제외).

## 세션/통신 보안
- 세션 재개 증명은 만료·회전·폐기가 가능하고 로그에 남기지 않는다. 서비스 인스턴스가 바뀌면(서버 재시작) 이전 토큰은 무효이며 토큰 불일치와 구별해 만료로 알린다. 재개 시 identity·권한·replay window를 다시 결합한다. 명령 도착률 제한은 replay 방지의 대체가 아니므로 빈도 제한과 session·sequence·command ID의 중복 판정을 분리한다.
- [TLS 1.3 RFC 9846 §8](https://www.rfc-editor.org/rfc/rfc9846.html#section-8)(2026-07-11 발행, RFC 8446을 대체, 확인 2026-10-15)은 0-RTT와 애플리케이션 재시도를 별개의 replay 원인으로 다룬다. TLS session resumption·QUIC migration은 게임 명령의 중복 실행을 막지 않으므로 early data는 기본 비활성으로 두고 구매·전투·소유권을 바꾸는 메시지는 별도 안전성 계약 없이 보내지 않는다.
- UDP 위의 자체·reliable 전송(KCP·ENet 등)은 첫 패킷의 크기·magic·토큰을 검사하기 전에는 연결별 상태·버퍼를 할당하지 않는다. upstream kcp2k는 새 endpoint마다 handshake 전에 연결 객체와 최대 메시지 크기의 버퍼를 만든다([Mirror 고정 소스 `KcpPeer`](https://github.com/MirrorNetworking/Mirror/blob/c4f3739966e151f405be1762d33502794fd034ff/Assets/Mirror/Transports/KCP/kcp2k/highlevel/KcpPeer.cs), 조회 2026-10-11). 이식할 때 이 할당 순서는 따르지 않는다.
- 게스트 계정의 기기 식별값은 bearer 비밀이다. 클라이언트가 CSPRNG로 만들어 **첫 요청 전에 로컬에 영속**해야 응답이 유실돼도 같은 값으로 재시도해 같은 계정을 받으며, 서버는 도메인 분리한 digest만 저장하고 식별값당 미사용 인증 grant를 하나로 제한한다. 타사 로그인은 `(iss, sub)` 쌍을 키로 쓴다([OIDC Core §5.7](https://openid.net/specs/openid-connect-core-1_0.html#ClaimStability)).

## 정보 가시성·관전자
- interest management는 성능 최적화이고 fog of war·비공개 상태는 인가 경계다. 클라이언트가 보낸 선택 대상·관심 ID·우선순위 힌트는 이미 인가된 후보 사이의 순서에만 쓰고 복제 범위를 넓히지 않는다. 클라이언트에 배포한 콘텐츠 정의 사본은 열람·변조 가능하므로 결과·보상·재화는 서버의 자기 버전으로 판정한다.

## 게임 클라이언트 보안
- Lua 5.4는 바이너리 청크 내부 코드의 일관성을 검사하지 않아 악의적인 bytecode 실행이 인터프리터를 크래시시킬 수 있다고 명시한다. 신뢰하지 않는 입력에 텍스트 전용 로드를 선택해도 host API·파일/프로세스 접근·native module 로드·메모리/실행 예산을 제한하지 않으면 sandbox가 아니다([Lua load](https://www.lua.org/manual/5.4/manual.html#pdf-load), [실행 예산](/development/execution.md#타이머이벤트스크립트)).
- 출하 빌드의 확률 고정·무적·임의 상태 주입 같은 테스트 훅은 무인가 사용 경로로 남기지 않는다. 봇·테스트는 실제 명령·게임 규칙을 거친다. 클라이언트 무결성·변조 탐지는 보조 신호이며 서버 검증을 대신하지 않는다.
