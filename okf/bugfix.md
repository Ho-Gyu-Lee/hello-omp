# 버그 수정 원칙

엣지 케이스 하나만 패치하면 다음 케이스에서 이전 수정을 롤백하거나 국소 패치를 또 얹는 수정→롤백→수정 루프가 생긴다. 위반된 불변조건을 고치고 이전·새 케이스를 함께 만족시켜 이를 막는다.

## 증상이 아니라 결함 클래스를 고친다
- 보고된 값이 아니라 그 값이 속한 입력 도메인과 위반된 불변조건을 먼저 규정하고, 같은 원인으로 깨지는 도메인 전체를 근본 위치에서 고친다. 특수값 분기·예외 삼키기·반환값 클램프로 증상만 억누르지 않는다.
- 영향받는 코드(참조·호출·데이터 흐름)를 확인하되 범위는 "연결된 전부"가 아니라 영향받는 범위와 각 계약 경계의 불변조건에서 자른다. `lsp`가 놓치는 연결(리플렉션·DI·문자열 키 디스패치·직렬화·크로스 서비스)은 테스트·런타임 관측으로 보완한다.
- 다른 구현의 수정은 코드 단위로 옮기지 않는다. 그 수정이 막는 결함 클래스를 규정하고 대상 구현의 동시성·수명주기 구조에서 성립하는지 따로 판정하며, 참조 구현에 남은 같은 클래스의 다른 경로도 확인한다. 예: 비동기 task용 연결 세대 검사는 스레드 join 후 큐를 비우는 구조에서는 불필요할 수 있다.

## 이전 수정을 롤백하지 않는다
- 새 엣지 케이스를 통과시키려고 이전 수정을 롤백하지 않는다. 이전 수정이 방어하던 케이스를 먼저 명시하고 이전·새 케이스를 동시에 만족하는 해를 찾는다. 진짜 충돌하면 조용히 덮지 말고 사용자에게 판단을 요청하며 포기한 케이스를 이력에 남긴다.
- 이유가 코드에 드러나지 않는 방어 코드는 바꾸거나 지우기 전에 이력(`git blame`/`git log`, 이전 결정)으로 존재 이유를 확인한다.

## 회귀 방지
- 소비자가 관찰하는 실패·경계·상태 전이를 재현하는 회귀 테스트를 추가하고 이전 수정이 방어하던 사례도 보호한다. 이번 수정 범위에서 소비자 계약이 아닌 문구·소스 텍스트·내부 호출 연결만 고정하는 테스트는 실제 동작 검증으로 바꾼다. 에러 메시지·프로토콜 문자열처럼 문구 자체가 계약인 테스트는 유지하고 무관한 테스트 정리는 끼우지 않는다.
- 영구 테스트가 부적합한 환경은 재현·스모크 증거와 자동 회귀 검증의 한계를 보고하며 단순 `not-throw`로 대체하지 않는다. 증거 기준과 독립 검토 시점은 [워크플로](/workflow.md)를 따르고, 접근이 불확실하거나 같은 지점이 반복 수정되면 fresh context `reviewer`·`security-reviewer`에 독립 평가를 맡긴다.

## YAGNI와의 경계
- YAGNI는 기능 범위에 적용된다. 요청하지 않은 기능·추상화·파일·확장점을 선제적으로 추가하지 않는다.
- 버그 수정 깊이에는 적용되지 않는다. 결함 클래스 전체를 고치고 영향 범위를 확인하고 회귀 테스트를 추가하는 것은 범위 초과가 아니며 "요청 범위만"을 이유로 증상만 패치하지 않는다. 깊이는 결함 클래스와 영향 경계까지이고 그 너머의 리팩토링·기능 개선은 별도 작업이다.
