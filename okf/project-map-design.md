# 목적

지속 프로젝트 지도는 사용자가 코드를 열지 않고 무엇이 어디에 있고, 어디까지 됐고, 무엇이 남았고, 무엇을 정해야 하는지 보려고 여는 화면이다. 에이전트의 작업 일지나 검증 영수증을 읽히는 곳이 아니다. 이 문서는 그 화면의 구성·글·디자인·칸반·시각 자료 기준을 정한다. 유지 선언·근거·신선도·게시 절차와 Archify 삽입 계약은 [프로젝트 지도와 작업 동기화](/project-navigation.md)가 정본이다.

이 기준을 만든 사례(2026-10-16): 한 게임 프로젝트의 유지 지도는 영역마다 첫 부분만 발표 자료 형태였고 그 아래는 작업 기록이었다. 16개 화면에 보이는 글이 약 22.8만 자였고 가장 긴 화면은 최대화 창 13.5개 높이였다. 본문에 커밋 해시가 323번, 시험 건수 표기가 494번, 코드 표기가 약 1,800개 있었고 화면별 문장 평균은 100~240자였다. 상태를 근거와 함께 보이라는 규칙을 화면 문장에 근거를 풀어 쓰라는 뜻으로 받아들이고, 갱신할 때마다 고쳐 쓰지 않고 덧붙인 결과다.

## 읽는 화면과 근거 기록

| 읽는 화면에 둔다 | 근거 기록으로 보낸다 |
|---|---|
| 한 줄 역할, 구현·검증 상태 표지, 남은 일, 정해야 할 것 | 커밋 해시, 세션·산출물 관리용 작업-ID, 명령줄, 시험 건수와 통과 수치 |
| 판단을 바꾸는 수치 하나(단위 포함) | 실행별 수치 목록, 환경 세부, 실패·재시도 이력 |
| 대표 그림·실제 화면, 한 줄 설명, 출처 표지 | 촬영 명령, runner, 스냅샷 hash, 원본 경로 |
| 결정 한 줄과 날짜 | 결정 경위, 검토 라운드, 대안 비교 |

- 근거 기록은 manifest(`sources.json`), 작업 디렉터리의 영수증·로그·원본 캡처, 프로젝트의 설계 문서다. 화면의 항목은 짧은 `근거` 링크 하나로 그 기록에 연결한다.
- 근거를 옮긴다고 경계까지 지우지 않는다. 미검증·재검증 필요·실패·차단·실제 화면 아님은 짧은 표지로 화면에 남긴다. 어떤 근거가 있어야 어떤 표지를 붙이는지는 [프로젝트 지도](/project-navigation.md#관계와-상태를-사실대로-표시)를 따른다.
- 지도의 기준(작업 트리 수동 대조 또는 커밋 근거), snapshot ID, 작성일은 화면 아래쪽이나 근거·신선도 화면에 한 줄로 둔다. 읽는 화면에서 hash 형태 문자열을 두는 곳은 이 한 줄뿐이다.

## 영역 화면: 슬라이드 한 장

영역 하나는 발표 슬라이드 한 장처럼 읽힌다. 최대화한 창의 첫 화면에 다음이 모두 들어온다.

1. 문장형 제목. 메뉴에는 짧은 영역 이름(`세션·동기화`)을, 본문 제목에는 그 영역의 핵심 사실을 말하는 문장 하나를 쓴다. 예: "입력은 클라이언트가 먼저 보여 주고 결과는 서버가 확정합니다." 두 줄을 넘기지 않는다.
2. 상태 표지. 구현·검증·결정 대기를 각각 짧은 말로 쓴다. 예: `구현됨`, `실기기 미검증`, `미관 수락 대기`.
3. 시각 근거. 실제 화면·다이어그램·짧은 영상이 첫 화면의 중심을 차지한다. 게임은 실제 플레이 화면을 먼저 쓴다.
4. 요점. 제목을 뒷받침하는 사실만 내용이 정한 개수만큼(보통 2~4개) 쓴다. 요점 하나는 한 줄, 한 사실이다.
5. 이 영역의 작업. 칸반에서 이 영역의 진행·차단·할 일 카드만 한 줄로 보인다.

스크롤 아래는 상세 자료다. 책임·파일·심볼 목차, 상세 지도, 관련 결정, 근거 링크를 둔다. 목차의 열 구성은 [프로젝트 지도](/project-navigation.md#문서-배치와-하나의-진입점)의 목차 계약을, 글은 아래 「글쓰기」를 따른다.

- 문장형 제목과 시각 근거, 두 줄 이내 제목, 2~4개 목록은 assertion-evidence 슬라이드 구조의 기준이다. 대형 강의의 예비 연구에서 문장형 제목은 단어·구 제목보다 핵심 주장의 기억률을 높였다(15문항 평균 69%→79%, 다른 설계 변경과 효과를 완전히 분리하지는 못함).
- 모든 화면을 같은 틀로 찍어 내지 않는다. 같은 개수·같은 길이의 요점과 같은 여백이 화면마다 반복되면 템플릿으로 보인다. 전체 요약·작업 보드·영역 화면은 역할에 맞게 다르게 구성하고, 영역마다 크게 보여 줄 것 하나(실제 화면·영상, 다이어그램)를 정한다.
- 보여 줄 근거가 없는 영역을 장식 이미지로 채우지 않는다. 그림이 없으면 제목·요점·목차로 구성한다.

## 글쓰기

- 독자는 프로젝트를 아는 개발자지만 작업 세션의 맥락은 모른다. 세션·산출물 관리용 작업-ID, 라운드 이름, 세션 안에서 붙인 별명을 쓰지 않는다. 칸반 카드의 안정된 ID는 예외다.
- 현재 상태를 쓴다. 경위와 "이전에는 ~였다"는 결정 기록이나 근거 기록으로 보낸다.
- 한 문장에 한 사실을 쓴다. 괄호·가운뎃점·쉼표로 사실을 이어 붙이지 않는다.
- 사용자가 알아보는 말로 쓴다. 요점에는 구현 이름 대신 하는 일을 쓰고(`PortraitLoadEscrow::Reap` 대신 "초상 로딩 정리"), 코드 이름은 목차의 `파일 · 심볼` 칸에 둔다.
- 같은 대상은 끝까지 같은 이름으로 부른다. 처음 나오는 약어는 한 번 풀어 쓴다.
- 숫자는 판단을 바꾸는 것만 단위와 함께 쓴다. 예: "세 계정 동시 접속 확인". 실행별 건수는 근거 기록에 둔다.
- 날짜는 결정일, 완료일, 촬영일, 외부 기한에만 붙인다.
- 문체는 그 프로젝트 문서의 기존 문체를 따른다.

AI가 쓴 글에서 흔히 보이는 패턴과 대안이다.

| 패턴 | 예 | 대신 |
|---|---|---|
| 굵은 라벨과 콜론으로 시작하는 목록 | `**연결:** A → B → C` | 라벨 없는 문장. 비교할 속성이 있으면 표 |
| 가운뎃점·괄호로 이은 명사 나열 | "실서버 멀티플레이 · 3지역 · R8 HUD · NPC 의뢰 · 경직 · 타격감(표시 전용)" | 한 문장으로 묶거나 목록으로 나눈다 |
| 부정 병렬과 되풀이되는 단서 | "~이며 ~가 아닙니다", "이력이며 승계하지 않습니다" | 상태 표지 하나 |
| 하지 않은 일과 유지한 것의 나열 | "기존 구조를 유지하면서 ~를 보존했습니다" | 바뀐 것만 쓴다 |
| 의의 부풀리기와 홍보 어조 | "핵심 축으로서 중요한 역할을 합니다", "강력하고 원활한" | 무엇을 하는지 그대로 쓴다 |
| 문장 끝에 붙인 효과 | "~함으로써 일관성을 보장합니다" | 확인한 효과면 사실로 쓰고 아니면 지운다 |
| 습관적인 세 개 묶음 | "빠르고, 안정적이며, 확장 가능한" | 개수는 내용대로 |
| 막연한 연결 | "세션 관리와 연계되어 있습니다" | 호출·소유·발행·읽기/쓰기 중 실제 관계 |
| 내용 없는 제목 | "핵심 요점", "개요", "현황 및 과제", "상세 책임·근거" | 내용이 드러나는 제목. 필요 없으면 제목 없이 |
| 대화체·안내 문장 | "아래는 ~입니다", "참고로" | 지운다 |
| 엠 대시와 화살표 사슬 문장 | "A — B", "A → B → C → D → E" | 문장을 나누고 흐름은 다이어그램으로 |
| 문단 안의 원 번호 | "① ~ ② ~ ③ ~" | 순서가 있으면 번호 목록, 없으면 문장을 나눈다 |
| 장식 이모지·기호 | "✅ 완료", "🚀" | 글자 표지 |

- 이 표는 위키백과 「Signs of AI writing」과 Anthropic frontend-design 스킬의 글쓰기 항목에서 고른 패턴에 실제 사례를 붙인 것이다. 출처 스스로 이 신호가 AI 사용의 증거가 아니며 겉모습만 고치면 탐지만 어려워진다고 경고한다. 목표는 탐지 회피가 아니라 독자가 바로 읽고 판단하게 하는 것이다. 패턴 하나는 우연일 수 있다. 여러 개가 겹치면 무엇을 말할지 정하지 않고 썼다는 신호로 보고 다시 쓴다.
- 영어 단어 목록(delve, robust 등)을 한국어 동의어 금지 목록으로 옮기지 않는다. 출처도 어떤 단어가 과용된다고 그 동의어까지 과용되는 것은 아니라고 적는다. 판단은 단어가 아니라 위 패턴으로 한다.

## 디자인

- **공용 템플릿:** 지도의 화면은 hello-omp `project-map` 스킬의 공용 템플릿으로 만든다. 모든 프로젝트가 같은 배치·외형·글꼴·상태색을 쓰므로 누가 만든 지도든 같은 방식으로 읽힌다. 화면 내용은 스킬이 정한 `src/` 데이터로 쓰고 템플릿이 그리며, 형식은 스킬의 `references/data-format.md`를 따른다. 프로젝트의 색은 사용자가 요청할 때만 `map.config.json`의 `tokens`로 바꾸고, 글꼴은 프로젝트마다 바꾸지 않고 공용 템플릿에서만 바꾼다(아래 글꼴 기준). 배치·상태색의 의미·접기 금지는 바꾸지 않는다. 적용한 템플릿 버전과 바꾼 토큰은 manifest에 남는다. 스킬이 배포되지 않은 환경이면 그 전제를 보고하고 다른 화면을 임의로 만들지 않는다. 프로젝트 지침이 화면 구성을 따로 정하면 공용 템플릿과 다른 점을 사용자에게 알리고 그 지침을 따르되, [프로젝트 지도](/project-navigation.md)의 「관계와 상태를 사실대로 표시」와 「근거와 신선도」의 사실 표시 규칙은 그대로 적용한다.
- **공용 템플릿의 외형을 바꿀 때:** 외형 변경은 스킬의 템플릿에서 하고 모든 지도에 함께 적용한다. 사용자가 UI 키트나 사이트(예: shadcn/ui blocks)를 참고 디자인으로 지정하면 그것이 외형의 근거다. 아래 기본값 목록보다 사용자의 지정이 우선한다. 참고 디자인의 구조·간격·컴포넌트 문법(사이드바와 본문 틀, 배지, 표, 카드의 모양)은 따르되 견본의 기본 토큰을 그대로 두지 않는다. 상태색의 의미와 용어는 유지하고, 견본에 있는 요소(지표 카드, 메뉴 아이콘, 접는 사이드바, 차트)는 지도 내용이 요구할 때만 쓴다. 이 문서의 금지(접기 UI 등)와 충돌하는 견본 동작은 빼고 그 이유를 남긴다. 선택한 참고 디자인과 바꾼 토큰은 템플릿 머리 주석과 변경 기록에 남긴다.
- **외형을 정할 때 시안으로 고르게 한다:** 공용 템플릿의 외형을 크게 바꿀 때는 같은 실제 내용으로 서로 다른 시안 몇 개(레이아웃·작업 보드 형태·색·글꼴)를 만들어 최대화 화면 캡처와 함께 보여 주고 사용자가 고르게 한다. 시안은 시안마다 별도 에이전트가 독립적으로 만들고, 메인이 같은 기준으로 비교한 결과와 추천을 함께 보고한다([여러 안을 만들어 비교할 때](/tools/subagents.md#여러-안을-만들어-비교할-때)). 비교는 외형(색·면 처리·모서리·컴포넌트 모양·글꼴)과 배치(영역의 위치·크기·비율, 첫 화면 구성)를 나눠 적는다. 사용자가 두 축을 서로 다른 시안에서 고르면 배치를 고른 시안을 바탕으로 다른 시안의 토큰과 컴포넌트 처리를 옮기고, 첫 화면 요소의 위치·크기를 측정해 배치가 바뀌지 않았는지 확인한다. 고른 시안만 적용하고, 고르지 않은 시안의 코드는 정본에 남기지 않는다.
- **글꼴:** 공용 템플릿은 본문에 LINE Seed Sans KR(400·700), 코드에 JetBrains Mono(400)를 쓰고, 스킬에 든 공식 배포본 파일과 사용 허가서를 지도의 `fonts/`로 복사한다(사용자 결정 2026-10-16). 코드 속 한글은 LINE Seed로 그려진다. 사용자가 다른 글꼴을 원하면 공용 템플릿의 글꼴을 바꿔 모든 지도에 함께 적용하고 프로젝트마다 다른 글꼴을 두지 않는다. 바꿀 때는 그 글꼴에 없는 굵기를 CSS에서도 실제 있는 굵기로 맞춘다(없는 굵기를 적어 두면 브라우저가 다른 굵기를 고르거나 합성한다). 글꼴 파일을 스킬에 넣기 전에 사용 허가서가 재배포와 웹 사용을 허용하는지 확인하고([UI 재사용·입력과 표시 검증](/development/ui-input.md#텍스트와-배치)의 폰트 라이선스 기준), 허용하지 않거나 확인할 수 없으면 넣지 않고 사용자에게 알린다. 넣으면 공식 배포본 파일을 바이트 그대로 두고 사용 허가서를 옆에 두며 출처와 원시 해시를 스킬의 `assets/fonts/SOURCES.md`에 고쳐 쓴다. 한글이 없는 코드 글꼴에 한글 글꼴을 덧붙일 때는 `unicode-range`로 한글 범위에만 쓰게 한다. Archify 3.0.1 관계도는 JetBrains Mono를 내장하고 글꼴 설정이 없어 한글이 시스템 글꼴로 바뀐다(Windows에서 굴림체 관측, 확인 2026-10-16). 생성된 HTML을 고치면 검증 영수증과 해시가 맞지 않게 되므로 고치지 않고, 이 차이를 사용자에게 알린다.
- 기본값으로 두지 말고 정한다. 아래는 AI가 만든 화면에서 흔한 기본값이며, 공용 템플릿이나 프로젝트 외형을 바꿀 때 사용자가 지정한 디자인이나 프로젝트 디자인에 근거가 있을 때만 쓴다. 하나를 피하려고 다음 기본값(보라 대신 에메랄드, 크림 대신 형광)으로 옮겨 가지 않는다.
  - 색: 보라·남색 그라디언트, 크림 배경과 테라코타 강조, 거의 검은 배경과 형광 강조색 하나, 제목·큰 숫자의 그라디언트, 같은 무게로 나눈 흐린 색 여러 개.
  - 글자: 별도 선택 없이 그대로 쓴 기본 글꼴, 크기 차이가 작은 평평한 위계, 제목마다 붙은 대문자·자간 넓힌 작은 라벨, 순서가 아닌 내용의 `01 / 02 / 03` 번호, 장식용 고정폭 글꼴.
  - 면: 같은 radius·같은 그림자의 카드 묶음, 카드 속 카드, 얇은 테두리와 넓은 그림자를 함께 쓴 카드, 일반 카드의 왼쪽 색 띠, 큰 숫자와 작은 라벨을 늘어놓은 지표 줄.
  - 움직임과 아이콘: 모든 구역의 페이드인, 모든 카드의 hover 효과, 이모지 아이콘, 의미와 무관하게 붙인 범용 아이콘.
- 위계는 크기와 굵기의 대비로 만든다. 제목·요점·보조 글의 세 단계면 충분하고 단계 사이 차이를 분명히 둔다. 글꼴은 공용 템플릿의 서체를 쓴다.
- 색은 역할을 고정한다. 중립색, 강조색 하나, 상태색을 정하고 상태색(통과·주의·실패·차단)은 상태에만 쓴다.
- 구분은 여백으로 한다. 모든 덩어리를 상자로 감싸지 않으며 테두리 처리는 한 가지로 정한다.
- 화면마다 눈에 띄는 요소는 하나다. 보통 실제 화면이나 다이어그램이며 나머지는 조용하게 둔다.
- 움직임은 사용자 동작에 대한 응답과 시연 영상에만 쓴다.

### 화면 구조

- **데스크톱 최대화 화면 전용:** 사용자는 데스크톱 브라우저를 최대화해 지도를 본다. 그 화면 하나를 기준으로 설계·검증하며 모바일·태블릿·좁은 창을 위한 반응형 레이아웃, 해상도별 분기와 검증, 창 크기 변경 대응은 만들지 않는다. 최대화한 실제 브라우저 창에서 잘림·겹침·과도한 빈 공간이 없는지로 확인한다.
- 기본 구조는 좌측 메뉴에 프로젝트의 실제 책임 영역, 본문에 선택한 영역 하나다. 상단 프로젝트명·검색·동작을 두고 오른쪽 사이드바나 모든 문서의 동시 출력을 기본으로 만들지 않는다. 영역은 프로젝트의 실제 구성대로 나누며 Overview/Planning/Development/Release/Decisions/Archive는 분류 예시다. 없는 Backend/Client 등을 억지로 만들지 않는다.
- 메뉴는 전체 요약, 작업 보드, 책임 영역, 검증·결정·근거 순서를 기본으로 한다. 전체 요약의 첫 화면에는 프로젝트를 한 문장으로 말하는 제목, 대표 화면, 정해야 할 것과 진행 중인 작업, 최근 변경 몇 줄을 둔다.
- 본문·메뉴에 펼치기/숨기기·접기 UI를 두지 않는다. 불필요한 내용은 삭제하고 필요한 역할·상태·근거·실패/차단 정보는 짧게 표시한다. 좌측 메뉴로 문서 한 항목을 선택하는 탐색과 내용 접기는 구분한다.

## 칸반 보드

진행 상황과 할 일은 칸반 보드로 보여 준다. 계획 항목의 의미(확정과 제안의 구분, 안정된 ID, 의존성·완료 기준, 계획 등록은 실행 승인이 아님)는 [프로젝트 지도](/project-navigation.md#할-일과-계획도-같은-화면에서-확인)가 정본이고, 이 절은 그것을 화면에 놓는 방법이다.

- 메뉴의 `작업 보드` 화면 하나가 전체 보드다. 전체 요약에는 정해야 할 카드와 진행 중인 카드를, 영역 화면에는 그 영역의 카드를 같은 계획 데이터에서 그린다. 같은 카드를 여러 곳에 복사해 쓰지 않는다.

| 열 | 들어오는 조건 | 나가는 조건 |
|---|---|---|
| 검토할 제안 | 근거(사용자 언급, 확인된 결함, 검증 공백)는 있으나 사용자가 요청·승인하지 않은 항목, 사용자가 보류한 항목 | 채택하면 할 일로, 기각하면 결정 기록으로 |
| 할 일 | 사용자가 보류하지 않은 항목 중 사용자가 요청·승인했거나 확정 계획에 있는 항목, 이미 승인된 작업 범위 안에서 확인된 결함. 완료 기준이 정해짐 | 작업을 시작하면 진행 중으로 |
| 진행 중 | 코드·데이터·문서 변경이 시작됨 | 완료 기준 검증이 통과하면 완료로, 막히면 차단·결정 대기로 |
| 차단·결정 대기 | 사용자 결정·수락, 환경·권한, 선행 작업 때문에 진행할 수 없음. 사유 필수 | 사유가 풀리면 원래 열로 |
| 완료 | 완료 기준을 확인한 근거가 근거 기록에 있음. 부분 검증은 완료가 아님 | 오래된 카드는 완료 기록 목록으로 |

- 열은 [프로젝트 지도](/project-navigation.md#할-일과-계획도-같은-화면에서-확인)의 상태 어휘에 맞춘다. 할 일은 `미착수`, 진행 중은 `진행`, 차단·결정 대기는 `차단`, 완료는 `완료`이며 검토할 제안은 확정 전 항목이다.
- 카드에는 ID, 한 줄 제목(사용자에게 생기는 변화나 고칠 결함), 영역, 검증 상태, 완료 기준 한 줄, 근거 링크를 둔다. 차단 카드에는 사유를, 결정 대기 카드에는 정해야 할 질문을 한 줄로 둔다. 날짜는 완료일과 외부 기한(인증서 만료 등)에만 쓴다.
- 진척은 열마다 카드 수로만 보인다. 백분율·진행 막대·예상 완료일·소요 기간은 쓰지 않는다.
- 완료 열에는 최근 완료한 카드 몇 개(기본 5개 안팎)만 카드로 두고 나머지는 같은 열 아래 한 줄 목록이나 완료 기록 화면으로 보낸다.
- 카드를 고르면 그 작업의 상세(완료 기준·의존성·관련 영역·근거)로 이동한다. 탐색이며 펼치기 UI가 아니다.
- 외형: 열은 이름과 카드 수만 가진 세로 목록이고 카드는 한 가지 테두리 처리를 쓴다. 강조색과 왼쪽 띠는 차단 카드에만 쓴다. 정적 스냅샷이므로 드래그·애니메이션을 두지 않는다.
- 작업 항목, 시작과 끝, 상태, 명시 정책을 보드에 드러내고 막힌 작업을 보이게 하는 것은 Kanban Guide의 작업 흐름 정의(Definition of Workflow)에서 가져왔다. 이 보드는 그중 시각화만 빌린다. 지도는 정적 스냅샷이고 일정을 예측하지 않으므로 WIP 제어, 서비스 수준 기대치(SLE), 흐름 지표는 쓰지 않는다.

## 시각 자료: 다이어그램·스크린샷·GIF·영상

- **고르는 기준:** 관계·흐름은 다이어그램(Archify), 화면·UI·레벨 배치는 스크린샷, 움직임·조작감·애니메이션·이펙트·전투 흐름처럼 정지 화면으로 전달되지 않는 것은 짧은 GIF·영상으로 보여 준다. 게임 프로젝트는 영역마다 실제 게임 화면을 우선한다.
- **사실 표시:** 화면에는 무엇을 보여 주는지 한 줄 설명, 출처 표지(실제 실행 화면, 목업, 컨셉 아트, 레퍼런스, 생성 이미지), 촬영일, 재촬영 필요 여부와 그 자료의 `근거` 링크만 둔다. 촬영 커밋·스냅샷·빌드 식별자·씬·실행 명령·원본 경로는 manifest의 시각 자료 항목에 기록한다([프로젝트 지도](/project-navigation.md#문서-배치와-하나의-진입점)의 `sources.json`). 문서화를 위해 커밋을 만들지 않는다. 목업이나 다른 게임의 화면을 현재 구현처럼 보이게 하지 않는다. 시각 자료도 스냅샷이다. 해당 영역의 코드·에셋이 바뀌면 다시 촬영하거나 `재촬영 필요`로 표시하며, 옛 캡처를 현재 동작의 증거로 쓰지 않는다.
- **게임 화면 촬영:** 실제 플레이와 실시간 동작을 보여 줄 때는 OS·외부 화면 녹화 도구(예: OBS Studio)로 찍는다. Godot Movie Maker(`--write-movie`·`--fixed-fps`·`--quit-after`)는 비실시간 offline 렌더라 출력의 프레임 간격이 항상 완벽하므로 연출·애니메이션 시연에는 쓰되 끊김·성능의 증거로 쓰지 않는다. 출력 형식 중 OGV는 편집기 빌드에서만 기록되고 웹 브라우저에서 재생되지 않으며, AVI(MJPEG)·PNG 시퀀스+WAV도 브라우저에 보이려면 MP4(H.264)나 WebM으로 변환한다([Godot 4.7 Creating movies](https://docs.godotengine.org/en/4.7/tutorials/animation/creating_movies.html), 확인 2026-10-15). 웹 UI는 실제 브라우저에서 캡처한다. 녹화·변환 도구(FFmpeg 등)가 없으면 설치하지 않고 없는 전제를 보고한다. 설치는 별도 승인 대상이다.
- **재생 방식:** 몇 초 안에 반복되는 동작은 GIF나 음소거 반복 영상(`<video autoplay muted loop>`)으로 바로 보이게 한다. 소리가 필요하거나 긴 시연은 `poster`를 둔 영상으로 두어 사용자가 재생한다. 음소거됐거나 오디오 트랙이 없는 영상은 일반적으로 자동 재생되지만 브라우저·사용자 설정에 따라 막힐 수 있으므로([MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay), 확인 2026-10-15) 짧은 반복 영상에도 `controls`나 명시적인 재생 버튼을 둔다. 지도는 로컬 파일로도 열리므로 자료는 진입점 기준 상대 경로로 넣고, 선택되지 않은 영역의 영상은 재생하지 않는다.
- **저장과 크기:** 게시본은 선언한 지도 경로의 `media/` 아래에 두고, 필요한 구간만 자르고 해상도·프레임 수를 줄여 크기를 관리한다. GitHub는 50 MiB를 넘는 파일에 경고하고 100 MiB를 넘는 파일을 막으며 저장소는 1 GB 미만을 권장한다([GitHub 대용량 파일 문서](https://docs.github.com/en/repositories/working-with-files/managing-large-files/about-large-files-on-github), 확인 2026-10-15). 큰 영상을 Git LFS·릴리스·외부 저장소 중 어디에 둘지는 사용자가 정하며, 임의로 LFS를 도입하거나 외부에 올리지 않는다.
- **공개 범위:** 캡처에 자격증명·내부 접속 정보·개인정보·운영 계정 정보가 나오지 않는지 게시 전에 확인한다. 구매 에셋·서드파티 화면이 들어간 자료는 저장소를 외부에 공개하기 전에 라이선스를 확인한다([공통 에셋·에디터 기준](/development/assets-editor.md#반입권리와-조립)의 에셋 사용 권리).

## 갱신할 때

- 고쳐 쓴다. 상태가 바뀌면 해당 제목·표지·요점·카드를 현재 사실로 바꾼다. 날짜별 작업 일지(예: "2026-10-16 후속 · …")를 본문에 쌓지 않는다.
- 변경 기록은 전체 요약의 최근 변경에 사용자 관점의 한 줄(날짜, 무엇이 바뀌었나)로 남긴다. 화면에는 최근 몇 줄만 두고 이전 기록과 검증 경위는 결정 기록이나 manifest로 보낸다.
- 카드는 열을 옮기고 근거 링크를 바꾼다. 같은 목표를 새 ID로 만들지 않는다.
- 작은 변경이어도 바뀐 영역의 첫 화면을 다시 읽어 제목이 여전히 사실인지 확인한다.
- 화면 내용은 구조화 데이터다. 영역별 제목·상태·요점·시각 자료·목차, 카드, 결정은 스킬의 `src/` 데이터이고 공용 템플릿이 그리므로 갱신은 필드 교체가 되어 문단이 쌓이지 않는다. 화면에 그리지 않는 메모·근거 수치는 `src/`에 두지 않고 작업 디렉터리나 manifest에 둔다.

## 게시 전 점검

[프로젝트 지도](/project-navigation.md#작업갱신게시-절차)의 검증 단계에서 함께 확인한다. 기계로 판정할 수 있는 항목은 스크립트로 검사한다.

1. 최대화한 실제 브라우저에서 영역마다 첫 화면에 제목·상태·요점이 스크롤 없이 보이고, 시각 자료가 있는 영역은 그 자료가 첫 화면에서 시작한다.
2. 제목은 문장이고 두 줄 이내다. 요점은 한 줄씩이고 첫 화면에 세 줄이 넘는 문단이 없다.
3. 읽는 화면에 커밋 해시, 세션·산출물 관리용 작업-ID, 명령줄, 시험 건수 목록, SHA-256이 없다(기준·snapshot 한 줄 제외). 정규식으로 검사하고 일부러 넣은 해시를 잡는지 한 번 확인한다.
4. 스크롤 아래 상세 자료에도 경위 설명과 작업 기록 문단이 없다. 날짜·해시가 없는 경위 문장도 같다.
5. 같은 대상을 다른 이름으로 부르지 않는다.
6. 모든 카드에 ID·열·완료 기준이 있고 차단·결정 대기 카드에 사유나 질문이 있다. 백분율과 예상 일정이 없다.
7. 상태색이 상태 밖에 쓰이지 않았고, 프로젝트 디자인에 근거가 없는 그라디언트·그림자·글로우·이모지가 없다.
8. 프로젝트 맥락이 없는 fresh-context 검토자에게 전체 요약과 영역 몇 곳의 첫 화면 캡처, 그 영역들의 스크롤 아래 본문을 주고 프로젝트가 무엇인지, 어디까지 됐는지, 다음에 무엇을 하는지, 무엇을 정해야 하는지 말하게 한다. 답이 지도의 의도와 다르거나 아래 본문이 작업 기록처럼 읽히면 그 화면을 고친다.

## 근거

확인 2026-10-16.

- Alley·Schreiber·Ramsdell·Muffo, [How the Design of Headlines in Presentation Slides Affects Audience Retention](https://www.writing.engr.psu.edu/alley_et_al_2006.pdf), Technical Communication 53(2), 2006: 두 줄 이내 문장형 제목의 기억률 69%→79%(유의수준 .001에서 유의한 차이). 저자도 다른 설계 변경의 효과와 완전히 분리하려면 추가 시험이 필요하다고 밝힌 예비 연구다.
- Penn State, [Checklist for Assertion–Evidence Slides](http://www.writing.engr.psu.edu/AE_checklist.pdf): 왼쪽 정렬한 두 줄 이내 문장형 제목, 목록 대신 시각 근거, 목록은 2~4개, 전부 대문자 금지.
- [Wikipedia: Signs of AI writing](https://en.wikipedia.org/wiki/Wikipedia:Signs_of_AI_writing): 굵은 글씨 남용, 인라인 헤더 목록, 부정 병렬, 3의 법칙, 피상적 분석, 홍보 어조, 막연한 연결, 편집 요약의 절차 서술, 엠 대시. 목록이 규칙이 아니라 관찰이며 신호만 고치면 탐지만 어려워진다는 경고, 단어의 동의어까지 과용되는 것은 아니라는 단서도 같은 문서에 있다.
- Anthropic, [frontend-design 스킬](https://github.com/anthropics/skills/blob/main/skills/frontend-design/SKILL.md)과 [소개 글](https://claude.com/blog/improving-frontend-design-through-skills)(2025-11-12): 생성 페이지의 흔한 기본값(크림 배경과 테라코타, 거의 검은 배경과 강조색 하나, 같은 카드·radius·그림자, 대문자 라벨, 가운뎃점 메타 문자열, 순서가 아닌 번호, 큰 숫자 지표, 페이드인)과 강조를 한 곳에 쓰라는 권고. 계속 바뀌는 문서다.
- [Signs of AI design](https://github.com/febbhav/signs-of-ai-design)과 [design-rules](https://github.com/febbhav/signs-of-ai-design/blob/main/design-rules.md): 왼쪽 색 띠는 의미 있는 경고에만, 카드 속 카드, 테두리와 그림자를 함께 쓴 카드, 획일적인 슬라이드 문법, 하나를 금지하면 다음 기본값으로 옮겨 간다는 관찰.
- [The Kanban Guide](https://kanbanguides.org/the-kanban-guide/) v2025.5: 작업 흐름 정의의 구성 요소(작업 항목, 시작과 끝, 상태, WIP 제어, 명시 정책, SLE), 보드는 그 정의의 시각화라는 설명, 막힌 작업의 해소.
