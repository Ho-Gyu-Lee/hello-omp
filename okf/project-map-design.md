# 목적

지속 프로젝트 지도는 사용자가 코드를 열지 않고 무엇이 어디에 있고, 어디까지 됐고, 무엇이 남았고, 무엇을 정해야 하는지 보는 화면이다. 에이전트의 작업 일지나 검증 영수증을 읽히는 곳이 아니다. 유지 선언·근거·신선도·게시 절차와 Archify 삽입 계약은 [프로젝트 지도와 작업 동기화](/project-navigation.md)가 정본이다.

## 읽는 화면과 근거 기록

| 읽는 화면에 둔다 | 근거 기록으로 보낸다 |
|---|---|
| 한 줄 역할, 상태 표지, 남은 일, 정해야 할 것 | 커밋 해시, 작업-ID, 명령줄, 시험 건수 |
| 판단을 바꾸는 수치 하나(단위 포함) | 실행별 수치, 환경 세부, 실패·재시도 이력 |
| 대표 그림·실제 화면, 한 줄 설명, 출처 표지 | 촬영 명령, runner, 스냅샷 hash, 원본 경로 |
| 결정 한 줄과 날짜 | 결정 경위, 검토 라운드, 대안 비교 |

- 근거 기록은 manifest(`sources.json`), 작업 디렉터리의 영수증·로그·원본 캡처, 프로젝트 설계 문서다. 화면 항목은 짧은 `근거` 링크 하나로 연결한다.
- 근거를 옮겨도 미검증·재검증 필요·실패·차단·실제 화면 아님은 짧은 표지로 남긴다([프로젝트 지도](/project-navigation.md#관계와-상태를-사실대로-표시)). 지도의 기준(작업 트리 수동 대조/커밋 근거)·snapshot ID·작성일은 화면 아래쪽이나 근거·신선도 화면에 한 줄로만 둔다. 읽는 화면에서 hash 형태 문자열을 두는 곳은 이 한 줄뿐이다.

## 영역 화면: 슬라이드 한 장

영역 하나는 발표 슬라이드 한 장처럼 읽힌다. 최대화한 창의 첫 화면에 다음이 모두 들어온다.

1. 문장형 제목: 메뉴에는 짧은 영역 이름을, 본문에는 핵심 사실을 말하는 두 줄 이내 문장을 쓴다.
2. 상태 표지: 구현·검증·결정 대기를 짧은 말로 쓴다(`구현됨`, `실기기 미검증`, `미관 수락 대기`).
3. 시각 근거: 실제 화면·다이어그램·짧은 영상이 첫 화면의 중심이다. 게임은 실제 플레이 화면을 먼저 쓴다.
4. 요점: 제목을 뒷받침하는 사실만 보통 2~4개, 한 줄에 한 사실씩 쓴다.
5. 이 영역의 작업: 칸반의 이 영역 카드만 한 줄로 보인다.

스크롤 아래는 상세 자료(책임·파일·심볼 목차, 상세 지도, 관련 결정, 근거 링크)다. 모든 화면을 같은 틀로 찍지 않는다. 같은 개수·길이의 요점과 여백이 반복되면 템플릿으로 보이므로 화면 역할에 맞게 구성하고 영역마다 크게 보여 줄 것 하나를 정한다. 보여 줄 근거가 없으면 장식 이미지로 채우지 않는다.

## 글쓰기

- 독자는 프로젝트를 아는 개발자지만 작업 세션 맥락은 모른다. 작업-ID·라운드 이름·세션 별명(칸반 카드 ID는 예외)을 쓰지 않고, 현재 상태를 쓰며 경위는 결정 기록·근거 기록으로 보낸다.
- 요점에는 구현 이름 대신 하는 일을 쓰고 코드 이름은 목차의 `파일 · 심볼` 칸에 둔다. 숫자는 판단을 바꾸는 것만 단위와 함께, 날짜는 결정일·완료일·촬영일·외부 기한에만 쓴다. 문체는 프로젝트 문서의 기존 문체를 따른다.
- AI 글처럼 보이는 패턴을 피한다. 기계로 잡히는 것은 스킬 `references/data-format.md`의 「금지 패턴」이 막고, 나머지는 직접 피한다: 의의 부풀리기·홍보 어조, 문장 끝에 붙인 효과("~함으로써 일관성을 보장합니다"), 하지 않은 일·유지한 것의 나열, 막연한 연결(호출·소유·발행·읽기/쓰기 중 실제 관계로 쓴다), 내용 없는 제목("개요"). 여러 개가 겹치면 다시 쓰고 영어 과용어 목록을 한국어 동의어 금지 목록으로 옮기지 않는다.

## 디자인

- **공용 템플릿:** hello-omp `project-map` 스킬의 공용 템플릿으로 만든다. 배치·외형·글꼴·상태색 의미·접기 금지는 모든 프로젝트가 같고 프로젝트의 색만 사용자가 요청할 때 `map.config.json`의 `tokens`로 바꾼다. 내용은 스킬의 `src/` 데이터(`references/data-format.md`)로 쓰며 적용한 템플릿 버전·토큰은 manifest에 남는다. 스킬이 없으면 그 전제를 보고하고 다른 화면을 임의로 만들지 않는다. 프로젝트 지침이 화면 구성을 따로 정하면 다른 점을 알리고 따르되 [프로젝트 지도](/project-navigation.md)의 사실 표시 규칙(「관계와 상태를 사실대로 표시」·「근거와 신선도」)은 유지한다.
- **외형 변경:** 스킬의 템플릿에서 모든 지도에 함께 바꾼다. 사용자가 참고 디자인(예: shadcn/ui blocks)을 지정하면 그것이 외형의 근거이며 아래 AI 기본값 목록보다 우선한다. 구조·간격·컴포넌트 문법은 따르되 견본의 기본 토큰은 그대로 두지 않고, 상태색 의미·용어와 이 문서의 금지(접기 UI 등)는 유지하며 견본 요소(지표 카드·메뉴 아이콘·차트)는 내용이 요구할 때만 쓴다. 참고 디자인·바꾼 토큰은 템플릿 머리 주석에 남긴다.
- **크게 바꿀 때:** 에이전트가 근거(참조 측정·기존 결정)로 한 안을 정해 전후 최대화 화면 캡처로 보이고 수락만 받는다.
- **글꼴:** 본문 LINE Seed Sans KR(400·700), 코드 JetBrains Mono(400)이며 스킬의 공식 배포본과 사용 허가서를 지도의 `fonts/`로 복사한다(사용자 결정 2026-10-16). 다른 글꼴은 공용 템플릿에서 바꿔 모든 지도에 적용하며, 새 글꼴은 사용 허가서가 재배포·웹 사용을 허용하는지 먼저 확인하고 허용하지 않거나 확인할 수 없으면 넣지 않고 알린다. 공식 배포본은 바이트 그대로 두고 허가서를 옆에 두며 출처·해시를 스킬의 `assets/fonts/SOURCES.md`에 고쳐 쓴다. Archify 3.0.1 관계도는 JetBrains Mono를 내장하고 글꼴 설정이 없어 한글이 시스템 글꼴로 바뀐다(Windows에서 굴림체 관측, 확인 2026-10-16). 생성 HTML을 고치면 영수증과 해시가 어긋나므로 고치지 않고 이 차이를 알린다.
- **AI 기본값 회피:** 사용자 지정이나 프로젝트 디자인 근거가 있을 때만 쓴다. 하나를 피하려고 다음 기본값(보라 대신 에메랄드, 크림 대신 형광)으로 옮겨 가지 않는다. 보라·남색 그라디언트, 크림 배경+테라코타 강조, 거의 검은 배경+형광 강조색, 제목·큰 숫자의 그라디언트, 평평한 위계, 제목마다 붙은 대문자·자간 넓힌 라벨, 순서 아닌 `01 / 02 / 03`, 같은 radius·그림자의 카드 묶음, 카드 속 카드, 일반 카드의 왼쪽 색 띠, 큰 숫자+작은 라벨 지표 줄, 모든 구역 페이드인·모든 카드 hover, 이모지·범용 아이콘.
- 상태색(통과·주의·실패·차단)은 상태에만 쓴다. 화면마다 눈에 띄는 요소는 하나(보통 실제 화면·다이어그램)이고 움직임은 사용자 동작의 응답과 시연 영상에만 쓴다.

### 화면 구조

- **데스크톱 최대화 화면 전용:** 모바일·태블릿·좁은 창을 위한 반응형 레이아웃, 해상도별 분기·검증, 창 크기 변경 대응은 만들지 않는다. 최대화한 실제 브라우저에서 잘림·겹침·과도한 빈 공간이 없는지 확인한다.
- 좌측 메뉴(프로젝트의 실제 책임 영역, 없는 Backend/Client 등을 만들지 않는다)와 선택한 영역 하나의 본문, 상단 프로젝트명·검색·동작이 기본이며 오른쪽 사이드바와 모든 문서의 동시 출력은 만들지 않는다. 메뉴 순서는 전체 요약, 작업 보드, 책임 영역, 검증·결정·근거이고, 전체 요약의 첫 화면에는 프로젝트를 한 문장으로 말하는 제목, 대표 화면, 정해야 할 것과 진행 중인 작업, 최근 변경 몇 줄을 둔다.
- 본문·메뉴에 펼치기/숨기기·접기 UI를 두지 않는다. 불필요한 내용은 삭제하고 필요한 역할·상태·근거·실패/차단 정보는 짧게 표시한다(메뉴로 문서 한 항목을 고르는 탐색은 접기가 아니다).

## 칸반 보드

진행 상황과 할 일은 칸반 보드로 보여 준다. 계획 항목의 의미(확정·제안, 안정된 ID, 의존성·완료 기준, 등록≠실행 승인)는 [프로젝트 지도](/project-navigation.md#할-일과-계획도-같은-화면에서-확인)가 정본이고 이 절은 화면 배치다. 메뉴의 `작업 보드` 하나가 전체 보드이며 전체 요약·영역 화면의 카드는 같은 계획 데이터에서 그린다.

| 열 (상태) | 들어오는 조건 | 나가는 조건 |
|---|---|---|
| 검토할 제안 (확정 전) | 근거(사용자 언급, 확인된 결함, 검증 공백)는 있으나 사용자가 요청·승인하지 않았거나 보류한 항목 | 채택하면 할 일로, 기각하면 결정 기록으로 |
| 할 일 (`미착수`) | 보류하지 않은 항목 중 요청·승인했거나 확정 계획에 있는 항목, 승인된 범위 안에서 확인된 결함. 완료 기준이 정해짐 | 시작하면 진행 중으로 |
| 진행 중 (`진행`) | 코드·데이터·문서 변경이 시작됨 | 완료 기준 검증 통과 시 완료로, 막히면 차단으로 |
| 차단·결정 대기 (`차단`) | 사용자 결정·수락, 환경·권한, 선행 작업 때문에 진행 불가. 사유 필수 | 사유가 풀리면 원래 열로 |
| 완료 (`완료`) | 완료 기준을 확인한 근거가 근거 기록에 있음. 부분 검증은 완료가 아님 | 오래된 카드는 완료 기록 목록으로 |

- 카드에는 ID, 한 줄 제목(사용자에게 생기는 변화나 고칠 결함), 영역, 검증 상태, 완료 기준 한 줄, 근거 링크를 둔다. 차단 카드에는 사유를, 결정 대기 카드에는 정해야 할 질문을 한 줄로 둔다. 날짜는 완료일·외부 기한에만 쓴다.
- 진척은 열마다 카드 수로만 보인다. 백분율·진행 막대·예상 완료일과 WIP 제어·서비스 수준 기대치·흐름 지표는 쓰지 않는다(정적 스냅샷, 일정 예측 없음). 작업 항목·상태·명시 정책·막힌 작업의 가시화만 [Kanban Guide](https://kanbanguides.org/the-kanban-guide/) v2025.5의 작업 흐름 정의에서 빌렸다.
- 완료 열에는 최근 몇 개(기본 5개 안팎)만 카드로 두고 나머지는 한 줄 목록이나 완료 기록 화면으로 보낸다. 카드를 고르면 상세로 이동한다(탐색이지 펼치기가 아니다). 열은 이름과 카드 수만 가진 세로 목록, 카드는 한 가지 테두리 처리이며 강조색·왼쪽 띠는 차단 카드에만 쓴다. 드래그·애니메이션은 두지 않는다.

## 시각 자료: 다이어그램·스크린샷·GIF·영상

- **고르는 기준:** 관계·흐름은 다이어그램(Archify), 화면·UI·레벨 배치는 스크린샷, 움직임·조작감·이펙트·전투 흐름처럼 정지 화면으로 전달되지 않는 것은 짧은 GIF·영상. 게임은 영역마다 실제 게임 화면을 우선한다.
- **사실 표시:** 화면에는 한 줄 설명, 출처 표지(실제 실행 화면·목업·컨셉 아트·레퍼런스·생성 이미지), 촬영일, 재촬영 필요 여부, `근거` 링크만 둔다. 촬영 커밋·스냅샷·빌드·씬·명령·원본 경로는 manifest에 기록하며 문서화를 위해 커밋을 만들지 않는다. 시각 자료도 스냅샷이므로 코드·에셋이 바뀌면 다시 촬영하거나 `재촬영 필요`로 표시하고, 옛 캡처를 현재 동작의 증거로 쓰거나 목업·다른 게임 화면을 현재 구현처럼 보이게 하지 않는다.
- **게임 화면 촬영:** 실제 플레이·실시간 동작은 OS·외부 도구(예: OBS Studio)로 찍는다. Godot 4.7 Movie Maker(`--write-movie`)는 비실시간 offline 렌더라 프레임 간격이 항상 완벽하므로 연출 시연에만 쓰고 끊김·성능 증거로 쓰지 않는다. OGV는 편집기 빌드에서만 기록되고 브라우저에서 재생되지 않으며 AVI(MJPEG)·PNG 시퀀스+WAV도 MP4(H.264)나 WebM으로 변환해야 브라우저에 보인다([Creating movies](https://docs.godotengine.org/en/4.7/tutorials/animation/creating_movies.html), 확인 2026-10-15). 녹화·변환 도구(FFmpeg 등)가 없으면 설치하지 않고 전제를 보고한다.
- **재생·저장:** 짧은 반복 동작은 GIF나 음소거 반복 영상, 소리가 필요하거나 긴 시연은 `poster`를 둔 영상으로 두며 자동 재생이 막힐 수 있으므로 재생 막대를 함께 둔다([MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay), 확인 2026-10-15). 큰 영상의 저장 위치(Git LFS·릴리스·외부 저장소)는 사용자가 정하며 임의로 LFS를 도입하거나 올리지 않는다. 캡처에 자격증명·개인정보가 없는지 확인하고 서드파티 화면·구매 에셋은 공개 전에 [에셋 사용 권리](/development/assets-editor.md#에셋의-ai-사용-권리)를 확인한다.

## 갱신할 때

- 고쳐 쓴다. 상태가 바뀌면 제목·표지·요점·카드를 현재 사실로 바꾸고 날짜별 작업 일지를 본문에 쌓지 않는다. 변경 기록은 전체 요약의 최근 변경에 사용자 관점 한 줄(날짜, 무엇이 바뀌었나)만 남기고 이전 기록·검증 경위는 결정 기록이나 manifest로 보낸다.
- 카드는 열을 옮기고 근거 링크를 바꾸며 같은 목표를 새 ID로 만들지 않는다. 작은 변경도 바뀐 영역의 첫 화면을 다시 읽어 제목이 여전히 사실인지 확인한다.

## 게시 전 점검

[프로젝트 지도](/project-navigation.md#작업갱신게시-절차)의 검증 단계에서 함께 확인한다. 기계로 판정할 수 있는 항목은 스크립트로 검사하며, build가 막는 항목(글자 수 한도, 금지 패턴, 카드 필수 필드)은 다시 확인하지 않는다.

1. 최대화한 실제 브라우저에서 영역마다 첫 화면에 제목·상태·요점이 스크롤 없이 보이고, 시각 자료가 있는 영역은 그 자료가 첫 화면에서 시작한다.
2. 제목은 문장이고 첫 화면에 세 줄이 넘는 문단이 없다.
3. 읽는 화면에 커밋 해시, 작업-ID, 명령줄, 시험 건수 목록, SHA-256이 없다(기준·snapshot 한 줄 제외). 정규식으로 검사한다.
4. 스크롤 아래 상세 자료에도 경위 설명과 작업 기록 문단이 없다(날짜·해시가 없는 경위 문장 포함).
5. 같은 대상을 다른 이름으로 부르지 않는다.
6. 카드에 백분율과 예상 일정이 없다.
7. 상태색이 상태 밖에 쓰이지 않았고 프로젝트 디자인에 근거가 없는 그라디언트·그림자·글로우·이모지가 없다.
8. 새 지도를 처음 게시하거나 화면 구조를 크게 바꿀 때만, 프로젝트 맥락이 없는 fresh-context 검토자에게 전체 요약과 영역 몇 곳의 첫 화면 캡처, 그 영역들의 스크롤 아래 본문을 주고 프로젝트가 무엇인지, 어디까지 됐는지, 다음에 무엇을 하는지, 무엇을 정해야 하는지 말하게 한다. 답이 지도의 의도와 다르거나 아래 본문이 작업 기록처럼 읽히면 그 화면을 고친다.
