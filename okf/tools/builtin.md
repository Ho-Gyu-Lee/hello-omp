# omp 기본 도구

omp는 배터리 포함 — 코딩 워크플로 대부분이 내장 도구로 처리된다. 기본으로 되는 일에 MCP를 두지 않는다.

## 코드 분석/탐색
- 현재 세션에 노출된 도구와 해당 호출 문서를 우선한다. 문서에 이름이 있다는 사실만으로 활성화·호출 가능성을 가정하지 않는다.
- `lsp` — 심볼·정의·참조·리네임·코드 액션·진단. 가용하면 코드 인텔리전스에 우선 사용하고 텍스트 검색으로 의미 분석을 대신하지 않는다.
- `ast_grep` — 노출된 경우 구조 검색. `ast_edit` — 노출된 경우 구조적 치환. OMP 18.10.0·18.11.0 기준 `astGrep.enabled` 기본값은 `false`, `astEdit.enabled` 기본값은 `true`다(`omp://tools/ast-grep.md`·설치본 `src/tools/settings.ts`, 확인: 2026-10-12, 18.11.0 재확인: 2026-10-15. 18.3.2 문서도 `astGrep.enabled=false`를 명시했다). 세션의 실제 노출 목록이 우선이며 사용을 전제로 설정을 임의 활성화하지 않는다.
- `grep` / `glob` — 내용·파일 검색(.gitignore 존중), `read` — 필요한 범위 읽기. 의미 분석·구조 검색을 쓸 수 없으면 검색의 한계를 밝히고 실제 코드·런타임으로 보완한다.
- `grep`의 `dir/*.ts`는 해당 디렉터리 바로 아래, `dir/**/*.ts`는 하위 디렉터리 포함이고 디렉터리 접두가 없는 `*.ts`만 모든 깊이에서 매칭된다. [OMP 18.3.2](https://github.com/can1357/oh-my-pi/releases/tag/v18.3.2)의 `dir/*.go` 정정과 [OMP 변경 내역](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/CHANGELOG.md) 18.4.1의 접두 없는 glob만 전 깊이 매칭 정정에 맞춰 전수 탐색 의도와 범위를 일치시킨다.

## 웹·문서
- `web_search` — 내장 일반 웹 검색. `web` 모델 역할의 폴백 체인으로 실행되며 기본 체인은 키 없는 경로를 포함하지만 과금이 없다는 보장은 아니다(`omp://tools/web_search.md`, OMP 18.10.0 확인: 2026-10-12, 18.11.0 재확인: 2026-10-15). xAI 자격증명이 있으면 같은 도구가 X 게시물 검색(`site:x.com`·`from:<handle>`)도 처리한다. 뉴스·영상·이미지·장소 수직 검색 모드는 없으므로 이때만 검색 MCP의 해당 도구를 쓴다(근거와 도구 목록의 정본은 [MCP 정책](/tools/mcp.md)).
- `read` — URL·문서·내부 URI 읽기.

## 라이브러리/API 조사
- `read`로 공식 문서·소스를 직접 확인하고 `web_search`로 보강한다. 넓은 읽기 전용 조사는 현재 제공되는 `scout`에 위임한다. 제공되지 않은 에이전트 이름을 가정하지 않는다([에이전트 가이드](/agents/guide.md)).

## 실행·디버깅·자동화
- `bash` — 기존 CLI·프로젝트 명령 실행. `eval` — 파일이 필요 없는 계산·변환·자동화는 `language: "js"`로 Bun에서 실행한다.
- 상태가 유지되는 `eval`/REPL에서 소스를 갱신한 뒤, 같은 파일 경로의 이전 객체와 새 모듈 함수를 섞지 않는다. 모듈 내부 `WeakMap`에 등록한 lease·capability나 클래스 identity는 해당 모듈 인스턴스의 계약이다([객체 identity와 WeakMap](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/WeakMap#key_equality)). 생성자·검증자 함수가 같은 인스턴스인지 대조하고, 실제 프로그램 검증은 새 프로세스의 정식 진입점에서 실행한다. 잘못 섞은 객체를 받아주도록 제품 검증을 완화하거나 가짜 lease를 만들지 않는다.
- `Bun.Subprocess.exitCode === null`만으로 실행 중이라고 판정하지 않는다. 신호 종료에서는 종료를 기다린 뒤에도 `exitCode`가 null이고 `signalCode`가 채워질 수 있다. 소유 프로세스의 `exited`를 기다린 결과와 `signalCode`를 함께 기록하며, 명시적 강제 종료를 정상 exit 0으로 바꾸지 않는다([Bun 종료 처리](https://bun.com/docs/runtime/child-process#exit-handling)). 이는 다른 프로세스나 하위 native 서비스의 종료 증거를 대신하지 않는다.
- 같은 `eval` 커널에 로그 tail·주기 표본 같은 비동기 관측 루프를 띄워 두었다면, 그 커널에서 `Bun.spawnSync` 같은 동기 호출을 실행하는 동안 관측 루프도 멈춘다. 그 구간에 생긴 줄은 호출이 끝난 뒤 한 시각으로 몰려 기록되므로 "관측 시각"의 차이를 지연 근거로 쓰지 않는다. 시각을 재야 하는 동안의 하위 프로세스는 `Bun.spawn`(비동기)으로 실행하거나 별도 프로세스에서 수집하고, 가능하면 측정 대상이 직접 찍은 시각을 쓴다. 이미 수집한 자료는 동기 호출 시작·종료 시각과 대조해 막힌 구간을 제외한다(2026-10-16 실제 사례: 60초 grace가 116~118초로 보였다가 측정 오류로 확인).
- IDE·터미널·WSL/원격 빌드의 환경변수와 경로 해석 주체를 구분한다. 별도 셸의 `export`가 IDE에서 시작한 빌드에도 전달된다고 가정하지 않는다. [Visual Studio의 CMake preset 처리](https://learn.microsoft.com/en-us/cpp/build/cmake-presets-vs)는 변수 확장 후 CMake를 호출하므로, target 의존성 경로는 target 환경에 명시하거나 `${sourceDir}`의 toolchain 진입 파일 안에서 실제 빌드 호스트 환경으로 결정한다. 미설정 변수를 `/scripts/...` 같은 유효하지 않은 절대 경로로 확장하지 않으며, 잘못 지정된 명시 경로를 다른 설치본으로 조용히 대체하지 않는다.
- `debug` — DAP 디버거(번들 어댑터 `gdb`·`lldb-dap`·`codelldb`·`debugpy`·`dlv`·`js-debug-adapter` 등, `omp://tools/debug.md`, OMP 18.10.0 확인: 2026-10-12, 18.11.0 재확인: 2026-10-15) 스테핑·브레이크포인트.
- `eval`의 `browser` facade — 활성화된 경우 `browser.open`으로 탭을 열고 관찰·상호작용·시각 확인 후 닫는다. 정적 URL은 `read`가 우선이다. 독립 Puppeteer 도구로 가정하지 않으며 실제 API는 `xd://eval/browser`를 읽는다. relay/CDP는 사용자의 실제 로그인 세션일 수 있으므로 대상 탭·행동 권한을 구분한다. 사용자가 이미 연 페이지를 쓰려면 `browser.targets()`로 목록을 확인해 `app.target`을 지정하고, 요청 없이 보이는 탭을 탐색하지 않는다(`browser.targets()`는 OMP 18.9.0에서 추가됐고 18.11.0 `xd://eval/browser`에서 재확인: 2026-10-15).
  - 로컬 `file://` 문서는 파일 간 접근 허용 플래그 없이 확인한다. 문서 스크립트가 다른 로컬 파일을 읽어야 할 때만 `allow_file_access`를 쓰며, 이 launch flag는 이미 실행 중인 공유 브라우저에 적용할 수 없으므로 설치된 Chrome 등을 `app.path`로 지정한 전용 브라우저에서 열고 확인 후 `close`한다(OMP 18.6.1 계약 확인, 18.10.0 `xd://eval/browser`에서 재확인: 2026-10-12, 18.11.0 재확인: 2026-10-15). 플래그를 켠 결과를 기본 브라우저 조건의 동작 증거로 쓰지 않는다. 교차 origin인 `file://` iframe 내부 측정은 `tab.frame(<iframe 선택자>)`의 `evaluate` 등을 우선 사용한다.
  - `read`가 로그인 벽·JS 챌린지에 막힌 공개 페이지는 막혔다고 결론 내기 전에 관리 Chromium(관찰한 호출은 `app: { tern: false }`, relay 아님)으로 연다. 2026-10-14 Reddit에서 `read`는 `www`·`old.reddit.com`·`.json` 경로 모두 로그인 화면이나 챌린지를 받았고 미러는 429를 받았지만, 관리 Chromium 탭은 JS 챌린지를 통과해 검색 목록과 스레드 본문·댓글(`shreddit-post`·`shreddit-comment` 요소)을 읽었다. 같은 세션의 위임 작업자들은 이 경로를 쓰지 않아 검색 스니펫만 근거로 남겼으므로, 커뮤니티 조사를 위임할 때는 이 경로와 원문 보존 위치를 지정한다. 로그인된 사용자 세션(relay)은 쓰지 않는다.
- `read` — 이미지 파일 디코딩·분석.
- 이미지 생성 편집으로 **정밀한 위치·간격 이동이나 특정 표식만 지우는 국소 수정**을 반복 요청하지 않는다. 생성 모델은 요청하지 않은 영역까지 다시 해석해 이미 고친 결함을 되살릴 수 있다. 유지할 기준 이미지가 있으면 생성 결과에서 바꾼 영역만 잘라 기준 위에 합성한다. 이동은 픽셀 측정값으로 결정적으로 적용하고, 기준·영역·이동량·출력 hash를 계보로 남긴 뒤 확대 crop과 독립 검토로 이음매·회귀를 확인한다. 기준 이미지를 재사용했다는 사실을 그 이미지의 사용자 수락으로 기록하지 않는다. 생성 결과를 다음 편집 입력으로 연쇄해 오류를 누적하지 않는다.

## 백그라운드 작업
- [OMP 18.3.0](https://github.com/can1357/oh-my-pi/releases/tag/v18.3.0)의 `wait`·`proc://`·`agent://` 경로를 사용한다. 이전 `hub` 호출을 복제하지 않으며 정확한 인자는 현재 세션 문서가 정본이다. `hub`은 18.3.0에서 폐기됐고 18.10.0·18.11.0 내장 도구 목록에도 없다(`src/tools/builtin-names.ts`, 확인: 2026-10-12, 18.11.0 재확인: 2026-10-15).
- 작업 결과·메시지는 자동 전달을 사용하고 할 일이 남아 있으면 진행한다. 외부 결과만 기다려야 할 때 `wait`를 사용하며 상태 조회를 반복하지 않는다. `wait`는 인수가 없고 호출자가 소유한 작업·서비스와 피어 메시지만 기다리며, 기다릴 대상이 없으면 즉시 `Nothing to wait for`로 반환한다(`omp://tools/wait.md`, OMP 18.5.1 이후, 18.11.0 재확인: 2026-10-15).
- 오래 걸리는 정상 작업은 진행 메시지 없이 끝까지 완료시키되, 장애나 잘못 작성한 스크립트로 진행할 수 없게 된 상태는 놓치지 않는다. 경과 시간만으로 실패를 판정하지 않는다. 실제 소요보다 짧은 상한으로 끊고 같은 조건으로 재시도하면 끝날 작업도 매번 실패하므로(예: 상한 5분, 실제 5분 10초) 이 방식을 쓰지 않는다. 도구 기본 상한보다 길 수 있는 작업은 실행 시 상한 자체를 바꾼다. 백그라운드(`async`) 실행이나 자동 백그라운드 전환은 상한을 늘리지 않으므로(OMP 18.10.0 `omp://tools/bash.md`: 기본 300초, `async`도 같은 상한 유지, 확인: 2026-10-12, 18.11.0 재확인: 2026-10-15) 끝나는 긴 작업에는 `timeout: 0` 또는 정상 소요를 확실히 넘는 상한을 명시하고, 상한은 바깥 안전선으로만 쓴다. 계속 떠 있어야 하는 서비스는 이름을 붙인 서비스 실행 계약을 따른다. 직접 작성한 스크립트·테스트는 일정 간격으로 현재 상태와 진행률(완료 단계, %, 처리 건수)을 로그로 남기고, 조건 대기는 실제 로직 상태를 일정 간격으로 확인해 그 값을 기록한다. 결과를 기다리다 깨어날 때마다 이 신호를 확인한다. 값이 여러 간격 동안 변하지 않는 것은 정체 후보일 뿐이다. 긴 링크·컴파일처럼 한 단계가 오래 걸리면 정상 실행 중에도 단계·%·건수가 그대로일 수 있으므로 작업은 계속 두고 프로세스 생존, CPU·디스크 출력 증가, 로그 끝부분, 기다리는 조건의 현재 값을 진단한다. 프로세스 종료, 오류 출력, 교착, 로직상 충족될 수 없는 조건처럼 실패나 진행 불가능의 근거를 확인했을 때만 중단하고 그때 사용자에게 알린다. 원인을 확인하기 전에 같은 조건으로 재시도하지 않는다.
- 에이전트 협의는 `write agent://<id>`, 프로세스 입력은 `write proc://<id>`, 중단은 명시적인 `proc://<id>/kill` 대상이다. 실행 중인 실제 식별자를 사용하며 URI만으로 권한이나 파괴적 작업 승인이 생기지 않는다.

## UTF-8이 아닌 파일 편집
- `edit`는 UTF-8이 아닌 파일(예: CP949 주석이 섞인 소스) 편집을 거부할 수 있다. 이때 파일 전체를 UTF-8로 다시 저장하지 않는다. 인코딩 변경은 무관한 줄까지 바꾸고 컴파일러·도구의 해석을 바꿀 수 있다.
- 바꿀 줄이 ASCII이면 `eval`의 `js`에서 파일을 Latin-1 바이트 그대로 읽고, 정확히 한 번 일치하는 줄만 치환해 같은 방식으로 쓴다. 쓴 뒤 비ASCII 바이트 열이 전과 같은지 확인한다. 바꿀 줄에 비ASCII 문자가 있으면 먼저 원래 인코딩을 확인하고 그 인코딩으로 처리한다.

## 작업용 스크립트와 실행 언어
- 적용 대상은 에이전트가 새로 작성하는 작업용 자동화·분석·재현·스모크 스크립트다. **저장 파일은 TypeScript(`.ts`), 실행은 `bun <파일.ts>`**로 통일한다. 저장 위치는 [워크플로](/workflow.md)의 작업 디렉터리를 따른다. 기존 제품 코드·영구 테스트·빌드 도구를 TypeScript로 이식하라는 뜻은 아니다.
- 전용 기본 도구 → 기존 프로젝트 명령·CLI → 파일이 필요 없는 `eval`의 `language: "js"` → 보존·재실행이 필요한 `.ts` 스크립트 순으로 선택한다. 가능한 작업을 스크립트로 감싸거나 별도 파일·패키지 설정을 만들지 않는다. `eval`의 `js`는 Bun에서 실행되는 JavaScript 경로이며, TypeScript 타입 문법을 강제로 넣지 않는다. 타입이 필요하면 `.ts` 파일을 사용한다.
- 표준 라이브러리·Bun 내장 기능·기존 프로젝트 의존성을 우선한다. 작업용 파일 하나 때문에 npm 패키지·Python·가상환경을 추가하거나 기존 셸/PowerShell 부트스트랩을 다시 작성하지 않는다.
- Python을 지원한다는 사실은 선택 사유가 아니다. 편의·습관·짧은 문법을 이유로 `eval language: "py"`, `python -c`, Python heredoc, 새 `.py` 파일로 전환하지 않는다. 같은 작업의 코드와 데이터 처리를 Python/JS 사이에 나누지 않는다.
- 다른 언어는 사용자 명시 지정, 기존 프로젝트의 코드·테스트·실행 환경, 실제 필수 도구·라이브러리의 런타임 제약이 있을 때만 사용한다. 적용 근거와 최소 범위를 밝히고 나머지 작업용 코드는 TypeScript+Bun을 유지한다. 편의용 라이브러리를 먼저 골라 예외를 만들지 않는다.
- 위 예외에 해당하지 않는 새 작업용 코드에 Bun이 필요하지만 사용할 수 없으면 기본 도구·기존 명령으로 해결 가능한지 확인한다. 불가능하면 필요한 실행 환경을 알리고 설치·대체의 승인을 받으며 Python으로 조용히 대체하지 않는다. 기존 프로젝트 언어·명시된 필수 런타임 예외를 적용하는 데 Bun 설치를 요구하지 않는다. 언어 지침은 도구의 Python 지원 자체를 제거하거나 기존 프로그램의 인터프리터를 막는 설정이 아니다.

## MCP와의 경계
- 기본 도구로 대체하는 MCP(brave-search의 일반 웹 검색·요약, serena의 시맨틱 분석, context7의 라이브러리 문서 등)와 외부 연동의 필요성·공급망 검토는 [MCP 정책](/tools/mcp.md)이 정본이다. 이 레포의 코드 탐색·검색·문서 조사에는 위 기본 경로를 사용하며 중복 MCP를 기본 설정에 추가하지 않는다.
