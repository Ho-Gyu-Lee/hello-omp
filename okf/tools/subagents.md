# 서브에이전트 위임

## 직접 vs 위임
- 단순 파일·심볼 조회와 이미 범위가 명확한 작업은 직접 처리한다. 먼저 직접 읽기·검색으로 경계를 잡고 호출 횟수만으로 위임하지 않는다.
- 넓고 미확인인 읽기 전용 저장소 조사가 남으면 현재 가용한 `scout`을 사용한다. 이미 연 파일의 사소한 정리나 단일 질문을 불필요하게 위임하지 않는다.
- `scout`에 명령 실행이 필요한 확인(`git diff --no-index`·`git log`·`--version`·빌드)을 맡기지 않는다. OMP 18.10.0 번들 정의의 `scout` 도구는 `read`·`find`·`grep`·`glob`·`web_search`·`yield`뿐이며(`omp agents unpack --dir <별도 검증 디렉터리> --json`, 확인: 2026-10-12) 관찰한 세션(2026-10-06)의 `scout`도 해당 요청을 미실행으로 반환했다. 가용 도구는 세션마다 확인하고, 실행 근거가 필요하면 통합 담당자가 직접 실행하거나 실행 도구가 있는 에이전트에 맡긴다. 번들 `reviewer`·`security-reviewer`에는 `write`·`edit`가 없어(`reviewer`는 `bash`가 있고 `security-reviewer`는 없다) 관찰한 세션(2026-10-12)에서 지정한 검토 파일을 만들지 못하고 결과를 본문으로 반환했다. 검토 결과를 파일로 보존해야 하면 통합 담당자가 반환값을 그대로 저장하고 저장자를 표시한다.
- 독립적으로 수행할 수 있는 실질적인 작업들이 있거나 읽을 자료가 메인 컨텍스트를 과도하게 차지할 때 분리한다. 병렬 위임은 같은 배치에 묶고, 공유 선행 조건은 통합 담당자가 해결한다. 독립 검토의 필수 시점은 [워크플로](/workflow.md)를 따른다.

## 병렬·격리
- 병렬 fan-out 전에 공유 인터페이스·데이터 형식·의존성·완료 기준과 각 작업의 정확한 write-set 소유권을 고정한다.
- 작업용 파일은 부모가 [워크플로](/workflow.md)의 정확한 작업 루트·작업-ID·파일 소유권을 전달하고 같은 디렉터리에 모은다. 격리 환경의 대응 경로·증거 수집과 TypeScript+Bun 실행 기준도 위임 계약에 포함한다. 이 기준을 context에서 빼면 작업자가 변이 검사 러너·일괄 치환을 Python으로 만든 사례가 있었다(2026-10-12). 반환 산출물의 언어를 확인하고 위반이면 `.ts`로 다시 만들게 하며, 기존 결과 파일은 증거로 남긴다.
- 위임 지시를 보내기 전에 프로젝트 지침의 실행 금지 목록(이 PC에서 돌리지 않는 부하 도구, 건드리지 않는 공유 stack 등)과 대조한다. 지시에 "예를 들어"로 든 도구도 작업자는 그대로 실행하며, '기능 확인만'·'수치는 근거로 쓰지 않음' 같은 단서는 금지된 실행을 허용하지 않는다. 같은 목적은 허용된 검사(예: 기존 기능 probe)로 지정한다. 이미 실행됐다면 다시 돌리지 않고 증거를 위반 기록으로 보존한 뒤 gate·검증 근거에서 제외하고 보고에서 정상 gate와 분리한다(2026-10-12 사례).
- 의존성이 없고 write-set이 겹치지 않는 작업만 같은 배치에서 병렬 실행한다. 공용 파일이나 통합 경계가 겹치면 한 소유자에게 합치거나 선행 계약을 확정한 뒤 순차화한다.
- 코드 변경이 포함된 병렬 작업은 task 요청에 `isolated`를 명시해 격리한다. `isolated` 필드는 `task.isolation.enabled`가 켜져 있고 plan mode가 아닐 때만 노출된다(`omp://tools/task.md`, OMP 18.10.0 확인: 2026-10-12). 실제 백엔드는 `isolation.backend`가 선택하며, 외부 캐시·서비스는 격리하지 않으므로 충돌 가능 리소스는 별도로 분리한다.
- 서브에이전트의 완료 보고는 산출물 수락이 아니다. 부모가 변경 파일과 계약 경계를 직접 다시 검증한 뒤 통합하며, `reviewer`·advisor의 판단은 실행 증거를 대체하지 않는다.
- 구조화 결과의 최종 payload만 읽고 검토를 끝내지 않는다. 관찰한 세션(OMP 18.10.0, 2026-10-12)의 `reviewer`는 지적을 여러 번의 `yield`로 나눠 보냈고, 최종 payload에는 판정·설명만 남아 "지적 3건"이라는 설명과 달리 `findings`가 비어 있었다. 설명의 지적 수와 payload의 항목 수가 다르면 해당 에이전트의 세션 기록에서 각 지적 본문을 확인한 뒤 반영 여부를 판단한다.
- `isolated` 작업의 성공 결과는 완료 시 부모 작업 트리에 자동 적용될 수 있다(`task.isolation.apply` 기본 `true`이며 `false`이면 적용하지 않고 patch로 보관한다. `omp://tools/task.md`, 확인: 2026-10-12). 단계 일부만 맡은 작업이 다른 소유자의 호출부 수정이 필요한 시그니처를 바꾸면, 적용 직후 부모 트리의 제품 빌드가 깨지고 같은 트리에서 빌드 중인 다른 작업자가 원인을 오인한다. 이런 작업은 부모 트리가 빌드 가능한 상태로 끝나도록 범위를 정하거나 patch만 산출하게 하고, 적용 뒤에는 작업자의 suite뿐 아니라 부모 트리의 전체 제품 빌드로 확인한다. 이미 적용됐다면 patch로 보관한 뒤 되돌리거나 통합 담당자가 남은 호출부를 갱신해 부모 트리 빌드를 복구하고, 어느 쪽이든 동시 작업자에게 알린다. 다른 작업자의 변경을 함께 되돌리지 않는다.
- 격리 백엔드가 submodule 내용이나 다른 OS의 빌드 환경(예: WSL Linux 빌드)을 재현하는지 확인되지 않은 병렬 C++ 작업은 작업자마다 독립 clone을 준다. 원격 상대 URL로 된 submodule은 로컬 정본 checkout 경로로 URL을 바꿔 초기화하고, 작업자는 그 clone에서만 빌드·테스트·커밋한다(push 금지, 부모 gitlink는 스테이징하지 않음). OMP 18.4.12부터 기본 서브에이전트는 빌드·테스트·스모크를 부모에 맡기므로([변경 내역](https://github.com/can1357/oh-my-pi/blob/main/packages/coding-agent/CHANGELOG.md) 18.4.12) 작업자 빌드를 요구하려면 위임 context에 명시한다. 통합 담당자는 커밋을 fetch해 cherry-pick하고, 공용 submodule 커밋은 한 checkout에서 확정한 뒤 다른 checkout을 같은 커밋으로 맞춘 다음 통합 트리 전체로 다시 빌드·테스트한다. 같은 빌드 디렉터리나 반쯤 수정된 소스를 공유하지 않으므로 서로의 실패 원인이 섞이지 않는다(2026-10-11 관찰: 세 작업자가 각자 clone에서 테스트를 통과한 커밋을 반환했고, 통합 트리 빌드·테스트도 통과했다). 작업자별 빌드 병렬도는 머신 코어·메모리 합계에 맞춰 제한한다. 같은 머신에서 빌드가 도는 동안에는 FPS·지연·용량을 관측하는 검증을 실행하지 않는다. 같은 관찰에서 병렬 빌드와 겹친 4개 클라이언트 렌더 검증의 HUD에 `FPS 1`·Ping 상승이 기록됐다. 이미 겹쳤다면 그 수치를 contended로 표시하고 성능 근거로 쓰지 않는다.
- 대규모 작업은 계획 수립 후 배치 실행하고 체크포인트에서 검증하며, 실패한 계약에 의존하는 작업은 진행하지 않는다.
- 결과 자동 전달과 메시지를 이용하며 실행 중 반복 조회하지 않는다. 기다림·협의 경로는 [기본 도구의 백그라운드 작업](/tools/builtin.md)을 따른다.

## 에이전트 선택
- 역할별 에이전트와 사용 시점은 [에이전트 가이드](/agents/guide.md) 참조.
- 현재 세션의 가용 에이전트 목록에서 이름을 선택한다. `modelRoles` 키를 에이전트 이름으로 가정하지 않으며([에이전트 가이드](/agents/guide.md)의 「가용 에이전트와 모델 역할의 구분」), 가이드와 설치본이 다르면 실제 목록을 우선한다.
- 위임받은 에이전트도 작업 전 관련 OKF 개념을 확인하고 omp 기본 도구·스킬을 우선 사용한다.
